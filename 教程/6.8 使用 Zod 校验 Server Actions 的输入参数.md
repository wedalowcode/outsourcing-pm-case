# 6.7 使用 Zod 校验 Server Actions 的输入参数

## 前言

上一篇（6.6），我们使用 Next.js Server Actions 打通了部门管理的写入通道。

前端调用 `createDeptAction()`，服务端接收参数，再调用 `service.ts` 中的 `createDept()`，最终完成数据库写入。

这条链路已经跑通，但还有一个问题：**我们如何确保服务端收到的参数是合法的？**

先看一个例子。

新增部门时，正常情况下，前端会提交这样的数据：

```typescript
{
  name: "研发部",
  parentId: null,
  sort: 10,
  status: 1,
  description: "负责研发工作"
}
```

但 Server Action 并不能假设调用方一定会提交这样的数据。

请求可能缺少 `name`，可能把 `sort` 传成字符串，也可能把 `status` 传成一个不支持的值。甚至调用方根本没有使用我们的页面，而是直接构造请求调用 Action。

如果只依赖 TypeScript 定义参数类型，这些问题能被发现吗？

```typescript
export async function createDeptAction(input: DeptInput) {
  // ...
}
```

这里的 `DeptInput` 是一个 TypeScript 类型。它可以帮助开发人员在编写代码时发现类型错误，但**类型本身不会在运行时自动检查收到的数据**。

因此，我们需要引入一个运行时数据校验工具。

本篇使用 **Zod**，为部门管理的 Server Actions 建立明确的输入校验规则，并将它与现有的 `DeptInput`、`actions.ts` 和 `service.ts` 结合起来。

学完这一篇，我们要解决三个问题：

1. Zod 是什么，它与 TypeScript 的类型定义有什么区别？
2. 如何为部门管理的输入参数定义 Schema？
3. 如何在 Server Actions 中校验数据，同时保留 Service 层的业务规则？

---

## 一、Zod 是什么？

Zod 是一个用于 JavaScript 和 TypeScript 的数据校验库。

它允许我们通过代码定义一组规则，然后把运行时收到的数据交给这些规则检查。

例如，部门名称必须是字符串，不能为空，最多 50 个字符：

```typescript
import { z } from "zod";

const DeptNameSchema = z
  .string()
  .trim()
  .min(1, "请填写部门名称")
  .max(50, "部门名称不能超过 50 个字");
```

这段代码定义了一个校验规则，但还没有执行校验。

当我们收到实际数据时，可以调用：

```typescript
const result = DeptNameSchema.safeParse("研发部");
```

如果数据符合规则，校验成功；如果不符合规则，Zod 会返回具体的错误信息。

### 1. Zod 与 TypeScript 有什么区别？

我们先用一个表格理解两者的分工。

| 对比项 | TypeScript | Zod |
| --- | --- | --- |
| 主要用途 | 开发时的类型检查 | 运行时的数据校验 |
| 是否检查实际输入 | 不会自动检查 | 可以检查 |
| 是否能验证字符串长度 | 不能仅靠普通类型定义 | 可以 |
| 是否能验证枚举取值 | 可以在开发时限制类型 | 可以在运行时检查 |
| 是否能返回校验错误 | 不负责运行时校验错误 | 可以返回具体错误信息 |

例如，我们已经有下面的类型：

```typescript
export type DeptStatus = 0 | 1;

export type DeptInput = {
  name: string;
  parentId: string | null;
  sort?: number;
  status?: DeptStatus;
  description?: string;
};
```

开发人员在 TypeScript 代码中写：

```typescript
const status: DeptStatus = 2;
```

编辑器和编译器通常就能发现问题，因为 `2` 不属于 `0 | 1`。

但如果运行时收到一份外部请求数据：

```typescript
const input = {
  name: "研发部",
  parentId: null,
  status: 2,
};
```

TypeScript 不会因为我们提前定义了 `DeptInput`，就自动检查这份数据。

这就是 Zod 的价值：它可以在程序运行时，对真实收到的数据进行校验。

### 2. Schema 不只是校验规则，还可以推导类型

Zod 的另一个优势，是可以从 Schema 推导出 TypeScript 类型。

```typescript
const DeptStatusSchema = z.union([
  z.literal(0),
  z.literal(1),
]);

type DeptStatus = z.infer<typeof DeptStatusSchema>;
```

推导出来的 `DeptStatus` 就是 `0 | 1`。

这样，我们可以让校验规则和 TypeScript 类型来自同一个定义，减少两份定义逐渐不一致的风险。

接下来，我们就把这种方式应用到部门管理中。

## 二、在项目中安装 Zod

在项目根目录打开终端，执行：

```bash
pnpm add zod
```

安装完成后，就可以在 TypeScript 文件中导入：

```typescript
import { z } from "zod";
```

这里使用的是 Zod 的常用 API。后面会用到：

- `z.object()`：定义对象结构。
- `z.string()`：要求值为字符串。
- `z.number()`：要求值为数字。
- `z.enum()` 或 `z.union()`：限制可选值。
- `.optional()`：允许字段不传。
- `.nullable()`：允许字段为 `null`。
- `.trim()`：去掉字符串首尾空白。
- `.min()`、`.max()`：限制最小值或最大值。
- `.safeParse()`：执行校验，并返回成功或失败结果。

先记住一个区别：**`.optional()` 表示可以不传，`.nullable()` 表示可以传 `null`。** 两者不是一回事。

例如，`parentId` 在新增顶级部门时需要允许 `null`，而 `sort` 可以不传，由服务端自动计算。

## 三、为部门管理定义 Zod Schema

我们先不急着修改 Action，而是先明确输入规则。

当前项目中，部门管理接收的数据结构是：

```typescript
export type DeptInput = {
  name: string;
  parentId: string | null;
  sort?: number;
  status?: DeptStatus;
  description?: string;
};
```

我们可以在 `server/dept/schema.ts` 中集中定义校验规则。

创建文件：

`server/dept/schema.ts`

```typescript
import { z } from "zod";

/** 部门状态：0 停用，1 启用 */
export const DeptStatusSchema = z.union([
  z.literal(0),
  z.literal(1),
]);

/** 部门新增、编辑共用的输入规则 */
export const DeptInputSchema = z.object({
  name: z
    .string({
      error: "部门名称必须是字符串",
    })
    .trim()
    .min(1, "请填写部门名称")
    .max(50, "部门名称不能超过 50 个字"),

  parentId: z
    .string()
    .min(1, "上级部门 ID 不能为空")
    .nullable(),

  sort: z
    .number()
    .int("排序必须是整数")
    .optional(),

  status: DeptStatusSchema.optional(),

  description: z
    .string()
    .trim()
    .max(500, "部门描述不能超过 500 个字")
    .optional(),
});

/** 从 Schema 自动推导 TypeScript 类型 */
export type DeptInput = z.infer<typeof DeptInputSchema>;
```

> 说明：以上示例使用较新的 Zod 错误配置写法。如果项目安装的是较早版本的 Zod 4，或使用 Zod 3，应根据安装版本调整错误参数；Zod 3 常用 `z.string({ required_error: "..." })` 等写法。核心校验规则不受影响。

下面逐项解释。

### 1. 校验部门名称

```typescript
name: z
  .string()
  .trim()
  .min(1, "请填写部门名称")
  .max(50, "部门名称不能超过 50 个字"),
```

它包含四个规则：

1. 必须是字符串。
2. 去掉首尾空白。
3. 不能为空。
4. 最多 50 个字符。

例如，用户提交 `" 研发部 "`，经过 `.trim()` 后会变成 `"研发部"`。

如果提交的内容只有空格，去掉空白后就会变成空字符串，从而触发 `.min(1)`。

这里还有一个细节：Zod 的字符串长度限制是字符串长度校验，并不是对汉字、英文、字节数分别计算。当前教程使用 50 作为部门名称的长度上限；如果业务要求按特定字符或字节规则计数，就需要单独定义规则。

### 2. 校验上级部门 ID

```typescript
parentId: z
  .string()
  .min(1, "上级部门 ID 不能为空")
  .nullable(),
```

我们规定：

- `null` 表示顶级部门。
- 非空字符串表示上级部门 ID。
- 不允许空字符串。

这里没有直接验证这个 ID 是否真实存在，因为 Schema 只检查输入的结构和基本格式，并不会自动查询数据库。

如果调用方提交了一个格式正确、但数据库里不存在的 ID，后续仍需要由 Service 层通过数据库查询确认。

这体现了不同层次的分工：Zod 检查输入格式，Service 检查业务关系。

### 3. 校验排序值

```typescript
sort: z
  .number()
  .int("排序必须是整数")
  .optional(),
```

排序值可以不传。未传时，Service 层会调用 `nextSort()` 自动生成排序值。

如果传入，则必须是整数。

需要注意：`z.number()` 不会自动把字符串 `"10"` 转换成数字 `10`。如果前端使用普通 HTML 输入框，得到的值往往是字符串，需要在提交前转换，或者明确使用 `z.coerce.number()` 并设置合理的转换规则。

对于本项目，我们先保持规则严格：**传入数字就按数字校验，传入字符串就拒绝。**

### 4. 校验部门状态

```typescript
export const DeptStatusSchema = z.union([
  z.literal(0),
  z.literal(1),
]);
```

我们约定：

- `0`：停用。
- `1`：启用。

因此，`2`、`-1`、`"1"` 等值都不符合规则。

这与原来的 TypeScript 类型 `0 | 1` 保持一致，但现在多了一层运行时保护。

### 5. 校验部门描述

```typescript
description: z
  .string()
  .trim()
  .max(500, "部门描述不能超过 500 个字")
  .optional(),
```

部门描述可以不传；如果传入，则必须是字符串，去掉首尾空白后长度不能超过 500。

这里选择 500 作为示例上限，实际项目应当与数据库字段长度、前端表单限制和业务需求保持一致。

另外，当前 Schema 允许空字符串。经过 `.trim()` 后，纯空格会变成 `""`，但不会因为 `.optional()` 而自动变成 `undefined`。

如果业务约定“空描述等于清空描述”，可以在 Schema 中进一步将空字符串转换为 `null`；如果编辑时未传描述应保留原值，则必须保留“未传”和“传入空字符串”之间的区别。

## 四、让 Schema 成为类型定义的来源

原来我们在 `server/dept/types.ts` 中单独定义了 `DeptStatus` 和 `DeptInput`。

现在，Schema 已经能够推导类型，可以改成从 Schema 导入类型，避免重复维护。

例如，将 `server/dept/types.ts` 改为：

```typescript
export type {
  DeptInput,
} from "@/server/dept/schema";

export type DeptStatus =
  import("@/server/dept/schema").DeptStatus;
```

不过，这里还有一种更直接的组织方式：如果其他模块只需要 `DeptInput`，就直接从 `schema.ts` 导入它；如果项目中很多地方已经依赖 `types.ts`，则可以暂时保留这个文件作为统一的类型导出入口。

关键不是文件名，而是避免两处定义同一套规则后逐渐发生偏差。

从现在开始，部门输入数据的类型和运行时校验规则，都由 `DeptInputSchema` 统一维护。

## 五、在 Server Actions 中执行校验

前面定义的 Schema 还没有发挥作用。接下来，把它接入 `actions.ts`。

核心方法是：

```typescript
const result = DeptInputSchema.safeParse(input);
```

`safeParse()` 不会因为普通的校验失败就直接抛出异常，而是返回一个带有成功或失败状态的结果。

成功时：

```typescript
{
  success: true,
  data: ...
}
```

失败时：

```typescript
{
  success: false,
  error: ...
}
```

其中，成功结果里的 `data` 是经过 Schema 解析后的数据。比如部门名称经过 `.trim()` 后，返回的数据中就不再带有首尾空格。

### 1. 为 Action 增加统一校验函数

在 `server/dept/actions.ts` 中导入：

```typescript
import { DeptInputSchema } from "./schema";
```

然后定义一个公共函数：

```typescript
function validateDeptInput(input: unknown) {
  const result = DeptInputSchema.safeParse(input);

  if (!result.success) {
    return {
      ok: false as const,
      message: result.error.issues[0]?.message ?? "输入数据不合法",
    };
  }

  return {
    ok: true as const,
    data: result.data,
  };
}
```

这里把参数类型写成 `unknown`，是为了明确表达：进入校验函数的数据尚未通过验证，不能直接当作合法的 `DeptInput` 使用。

校验成功后，`result.data` 才是通过 Schema 验证并解析的数据。

为什么这里先返回第一条错误？

因为这是最简单的入门写法，足以让前端显示一个明确的错误提示。后续如果表单需要同时展示多个字段的校验错误，可以把 `result.error.issues` 转换成字段级错误结构。

### 2. 修改新增 Action

将原来的新增 Action 改为：

```typescript
export async function createDeptAction(input: unknown) {
  // TODO：先校验登录态和新增权限

  const validation = validateDeptInput(input);

  if (!validation.ok) {
    return validation;
  }

  return run(
    () => deptService.createDept(validation.data),
    "保存失败，请稍后重试",
  );
}
```

调用流程就变成：

```text
接收不可信数据
      ↓
  Zod Schema 校验
      ↓
  校验失败？ ── 是 ──→ 返回校验错误
      │
      否
      ↓
  调用 createDept()
      ↓
  执行业务规则与事务
      ↓
  返回操作结果
```

这时，非法输入会在进入 Service 层之前被拦截。

当然，Service 层仍然要保留自己的必要校验。原因是它不应该只能依赖某个 Action 才能被安全调用；其他服务端入口将来可能也会复用同一个 Service。

### 3. 修改编辑 Action

编辑 Action 同样需要校验输入：

```typescript
export async function updateDeptAction(
  id: string,
  input: unknown,
) {
  // TODO：先校验登录态和编辑权限

  if (typeof id !== "string" || id.trim() === "") {
    return {
      ok: false as const,
      message: "部门 ID 不合法",
    };
  }

  const validation = validateDeptInput(input);

  if (!validation.ok) {
    return validation;
  }

  return run(
    () => deptService.updateDept(id, validation.data),
    "保存失败，请稍后重试",
  );
}
```

这里除了校验部门表单数据，还单独检查了 `id`。

原因很简单：`id` 也是调用方传入的参数，不能因为它在 TypeScript 中被声明为 `string`，就认为它一定是合法的。

这只是最基本的非空检查。如果项目对 ID 有固定格式要求，还可以进一步使用对应的格式校验。

### 4. 修改删除 Action

删除操作没有复杂的表单，但仍然需要检查 ID。

```typescript
export async function deleteDeptAction(id: unknown) {
  // TODO：先校验登录态和删除权限

  if (typeof id !== "string" || id.trim() === "") {
    return {
      ok: false as const,
      message: "部门 ID 不合法",
    };
  }

  return run(
    () => deptService.deleteDept(id),
    "删除失败，请稍后重试",
  );
}
```

如果希望让三个 Action 的代码风格更加统一，后续也可以为 ID 单独定义一个 Zod Schema。

例如：

```typescript
export const DeptIdSchema = z
  .string()
  .trim()
  .min(1, "部门 ID 不能为空");
```

再通过：

```typescript
const result = DeptIdSchema.safeParse(id);
```

完成校验。

本篇先展示最直接的写法，避免为了少量代码过早引入过多抽象。

## 六、Zod 校验和 Service 校验，为什么不能只留一个？

看到这里，可能会产生一个疑问：

我们原来的 `service.ts` 已经有 `validate()`，现在又增加 Zod，是不是重复校验了？

确实存在一部分规则重叠，但它们的职责并不完全相同。

可以把当前的校验分为三个层次。

| 层次 | 主要检查什么 | 例子 |
| --- | --- | --- |
| Zod Schema | 输入结构和数据格式 | 名称是否为字符串、排序是否为整数 |
| Service 层 | 业务规则和操作约束 | 名称不能为空、上级部门是否存在、能否形成循环 |
| 数据库 | 最终的数据完整性约束 | 外键、唯一约束、事务一致性 |

需要注意，这张表描述的是职责划分，并不是说所有规则只能存在于某一层。例如，名称不能为空可以在 Zod 和 Service 中都检查，以保证不同调用入口复用 Service 时仍然安全。

真正不应该做的是：**把业务正确性完全寄托在前端或某一个 Action 的校验上。**

### 1. Zod 适合处理哪些问题？

Zod 特别适合处理外部输入：

- 必填字段是否存在。
- 字段类型是否正确。
- 字符串长度是否符合要求。
- 数值是否为整数。
- 枚举值是否属于允许范围。
- 对象结构是否符合约定。

这些规则可以直接写成 Schema，集中维护和测试。

### 2. Service 层适合处理哪些问题？

Service 层更适合处理需要结合业务流程和数据库状态才能判断的事情。

例如：

- 上级部门是否存在。
- 修改上级后是否形成循环。
- 部门编码是否需要重新生成。
- 删除部门时是否存在下级部门。
- 修改层级后是否需要同步更新后代编码。

这些规则不仅取决于用户提交的数据，还取决于数据库当前的状态。

因此，即使 Zod 校验通过，也不代表操作一定可以执行。

### 3. 数据库约束为什么仍然重要？

假设 Zod 检查通过，Service 也检查了某个字段，但在并发请求下，数据仍可能发生变化。

例如，两个请求几乎同时判断某个编码尚未使用，随后都尝试插入相同编码。

如果业务要求编码必须唯一，最终仍应由数据库唯一约束兜底，而不能只依赖应用层的预先查询。

这就是分层设计的意义：每一层负责自己能够可靠保障的事情。

## 七、用几组数据验证 Schema

Schema 写完之后，我们可以用 `safeParse()` 验证规则是否符合预期。

例如，在临时测试文件或测试用例中执行：

```typescript
import { DeptInputSchema } from "@/server/dept/schema";

const cases = [
  {
    name: "正常数据",
    input: {
      name: "研发部",
      parentId: null,
      sort: 10,
      status: 1,
    },
  },
  {
    name: "名称为空",
    input: {
      name: "   ",
      parentId: null,
    },
  },
  {
    name: "排序不是整数",
    input: {
      name: "研发部",
      parentId: null,
      sort: 1.5,
    },
  },
  {
    name: "状态不合法",
    input: {
      name: "研发部",
      parentId: null,
      status: 2,
    },
  },
];

for (const item of cases) {
  const result = DeptInputSchema.safeParse(item.input);

  console.log(
    item.name,
    result.success
      ? { success: true, data: result.data }
      : {
          success: false,
          message: result.error.issues[0]?.message,
        },
  );
}
```

预期结果：

| 测试数据 | 预期结果 |
| --- | --- |
| 正常数据 | 校验通过 |
| 名称只有空格 | 校验失败 |
| 排序为 `1.5` | 校验失败 |
| 状态为 `2` | 校验失败 |

还可以补充测试：

- 缺少 `name`。
- `parentId` 既不是字符串也不是 `null`。
- `description` 超过长度限制。
- `sort` 传入字符串 `"10"`。
- 部门名称首尾有空格。

通过这些例子，我们可以验证 Schema 是否真正覆盖了预期的输入边界。

在实际项目中，建议把这些用例整理为自动化测试，避免以后修改校验规则时引入回归问题。

---

## 八、一个需要提前处理的细节：编辑时，未传字段和空值不是一回事

在部门管理中，新增和编辑共用 `DeptInput`，但两种操作对数据的要求不完全相同。

新增部门时，`description` 没有传入，通常可以将其保存为 `null`。

但编辑部门时，如果调用方根本没有提交 `description`，我们往往希望保留数据库中原有的描述，而不是清空它。

因此，需要明确区分：

- `description` 未传：不修改该字段。
- `description: ""`：根据业务约定，可能表示清空描述。
- `description: "研发说明"`：更新为新描述。

这不是 Zod 自动决定的业务行为，而是我们需要明确设计的输入语义。

同时，Zod 的对象 Schema 默认会剔除未声明的额外字段。对于本项目，这是一个有用的默认行为，但也要明确：**字段被剔除不等于整个请求一定会失败。**

如果希望调用方一旦提交未知字段就被拒绝，可以在 Schema 中使用严格对象模式。具体 API 以项目安装的 Zod 版本为准。

本篇暂时不改变部门服务层的业务逻辑。真正接入前，需要把 Schema 的字段语义与 `createDept()`、`updateDept()` 的处理方式对齐，尤其是编辑时的可选字段处理。

## 小结

本篇引入了 Zod，并将它应用到部门管理的 Server Actions 中。

我们理解了三个关键概念：

1. **TypeScript 类型**：帮助开发阶段检查代码中的类型是否匹配。
2. **Zod Schema**：在运行时检查外部输入，并可从 Schema 推导 TypeScript 类型。
3. **Service 层业务校验**：结合业务规则和数据库状态，判断某项操作是否允许执行。

对于当前项目，Zod 负责在进入 Service 层之前检查参数结构和基本格式；Service 继续负责部门层级、编码、删除限制等业务规则；数据库则通过事务和约束保障数据完整性。

这不是简单地多加一个校验库，而是把原本散落在代码里的输入规则变成明确、可复用、可测试的定义。
