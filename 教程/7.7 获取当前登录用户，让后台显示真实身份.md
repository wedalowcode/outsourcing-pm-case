# 7.7 获取当前登录用户，让后台显示真实身份

在上一节中，我们已经实现了登录功能。用户输入用户名和密码后，服务端验证身份、创建会话，并通过 Cookie 保存会话凭证。进入后台时，系统会检查登录状态，未登录的用户将被重定向到登录页。

现在，登录流程已经跑通，但还有一个细节没有完成。

打开后台页面，可以看到右上角仍然显示着固定的“管理员”。无论使用哪个账号登录，显示的内容都不会变化。

这说明，**系统虽然已经知道谁登录了，但页面还没有真正使用当前用户的信息。**

本节就从这个问题出发，把登录会话中已有的用户信息传递给后台布局，让页面显示真实的登录用户。

## 一、先看看上一节已经实现了什么

在 `server/auth/session.ts` 中，我们已经实现了 `getCurrentSession()`，用于根据浏览器中的 Session Cookie 查找当前登录会话。

它的核心逻辑如下：

```ts
export async function getCurrentSession() {
  const cookieStore = await cookies();
  const token = cookieStore.get(SESSION_COOKIE_NAME)?.value;

  if (!token) return null;

  const session = await db.session.findUnique({
    where: { tokenHash: hashToken(token) },
    select: {
      id: true,
      userId: true,
      expiresAt: true,
      user: {
        select: {
          id: true,
          username: true,
          name: true,
          status: true,
        },
      },
    },
  });

  if (!session) return null;
  if (session.expiresAt.getTime() <= Date.now()) return null;
  if (session.user.status !== "ACTIVE") return null;

  return {
    sessionId: session.id,
    user: session.user,
    expiresAt: session.expiresAt,
  };
}
```

这里不需要重新实现一套获取用户信息的逻辑。这个函数已经完成了几件事情：

1. 从 Cookie 中读取会话凭证。
2. 根据凭证查询数据库中的 Session。
3. 检查会话是否存在、是否过期。
4. 检查关联用户是否处于启用状态。
5. 返回当前会话及其关联用户的信息。

其中，`session.user` 就是我们需要的当前用户对象，包含用户 ID、用户名、姓名和状态。

例如，查询成功后，返回的数据结构大致如下：

```ts
{
  sessionId: "session-id",
  user: {
    id: "user-id",
    username: "admin",
    name: "系统管理员",
    status: "ACTIVE"
  },
  expiresAt: new Date()
}
```

这段数据只是为了说明返回结构，实际值由数据库中的记录决定。

因此，本节不需要再写一个重复查询用户的函数。我们只需要解决一个问题：**如何把已经获取到的用户信息传递给后台界面？**

## 二、在后台布局中获取当前用户

先看当前的 `app/(dashboard)/layout.tsx`：

```tsx
import type { ReactNode } from "react";
import { redirect } from "next/navigation";
import { DashboardShell } from "@/components/layout/dashboard-shell";
import { getCurrentSession } from "@/server/auth/session";

export default async function DashboardLayout({
  children,
}: {
  children: ReactNode;
}) {
  const session = await getCurrentSession();

  if (!session) {
    redirect("/login");
  }

  return <DashboardShell>{children}</DashboardShell>;
}
```

这里已经调用了 `getCurrentSession()`，并在用户未登录时跳转到登录页。

但仔细看最后一行：

```tsx
return <DashboardShell>{children}</DashboardShell>;
```

虽然前面已经取得了 `session`，却没有把它传递给 `DashboardShell`。因此，后台布局知道当前用户是谁，顶部导航组件却无法使用这些信息。

我们需要做两件事：

- 把当前用户传递给 `DashboardShell`。
- 在 `DashboardShell` 中使用用户的真实姓名。

先修改 `DashboardLayout`：

```tsx
return (
  <DashboardShell user={session.user}>
    {children}
  </DashboardShell>
);
```

这样，服务端布局就把当前用户对象作为 `user` 属性传给了后台外壳组件。

这里还有一个值得注意的设计：`DashboardLayout` 是服务端组件，而 `DashboardShell` 是客户端组件。服务端组件可以查询会话，再将需要展示的普通数据作为属性传给客户端组件。

我们不需要为了展示一个姓名，就让客户端组件直接访问数据库，也不需要把 Session Cookie 暴露给客户端代码。

## 三、让 DashboardShell 接收用户信息

接下来打开 `components/layout/dashboard-shell.tsx`。

这个组件负责后台的整体外观，包括侧边栏、顶部导航和页面内容。现在，它只接收 `children`：

```tsx
type DashboardShellProps = {
  children: React.ReactNode;
};
```

我们需要增加 `user` 属性。

首先，为用户信息定义一个明确的类型：

```tsx
type DashboardUser = {
  id: string;
  username: string;
  name: string;
  status: "ACTIVE" | "DISABLED";
};

type DashboardShellProps = {
  children: React.ReactNode;
  user: DashboardUser;
};
```

这里的字段与 `getCurrentSession()` 查询出来的用户字段保持一致。虽然当前页面只需要显示姓名，但保留这个明确的用户类型，也方便后续顶部导航根据用户信息展示其他内容。

然后修改组件的参数：

```tsx
export function DashboardShell({
  children,
  user,
}: DashboardShellProps) {
  // 保留原有的布局和导航代码
}
```

实际修改时，不要删除原有的侧边栏、菜单和页面布局，只需要让组件额外接收 `user` 即可。

如果项目已经有统一的用户类型，也可以直接复用，不必再重复定义。这里使用 `DashboardUser`，只是为了把本组件需要接收的数据结构表达清楚。

## 四、把固定的“管理员”改成真实姓名

现在，回到 `DashboardShell` 的顶部导航区域。

原来的代码是：

```tsx
<span className="text-sm text-slate-600">
  管理员
</span>
```

这是一段固定文本，不会随着登录账号变化。

将它替换为：

```tsx
<span className="text-sm text-slate-600">
  {user.name}
</span>
```

修改完成后，页面展示的内容就来自当前登录用户在数据库中保存的姓名。

例如：

| 登录用户 | 页面显示 |
|---|---|
| `admin` | 系统管理员 |
| `zhangsan` | 张三 |
| `lisi` | 李四 |

以上仅为示例，实际显示内容取决于用户记录中的 `name` 字段。

至此，当前用户信息就从数据库查询一路传递到了页面：

```text
浏览器携带 Session Cookie
          ↓
getCurrentSession()
          ↓
查询并验证当前会话
          ↓
取得 session.user
          ↓
DashboardLayout
          ↓
DashboardShell user={session.user}
          ↓
顶部导航显示 user.name
```

这个过程没有增加新的数据库查询，也没有重复实现会话校验，而是直接利用了上一节已经完成的功能。

## 五、运行验证

修改完成后，启动项目并进行验证。

1. 使用账号 A 登录，检查后台右上角是否显示账号 A 对应的姓名。
2. 退出登录，再使用账号 B 登录，检查姓名是否随账号发生变化。
3. 清除登录 Cookie 或使用未登录状态访问后台，确认系统仍然会跳转到登录页。
4. 检查侧边栏、菜单和页面主体，确认修改用户属性后没有影响原有布局。

如果页面仍然显示旧的固定文字，优先检查两处：`DashboardLayout` 是否传递了 `user`，以及 `DashboardShell` 是否已经将原来的静态文本替换为 `{user.name}`。

## 六、为什么不再单独封装 getCurrentUser()？

看到这里，你可能会想到：既然多个页面都可能需要当前用户信息，是否应该再封装一个 `getCurrentUser()`？

这当然可以，但不是当前必须做的事情。

目前的 `getCurrentSession()` 不只是获取用户信息，还承担着会话有效性检查的职责。如果再增加一个函数，仅仅为了返回 `session.user`，代码可能会变成：

```ts
export async function getCurrentUser() {
  const session = await getCurrentSession();
  return session?.user ?? null;
}
```

这个封装本身没有问题。当多个业务模块都需要只获取用户对象、不关心 Session 细节时，它可以让调用代码更加简洁。

但在当前项目中，后台布局本来就需要判断会话是否有效，而且 `getCurrentSession()` 已经返回了用户信息。此时额外增加一层函数，并没有解决新的实际问题。

所以，我们先保留现有结构。

随着项目继续开发，如果多个模块都出现重复的用户信息提取逻辑，再考虑是否需要引入 `getCurrentUser()`。**抽象应该来自真实的重复和明确的职责，而不是为了让代码看起来更完整。**

## 本节小结

本节没有重新实现登录功能，而是把上一节已经建立的会话机制真正用到了后台界面中。

我们完成了三个改动：

1. 在 `DashboardLayout` 中复用 `getCurrentSession()` 获取当前用户。
2. 将 `session.user` 作为属性传递给 `DashboardShell`。
3. 使用 `user.name` 替换顶部导航中的固定“管理员”文本。

这也说明，开发全栈应用时，功能不是孤立存在的。登录模块负责确认用户身份，布局模块负责将身份信息传递给界面，具体业务模块则会在后续开发中利用这些信息完成权限判断和业务操作。

下一节，我们继续完善登录与后台之间的导航体验：用户已经登录后再次访问登录页应该怎么办？登录后应该进入哪个页面？这些看似细小的问题，会直接影响系统的使用体验。
