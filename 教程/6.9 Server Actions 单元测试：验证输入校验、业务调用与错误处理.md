# 6.8 Server Actions 单元测试：验证输入校验、业务调用与错误处理

## 前言

上一篇（6.7），我们引入了 Zod，为部门管理的 Server Actions 增加了运行时输入校验。

现在，新增、编辑、删除的调用链路已经逐渐完整：

```text
前端组件
    ↓
Server Actions
    ↓
Zod 输入校验
    ↓
Service 业务处理
    ↓
数据库
```

但代码写完了，不代表每一个环节都符合预期。

例如：

- 用户提交空的部门名称，Action 是否会阻止请求进入 Service？
- 新增成功后，是否真的调用了 `revalidatePath("/dept")`？
- 删除部门时，如果 Service 抛出“存在下级部门”的业务错误，Action 能否将具体原因返回给前端？
- 如果数据库发生异常，Action 是否会隐藏底层错误，而不是把数据库信息直接返回给用户？
- 如果 Service 执行失败，Action 是否还会错误地刷新页面缓存？

这些问题都可以通过自动化测试验证。

本篇继续使用项目已有的 Vitest，为 `server/dept/actions.ts` 编写单元测试。

完成后，我们将拥有三类测试：

1. 工具函数测试：验证部门编码、排序等计算规则。
2. Service 层测试：验证业务逻辑、事务调用和层级约束。
3. Action 层测试：验证参数校验、服务调用、错误处理和页面重新验证。

这三层各司其职，不需要每一层都连接真实数据库。

---

## 一、先确定 Action 层测试什么

编写测试之前，先明确测试对象的职责。

上一篇的 `actions.ts` 主要做四件事：

1. 接收前端传入的参数。
2. 使用 Zod 校验输入。
3. 调用对应的 Service 函数。
4. 根据执行结果返回状态，并在成功后调用 `revalidatePath()`。

因此，我们的测试应该围绕这四项职责展开。

| 测试对象 | 输入场景 | 需要验证的结果 |
| --- | --- | --- |
| 新增 Action | 合法参数 | 调用新增 Service，返回成功 |
| 新增 Action | 名称为空 | 返回校验错误，不调用 Service |
| 编辑 Action | 合法 ID 和参数 | 调用编辑 Service，参数正确 |
| 编辑 Action | ID 为空 | 返回错误，不调用 Service |
| 删除 Action | 合法 ID | 调用删除 Service，返回成功 |
| 删除 Action | ID 不合法 | 返回错误，不调用 Service |
| 错误处理 | Service 抛出 `BizError` | 返回具体业务错误 |
| 错误处理 | Service 抛出普通异常 | 记录日志，返回通用错误 |
| 页面刷新 | Service 执行成功 | 调用 `revalidatePath("/dept")` |
| 页面刷新 | Service 执行失败 | 不调用 `revalidatePath()` |

这里要特别注意：我们不需要在 Action 测试里再次验证“部门存在下级时不能删除”。

这个规则属于 Service 层。Action 测试只需要模拟 Service 抛出对应的 `BizError`，然后验证 Action 是否正确处理它。

**测试应该验证当前模块自己的职责，而不是把所有模块的逻辑重新测试一遍。**

## 三、为什么要模拟 Service 和 Next.js？

在开始写测试前，我们先看一下 Action 的依赖：

```typescript
import { revalidatePath } from "next/cache";
import * as deptService from "./service";
import { DeptInputSchema } from "./schema";
```

其中：

- `DeptInputSchema` 负责校验输入，是本次测试需要实际运行的代码。
- `deptService` 负责执行数据库业务，是我们需要模拟的依赖。
- `revalidatePath` 是 Next.js 提供的页面缓存重新验证函数，需要模拟。

为什么不直接调用真实 Service？

因为我们正在测试 Action。如果调用真实 Service，就会把数据库连接、事务、部门层级等逻辑一起带进来。测试一旦失败，就很难确定问题究竟出在 Action 还是 Service。

因此，我们用 Mock（模拟对象）替代外部依赖。

测试时，我们可以人为控制 Service 的行为：

- 让它正常返回，验证 Action 的成功流程。
- 让它抛出 `BizError`，验证业务错误处理。
- 让它抛出普通异常，验证系统错误处理。

这样，测试就能够稳定地聚焦在 Action 本身。

## 四、编写完整的 Action 测试文件

将下面代码完整放入 `tests/dept-actions.test.ts`。

这份代码对应前一篇中的实现：Action 使用 `DeptInputSchema.safeParse()` 校验输入，成功后调用 Service，并通过 `run()` 统一处理异常与页面重新验证。

```typescript
import {
  beforeEach,
  describe,
  expect,
  it,
  vi,
} from "vitest";

import { BizError } from "@/lib/biz-error";

// 使用 vi.hoisted 创建 Mock 函数，确保它们可以被 vi.mock 使用。
const mocks = vi.hoisted(() => ({
  createDept: vi.fn(),
  updateDept: vi.fn(),
  deleteDept: vi.fn(),
  revalidatePath: vi.fn(),
}));

// 模拟 Service 层，不连接真实数据库。
vi.mock("@/server/dept/service", () => ({
  createDept: mocks.createDept,
  updateDept: mocks.updateDept,
  deleteDept: mocks.deleteDept,
}));

// 模拟 Next.js 的缓存重新验证函数。
vi.mock("next/cache", () => ({
  revalidatePath: mocks.revalidatePath,
}));

// 引入待测试的 Action。
import {
  createDeptAction,
  updateDeptAction,
  deleteDeptAction,
} from "@/server/dept/actions";

describe("部门管理 Server Actions", () => {
  beforeEach(() => {
    // 清除上一次测试的调用记录。
    vi.clearAllMocks();

    // 默认让 Service 正常执行。
    mocks.createDept.mockResolvedValue({});
    mocks.updateDept.mockResolvedValue({});
    mocks.deleteDept.mockResolvedValue(undefined);
  });

  describe("createDeptAction", () => {
    it("合法输入：调用 Service 并返回成功", async () => {
      const input = {
        name: "研发部",
        parentId: null,
        sort: 10,
        status: 1,
        description: "负责研发工作",
      };

      const result = await createDeptAction(input);

      expect(result).toEqual({ ok: true });

      // 验证传给 Service 的数据已经通过 Schema 解析。
      expect(mocks.createDept).toHaveBeenCalledWith(input);

      // 验证成功后重新验证部门页面。
      expect(mocks.revalidatePath).toHaveBeenCalledWith("/dept");
    });

    it("名称为空：返回校验错误，不调用 Service", async () => {
      const result = await createDeptAction({
        name: "   ",
        parentId: null,
      });

      expect(result).toEqual({
        ok: false,
        message: "请填写部门名称",
      });

      expect(mocks.createDept).not.toHaveBeenCalled();
      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("名称带有首尾空格：传给 Service 的名称已经去空格", async () => {
      await createDeptAction({
        name: "  研发部  ",
        parentId: null,
      });

      expect(mocks.createDept).toHaveBeenCalledWith({
        name: "研发部",
        parentId: null,
      });
    });

    it("Service 抛出业务错误：返回具体错误信息", async () => {
      mocks.createDept.mockRejectedValue(
        new BizError("部门名称已被占用"),
      );

      const result = await createDeptAction({
        name: "研发部",
        parentId: null,
      });

      expect(result).toEqual({
        ok: false,
        message: "部门名称已被占用",
      });

      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("Service 抛出普通异常：返回通用提示", async () => {
      const error = new Error("数据库连接失败");

      mocks.createDept.mockRejectedValue(error);

      const consoleSpy = vi
        .spyOn(console, "error")
        .mockImplementation(() => {});

      try {
        const result = await createDeptAction({
          name: "研发部",
          parentId: null,
        });

        expect(result).toEqual({
          ok: false,
          message: "保存失败，请稍后重试",
        });

        expect(consoleSpy).toHaveBeenCalledWith(error);
        expect(mocks.revalidatePath).not.toHaveBeenCalled();
      } finally {
        consoleSpy.mockRestore();
      }
    });
  });

  describe("updateDeptAction", () => {
    it("合法输入：使用正确的 ID 和参数调用 Service", async () => {
      const input = {
        name: "研发中心",
        parentId: null,
        status: 1,
      };

      const result = await updateDeptAction(
        "dept-001",
        input,
      );

      expect(result).toEqual({ ok: true });

      expect(mocks.updateDept).toHaveBeenCalledWith(
        "dept-001",
        input,
      );

      expect(mocks.revalidatePath).toHaveBeenCalledWith("/dept");
    });

    it("ID 为空：拒绝调用 Service", async () => {
      const result = await updateDeptAction(
        "   ",
        {
          name: "研发中心",
          parentId: null,
        },
      );

      expect(result).toEqual({
        ok: false,
        message: "部门 ID 不合法",
      });

      expect(mocks.updateDept).not.toHaveBeenCalled();
      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("输入校验失败：不调用 Service", async () => {
      const result = await updateDeptAction(
        "dept-001",
        {
          name: "",
          parentId: null,
        },
      );

      expect(result).toEqual({
        ok: false,
        message: "请填写部门名称",
      });

      expect(mocks.updateDept).not.toHaveBeenCalled();
      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("Service 抛出业务错误：返回具体原因", async () => {
      mocks.updateDept.mockRejectedValue(
        new BizError("不能把自己设为上级部门"),
      );

      const result = await updateDeptAction(
        "dept-001",
        {
          name: "研发中心",
          parentId: null,
        },
      );

      expect(result).toEqual({
        ok: false,
        message: "不能把自己设为上级部门",
      });

      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });
  });

  describe("deleteDeptAction", () => {
    it("合法 ID：调用 Service 并返回成功", async () => {
      const result = await deleteDeptAction("dept-001");

      expect(result).toEqual({ ok: true });

      expect(mocks.deleteDept).toHaveBeenCalledWith("dept-001");
      expect(mocks.revalidatePath).toHaveBeenCalledWith("/dept");
    });

    it("ID 不合法：拒绝调用 Service", async () => {
      const result = await deleteDeptAction("   ");

      expect(result).toEqual({
        ok: false,
        message: "部门 ID 不合法",
      });

      expect(mocks.deleteDept).not.toHaveBeenCalled();
      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("存在下级部门：将业务错误返回给前端", async () => {
      mocks.deleteDept.mockRejectedValue(
        new BizError("存在下级部门，不能删除，建议改用停用"),
      );

      const result = await deleteDeptAction("dept-001");

      expect(result).toEqual({
        ok: false,
        message: "存在下级部门，不能删除，建议改用停用",
      });

      expect(mocks.revalidatePath).not.toHaveBeenCalled();
    });

    it("数据库异常：返回通用删除失败提示", async () => {
      const error = new Error("数据库连接失败");

      mocks.deleteDept.mockRejectedValue(error);

      const consoleSpy = vi
        .spyOn(console, "error")
        .mockImplementation(() => {});

      try {
        const result = await deleteDeptAction("dept-001");

        expect(result).toEqual({
          ok: false,
          message: "删除失败，请稍后重试",
        });

        expect(consoleSpy).toHaveBeenCalledWith(error);
        expect(mocks.revalidatePath).not.toHaveBeenCalled();
      } finally {
        consoleSpy.mockRestore();
      }
    });
  });
});
```

接下来，我们逐步理解这份测试代码的设计。

## 五、理解测试中的关键写法

### 1. `vi.mock()`：把外部依赖替换成模拟对象

例如：

```typescript
vi.mock("@/server/dept/service", () => ({
  createDept: mocks.createDept,
  updateDept: mocks.updateDept,
  deleteDept: mocks.deleteDept,
}));
```

这段代码告诉 Vitest：测试运行时，不使用真实的 Service 实现，而使用我们准备好的 Mock 函数。

因此，当 Action 调用：

```typescript
deptService.createDept(input);
```

实际执行的是测试中的模拟函数，不会连接 PostgreSQL。

同样，`next/cache` 也被替换了：

```typescript
vi.mock("next/cache", () => ({
  revalidatePath: mocks.revalidatePath,
}));
```

这样我们可以检查页面重新验证函数有没有被调用，而不需要启动真正的 Next.js 页面渲染流程。

### 2. `mockResolvedValue()`：模拟成功结果

在 `beforeEach()` 中：

```typescript
mocks.createDept.mockResolvedValue({});
```

表示默认情况下，调用 `createDept()` 会返回一个成功完成的 Promise，其结果是 `{}`。

这里并不关心数据库实际返回了哪条部门记录，因为当前 Action 只返回 `{ ok: true }`，不把 Service 返回的部门记录传递给前端。

如果未来 Action 需要返回新建部门的 ID，就应该同步调整 Action 的实现和测试预期。

### 3. `mockRejectedValue()`：模拟异常

例如：

```typescript
mocks.deleteDept.mockRejectedValue(
  new BizError("存在下级部门，不能删除，建议改用停用"),
);
```

我们人为让 Service 抛出一个业务错误。

随后调用 `deleteDeptAction()`，就可以检查它是否返回了正确的业务提示。

这个测试并没有真正创建一个拥有下级部门的数据库记录，也没有重新测试删除规则。它只是在验证：**当 Service 告诉 Action“这次操作不允许执行”时，Action 是否正确传达这个结果。**

### 4. `toHaveBeenCalledWith()`：验证实际调用参数

例如：

```typescript
expect(mocks.updateDept).toHaveBeenCalledWith(
  "dept-001",
  input,
);
```

这不仅验证 Action 返回成功，还验证它把正确的 ID 和数据传给了 Service。

同理：

```typescript
expect(mocks.createDept).not.toHaveBeenCalled();
```

用于验证输入校验失败后，Action 确实在调用 Service 之前就终止了流程。

这些断言比单纯检查返回值更有价值，因为它们能帮助我们发现调用顺序或参数传递错误。

### 5. 为什么还要检查 `revalidatePath()`？

成功测试中：

```typescript
expect(mocks.revalidatePath).toHaveBeenCalledWith("/dept");
```

失败测试中：

```typescript
expect(mocks.revalidatePath).not.toHaveBeenCalled();
```

这两类断言共同验证了一个重要约束：

- 业务操作成功后，刷新相关页面缓存。
- 业务操作失败时，不执行成功路径中的缓存重新验证。

这正是 `run()` 这个公共包装函数应该保证的行为。

### 6. 为什么要用 `try/finally` 恢复 `console.error`？

在测试普通异常时，我们使用：

```typescript
const consoleSpy = vi
  .spyOn(console, "error")
  .mockImplementation(() => {});
```

这样可以检查错误是否被记录，同时避免测试过程中输出大量预期内的错误日志。

使用 `finally` 恢复原始函数，可以避免这个测试影响后续测试。

测试环境中的 Mock 也需要明确管理，否则测试之间可能相互干扰。

## 六、运行测试

在项目根目录执行：

```bash
pnpm exec vitest run tests/dept-actions.test.ts
```

这条命令只运行当前文件，不会启动监听模式，适合我们在编写测试时快速验证结果。

如果希望使用 `package.json` 中的脚本，也可以执行：

```bash
pnpm test -- tests/dept-actions.test.ts
```

测试通过后，可以看到 Vitest 汇总的测试文件和用例执行结果。

如果有测试失败，优先检查以下几个方面：

1. `actions.ts` 中实际返回的错误消息是否与测试预期一致。
2. `DeptInputSchema` 是否按照预期执行了 `.trim()` 等数据转换。
3. Action 中导入 Service 的路径是否与 `vi.mock()` 使用的路径一致。
4. Vitest 是否正确配置了 `@/` 路径别名。
5. Action 的实际实现是否与本文测试代码保持一致。

特别要注意，本文的测试文件是基于上一篇展示的 Action 和 Schema 版本编写的。如果你在自己的项目中调整过错误消息、返回结构或 ID 校验逻辑，应同步调整测试预期，而不是为了让测试通过就随意修改业务实现。

## 七、这些测试仍然没有覆盖什么？

测试通过，只能说明我们验证过的行为符合预期，并不意味着整个部门管理模块已经没有问题。

当前测试有三个明确边界。

### 1. 没有验证真实数据库操作

因为 Service 已经被 Mock，测试无法验证：

- 数据库事务是否正确提交或回滚。
- 部门编码是否真正写入数据库。
- 修改部门层级时，后代编码是否同步更新。
- 删除部门时，数据库约束是否正常工作。

这些问题应当由 Service 单元测试和必要的数据库集成测试覆盖。

### 2. 没有验证真实的 Next.js 缓存行为

这里模拟的是 `revalidatePath()` 函数。

测试可以证明 Action 在成功时调用了它，但不能证明真实页面的所有缓存和数据依赖都已经正确配置。

页面重新验证的实际效果，仍需要结合 Next.js 运行环境进行验证。

### 3. 没有验证登录态和权限控制

当前代码中的登录态和权限检查仍然是 `TODO`。

所以，即使上述测试全部通过，也不能认为 Action 已经具备生产级安全能力。

正式接入用户认证和权限模块后，还应增加相应测试，例如：

- 未登录用户调用 Action 时拒绝操作。
- 没有新增权限的用户不能新增部门。
- 没有删除权限的用户不能删除部门。
- 用户不能越权修改无权管理的数据。

**测试不能替代安全设计，只能帮助我们验证已经实现的安全规则。**

- 工具函数层：验证纯计算规则。
