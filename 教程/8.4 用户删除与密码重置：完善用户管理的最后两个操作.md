# 8.4 用户删除与密码重置：完善用户管理的最后两个操作

在前面的章节中，我们已经完成了用户新增和用户编辑。

- 8.2 用户新增：完成用户信息校验、密码哈希和数据库写入。
- 8.3 用户编辑：修改姓名、邮箱、手机号和状态，不在资料编辑表单中修改密码。
- 8.4 用户删除与密码重置：处理用户生命周期中的删除操作，以及账号凭据管理。

本节继续沿用项目现有的 Next.js App Router、Prisma、Zod、Server Actions 和 shadcn/Base UI 技术栈，完成两个独立的业务操作。

本节的目标不是简单地给表格增加两个按钮，而是让用户管理具备完整的业务规则、服务端校验、数据一致性和操作反馈。

## 一、明确业务规则

在编写代码之前，先确定删除用户和重置密码的业务规则。

| 操作 | 业务规则 |
| --- | --- |
| 删除用户 | 禁止删除当前登录用户；检查关联数据；不允许破坏历史业务记录 |
| 重置密码 | 使用独立弹窗；校验新密码；只保存密码哈希 |
| 会话管理 | 密码重置后使已有登录会话失效 |
| 权限控制 | 在服务端验证操作权限，不能只隐藏前端按钮 |
| 操作反馈 | 成功后刷新列表，失败时显示明确原因 |

这里有一个重要的设计原则：**用户删除与用户停用不是同一件事。**

在实际的项目管理平台中，一个用户可能已经参与过项目、任务分配、工时填报或费用记录。如果直接删除用户，可能导致历史数据失去对应人员，甚至触发数据库外键约束错误。

因此，本节采用以下策略：

1. 对没有不可删除关联记录的用户，可以执行物理删除。
2. 对已经关联历史业务数据的用户，拒绝物理删除，优先通过用户编辑功能将其停用。
3. 删除操作必须在服务端再次检查，不能把弹窗确认当成安全保障。

## 二、增加删除与重置密码的 Zod Schema

打开 `server/user/schema.ts`。

保留前面章节已经定义的 `createUserSchema`、`updateUserSchema` 和密码校验规则，在文件中追加以下内容。

```ts
import { z } from "zod";

export const deleteUserSchema = z.object({
  id: z.string().trim().min(1, "用户 ID 不能为空"),
});

export type DeleteUserInput = z.infer<
  typeof deleteUserSchema
>;

export const resetUserPasswordSchema = z.object({
  id: z.string().trim().min(1, "用户 ID 不能为空"),
  password: passwordSchema,
});

export type ResetUserPasswordInput = z.infer<
  typeof resetUserPasswordSchema
>;
```

如果文件顶部已经导入了 `z`，不需要重复导入。

这里定义了两种不同的输入结构：

- `DeleteUserInput`：只需要用户 ID。
- `ResetUserPasswordInput`：需要用户 ID 和新密码。

客户端传入的用户 ID 只用于指定操作对象，并不代表客户端已经获得操作权限。身份认证、授权检查和参数校验是三个独立的步骤。

密码规则直接复用 8.2 封装的 `passwordSchema`（包含长度限制与弱密码黑名单），而不是在这里重复校验长度。客户端弹窗里的长度检查只是即时反馈，最终以服务端 `passwordSchema` 为准。

## 三、在 Service 层实现删除用户

Service 层负责业务规则与数据库操作，不负责弹窗状态、页面刷新或前端提示。

打开 `server/user/service.ts`，根据当前项目的导入路径复用已有的 `db` 实例。

### 3.1 检查删除条件

在删除用户之前，需要检查以下事项：

1. 用户是否存在。
2. 操作对象是否为当前登录用户。
3. 用户是否关联了不可删除的业务数据。
4. 用户角色和登录会话是否需要清理。

当前项目的 `User` 模型已经关联 `UserRole` 和 `Session`。随着项目继续开发，还可能增加任务执行人、项目负责人、工时记录等关联关系。

这些关联必须以实际的 Prisma Schema 为准。下面给出删除服务的基础实现：

```ts
export async function deleteUser(
  id: string,
  currentUserId: string,
) {
  if (id === currentUserId) {
    throw new Error("不能删除当前登录用户");
  }

  return db.$transaction(async (tx) => {
    const user = await tx.user.findUnique({
      where: { id },
      select: {
        id: true,
        username: true,
      },
    });

    if (!user) {
      throw new Error("用户不存在或已被删除");
    }

    // 在这里检查项目中所有不可删除的业务关联。
    // 如果存在历史业务记录，拒绝物理删除。
    //
    // 例如：项目负责人、任务执行人、工时记录等。
    // 具体查询必须根据当前 Prisma Schema 实现。

    await tx.session.deleteMany({
      where: { userId: id },
    });

    await tx.userRole.deleteMany({
      where: { userId: id },
    });

    await tx.user.delete({
      where: { id },
    });

    return { id: user.id };
  });
}
```

**注意：以上代码只有在补齐业务关联检查后才能用于正式删除。** 注释中的业务检查是上线前必须完成的实现任务，不是可以忽略的可选功能。

如果项目中存在引用用户的业务记录，应先查询这些记录。一旦发现不可删除的关联，就抛出业务错误，停止删除流程。

这里使用 Prisma 事务，是因为删除用户涉及多个数据库写操作。事务能够确保这些写入作为一个整体提交或回滚。<https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions>

需要注意，事务本身并不能替代业务规则。它只能保证操作的一致性，不能自动判断历史业务数据是否允许删除。

## 四、在 Service 层实现密码重置

密码重置不属于用户资料编辑。它是独立的账号凭据管理操作。

打开 `server/user/service.ts`，复用 8.2 中已经封装的密码哈希函数。

```ts
import { hashPassword } from "@/server/auth/password";

export async function resetUserPassword(
  id: string,
  password: string,
  currentUserId: string,
) {
  if (id === currentUserId) {
    throw new Error("不能通过此操作重置自己的密码");
  }

  const passwordHash = await hashPassword(password);

  return db.$transaction(async (tx) => {
    const user = await tx.user.findUnique({
      where: { id },
      select: { id: true },
    });

    if (!user) {
      throw new Error("用户不存在");
    }

    await tx.user.update({
      where: { id },
      data: { passwordHash },
    });

    await tx.session.deleteMany({
      where: { userId: id },
    });

    return { id: user.id };
  });
}
```

如果 `hashPassword()` 已经在文件顶部导入，不需要再次导入。函数名称和参数应与 8.2 中的实际实现保持一致。

密码重置有三个需要特别关注的地方。

**第一，数据库只保存哈希。**

不要把明文密码保存到数据库，也不要在日志中输出明文密码或密码哈希。

**第二，密码重置成功后清理旧会话。**

当前项目使用 `Session` 表管理登录会话，因此删除目标用户的现有会话可以使这些会话失效。实际效果仍取决于会话校验是否在每次请求中检查数据库中的会话记录。

**第三，事务中不要混入无关操作。**

密码哈希可以在事务开始前计算，事务内部只负责检查用户、更新密码和清理会话，减少数据库事务持续时间。

## 五、在 Server Action 层提供操作入口

用户删除和密码重置都属于由页面主动触发的写操作，适合通过 Server Action 调用 Service。

打开 `server/user/actions.ts`，将新导入合并到文件顶部，追加以下两个 Action。与 8.2、8.3 相同，项目的 Server Action 统一放在 `server/<模块>/actions.ts` 中，业务组件通过 `@/server/user/actions` 导入。

下面沿用前面章节的 `CreateUserActionState` 作为返回类型示例。如果项目已经统一成 `ActionResult`，应直接复用项目当前的统一类型。

```ts
"use server";

import { revalidatePath } from "next/cache";
import { getCurrentSession } from "@/server/auth/session";

import {
  deleteUserSchema,
  resetUserPasswordSchema,
} from "@/server/user/schema";

import {
  deleteUser,
  resetUserPassword,
} from "@/server/user/service";

export async function deleteUserAction(
  input: unknown,
): Promise<CreateUserActionState> {
  const session = await getCurrentSession();

  if (!session) {
    return {
      success: false,
      message: "请先登录",
    };
  }

  // 必须在这里接入真实的用户删除权限检查。

  const parsed = deleteUserSchema.safeParse(input);

  if (!parsed.success) {
    return {
      success: false,
      message: "请求参数不正确",
    };
  }

  try {
    await deleteUser(
      parsed.data.id,
      session.user.id,
    );

    revalidatePath("/users");

    return {
      success: true,
      message: "用户删除成功",
    };
  } catch (error) {
    return {
      success: false,
      message:
        error instanceof Error
          ? error.message
          : "删除用户失败",
    };
  }
}

export async function resetUserPasswordAction(
  input: unknown,
): Promise<CreateUserActionState> {
  const session = await getCurrentSession();

  if (!session) {
    return {
      success: false,
      message: "请先登录",
    };
  }

  // 必须在这里接入真实的密码重置权限检查。

  const parsed = resetUserPasswordSchema.safeParse(input);

  if (!parsed.success) {
    return {
      success: false,
      message:
        parsed.error.issues[0]?.message ??
        "请求参数不正确",
    };
  }

  try {
    await resetUserPassword(
      parsed.data.id,
      parsed.data.password,
      session.user.id,
    );

    revalidatePath("/users");

    return {
      success: true,
      message: "密码重置成功，用户需要重新登录",
    };
  } catch (error) {
    return {
      success: false,
      message:
        error instanceof Error
          ? error.message
          : "重置密码失败",
    };
  }
}
```

注意以下几点：

- `"use server"` 应放在文件顶部。若现有文件已经有该声明，不要重复添加。
- `session.user.id` 必须与项目中 `getCurrentSession()` 的实际返回结构一致。
- `CreateUserActionState` 只是沿用前面章节的示例类型。如果项目已有通用 Action 返回类型，应直接使用通用类型。
- `revalidatePath("/users")` 用于刷新用户列表对应的服务端缓存。

### 5.1 必须补齐真实权限检查

上面的权限检查注释不能直接留到生产环境。

有效登录会话只代表请求者已经登录，并不代表他有权删除用户或重置其他人的密码。

项目已经有角色和权限相关的数据模型，后续需要通过统一的服务端权限服务分别校验：

- 用户删除权限。
- 用户密码重置权限。

检查必须在 Server Action 中执行，不能只在页面上隐藏操作按钮。

## 六、实现删除用户确认弹窗

新建文件：

`app/(dashboard)/users/_components/delete-user-dialog.tsx`

删除操作需要二次确认，避免管理员误操作。

下面按照项目常见的 shadcn `AlertDialog` 组件接口编写。如果当前封装基于 Base UI 的 API 与示例不同，应以项目实际组件导出和事件签名为准。

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

import { deleteUserAction } from "@/server/user/actions";

import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
} from "@/components/ui/alert-dialog";

type DeleteUserDialogProps = {
  user: {
    id: string;
    username: string;
    name: string;
  };
  open: boolean;
  onOpenChange: (open: boolean) => void;
};

export function DeleteUserDialog({
  user,
  open,
  onOpenChange,
}: DeleteUserDialogProps) {
  const router = useRouter();

  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  async function handleDelete() {
    setLoading(true);
    setError("");

    try {
      const result = await deleteUserAction({
        id: user.id,
      });

      if (!result.success) {
        setError(result.message ?? "删除失败");
        return;
      }

      onOpenChange(false);
      router.refresh();
    } catch {
      setError("请求失败，请稍后重试");
    } finally {
      setLoading(false);
    }
  }

  // Base UI 弹窗用条件渲染控制开关，避免关闭动画被打断后卡死
  if (!open) return null;

  return (
    <AlertDialog
      open
      onOpenChange={(nextOpen) => {
        if (!loading) {
          onOpenChange(nextOpen);
        }
      }}
    >
      <AlertDialogContent>
        <AlertDialogHeader>
          <AlertDialogTitle>
            确认删除用户？
          </AlertDialogTitle>

          <AlertDialogDescription>
            即将删除用户「{user.name}」
            （{user.username}）。
            如果该用户关联了历史业务数据，
            系统将拒绝物理删除。
          </AlertDialogDescription>
        </AlertDialogHeader>

        {error && (
          <p className="text-sm text-destructive">
            {error}
          </p>
        )}

        <AlertDialogFooter>
          <AlertDialogCancel disabled={loading}>
            取消
          </AlertDialogCancel>

          <AlertDialogAction
            onClick={(event) => {
              event.preventDefault();
              void handleDelete();
            }}
            disabled={loading}
          >
            {loading ? "删除中..." : "确认删除"}
          </AlertDialogAction>
        </AlertDialogFooter>
      </AlertDialogContent>
    </AlertDialog>
  );
}
```

弹窗组件只负责展示确认信息、触发 Action 和反馈结果。真正的删除规则仍然放在服务端。

与 8.2、8.3 相同，本组件有两处结合项目实际的调整：`AlertDialog` 外层用 `if (!open) return null` 条件渲染控制开关，规避 Base UI 关闭动画被打断导致弹窗卡死；`deleteUserAction` 从 `@/server/user/actions` 导入。

## 七、实现重置密码弹窗

新建文件：

`app/(dashboard)/users/_components/reset-user-password-dialog.tsx`

密码重置使用独立表单，提供新密码和确认密码两个输入框。

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

import { resetUserPasswordAction } from "@/server/user/actions";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

import {
  Dialog,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
} from "@/components/ui/dialog";

type ResetUserPasswordDialogProps = {
  user: {
    id: string;
    username: string;
    name: string;
  };
  open: boolean;
  onOpenChange: (open: boolean) => void;
  /** 重置成功后由父组件展示成功提示 */
  onSuccess?: (message: string) => void;
};

export function ResetUserPasswordDialog({
  user,
  open,
  onOpenChange,
  onSuccess,
}: ResetUserPasswordDialogProps) {
  const router = useRouter();

  const [password, setPassword] = useState("");
  const [confirmPassword, setConfirmPassword] = useState("");
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  function handleOpenChange(nextOpen: boolean) {
    if (loading) return;

    onOpenChange(nextOpen);

    if (!nextOpen) {
      setPassword("");
      setConfirmPassword("");
      setError("");
    }
  }

  async function handleSubmit(
    event: React.FormEvent<HTMLFormElement>,
  ) {
    event.preventDefault();
    setError("");

    if (password.length < 12 || password.length > 128) {
      setError("密码长度必须为 12–128 个字符");
      return;
    }

    if (password !== confirmPassword) {
      setError("两次输入的密码不一致");
      return;
    }

    setLoading(true);

    try {
      const result = await resetUserPasswordAction({
        id: user.id,
        password,
      });

      if (!result.success) {
        setError(result.message ?? "重置密码失败");
        return;
      }

      onSuccess?.(result.message || "密码重置成功");
      handleOpenChange(false);
      router.refresh();
    } catch {
      setError("请求失败，请稍后重试");
    } finally {
      setLoading(false);
    }
  }

  // Base UI 弹窗用条件渲染控制开关，避免关闭动画被打断后卡死
  if (!open) return null;

  return (
    <Dialog
      open
      onOpenChange={handleOpenChange}
    >
      <DialogContent>
        <DialogHeader>
          <DialogTitle>重置用户密码</DialogTitle>

          <DialogDescription>
            为用户「{user.name}」
            （{user.username}）设置新密码。
            重置成功后，该用户需要重新登录。
          </DialogDescription>
        </DialogHeader>

        <form
          onSubmit={handleSubmit}
          className="space-y-4"
        >
          <div className="space-y-2">
            <Label htmlFor="reset-password">
              新密码
            </Label>

            <Input
              id="reset-password"
              type="password"
              autoComplete="new-password"
              value={password}
              onChange={(event) =>
                setPassword(event.target.value)
              }
              minLength={12}
              maxLength={128}
              required
            />
          </div>

          <div className="space-y-2">
            <Label htmlFor="confirm-password">
              确认新密码
            </Label>

            <Input
              id="confirm-password"
              type="password"
              autoComplete="new-password"
              value={confirmPassword}
              onChange={(event) =>
                setConfirmPassword(event.target.value)
              }
              minLength={12}
              maxLength={128}
              required
            />
          </div>

          {error && (
            <p className="text-sm text-destructive">
              {error}
            </p>
          )}

          <DialogFooter>
            <Button
              type="button"
              variant="outline"
              disabled={loading}
              onClick={() => handleOpenChange(false)}
            >
              取消
            </Button>

            <Button
              type="submit"
              disabled={loading}
            >
              {loading ? "提交中..." : "确认重置"}
            </Button>
          </DialogFooter>
        </form>
      </DialogContent>
    </Dialog>
  );
}
```

这里有几个实现细节值得注意：

1. 使用 `type="password"` 避免直接显示输入内容。
2. 使用 `autoComplete="new-password"` 告诉浏览器这是新密码输入框。
3. 关闭弹窗时清空密码，避免重新打开时残留上一次的输入。
4. 客户端检查两次密码是否一致，服务端仍然独立验证密码长度和弱密码规则。
5. 密码只提交给 Server Action，不放在 URL、日志或用户列表数据中。

此外，本组件与 8.2、8.3 相同采用条件渲染控制弹窗开关（`if (!open) return null`），`resetUserPasswordAction` 从 `@/server/user/actions` 导入。

组件还接收可选的 `onSuccess` 回调：重置成功后，弹窗把 Action 返回的成功消息交给父组件展示，随后关闭弹窗并刷新列表。这样即使弹窗立即关闭，操作者仍能在列表上方看到明确的成功提示，而不是面对一个悄然消失的窗口。

接下来，把 8.3 增加的编辑按钮改为按钮组，并加入重置密码与删除：

```tsx
<div className="flex items-center gap-2">
  <Button
    variant="outline"
    size="sm"
    onClick={() => setEditingUser(user)}
  >
    编辑
  </Button>

  <Button
    variant="outline"
    size="sm"
    onClick={() => setResettingPasswordUser(user)}
  >
    重置密码
  </Button>

  <Button
    variant="destructive"
    size="sm"
    onClick={() => setDeletingUser(user)}
  >
    删除
  </Button>
</div>
```

最后，在工作区的 JSX 中渲染两个弹窗：

```tsx
{deletingUser && (
  <DeleteUserDialog
    user={deletingUser}
    open={true}
    onOpenChange={(open) => {
      if (!open) setDeletingUser(null);
    }}
  />
)}

{resettingPasswordUser && (
  <ResetUserPasswordDialog
    user={resettingPasswordUser}
    open={true}
    onOpenChange={(open) => {
      if (!open) setResettingPasswordUser(null);
    }}
    onSuccess={(message) => setSuccessMessage(message)}
  />
)}
```

以上代码假设列表数据至少包含 `id`、`username` 和 `name`。如果当前查询没有返回这些字段，需要同步调整查询结果和类型定义。

由于弹窗成功后会立即关闭，本项目在工具栏与表格之间增加了一条成功提示条：`successMessage` 有值时显示绿色文本（`role="status"`），4 秒后自动清除。提示条放在 JSX 中表格容器之前：

```tsx
{successMessage && (
  <p
    role="status"
    className="text-sm text-green-600"
  >
    {successMessage}
  </p>
)}
```

删除、编辑、新增目前沿用关闭即刷新的反馈方式。如果后续希望所有操作都有统一提示，可以把这条提示条与 `setSuccessMessage` 复用到其他弹窗。

至此，用户列表就拥有了四项基础操作：新增、编辑、重置密码和删除。

## 九、验证操作是否真正完成

不要只检查按钮和弹窗是否能够正常显示，还需要验证服务端和数据库行为。

| 测试场景 | 预期结果 |
| --- | --- |
| 删除当前登录用户 | 服务端拒绝，用户记录不变 |
| 删除不存在的用户 | 返回明确错误 |
| 删除有关联业务数据的用户 | 拒绝物理删除 |
| 删除允许删除的用户 | 用户、角色关联和会话一致清理 |
| 密码长度不足 | 客户端提示，服务端再次拒绝 |
| 两次密码不一致 | 不提交重置请求 |
| 重置密码成功 | 更新密码哈希，旧会话失效 |
| 未登录用户执行操作 | 服务端拒绝 |
| 无删除或重置权限的用户执行操作 | 服务端拒绝 |
| 操作成功后刷新页面 | 列表反映最新数据 |

尤其需要验证密码重置后的会话失效。如果项目只在登录时校验会话，而没有在后续请求中检查会话是否仍存在，那么删除 `Session` 记录未必能立即阻止已有会话继续访问。必须结合实际的会话验证流程确认。

## 十、本节总结

本节完成了用户管理的最后两个基础操作。

**删除用户** 不只是执行 `delete()`，而是需要检查关联数据、保护当前登录用户，并通过事务保证多表操作的一致性。

**重置密码** 不应混入资料编辑表单，而应独立完成密码校验、哈希处理、数据库更新和旧会话清理。

经过 8.2、8.3 和 8.4，用户管理的基础 CRUD 与凭据管理已经形成完整的分层结构：

- Schema：定义并校验输入数据。
- Service：实现业务规则和数据库操作。
- Server Action：验证请求身份、执行授权检查并调用 Service。
- UI：负责交互、确认和操作反馈。

正式上线前，还需要根据完整 Prisma Schema 补齐用户删除的业务关联检查，并接入真实的服务端权限服务。只有这两项完成后，用户管理模块才具备可靠的生产使用基础。
