# 前言

上一篇（6.5），我们完成了部门管理的服务层：`createDept`、`updateDept` 和 `deleteDept`。

这三个函数已经具备了基本的业务处理能力。例如，新增部门时生成部门编码、计算排序；修改部门时检查层级关系、同步更新下级部门编码；删除部门时判断是否存在下级部门。

但现在有一个问题：**这些函数虽然能操作数据库，浏览器里的按钮却不能直接调用它们。**

为什么？

因为 `service.ts` 属于服务端代码，它依赖数据库客户端，负责执行真正的业务操作。如果让浏览器直接接触数据库，不仅破坏了前后端的安全边界，也会让数据库连接、业务规则和权限控制暴露在不合理的位置。

前面几课，我们主要解决的是“读数据”：服务端组件查询数据库，再把查询结果渲染成页面。

现在要解决的是“写数据”：用户在页面上点击新增、编辑或删除，服务端如何安全地接收到请求，调用对应的业务函数，并把执行结果返回给前端？

这就需要建立一条新的调用通道。

本篇（6.6），我们使用 **Next.js Server Actions**，把前端操作与上一课的服务层连接起来。

完成后，部门管理就具备了从前端发起写入操作的服务端入口。下一篇再实现表单弹窗，让用户能够通过界面实际操作这些功能。

# 实操步骤

## 第四步：使用 Server Actions 打通写入通道

先看一下我们要实现的调用链路：

```text
用户点击新增 / 编辑 / 删除
            ↓
        前端组件
            ↓
       Server Action
    接收参数、校验权限
            ↓
        Service 层
    执行业务规则与事务
            ↓
          数据库
            ↓
       返回执行结果
            ↓
      前端显示提示信息
            ↓
     重新获取页面数据
```

这里需要明确两个职责。

- **Service 层**：负责业务规则、数据校验和数据库操作。
- **Server Actions 层**：负责为前端提供服务端调用入口，处理调用结果，并在成功后刷新相关页面数据。

这样划分后，前端不需要了解部门编码如何生成、数据库事务如何执行，也不需要重复实现业务规则。它只需要调用对应的 Action，再根据返回结果决定显示成功提示还是错误信息。

### 1. 创建 Action 文件

在项目中创建 `server/dept/actions.ts`。

```typescript
"use server";

import { revalidatePath } from "next/cache";
import { Prisma } from "@/lib/generated/prisma/client";
import { BizError } from "@/lib/biz-error";
import * as deptService from "./service";
import type { DeptInput } from "@/server/dept/types";

/**
 * 统一处理服务层调用结果。
 *
 * 成功：刷新部门管理页面，并返回成功状态。
 * 业务错误：返回具体原因。
 * 其他错误：记录服务端日志，返回通用提示。
 */
async function run(
  fn: () => Promise<unknown>,
  fallback: string,
) {
  try {
    await fn();

    revalidatePath("/dept");

    return { ok: true as const };
  } catch (error) {
    if (error instanceof BizError) {
      return {
        ok: false as const,
        message: error.message,
      };
    }

    // 并发写入导致编码撞上唯一约束：提示重试，而不是暴露数据库错误
    if (
      error instanceof Prisma.PrismaClientKnownRequestError &&
      error.code === "P2002"
    ) {
      return {
        ok: false as const,
        message: "编码冲突，请重试或联系管理员",
      };
    }

    // 外键约束：删除时仍被其他数据引用（例如并发插入了子部门）
    if (
      error instanceof Prisma.PrismaClientKnownRequestError &&
      error.code === "P2003"
    ) {
      return {
        ok: false as const,
        message: "该部门仍被其他数据引用，不能删除",
      };
    }

    console.error(error);

    return {
      ok: false as const,
      message: fallback,
    };
  }
}

/** 新增部门 */
export async function createDeptAction(input: DeptInput) {
  // TODO：接入登录态校验与新增权限检查
  return run(
    () => deptService.createDept(input),
    "保存失败，请稍后重试",
  );
}

/** 修改部门 */
export async function updateDeptAction(
  id: string,
  input: DeptInput,
) {
  // TODO：接入登录态校验与编辑权限检查
  return run(
    () => deptService.updateDept(id, input),
    "保存失败，请稍后重试",
  );
}

/** 删除部门 */
export async function deleteDeptAction(id: string) {
  // TODO：接入登录态校验与删除权限检查
  return run(
    () => deptService.deleteDept(id),
    "删除失败，请稍后重试",
  );
}
```

代码不长，但它把前端操作与已有的服务层连接起来了。接下来，我们逐一理解其中的关键设计。

## 2. `"use server"` 到底做了什么？

文件第一行是：

```typescript
"use server";
```

这是 Next.js 的 Server Actions 指令。放在模块顶部时，该模块导出的函数会被标记为 Server Functions，供客户端通过 Next.js 提供的调用机制请求执行。

例如，前端可以这样调用：

```typescript
const result = await createDeptAction({
  name: "研发部",
  parentId: null,
});
```

调用形式看起来像普通的异步函数，但它不是让浏览器直接执行 `createDeptAction` 的业务代码。Next.js 会负责将调用转化为发往服务端的请求，再由服务端执行对应函数。

这意味着：

- 前端不需要自行编写一套 API 路由来接收这次操作。
- `service.ts` 中的数据库操作仍然在服务端执行。
- 前端可以直接使用返回结果，判断操作是否成功。

不过，要注意：**Server Actions 只是简化了服务端调用方式，并没有消除前后端之间的网络请求，也不会自动完成身份认证和权限控制。**

另外，`"use server"` 并不意味着模块里的所有内容都会自动变得安全。Server Action 的导出函数仍然需要严格控制能够执行的操作和能够接收的参数。

## 3. 为什么需要统一的 `run()` 函数？

观察三个 Action，会发现它们的结构几乎完全相同：

```typescript
return run(
  () => deptService.createDept(input),
  "保存失败，请稍后重试",
);
```

如果没有 `run()`，三个函数就都需要重复编写 `try/catch`、错误判断和页面刷新逻辑。

随着项目继续扩展，后续还会出现部门停用、部门启用、部门排序等操作。如果每个 Action 都复制一套相同的处理代码，维护成本就会不断增加。

因此，我们将这些公共逻辑抽取到 `run()` 中。

它主要完成三件事。

### 第一件事：执行服务层函数

```typescript
await fn();
```

`fn` 是一个函数，调用后返回一个 Promise。

例如：

```typescript
() => deptService.createDept(input)
```

这里传入的是函数本身，而不是提前执行后的结果。

`run()` 在自己的 `try` 代码块中调用它，因此能够统一捕获服务层执行过程中抛出的异常。

同时，新增、修改、删除的具体业务仍然留在 Service 层。`run()` 不需要知道部门编码怎么生成，也不需要知道删除部门时为什么要检查下级部门。

### 第二件事：区分业务错误和系统错误

```typescript
if (error instanceof BizError) {
  return {
    ok: false as const,
    message: error.message,
  };
}

console.error(error);

return {
  ok: false as const,
  message: fallback,
};
```

上一篇已经定义了 `BizError`，用于表达可以向用户说明的业务问题。

例如：

- 部门名称不能为空。
- 部门不存在，可能已被删除。
- 存在下级部门，不能删除，建议改用停用。
- 不能把自己或自己的下级设置为上级。

这些错误是业务规则的正常反馈，不应该让用户只能看到一个笼统的“操作失败”。

因此，遇到 `BizError` 时，我们把具体的错误消息返回给前端。

但数据库连接失败、程序异常等系统错误，不应该把底层错误详情直接暴露给用户。我们在服务端记录异常日志，再返回通用提示。

这里的设计原则是：

**业务错误用于指导用户，系统错误用于帮助开发人员排查问题。**

需要注意，`console.error()` 只是示例中的基础日志方式。正式项目还应结合实际部署环境配置日志采集、访问控制和敏感信息脱敏。

除了 `BizError`，还有两类数据库约束错误同样可以给出可理解的提示：

- `P2002`：唯一约束冲突。编码由服务层分配，并发写入时仍可能撞号，提示用户重试即可。
- `P2003`：外键约束冲突。删除前的“是否有下级”检查和真正删除之间，可能有人并发插入了子部门；此时数据库会阻止删除，需要转换为“仍被其他数据引用”。

这两类错误虽然来自数据库，但对用户是可解释的，所以放在 `BizError` 之后、通用兜底之前处理。

### 第三件事：成功后刷新页面数据

```typescript
revalidatePath("/dept");
```

在部门管理页面中，服务端组件可能会通过数据库查询获取部门树和部门列表。

当用户新增或修改部门后，即使数据库中的数据已经更新，如果页面没有重新获取数据，用户仍然可能看到旧的内容。

`revalidatePath("/dept")` 用于重新验证指定路径对应的缓存。对于通过该路径重新渲染的服务端内容，Next.js 可以重新获取数据。

这里要注意：它不是简单地在浏览器里执行一次刷新，也不是对所有页面进行全局刷新。它针对的是指定路径相关的缓存与渲染行为。

本篇统一使用 `/dept`，因为它是当前部门管理页面的路径。如果后续编辑功能同时影响其他页面或缓存，还需要根据实际的数据依赖补充相应的重新验证策略。

还有一个容易忽略的细节：当前 `run()` 先执行服务层操作，再调用 `revalidatePath()`。如果业务操作成功，但重新验证时发生异常，当前实现可能仍然返回失败。这不一定代表数据库写入失败。因此，正式项目可以进一步区分“业务执行失败”和“缓存重新验证失败”，避免给用户造成误解。

## 4. 为什么新增、修改、删除都要单独定义 Action？

我们分别定义了三个函数：

```typescript
createDeptAction(input)
updateDeptAction(id, input)
deleteDeptAction(id)
```

看起来它们只是简单地调用服务层，但这层边界非常重要。

首先，它们代表三个不同的业务操作，后续可以分别添加新增、编辑、删除权限。

其次，它们的参数也不同：

| Action | 参数 | 对应的业务操作 |
| --- | --- | --- |
| `createDeptAction` | 部门表单数据 | 新增部门 |
| `updateDeptAction` | 部门 ID、表单数据 | 修改部门 |
| `deleteDeptAction` | 部门 ID | 删除部门 |

最后，统一的返回结构让前端不需要针对每个操作设计不同的结果处理方式。

成功时：

```typescript
{ ok: true }
```

失败时：

```typescript
{ ok: false, message: "存在下级部门，不能删除，建议改用停用" }
```

前端只需要判断 `ok`。如果为 `false`，就读取 `message` 并展示错误提示。

需要说明的是，这里的 `run()` 只负责返回操作状态，并不负责返回创建或更新后的部门记录。如果下一篇的界面需要立即使用新记录的 ID 或编码，就需要进一步设计 Action 的返回数据结构。

## 5. 两个必须明确的安全边界

目前的代码已经打通了调用链路，但还不能直接视为完整的生产级权限实现。

### 边界一：Server Action 不能代替身份认证和权限控制

代码中有这样的注释：

```typescript
// TODO：接入登录态校验与新增权限检查
```

它目前只是提醒，并没有真正实现安全控制。

Server Action 应当被视为可以通过请求触达的服务端入口。不能因为前端页面没有显示删除按钮，就认为用户无法调用删除操作。

真实项目中，每个 Action 都应当在执行业务之前完成必要的检查：

1. 确认当前请求对应的用户已经登录。
2. 检查用户是否拥有当前操作的权限。
3. 对需要按数据范围控制的操作，确认用户有权操作对应的部门。
4. 校验调用方提交的参数。

例如，即使用户没有看到删除按钮，也不能让他通过直接构造请求绕过前端限制。

**前端控制的是操作入口的展示，服务端控制的才是真正的操作权限。**

### 边界二：服务层校验参数，不代表所有安全问题都解决了

上一篇的 `service.ts` 已经实现了部门名称、排序、状态等业务校验。这些规则仍然应该保留，因为业务规则不应该只依赖前端表单。

但是，调用方传入的数据始终是不可信的。

例如，`input` 的 TypeScript 类型是 `DeptInput`，并不意味着运行时收到的数据一定符合这个类型。TypeScript 类型检查不会自动替代运行时校验。

正式项目还应根据实际需要校验参数结构、字符串长度、字段类型以及用户权限，并为数据库中的唯一约束、关联关系等设置必要的保护。

此外，当前示例中的 `instanceof BizError` 依赖异常对象与当前服务端模块中的 `BizError` 类型一致。若未来引入跨运行时边界或特殊的序列化处理，应重新评估错误识别方式。

# 小结

本篇完成了部门管理写入通道的第四步：创建 Server Actions，将前端操作连接到服务层。

我们得到了一套清晰的分层结构：

- **前端组件**负责收集用户输入、触发操作和展示反馈。
- **Server Actions**负责提供服务端调用入口、处理结果和刷新相关页面数据。
- **Service 层**负责业务规则、数据校验和数据库事务。
- **数据库**负责持久化数据，并通过约束保障数据完整性。

其中，`run()` 将重复的异常处理和页面重新验证逻辑统一起来；`BizError` 则把用户可以理解的业务问题与需要排查的系统异常区分开来。

但要记住：**调用通道打通，不等于安全机制已经完善。** 在正式项目中，登录态、操作权限和运行时参数校验都必须落实到服务端。
