# 7.8 为网站根路径增加登录检查

在上一节中，我们已经实现了登录功能，并且在后台布局中加入了登录状态检查。

但是，目前直接访问 `http://localhost:3000` 时，还没有按照登录状态进行跳转。我们希望网站入口也能具备基本的认证判断：

- 未登录用户访问网站根路径，自动跳转到登录页。
- 已登录用户访问网站根路径，直接进入后台部门管理页面。

本节就来实现这个功能。

## 一、创建根路径页面

在 Next.js App Router 中，`app/page.tsx` 对应网站根路径 `/`。

因此，我们在 `app/page.tsx` 中实现登录检查和页面跳转。

```tsx
import { redirect } from "next/navigation";
import { getCurrentSession } from "@/server/auth/session";

export default async function HomePage() {
  const session = await getCurrentSession();

  if (!session) {
    redirect("/login");
  }

  redirect("/dept");
}
```

这段代码的核心只有三个步骤。

首先，调用 `getCurrentSession()` 获取当前登录会话。这个函数已经在前面的章节中实现，会检查 Cookie 对应的会话是否有效，以及用户是否处于启用状态。

其次，判断会话是否存在：

```tsx
if (!session) {
  redirect("/login");
}
```

如果没有有效会话，说明用户尚未登录，或者原有登录状态已经失效。此时使用 Next.js 的 `redirect()` 将用户重定向到登录页。

最后，如果会话有效，则执行：

```tsx
redirect("/dept");
```

将已经登录的用户直接带到后台部门管理页面。

这里不需要额外编写登录逻辑，也不需要在客户端使用 `useEffect()` 或 `useRouter()`。因为 `app/page.tsx` 是服务端组件，可以在服务端读取当前会话，并在页面渲染前完成判断和跳转。

## 二、验证登录检查

启动项目后，分别测试以下两种情况。

**场景一：用户尚未登录**

在浏览器中访问：

`http://localhost:3000`

预期行为：

```text
访问 /
  ↓
getCurrentSession()
  ↓
没有有效会话
  ↓
跳转到 /login
```

浏览器最终进入登录页面，用户可以输入用户名和密码进行登录。

**场景二：用户已经登录**

先正常登录系统，再访问：

`http://localhost:3000`

预期行为：

```text
访问 /
  ↓
getCurrentSession()
  ↓
存在有效会话
  ↓
跳转到 /dept
```

浏览器直接进入后台部门管理页面，不再停留在根路径。

## 三、修复联调中发现的登录表单问题

根路径检查做完后，实际联调时可能会遇到一个现象：访问 `/` 能正常跳到 `/login`，但输入用户名和密码点登录后，地址栏却变成：

```text
http://localhost:3000/login?username=admin&password=Local-Dev-Admin-2026
```

页面没有登录成功，还需要再输入一次才能进入后台。

这里有两个问题需要说明。

**第一，密码出现在 URL 里是不允许的。** URL 会进入浏览器历史、代理日志和服务器访问日志，密码一旦拼进查询字符串，就等同于明文泄露。

**第二，这是一次原生表单提交，不是我们写的 `loginAction` 调用。** 观察参数名 `username` 和 `password`，正好是 `register("username")` 自动生成的表单字段 `name`。当浏览器直接提交表单时，`<form>` 没有声明 `method`，默认按 GET 发送，于是所有字段被拼进查询字符串。

也就是说，这一次提交发生在 **React 还没有完成水合（hydration）的时候**。服务端返回的 HTML 上没有绑定 `onSubmit`，浏览器就按 HTML 的默认行为把表单提交了出去。这种情况在开发环境中尤其容易出现：`/` 跳转到 `/login` 时该路由的客户端脚本还在按需编译，如果浏览器自动填充了账号密码、用户紧接着按回车或点登录，就会赶在脚本就绪之前提交。

因此，修复的关键不是再写一次登录逻辑，而是**保证表单不可能在客户端就绪前被原生提交**。

### 1. 为表单显式声明提交方式

```tsx
<form
  onSubmit={handleSubmit(onSubmit)}
  className="space-y-5"
  method="post"
  noValidate
>
```

`method="post"` 是一道兜底防线：即使真的发生原生提交，凭据也会放在请求体里，而不是出现在 URL 中。

### 2. 记录客户端是否已完成水合

```tsx
const [hydrated, setHydrated] = useState(false);

// 只有客户端水合完成后，才允许提交表单。
// 否则用户在页面尚未就绪时提交，浏览器会按原生表单行为把
// username / password 拼进 URL（GET /login?username=...&password=...）。
useEffect(() => {
  setHydrated(true);
}, []);
```

首次渲染时 `hydrated` 为 `false`，`useEffect` 只在客户端执行，水合完成后才置为 `true`。这样服务端 HTML 与客户端首帧保持一致，不会产生水合不匹配。

### 3. 水合完成前禁用提交按钮

```tsx
<Button
  type="submit"
  className="w-full"
  disabled={!hydrated || isSubmitting}
>
  {isSubmitting ? "验证中..." : "登录"}
</Button>
```

表单包含两个输入框，浏览器的隐式提交依赖于默认提交按钮；当这个按钮处于 `disabled` 状态时，无论是点击还是回车，浏览器都不会执行原生提交。按钮在页面就绪后自动恢复可用，用户几乎感知不到这一瞬间的差异。

修复后重新验证：

1. 直接查看服务端返回的 HTML，提交按钮应带有 `disabled` 属性。
2. 页面脚本加载完成后，按钮恢复可用。
3. 输入正确凭据登录，地址栏停留在 `/dept`，不再出现任何查询参数。
4. 输入错误凭据，页面原地显示统一错误提示，URL 保持不变。

这个问题的本质与登录逻辑无关，而是**服务端渲染页面在客户端接管之前，仍具备浏览器的原生行为**。凡是把敏感信息放在表单字段里的页面，都应该像这样显式约束提交方式，而不是假设脚本一定先于用户动作就绪。

## 四、本节小结

本节只修改了一个入口页面，却让网站访问流程更加完整。

通过在 `app/page.tsx` 中复用已有的 `getCurrentSession()`，我们实现了根路径的登录检查：

- 未登录，跳转到 `/login`。
- 已登录，跳转到 `/dept`。

这也体现了一个重要的开发原则：已有的认证能力应该在不同路由中复用，而不是每遇到一个页面就重新实现一遍。

需要注意，根路径的登录检查只负责 `/` 的访问行为。其他后台页面仍然由 `app/(dashboard)/layout.tsx` 进行登录校验，服务端业务操作也需要保留各自的认证检查。
