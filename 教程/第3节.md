# 三、理解 Dept 的每个字段

## id：每条数据的唯一身份证

首先：

```prisma
id String @id @default(cuid())
```

拆开来看：

```text
id
↓
字段名称

String
↓
字符串类型

@id
↓
主键

@default(cuid())
↓
自动生成唯一 ID
```

所以：

```prisma
id String @id @default(cuid())
```

表示：

> 每个部门都有一个唯一的字符串 ID，并且创建数据时自动生成。

例如数据库中可能出现：

```text
cmj8x7...
cmj8x9...
cmj8za...
```

为什么不用：

```prisma
id Int @id @default(autoincrement())
```

也可以。

但在这种企业级系统里，我们更倾向于使用字符串 ID。

原因之一是：

> ID 不直接暴露业务数据的数量和顺序。

例如：

```text
1
2
3
4
```

很容易看出这是连续编号。

而：

```text
cmj8x7...
```

就没有这种明显的信息。

这一点不是绝对规则，但作为本课程的统一设计，我们采用：

```text
String + cuid()
```

---

## name：部门名称

```prisma
name String
```

非常简单：

```text
name
 ↓
部门名称
```

例如：

```text
技术部
销售部
财务部
行政部
```

数据库中最终可能是：

```text
id          name
----        ----
xxx         技术部
xxx         销售部
xxx         财务部
```

这里没有使用：

```prisma
String?
```

而是：

```prisma
String
```

表示：

> 部门名称是必填字段。

---

## code：部门编码

```prisma
code String @unique
```

例如：

```text
TECH
SALES
FIN
ADMIN
```

这里最重要的是：

```prisma
@unique
```

它表示：

> **这个字段的值不能重复。**

例如：

```text
技术部    TECH
销售部    SALES
财务部    FIN
```

是合法的。

但不能出现：

```text
技术部    TECH
研发部    TECH
```

因为：

```text
TECH
```

已经存在。

这就是数据库约束。

---

## 为什么企业系统需要编码？

很多刚接触数据库的人会认为：

> “部门不是已经有名称了吗？为什么还要编码？”

因为：

```text
名称
```

是给人看的。

而：

```text
编码
```

更适合系统使用。

例如：

```text
技术部
```

可能未来改成：

```text
研发技术中心
```

但是业务系统内部可能仍然希望使用：

```text
TECH
```

作为稳定的业务标识。

所以企业系统中经常会出现：

```text
名称
+
编码
```

这样的设计。

后面的：

```text
客户
合同
项目
产品
员工
```

都会大量使用这种思路。

---

## parentId：解决部门上下级关系

接下来：

```prisma
parentId String?
```

这个字段非常重要。

它表示：

> **当前部门的上级部门 ID。**

例如：

```text
总公司
├── 技术部
│   ├── 前端组
│   └── 后端组
│
└── 销售部
```

可以理解成：

```text
总公司
parentId = null

技术部
parentId = 总公司的 id

前端组
parentId = 技术部的 id

后端组
parentId = 技术部的 id

销售部
parentId = 总公司的 id
```

这里：

```prisma
String?
```

后面的：

```text
?
```

表示这个字段可以为空。

为什么？

因为：

```text
总公司
```

没有上级部门。

所以：

```text
parentId = null
```

是合法的。

---

## 这是一个树形数据结构

因此，一张 Dept 表就可以表达：

```text
总公司
├── 技术部
│   ├── 前端组
│   └── 后端组
│
├── 销售部
│
└── 财务部
```

这种结构叫：

> **树形结构。**

而：

```prisma
parentId
```

就是实现这种树形结构的关键。

后面做组织架构页面的时候，我们就可以根据：

```text
parentId
```

把数据库中的平面数据重新组织成：

```text
树
```

---

## sort：控制显示顺序

```prisma
sort Int @default(0)
```

表示：

> 部门排序值。

例如：

```text
技术部    1
销售部    2
财务部    3
行政部    4
```

页面查询的时候：

```ts
orderBy: {
  sort: "asc"
}
```

就可以按照：

```text
1 → 2 → 3 → 4
```

显示。

为什么不直接按照部门名称排序？

因为企业业务中经常需要：

> **人工控制顺序。**

例如：

```text
总经理办公室
技术部
销售部
财务部
```

这不一定符合自然字母顺序。

所以增加：

```text
sort
```

非常常见。

---

## status：数据状态

```prisma
status Int @default(1)
```

这里我们约定：

```text
1 = 启用
0 = 禁用
```

例如：

```text
技术部    1
销售部    1
已经撤销的部门    0
```

这里有一个企业系统非常重要的思想：

> **数据不一定要真正删除。**

例如一个部门已经撤销。

如果直接：

```text
DELETE
```

可能会影响历史员工、项目、合同等数据。

所以很多企业系统会采用：

```text
status = 0
```

表示：

> 这个部门已经停用。

但历史数据仍然保留。

这就是后面我们会经常讲到的：

> **业务数据的生命周期。**

---

## description：描述

```prisma
description String?
```

部门描述不是必填字段。

所以使用：

```prisma
String?
```

例如：

```text
负责公司软件研发、技术架构以及系统运维。
```

如果没有描述：

```text
null
```

也是合法的。

---

## createdAt 和 updatedAt

最后两个字段：

```prisma
createdAt DateTime @default(now())

updatedAt DateTime @updatedAt
```

分别表示：

```text
createdAt
    ↓
创建时间

updatedAt
    ↓
最后更新时间
```

例如：

```text
创建：
2026-09-08 13:00

修改：
2026-09-09 10:30
```

那么：

```text
createdAt = 2026-09-08 13:00

updatedAt = 2026-09-09 10:30
```

其中：

```prisma
@default(now())
```

表示创建数据的时候自动设置当前时间。

而：

```prisma
@updatedAt
```

表示每次更新数据时自动刷新。

这两个字段几乎是企业业务表的标配。

# 四、执行 Migration：模型落地成表

## 执行第一次 Migration

现在我们只是修改了：

```text
schema.prisma
```

注意：

> **修改 schema 并不会自动修改 PostgreSQL。**

现在 PostgreSQL 还不知道：

```text
Dept
```

这张表存在。

所以我们需要执行：

```bash
pnpm prisma migrate dev --name init_dept
```

Prisma 会根据：

```text
schema.prisma
```

生成数据库迁移。

大致过程：

```text
schema.prisma
      ↓
比较数据库结构
      ↓
生成 SQL
      ↓
执行 SQL
      ↓
PostgreSQL
```

执行成功以后，数据库里才真正出现：

```text
Dept
```

表。

---

## Migration 到底是什么？

Migration 可以理解成：

> **数据库结构的版本记录。**

例如今天我们创建：

```text
Dept
```

产生：

```text
migration 001
```

以后增加：

```text
Employee
```

产生：

```text
migration 002
```

以后给 Project 增加一个字段：

```text
budget
```

产生：

```text
migration 003
```

于是整个数据库结构变化就有了完整记录：

```text
001 init_dept
      ↓
002 init_employee
      ↓
003 add_project_budget
```

这对于团队协作非常重要。

因为：

> **数据库结构本身也需要版本管理。**

---
## 解决权限不足的问题
执行migration的时候控制台报错，提示权限不足，可以让agent修复，选中错误添加到对话
![在这里插入图片描述](https://i-blog.csdnimg.cn/direct/d485e2408bc442bcb75cc26192551ac7.png)

报错信息里通常会有这样一句：

```text
Prisma Migrate could not create the shadow database.
错误: 创建数据库权限不够
```

**为什么会权限不足？**

Prisma 在执行 migration 的时候，会先临时创建一个叫做 shadow database（影子数据库）的数据库，在里面模拟整个迁移过程，确认没有问题以后再把改动应用到正式数据库，最后自动删除它。

所以执行迁移的数据库用户必须拥有"创建数据库"的权限，而 `pm_user_case` 默认没有这个权限。

**手动修复方法**

用超级用户 `postgres` 登录 PostgreSQL（密码是安装 PostgreSQL 时为 postgres 用户设置的密码）：

```bash
psql -U postgres -d postgres -h localhost
```

登录成功以后，执行授权语句：

```sql
ALTER ROLE pm_user_case CREATEDB;
```

看到返回 `ALTER ROLE` 就表示授权成功，输入 `\q` 退出。

然后回到项目目录，重新执行 migration：

```bash
pnpm prisma migrate dev --name init_dept
```

这次就可以顺利生成迁移文件了。

Migration 成功之后，我们还需要确保 Prisma Client 已经生成。

执行：

```bash
pnpm prisma generate
```

Prisma 会根据：

```text
schema.prisma
```

生成对应的 TypeScript Client。

现在：

```text
Dept
```

这个模型就会进入 TypeScript 世界。

于是我们才能写：

```ts
db.dept
```

这就是 Prisma 非常重要的一点：

```text
schema.prisma
       ↓
Prisma Client
       ↓
TypeScript
```

## 创建统一数据库入口

创建：

```text
lib/db.ts
```

写入：

```ts
import "dotenv/config";

import { PrismaClient } from "@/lib/generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

const adapter = new PrismaPg({
  connectionString: process.env.DATABASE_URL!,
});

export const db =
  globalForPrisma.prisma ??
  new PrismaClient({
    adapter,
  });

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = db;
}
```

这里需要注意：

你的 `schema.prisma` 当前配置：

```prisma
output = "../lib/generated/prisma"
```

因此生成目录是：

```text
lib/generated/prisma
```

所以：

```ts
import { PrismaClient } from "@/lib/generated/prisma/client";
```

要和你的实际项目结构保持一致。

## 第一次插入部门数据

现在我们真正给数据库添加第一条业务数据。

这段代码写在哪里呢？就写在上一节打开的服务器组件里：

```text
app/page.tsx
```

把插入代码加在 `Page` 函数中、`findMany()` 查询的前面，完整代码如下：

```tsx
import { db } from "@/lib/db";

export default async function Page() {
  // 临时插入一条数据，验证完成后记得删除这一整段
  const dept = await db.dept.create({
    data: {
      name: "技术部",
      code: "TECH",
      sort: 1,
      status: 1,
      description: "负责公司技术研发工作",
    },
  });

  const depts = await db.dept.findMany();

  return (
    <main className="p-8">
      <h1 className="text-2xl font-bold">
        部门列表
      </h1>

      <pre className="mt-6">
        {JSON.stringify(depts, null, 2)}
      </pre>
    </main>
  );
}
```

保存文件以后，在浏览器中刷新一次页面。

因为这是一个服务器组件，它的代码会在每次收到浏览器请求时在服务器端执行，所以刷新页面就会执行一次 `create()`。刷新成功后，页面上原来显示的空数组：

```json
[]
```

会变成一条包含技术部的 JSON 数据，说明数据已经真正写入了数据库。

**验证成功以后，记得把 `db.dept.create(...)` 这一整段删掉。**

因为 `create()` 每次执行都会插入一条新数据，而我们在 schema 中给 `code` 加了 `@unique` 唯一约束。如果不删除，第二次刷新页面时 Prisma 会再次插入 `code: "TECH"`，就会报唯一约束冲突的错误。删除后让 `app/page.tsx` 恢复成只保留 `findMany()` 查询的样子即可。

这里：

```ts
db.dept.create()
```

表示：

> 向 `Dept` 表创建一条数据。

注意：

```text
id
createdAt
updatedAt
```

我们都没有填写。

## 从一张 Dept 表开始理解企业系统

现在我们重新看一下：

```prisma
model Dept {
  id          String   @id @default(cuid())
  name        String
  code        String   @unique
  parentId    String?
  sort        Int      @default(0)
  status      Int      @default(1)
  description String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
```

它看起来只是十几个字段。

但是实际上已经表达了一个完整的业务对象：

```text
部门
│
├── 身份
│   └── id
│
├── 基础信息
│   ├── name
│   └── code
│
├── 组织关系
│   └── parentId
│
├── 展示控制
│   └── sort
│
├── 业务状态
│   └── status
│
├── 扩展信息
│   └── description
│
└── 生命周期
    ├── createdAt
    └── updatedAt
```

这就是我们后面设计所有业务表时需要建立的思维。

不要只问：

> “这一页需要哪些字段？”

而要问：

> **“这个业务对象到底是什么？”**

它有什么：

```text
属性？
关系？
状态？
生命周期？
行为？
```

这才是企业系统的数据建模。
