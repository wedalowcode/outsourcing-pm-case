# 8.5 从角色到权限：建立 RBAC 授权模型

在前面的章节中，我们已经建立了用户管理的基础能力，包括用户创建、基本信息修改、用户删除和密码重置。

但现在的系统仍然缺少一个关键问题：

**用户登录系统之后，究竟可以做什么？**

例如，在外包项目管理平台中：

- 销售人员可以查看客户和商机，但不应该随意修改项目成本。
- 项目经理可以管理自己负责的项目和任务。
- 开发人员可以填写工时、处理任务，但不应该拥有用户管理权限。
- 管理员可以维护系统用户、角色和权限。

如果我们仅仅判断用户是否登录，就无法区分这些不同的操作权限。

因此，本节开始建立 RBAC 授权模型，让系统从“用户身份管理”逐步走向“用户权限管理”。

本节只完成数据模型设计和数据库迁移。角色分配、权限校验、菜单控制等功能放在后续章节实现。

---

## 一、先理解用户、角色和权限

在设计数据库之前，我们先明确三个核心概念。

### 1.1 用户：谁在使用系统

用户代表一个可以登录系统的账号。

例如：

| 用户名 | 姓名 | 说明 |
|---|---|---|
| zhangsan | 张三 | 销售人员 |
| lisi | 李四 | 项目经理 |
| wangwu | 王五 | 开发人员 |

用户解决的是身份问题：

> 当前登录系统的人是谁？

我们已经有了 `User` 模型，因此本节不需要重新创建用户表，而是在现有用户模型上建立角色关联。

### 1.2 角色：用户在组织中承担什么职责

角色用于归纳一组具有相同业务职责的用户。

例如：

| 角色编码 | 角色名称 | 业务职责 |
|---|---|---|
| ADMIN | 系统管理员 | 维护系统基础配置 |
| SALES | 销售人员 | 管理客户和商机 |
| PM | 项目经理 | 管理项目和任务 |
| DEVELOPER | 开发人员 | 处理任务、登记工时 |

角色不是某个具体的人，而是一种职责定义。

如果系统有 20 名开发人员，我们不应该给每个人分别配置一遍相同的权限，而应该将他们关联到 `DEVELOPER` 角色。

### 1.3 权限：用户具体可以执行什么操作

权限描述系统允许执行的操作。

例如：

| 权限编码 | 权限名称 | 说明 |
|---|---|---|
| user:read | 查看用户 | 查询用户列表和详情 |
| user:create | 创建用户 | 新增系统用户 |
| user:update | 修改用户 | 修改用户基本信息 |
| user:delete | 删除用户 | 删除符合条件的用户 |
| project:read | 查看项目 | 查询有权访问的项目 |
| task:update | 修改任务 | 更新任务信息 |

这里的权限编码采用 `资源:操作` 的形式。

例如：

```text
user:read
```

表示对用户资源具有读取权限。

这种编码方式有利于后续在 Server Action、Service 和菜单系统中统一引用权限标识。

需要注意：权限编码只是标识，不是安全机制本身。真正执行操作时，服务端仍然必须进行授权检查。

### 1.4 三者之间是什么关系

将这三个概念放在一起，就形成了 RBAC 的基本模型。

```text
User 用户
   │
   │ 一个用户可以拥有多个角色
   ▼
UserRole 用户角色关联
   │
   ▼
Role 角色
   │
   │ 一个角色可以拥有多个权限
   ▼
RolePermission 角色权限关联
   │
   ▼
Permission 权限
```

完整关系可以表示为：

```text
一个用户 ── 多个角色
一个角色 ── 多个用户

一个角色 ── 多个权限
一个权限 ── 多个角色
```

因此，用户与角色之间是多对多关系，角色与权限之间同样是多对多关系。

这也是我们需要建立四类模型的原因：

- `User`：用户
- `Role`：角色
- `Permission`：权限
- `UserRole`、`RolePermission`：关联模型

## 二、为什么不能直接给 User 增加一个 role 字段

初学者设计权限系统时，最容易想到的方案是在用户表中增加一个角色名称。

例如：

```prisma
model User {
  id       String @id @default(cuid())
  username String @unique
  name     String
  role     String
}
```

这个方案看起来很简单，但它隐含了一个问题：

**一个用户只能拥有一个角色。**

例如，张三既是销售人员，又兼任项目经理。

如果 `role` 只能保存一个字符串，就只能选择其中一个：

```text
张三
  └── SALES
```

或者：

```text
张三
  └── PM
```

无法自然地表达两个角色同时存在的情况。

另一种做法是把多个角色写在一个字符串中：

```text
SALES,PM
```

或者：

```json
["SALES", "PM"]
```

但这样会把关系数据塞进一个字段中，带来一系列问题：

1. 无法通过普通外键约束保证角色真实存在。
2. 查询拥有某个角色的用户更加复杂。
3. 很难对角色分配建立唯一约束。
4. 删除角色时，不容易可靠地维护用户关联。
5. 后续给角色增加状态、说明、权限等属性时，数据结构会越来越混乱。

数据库设计应该让关系本身成为明确的数据结构，而不是将多个关系隐藏在一个字段中。

因此，我们采用独立的 `Role` 表和 `UserRole` 关联表。

## 三、设计 Role 角色模型

角色是系统中的独立业务对象，不能只是一个字符串。

一个角色至少需要具备以下属性：

| 字段 | 含义 |
|---|---|
| id | 角色主键 |
| code | 角色编码 |
| name | 角色名称 |
| description | 角色说明 |
| status | 角色状态 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

其中，`code` 是系统内部稳定使用的编码，`name` 是展示给用户看的名称。

例如：

```text
code: DEVELOPER
name: 开发人员
```

即使以后将角色名称从“开发人员”修改为“研发工程师”，内部引用的角色编码也不需要跟着变化。

### 3.1 定义角色状态

在 `prisma/schema.prisma` 中增加：

```prisma
enum RoleStatus {
  ACTIVE
  DISABLED
}
```

角色停用后，后续授权逻辑应当拒绝通过该角色获得权限。

需要强调的是，定义状态字段并不会自动阻止授权。后续服务端读取角色权限时，必须主动过滤停用角色。

### 3.2 定义 Role 模型

继续在 `schema.prisma` 中增加：

```prisma
model Role {
  id          String     @id @default(cuid())
  code        String     @unique @db.VarChar(50)
  name        String     @db.VarChar(100)
  description String?    @db.VarChar(500)
  status      RoleStatus @default(ACTIVE)

  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt

  userRoles       UserRole[]
  rolePermissions RolePermission[]

  @@index([status])
}
```

这里有几个需要理解的地方。

**第一，`@unique` 保证角色编码唯一。**

不能同时存在两个编码为 `DEVELOPER` 的角色。

**第二，角色名称不一定唯一。**

本模型允许不同角色拥有相同的展示名称，但实际管理界面应尽量避免产生难以区分的角色。

**第三，`userRoles` 和 `rolePermissions` 是关系字段。**

它们用于描述 Prisma 模型之间的关联，并不是 `Role` 表中实际保存的两个数组字段。

真正保存关系的是后面要创建的两张关联表。

## 四、设计 Permission 权限模型

角色用于归纳职责，权限用于描述具体操作。

如果把权限直接写死在代码中，虽然初期实现起来比较快，但后续会遇到几个问题：

- 无法方便地查询系统中有哪些权限。
- 不容易维护角色与权限的对应关系。
- 很难建设统一的角色授权界面。
- 不容易对权限编码进行集中管理。

因此，我们单独建立 `Permission` 模型。

### 4.1 权限模型需要哪些字段

| 字段 | 含义 |
|---|---|
| id | 权限主键 |
| code | 权限编码 |
| name | 权限名称 |
| resource | 资源标识 |
| action | 操作标识 |
| description | 权限说明 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

这里将 `resource` 和 `action` 分开保存，方便后续按资源或操作分类查询。

例如：

```text
code: user:read
resource: user
action: read
name: 查看用户
```

### 4.2 定义 Permission 模型

在 `schema.prisma` 中增加：

```prisma
model Permission {
  id          String   @id @default(cuid())
  code        String   @unique @db.VarChar(100)
  name        String   @db.VarChar(100)
  resource    String   @db.VarChar(50)
  action      String   @db.VarChar(50)
  description String?  @db.VarChar(500)

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  rolePermissions RolePermission[]

  @@unique([resource, action])
  @@index([resource])
}
```

这里有两种不同的唯一约束。

第一种：

```prisma
code String @unique
```

保证权限编码唯一。

第二种：

```prisma
@@unique([resource, action])
```

保证同一个资源与操作组合只能对应一条权限记录。

例如：

```text
user + read
```

只能存在一次。

这种约束适用于当前采用的简单权限模型。如果未来要支持同一资源下具有不同业务上下文的多个同名操作，就需要重新评估这条约束。

另外，权限模型暂时没有 `status` 字段。是否启用某个权限，可以在后续根据权限生命周期和授权规则决定，而不是为了让所有表结构完全一致就盲目增加字段。

## 五、设计 UserRole 用户角色关联表

现在我们已经有了 `User` 和 `Role` 两个模型。

接下来要解决的问题是：

一个用户如何关联多个角色？

我们需要增加一张关联表：

```text
UserRole
```

它不负责描述用户本身，也不负责描述角色本身，而是专门记录：

> 哪个用户被分配了哪个角色。

### 5.1 为什么关联表需要独立存在

假设系统中有以下用户：

```text
张三
李四
王五
```

以及以下角色：

```text
销售人员
项目经理
开发人员
```

关联关系可能是：

```text
张三 → 销售人员
张三 → 项目经理

李四 → 项目经理

王五 → 开发人员
王五 → 项目经理
```

如果把关系存储在独立的关联表中，就可以使用多条记录表示一个用户拥有多个角色。

### 5.2 定义 UserRole 模型

```prisma
model UserRole {
  userId String
  roleId String

  createdAt DateTime @default(now())

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  role Role @relation(
    fields: [roleId],
    references: [id],
    onDelete: Cascade
  )

  @@id([userId, roleId])
  @@index([roleId])
}
```

这张表没有额外的自增主键，而是采用组合主键：

```prisma
@@id([userId, roleId])
```

它意味着：

**同一个用户与同一个角色之间，只能存在一条关联记录。**

例如，下面这两条记录可以同时存在：

| userId | roleId |
|---|---|
| user_001 | role_sales |
| user_001 | role_pm |

但是，下面的重复记录不允许存在：

| userId | roleId |
|---|---|
| user_001 | role_sales |
| user_001 | role_sales |

组合主键在这里不仅用于标识一条关联记录，更重要的是从数据库层面防止重复分配。

### 5.3 为什么增加 `@@index([roleId])`

组合主键按照 `[userId, roleId]` 的顺序建立索引。

当我们根据用户查询角色时，这个索引可以发挥作用。

但是，当我们需要查询某个角色关联了哪些用户时，单独为 `roleId` 建立索引更合适。

这属于根据实际查询方向设计索引，而不是简单地给每个字段都添加索引。

### 5.4 为什么使用 `onDelete: Cascade`

当一个用户或角色被物理删除时，对应的关联记录不应继续保留。

因此这里允许关联记录级联删除。

需要注意：

- 删除 `UserRole` 记录不会删除用户或角色。
- 删除用户会删除其 `UserRole` 关联记录。
- 删除角色会删除其 `UserRole` 关联记录。
- 这不会自动删除其他业务数据。

级联规则只应当用于明确属于父对象的关联记录，不能随意应用到项目、合同等需要保留历史的业务数据上。

## 六、设计 RolePermission 角色权限关联表

用户与角色之间已经建立了多对多关系。

接下来还需要建立：

```text
Role ↔ Permission
```

例如：

```text
系统管理员
  ├── user:read
  ├── user:create
  ├── user:update
  └── user:delete

开发人员
  ├── task:read
  └── task:update
```

一个角色可以关联多个权限，同一个权限也可以分配给多个角色。

因此，同样需要一张关联表。

### 6.1 定义 RolePermission 模型

```prisma
model RolePermission {
  roleId       String
  permissionId String

  createdAt DateTime @default(now())

  role Role @relation(
    fields: [roleId],
    references: [id],
    onDelete: Cascade
  )

  permission Permission @relation(
    fields: [permissionId],
    references: [id],
    onDelete: Cascade
  )

  @@id([roleId, permissionId])
  @@index([permissionId])
}
```

这张表的结构与 `UserRole` 非常相似。

区别在于：

- `UserRole` 维护用户与角色之间的关系。
- `RolePermission` 维护角色与权限之间的关系。

同样使用组合主键：

```prisma
@@id([roleId, permissionId])
```

可以防止同一个角色被重复分配相同的权限。

而：

```prisma
@@index([permissionId])
```

则方便后续查询某项权限被哪些角色引用。

## 七、将关联关系补充到现有 User 模型

前面三个模型已经定义了角色、权限以及两张关联表。

现在还需要检查现有的 `User` 模型。

在本项目中，`User` 已经包含用户基础信息以及会话关系。因此，不要重新创建 `User` 模型，也不要覆盖已有的密码字段、状态字段、时间字段或其他业务关联。

只需要确保 `User` 模型包含以下关系字段：

```prisma
userRoles UserRole[]
```

如果现有模型已经包含这一字段，就不需要重复添加。

完整关系应当是：

```text
User
 └── userRoles: UserRole[]

Role
 ├── userRoles: UserRole[]
 └── rolePermissions: RolePermission[]

Permission
 └── rolePermissions: RolePermission[]
```

Prisma 需要在关系两侧定义对应的关系字段，才能正确识别这些关联。外键字段则保存在关联模型中。

官方文档对 Prisma 的关系字段、外键和多对多关系有详细说明：

- [Prisma ORM 7：模型关系](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/relations)
- [Prisma ORM 7：多对多关系](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/relations/many-to-many-relations)

## 八、检查最终的数据关系

完成模型设计后，整体结构如下：

```text
┌──────────────┐
│     User     │
└──────┬───────┘
       │ 1
       │
       │ N
┌──────▼───────┐
│   UserRole   │
└──────┬───────┘
       │ N
       │
       │ 1
┌──────▼───────┐
│     Role     │
└──────┬───────┘
       │ 1
       │
       │ N
┌──────▼───────────┐
│  RolePermission  │
└──────┬───────────┘
       │ N
       │
       │ 1
┌──────▼───────┐
│  Permission  │
└──────────────┘
```

这里的 `1` 和 `N` 表示关系基数。

例如，一个用户可以有多条 `UserRole` 记录；每条 `UserRole` 记录只指向一个用户和一个角色。

通过这种方式，系统可以在不修改用户表结构的情况下，灵活调整用户角色分配。

## 九、使用 Prisma 完成数据库迁移

数据模型定义完成后，还需要将这些变更应用到 PostgreSQL。

Prisma 的 `schema.prisma` 描述的是目标数据结构；数据库迁移则负责记录并执行结构变化。

### 9.1 检查 Schema

首先确认 `schema.prisma` 中：

- `RoleStatus` 枚举已定义。
- `Role` 模型已定义。
- `Permission` 模型已定义。
- `UserRole` 模型已定义。
- `RolePermission` 模型已定义。
- 现有 `User` 模型包含 `userRoles UserRole[]`。
- 所有关系字段都能找到对应的另一端。

然后执行：

```bash
pnpm prisma validate
```

如果验证失败，先修复 Schema 错误，不要继续迁移。

### 9.2 创建迁移

执行：

```bash
pnpm prisma migrate dev --name add_rbac
```

Prisma 会根据当前 Schema 和迁移历史生成数据库结构变更，并在开发数据库中应用迁移。

如果项目已经存在迁移历史，这一步只应生成本次新增的结构变化，不应该重新初始化整个数据库。

### 9.3 已有数据时的迁移：先回填，再收紧约束

本项目的 `Role`、`Permission`、`UserRole`、`RolePermission` 在 7.2 已经建好，本节实际只是给 `Role` 补 `status`、给 `Permission` 补 `resource` 和 `action`。而 `Permission` 表里已经有 9 条由 `seed-admin.ts` 写入的记录。

此时直接执行 `migrate dev --name add_rbac` 会失败：

```text
⚠️ We found changes that cannot be executed:
  • Added the required column `action` to the `Permission` table without a default value.
    There are 9 rows in this table, it is not possible to execute this step.
  • Added the required column `resource` to the `Permission` table without a default value.
```

Prisma 不会替历史行编造 `resource` 和 `action`。而且 `migrate dev` 是交互式命令，在脚本、CI 等非交互环境中会直接报错：

```text
Error: Prisma Migrate has detected that the environment is non-interactive, which is not supported.
```

正确做法是把迁移拆成三步：生成 SQL、手写回填、应用迁移。

第一步，用 `migrate diff` 让 Prisma 生成增量 SQL。注意 Prisma 7 已经移除了 `--from-url`，改为读取配置文件里的数据源：

```bash
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script
```

输出中会看到这条无法执行的语句：

```sql
-- AlterTable
ALTER TABLE "Permission" ADD COLUMN     "action" VARCHAR(50) NOT NULL,
ADD COLUMN     "resource" VARCHAR(50) NOT NULL;
```

第二步，在 `prisma/migrations/<时间戳>_add_rbac/migration.sql` 中把它改成「加可空列 → 回填 → 收紧为非空」：

```sql
-- CreateEnum
CREATE TYPE "RoleStatus" AS ENUM ('ACTIVE', 'DISABLED');

-- AlterTable
ALTER TABLE "Role" ADD COLUMN "status" "RoleStatus" NOT NULL DEFAULT 'ACTIVE';

-- AlterTable
-- Permission 表已有历史数据，直接添加非空列会失败。
-- 因此先以可空方式加列，回填后再收紧为非空。
ALTER TABLE "Permission" ADD COLUMN "resource" VARCHAR(50),
ADD COLUMN "action" VARCHAR(50);

-- 回填：权限编码遵循「资源:操作」的约定，历史数据按冒号拆分
UPDATE "Permission"
SET "resource" = split_part("code", ':', 1),
    "action" = split_part("code", ':', 2)
WHERE "resource" IS NULL OR "action" IS NULL;

-- 不符合「资源:操作」格式的历史数据统一归入 unknown，避免迁移中断
UPDATE "Permission"
SET "resource" = COALESCE(NULLIF("resource", ''), 'unknown'),
    "action" = COALESCE(NULLIF("action", ''), 'unknown');

ALTER TABLE "Permission"
ALTER COLUMN "resource" SET NOT NULL,
ALTER COLUMN "action" SET NOT NULL;

-- CreateIndex
CREATE INDEX "Permission_resource_idx" ON "Permission"("resource");

-- CreateIndex
CREATE UNIQUE INDEX "Permission_resource_action_key" ON "Permission"("resource", "action");

-- CreateIndex
CREATE INDEX "Role_status_idx" ON "Role"("status");
```

## 下一节预告

下一步，我们可以开始实现角色与权限的业务管理：

1. 创建角色、修改角色和停用角色。
2. 为用户分配多个角色。
3. 为角色分配多个权限。
4. 在服务端查询用户有效权限。
5. 将权限检查接入 Server Action 和 Service。

最终形成一条完整的授权链路：

```text
当前登录用户
    ↓
查询用户角色
    ↓
查询角色权限
    ↓
判断当前操作是否被授权
    ↓
执行或拒绝业务操作
```

**RBAC 的价值并不是多建几张表，而是让系统从“谁登录了”进一步回答“这个人依据什么职责，有权执行什么操作”。**
