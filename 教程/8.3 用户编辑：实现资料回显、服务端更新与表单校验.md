# 8.3 用户编辑：实现资料回显、服务端更新与表单校验

上一节已经完成了用户新增，建立了从表单到 Server Action，再到 Service 和 Prisma 的写入流程。

本节继续实现用户资料编辑。与新增用户相比，编辑操作有三个不同点：

- 编辑时必须先加载数据库中的现有资料，并将其回显到表单。
- 编辑时只能修改允许修改的字段，不能让客户端任意更新数据库字段。
- 编辑用户资料不涉及密码，不能因为表单没有密码字段，就意外覆盖原有密码。

本节最终实现的功能是：在用户列表中点击“编辑”，弹出资料编辑窗口，修改姓名、邮箱、手机号和状态，提交后由服务端校验并保存，成功后刷新列表。

## 一、明确允许修改的字段

当前 `User` 模型包含以下字段：

```prisma
model User {
  id           String     @id @default(cuid())
  username     String     @unique @db.VarChar(50)
  passwordHash String     @db.VarChar(255)
  name         String     @db.VarChar(100)
  email        String?    @db.VarChar(255)
  phone        String?    @db.VarChar(30)
  status       UserStatus @default(ACTIVE)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  userRoles UserRole[]
  sessions  Session[]
}
```

编辑功能不能简单地把整个 `User` 对象传给 Prisma 更新。我们需要明确区分哪些字段可以修改。

| 字段 | 本节是否允许修改 | 原因 |
|---|---|---|
| `id` | 否 | 数据记录的唯一标识 |
| `username` | 否 | 登录标识，创建后保持不变 |
| `passwordHash` | 否 | 密码通过独立的重置密码功能处理 |
| `name` | 是 | 用户基本资料 |
| `email` | 是 | 用户基本资料 |
| `phone` | 是 | 用户基本资料 |
| `status` | 是 | 控制账号是否可正常登录 |
| `createdAt` | 否 | 创建时间 |
| `updatedAt` | 自动更新 | 由 Prisma 维护 |

这里最重要的设计是：**前端提交什么字段，不代表服务端就允许修改什么字段。**

即使有人绕过界面，直接提交 `passwordHash`、`username` 或 `id`，服务端也不应该把这些字段交给更新操作。

## 二、定义用户编辑的 Zod Schema

打开 `server/user/schema.ts`，在现有的 `createUserSchema` 后增加编辑专用的 Schema。

```ts
// server/user/schema.ts

export const updateUserSchema = z.object({
  id: z.string().min(1, "用户 ID 不能为空"),

  name: z
    .string()
    .trim()
    .min(1, "请输入姓名")
    .max(100, "姓名不能超过 100 个字符"),

  email: optionalEmailSchema,

  phone: optionalPhoneSchema,

  status: z.enum(["ACTIVE", "DISABLED"]),
});

export type UpdateUserInput = z.infer<
  typeof updateUserSchema
>;
```

注意，文件开头已经存在 `z` 的导入，并且 `optionalEmailSchema`、`optionalPhoneSchema` 是前一节定义的模块内校验规则，可以直接复用。

为什么不把新增用户的 Schema 直接拿来修改？

因为新增和编辑的业务规则不同。新增需要用户名和初始密码，编辑不需要。把两者混成一个 Schema，容易出现编辑时要求输入密码、或者新增和编辑字段边界不清楚的问题。

现在两个 Schema 的职责非常明确：

- `createUserSchema`：校验创建用户所需的完整输入。
- `updateUserSchema`：校验允许修改的用户资料。

## 三、实现用户更新 Service

打开 `server/user/service.ts`，保留已有的 `listUserPage()` 和 `createUser()`，增加下面的更新方法。

```ts
// server/user/service.ts

import type { UpdateUserInput } from "./schema";

export type UpdateUserResult =
  | { success: true }
  | {
      success: false;
      code: "NOT_FOUND";
      message: string;
    };

export async function updateUser(
  input: UpdateUserInput,
): Promise<UpdateUserResult> {
  const existingUser = await db.user.findUnique({
    where: { id: input.id },
    select: { id: true },
  });

  if (!existingUser) {
    return {
      success: false,
      code: "NOT_FOUND",
      message: "用户不存在或已被删除",
    };
  }

  await db.user.update({
    where: { id: input.id },
    data: {
      name: input.name.trim(),
      email: input.email,
      phone: input.phone,
      status: input.status,
    },
  });

  return { success: true };
}
```

这段代码有三个关键点。

### 1. 先检查目标用户是否存在

用户列表打开之后，目标用户可能已经被其他管理员删除。因此，编辑提交时不能假设这条记录仍然存在。

预先查询可以提供更明确的业务提示。不过，预先查询和后续更新不是一个原子操作，如果并发删除仍导致更新失败，Action 还应处理相应的 Prisma 异常。

### 2. 显式指定允许修改的字段

这里没有写：

```ts
data: input
```

而是明确列出 `name`、`email`、`phone` 和 `status`。

这样，即使输入对象以后增加了其他属性，也不会因为对象整体传入而意外修改密码哈希、用户名等敏感字段。

### 3. 不需要手动更新 `updatedAt`

当前 Prisma Schema 使用了：

```prisma
updatedAt DateTime @updatedAt
```

因此，正常执行更新时，Prisma 会自动维护该字段。

## 四、实现更新用户的 Server Action

接下来创建更新用户的服务端调用入口。

在 `server/user/actions.ts` 中，保留上一节已有的 `createUserAction`，增加以下代码。与 8.2 节相同，项目的 Server Action 统一放在 `server/<模块>/actions.ts` 中，而不是页面路由目录里。

```ts
// server/user/actions.ts

import { updateUserSchema } from "@/server/user/schema";
import { updateUser } from "@/server/user/service";

export async function updateUserAction(
  input: unknown,
): Promise<CreateUserActionState> {
  const session = await getCurrentSession();

  if (!session) {
    return {
      success: false,
      message: "登录状态已失效，请重新登录",
    };
  }

  // 必须在这里接入真实的用户编辑权限检查。
  // 例如：requirePermission("user:update")

  const parsed = updateUserSchema.safeParse(input);

  if (!parsed.success) {
    return {
      success: false,
      message: "请检查输入内容",
      fieldErrors: parsed.error.flatten().fieldErrors,
    };
  }

  try {
    const result = await updateUser(parsed.data);

    if (!result.success) {
      return {
        success: false,
        message: result.message,
      };
    }

    revalidatePath("/users");

    return {
      success: true,
      message: "用户资料更新成功",
    };
  } catch (error) {
    console.error("updateUserAction failed", error);

    return {
      success: false,
      message: "更新用户资料失败，请稍后重试",
    };
  }
}
```

这里复用了上一节已有的 `CreateUserActionState` 返回类型。虽然名字叫 `CreateUserActionState`，但它实际描述的是新增操作的返回结果。如果后续新增、编辑、删除和重置密码都使用同样的返回约定，可以在公共服务端类型文件中统一定义一个 `ActionResult`，避免类型名称与实际用途不一致。

另外，以上代码假设文件开头已经导入 `getCurrentSession`、`revalidatePath` 等依赖。将新增导入合并到原文件中即可，不要重复声明 `"use server"`。

**权限提醒：** 当前会话检查只能确认用户已登录，并不代表其拥有编辑用户的权限。必须接入项目实际的服务端权限机制，并确保未授权的请求在调用 Service 之前被拒绝。不能仅通过前端隐藏“编辑”按钮来实现权限控制。

## 五、实现编辑用户弹窗

接下来实现前端组件。

当前项目的用户列表页面 `page.tsx` 使用 `./user-workspace` 导入工作区组件，因此本节沿用现有用户模块的目录组织，将编辑组件放在：

```text
app/(dashboard)/users/
├── actions.ts
├── page.tsx
├── user-workspace.tsx
└── _components/
    └── edit-user-dialog.tsx
```

如果项目尚未创建 `_components/` 目录，可以直接新建。

新建 `app/(dashboard)/users/_components/edit-user-dialog.tsx`：

```tsx
"use client";

import { useEffect, useState, useTransition } from "react";
import { useRouter } from "next/navigation";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";
import {
  Dialog,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
} from "@/components/ui/dialog";
import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from "@/components/ui/select";

import { updateUserAction } from "@/server/user/actions";

export type EditableUser = {
  id: string;
  username: string;
  name: string;
  email: string | null;
  phone: string | null;
  status: "ACTIVE" | "DISABLED";
};

type Props = {
  user: EditableUser;
  open: boolean;
  onOpenChange: (open: boolean) => void;
};

/** 状态下拉选项：value 用内部枚举，label 用中文，按钮上显示中文 */
const statusItems = [
  { value: "ACTIVE", label: "启用" },
  { value: "DISABLED", label: "停用" },
];

export function EditUserDialog({
  user,
  open,
  onOpenChange,
}: Props) {
  const router = useRouter();
  const [pending, startTransition] = useTransition();

  const [name, setName] = useState(user.name);
  const [email, setEmail] = useState(user.email ?? "");
  const [phone, setPhone] = useState(user.phone ?? "");
  const [status, setStatus] = useState<
    "ACTIVE" | "DISABLED"
  >(user.status);

  const [message, setMessage] = useState("");
  const [fieldErrors, setFieldErrors] = useState<
    Record<string, string[] | undefined>
  >({});

  // 每次打开编辑窗口，都使用最新的用户资料初始化表单。
  useEffect(() => {
    if (!open) return;

    setName(user.name);
    setEmail(user.email ?? "");
    setPhone(user.phone ?? "");
    setStatus(user.status);
    setMessage("");
    setFieldErrors({});
  }, [open, user]);

  function handleSubmit(
    event: React.FormEvent<HTMLFormElement>,
  ) {
    event.preventDefault();

    setMessage("");
    setFieldErrors({});

    startTransition(async () => {
      const result = await updateUserAction({
        id: user.id,
        name,
        email,
        phone,
        status,
      });

      if (!result.success) {
        setMessage(result.message);
        setFieldErrors(result.fieldErrors ?? {});
        return;
      }

      onOpenChange(false);
      router.refresh();
    });
  }

  function errorFor(field: string) {
    return fieldErrors[field]?.[0];
  }

  // Base UI 弹窗用条件渲染控制开关，避免关闭动画被打断后卡死
  if (!open) return null;

  return (
    <Dialog
      open
      onOpenChange={(nextOpen) => {
        if (!pending) {
          onOpenChange(nextOpen);
        }
      }}
    >
      <DialogContent className="sm:max-w-lg">
        <DialogHeader>
          <DialogTitle>编辑用户</DialogTitle>
          <DialogDescription>
            修改用户基本资料。用户名不可修改，密码需要通过独立的重置功能处理。
          </DialogDescription>
        </DialogHeader>

        <form onSubmit={handleSubmit} className="space-y-4">
          <div className="space-y-2">
            <Label htmlFor="edit-username">用户名</Label>
            <Input
              id="edit-username"
              value={user.username}
              disabled
              readOnly
            />
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-name">姓名 *</Label>
            <Input
              id="edit-name"
              value={name}
              onChange={(event) =>
                setName(event.target.value)
              }
              aria-invalid={Boolean(errorFor("name"))}
              disabled={pending}
              required
            />
            {errorFor("name") && (
              <p className="text-sm text-destructive">
                {errorFor("name")}
              </p>
            )}
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-email">邮箱</Label>
            <Input
              id="edit-email"
              type="email"
              value={email}
              onChange={(event) =>
                setEmail(event.target.value)
              }
              aria-invalid={Boolean(errorFor("email"))}
              disabled={pending}
            />
            {errorFor("email") && (
              <p className="text-sm text-destructive">
                {errorFor("email")}
              </p>
            )}
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-phone">手机号</Label>
            <Input
              id="edit-phone"
              value={phone}
              onChange={(event) =>
                setPhone(event.target.value)
              }
              aria-invalid={Boolean(errorFor("phone"))}
              disabled={pending}
            />
            {errorFor("phone") && (
              <p className="text-sm text-destructive">
                {errorFor("phone")}
              </p>
            )}
          </div>

          <div className="space-y-2">
            <Label>用户状态</Label>

            <Select
              items={statusItems}
              value={status}
              onValueChange={(value) => {
                if (
                  value === "ACTIVE" ||
                  value === "DISABLED"
                ) {
                  setStatus(value);
                }
              }}
              disabled={pending}
            >
              <SelectTrigger className="w-full">
                <SelectValue placeholder="选择用户状态" />
              </SelectTrigger>

              <SelectContent>
                {statusItems.map((item) => (
                  <SelectItem key={item.value} value={item.value}>
                    {item.label}
                  </SelectItem>
                ))}
              </SelectContent>
            </Select>
          </div>

          {message && (
            <p role="alert" className="text-sm text-destructive">
              {message}
            </p>
          )}

          <DialogFooter>
            <Button
              type="button"
              variant="outline"
              disabled={pending}
              onClick={() => onOpenChange(false)}
            >
              取消
            </Button>

            <Button type="submit" disabled={pending}>
              {pending ? "正在保存..." : "保存修改"}
            </Button>
          </DialogFooter>
        </form>
      </DialogContent>
    </Dialog>
  );
}
```

### 这一组件解决了什么问题？

**第一，资料回显。** 弹窗打开时，表单显示当前用户的姓名、邮箱、手机号和状态，而不是始终显示空白表单。

**第二，防止误改。** 用户名以只读形式展示，不提供修改入口；密码字段完全不存在。

**第三，处理异步状态。** 提交过程中禁用相关控件，避免连续点击造成重复提交。

**第四，使用现有组件库。** 弹窗、输入框、按钮、标签和状态选择器均复用项目现有组件。

这里需要注意：`useEffect` 的作用是每次打开弹窗时同步当前用户数据。如果将来编辑窗口改为同时支持切换不同用户，仍然要确保父组件正确传入最新的用户对象。

与 8.2 节相同，本组件有三处结合项目实际的调整：

1. **弹窗用条件渲染控制开关。** 组件在 `open` 为 `false` 时直接返回 `null`，`Dialog` 始终以 `open` 渲染，避免 Base UI 关闭动画被打断导致弹窗卡死。
2. **状态选择器通过 `items` 传入选项。** `value` 用内部枚举（`ACTIVE` / `DISABLED`），`label` 用中文（启用 / 停用），按钮上始终显示中文标签。
3. `updateUserAction` 从 `@/server/user/actions` 导入，与项目把 Action 放在 `server/<模块>/actions.ts` 的约定一致。

## 六、在用户列表中接入编辑按钮

现在将编辑弹窗连接到用户列表。

打开 `app/(dashboard)/users/user-workspace.tsx`，在现有组件中引入：

```tsx
import { useState, useTransition } from "react"; // 与上一节已有的 useTransition 合并导入
import { Button } from "@/components/ui/button";
import {
  EditUserDialog,
  type EditableUser,
} from "./_components/edit-user-dialog";
```

在 `UserWorkspace` 内部增加状态：

```tsx
const [editingUser, setEditingUser] =
  useState<EditableUser | null>(null);
```

本项目的 `EditableUser` 类型直接从编辑组件中导出（`edit-user-dialog.tsx` 同时导出 `EditUserDialog` 和 `EditableUser`），工作区组件导入复用，避免重复声明。

在用户列表的操作列中增加编辑按钮：

```tsx
<Button
  variant="outline"
  size="sm"
  onClick={() => setEditingUser(user)}
>
  编辑
</Button>
```

最后，在工作区 JSX 中加入弹窗：

```tsx
{editingUser && (
  <EditUserDialog
    user={editingUser}
    open={true}
    onOpenChange={(open) => {
      if (!open) {
        setEditingUser(null);
      }
    }}
  />
)}
```

这里的 `user` 指当前表格行对应的用户记录。请将示例中的变量名与实际表格循环中的变量保持一致。

当用户点击编辑按钮时，父组件保存当前用户对象并显示弹窗。保存成功后，弹窗关闭，`router.refresh()` 重新读取服务端列表数据。

如果你已经有统一的操作菜单，也可以把“编辑”按钮放入现有操作菜单，不需要为此重写整个列表。

## 七、验证编辑功能

开发完成后，至少验证以下场景：

| 测试场景 | 预期结果 |
| --- | --- |
| 点击编辑 | 弹窗正确显示目标用户的现有资料 |
| 修改姓名后保存 | 数据库姓名更新，列表同步更新 |
| 邮箱留空 | 保存为 `null` |
| 邮箱格式错误 | 服务端拒绝并显示错误提示 |
| 姓名为空 | 服务端拒绝 |
| 修改用户状态为停用 | 数据库状态更新 |
| 修改用户名 | 界面没有编辑入口，服务端也不接受该字段作为更新内容 |
| 提交 `passwordHash` 等额外字段 | 不会被写入更新操作 |
| 目标用户已不存在 | 返回用户不存在的提示 |
| 未登录或无编辑权限 | 服务端拒绝更新 |
| 连续点击保存 | 提交期间按钮禁用，避免重复提交 |

特别要验证最后两项：**客户端的控件禁用不是安全措施，真正的安全边界仍然在服务端。**

如果用户状态改为 `DISABLED`，现有会话校验逻辑会拒绝该账号继续通过正常的会话验证。但如果业务要求立即撤销其所有既有会话，还需要在停用操作中额外删除该用户的 `Session` 记录。这个行为可以在后续完善用户状态管理时统一处理。

## 八、本节小结

本节完成了用户资料编辑的核心流程：

```text
用户列表
   ↓
选择目标用户
   ↓
打开编辑弹窗并回显资料
   ↓
提交允许修改的字段
   ↓
Server Action
   ├── 检查登录和权限
   ├── Zod 输入校验
   └── 调用 Service
          ↓
       Prisma 更新
          ↓
       刷新用户列表
```

到这里，用户新增和编辑已经共享相同的分层原则，但各自保留独立的输入规则与业务逻辑。

新增需要设置初始密码；编辑只处理基本资料；重置密码将作为独立功能实现。这样的拆分可以避免用户资料更新与账号安全操作互相干扰。
