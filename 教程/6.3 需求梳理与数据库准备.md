# 6.3 部门管理实战：从需求出发，设计新增、修改与删除

# 前言

上一课，我们已经完成了部门管理页面的查询功能。

现在，用户可以查看部门树、搜索部门、筛选状态，还可以通过分页浏览部门列表。左侧的部门树与右侧的表格也已经联动起来。

但这套功能还存在一个明显的问题：**用户只能查看部门，无法维护部门。**

假设公司组织架构发生了变化，需要新增一个部门；发现某个部门名称填写错误，需要修改名称；或者某个部门已经撤销，需要删除它。

这些操作看起来只是增加三个按钮，真正需要考虑的却是数据的一致性和业务规则。

例如：

- 新建部门时，编码应该由谁生成？
- 两个人同时新增部门，会不会生成相同的编码？
- 删除部门后，原来的编码还能不能使用？
- 将部门移动到另一个上级下面时，下级部门的编码怎么办？
- 一个部门还有下级，是否允许直接删除？
- 前端已经做过校验，服务端还需要做什么？

如果不先回答这些问题，就直接开始写按钮和表单，很容易在后续开发中不断补丁式修改。

这一篇，我们先不急着写新增、修改和删除的业务代码，而是从需求出发，把需要遵守的规则、各层的职责以及数据库设计推导清楚。

# 一、先把业务需求说清楚

## 1. 新增部门

新增部门时，用户需要填写部门名称、上级部门、状态和描述等信息。

但并不是所有字段都应该由用户决定。

例如，部门编码需要遵守统一规则，排序值也需要由系统根据同级部门自动计算。如果让用户手动填写，就容易出现编码重复、格式不统一以及排序混乱等问题。

因此，新增部门需要解决以下问题：

1. 部门名称等用户输入是否符合要求？
2. 选择的上级部门是否真实存在？
3. 部门编码应该如何自动生成？
4. 排序值应该如何计算？
5. 如果保存过程中发生错误，能否保证数据一致？

## 2. 修改部门

修改部门不仅仅是更新几个字段。

修改名称、状态和描述相对简单，但修改上级部门会改变组织结构。

假设当前组织结构如下：

```text
总公司
└── 技术部
    └── 前端组
        └── Web 小组
```

如果将「前端组」移动到另一个部门下面，它的下级部门也需要跟着移动。

因此，修改部门时至少要区分两种情况：

- **普通修改**：修改名称、状态、描述等字段，不改变组织结构。
- **结构修改**：修改上级部门，需要检查是否形成循环引用，并考虑整个下级子树的编码。

这两种操作虽然可以使用同一个表单，但服务端处理逻辑并不完全相同。

## 3. 删除部门

删除部门看起来最简单，实际却涉及数据完整性。

如果一个部门还有下级，直接删除会导致组织结构不完整。

因此，本模块先采用一条明确的规则：

**存在下级部门时，不允许删除当前部门。**

用户需要先处理下级部门，再删除上级部门。

另外，删除部门并不意味着可以重新使用它以前的编码。编码是否复用，需要有独立的规则，不能简单地根据当前剩余记录数量决定。

# 二、从需求推导技术方案

## 1. 哪些校验应该放在 Zod？

首先需要区分输入是否合法，以及操作在当前业务状态下是否允许。

这两个问题不是一回事。

例如，用户提交以下数据：

```text
部门名称：技术部
状态：1
排序：10
```

这些字段属于输入数据。我们可以使用 Zod 描述它们的格式与约束。

```typescript
import { z } from "zod";

export const deptInputSchema = z.object({
  name: z.string().trim().min(1, "请输入部门名称"),
  parentId: z.string().nullable(),
  status: z.union([z.literal(0), z.literal(1)]),
  description: z.string().max(500).nullable(),
});

export type DeptInput = z.infer<typeof deptInputSchema>;
```

这段代码只是说明 Schema 应该承担什么职责。实际项目中，还需要根据表单组件的提交格式，处理空字符串、缺失字段以及可选字段的转换。

例如，表单中没有填写描述时，提交的数据可能是空字符串；数据库却可能使用 `null`。这类数据转换应该在输入解析边界统一处理，而不是散落在每个业务函数里。

Zod 适合解决以下问题：

- 字段是否存在；
- 字段类型是否正确；
- 字符串是否为空；
- 字符串长度是否超出限制；
- 状态是否属于允许的枚举值；
- 数字是否满足整数、范围等要求。

这些规则可以在前端复用，以便及时反馈错误，也必须在服务端执行，以防止客户端绕过校验。

但 Zod 无法单独判断某个部门在数据库中是否存在，也无法仅凭输入数据判断修改上级后是否会形成环。

这些属于业务状态校验。

## 2. Service 还需要负责什么？

Service 不应该重复编写一遍所有输入字段的必填判断，而应该负责真正的部门业务规则。

例如：

| 操作 | Service 需要处理的问题 |
| --- | --- |
| 新增 | 校验上级部门存在，生成编码与排序值，完成写入 |
| 修改 | 确认部门存在，检查新上级是否合法，处理编码变化 |
| 删除 | 确认部门存在，检查是否存在下级，再执行删除 |
| 所有写操作 | 通过事务保证关联数据的一致性 |

这里要注意，输入校验和业务校验虽然职责不同，但并不意味着 Service 可以完全信任任意调用方。

合理的做法是让每个外部入口先完成输入解析，Service 再接收明确的业务输入；如果 Service 还会被其他入口直接调用，就应在服务边界建立统一、清晰的输入契约，而不是依赖某个前端页面已经做过校验。

## 3. 数据库为什么还需要约束？

即使服务端已经检查过，数据库仍然需要承担最后一道数据完整性保障。

原因是：**先查询、再写入，并不能自动保证并发情况下的数据安全。**

例如，两次新增请求几乎同时检查某个编码是否可用，都可能得到「没有重复」的结果。如果没有数据库唯一约束，两次写入就可能同时成功。

因此，我们需要不同层次的保障：

- Zod：保证输入符合约定。
- Service：保证操作符合业务规则。
- 数据库约束：保证最终存储的数据满足不可违反的完整性要求。
- 事务：保证一次业务操作涉及的多项写入，要么全部成功，要么全部回滚。

这四者解决的是不同问题，不能互相替代。

# 三、先确定部门编码规则

编码是本模块最值得提前设计的部分，因为它不仅影响新增，还会影响修改、删除以及历史数据。

## 1. 编码格式

本项目采用分层编码。

| 层级 | 编码示例 | 规则 |
| --- | --- | --- |
| 顶级部门 | `D001` | 固定前缀 `D` 加三位序号 |
| 二级部门 | `D001-01` | 上级编码加两位序号 |
| 三级部门 | `D001-01-02` | 继续追加两位序号 |

编码反映部门在组织结构中的位置。

因此，编码不是用户可以随意填写的普通字段，而是由系统根据上级部门和序号规则生成的业务标识。

创建后，用户不能直接编辑编码。

## 2. 为什么不能使用 `count + 1`？

一种直观的做法，是先查询同级部门数量，再将数量加一作为新部门的序号。

例如，某个部门下面已经有三个子部门，就生成第四个子部门的编码。

但这个方案存在一个问题：**记录数量不等于历史上已经分配的最大序号。**

假设某个部门先后分配了三个编码：

```text
D001-01
D001-02
D001-03
```

删除第二个部门后，数据库只剩下两个子部门。

此时，如果使用 `count + 1`，计算结果就是 `3`，会与现存的第三个部门发生冲突。

因此，我们需要记录每个范围已经分配到的最大序号，而不是根据当前记录数量推算。

## 3. 使用计数器记录已分配序号

为此，我们新增一张部门编码计数器表。

每个计数范围对应一条记录：

- 顶级部门使用固定范围 `__ROOT__`。
- 子部门使用其上级部门的 `id` 作为范围。

例如：

| 范围 | 已分配最大序号 |
| --- | ---: |
| `__ROOT__` | 1 |
| 总公司的 ID | 3 |
| 技术部的 ID | 2 |

这里的数值表示历史上已经分配出去的最大序号。

新增时，系统先在事务中递增对应计数器，再使用递增后的序号生成编码。

删除部门时，不减少计数器。

因此，即使删除了序号为 `02` 的部门，后续新增仍然会继续使用下一个序号，而不是重新分配 `02`。

需要强调的是，这个设计保证的是**序号不因删除而回收**，并不意味着仅靠计数器就能保证所有并发请求安全。计数器更新仍然需要采用具有并发安全性的数据库操作，并与部门插入放在同一个事务中。

# 四、排序值应该如何生成？

编码解决的是部门标识问题，排序解决的是同级部门的显示顺序问题。

本项目采用以下规则：

**新部门的排序值等于同级现有最大排序值加 10；没有同级部门时，默认从 10 开始。**

例如：

```text
技术部      sort = 10
产品部      sort = 20
运营部      sort = 30
```

新增同级部门时，系统自动分配 `40`。

这样既能保持默认顺序，也能在未来插入部门时保留一定的排序空间。

排序值由系统计算，不让用户在新增表单中随意填写。

如果以后需要支持用户拖拽调整顺序，可以再单独设计排序更新功能，而不是让新增逻辑承担所有排序需求。

# 五、修改上级部门时，编码如何变化？

由于编码包含上级部门的编码前缀，因此修改上级部门会影响整个下级子树。

假设原来的组织结构为：

```text
总公司
└── 技术部
    └── 前端组
        └── Web 小组
```

其中：

```text
技术部    D001-01
前端组    D001-01-01
Web 小组  D001-01-01-01
```

如果将「前端组」移动到另一个上级部门下面，就不能只更新 `parentId`。

否则，数据库中的实际层级与编码表达的层级就会不一致。

因此，修改上级部门时，需要：

1. 确认当前部门和新上级部门都存在。
2. 检查新上级是否为当前部门自身。
3. 检查新上级是否属于当前部门的下级，避免形成循环引用。
4. 根据新上级生成当前部门的新编码。
5. 同步更新所有下级部门的编码前缀。
6. 将相关更新放在同一个事务中。

这里还存在一个重要的实现问题：移动部门时，不能只更新直接子部门，而要递归处理整棵下级子树。

另外，如果未来允许多个请求同时调整组织结构，还需要考虑并发修改带来的竞态，不能只依赖单次请求中的防环检查。

# 六、删除部门时，如何防止组织结构被破坏？

删除部门之前，需要先确认它是否存在下级。

如果存在，就返回明确的业务错误，提示用户先处理下级部门。

如果不存在，才允许删除。

不过，仅仅在 Service 中执行一次查询还不够。

在查询下级部门与执行删除之间，可能发生另一笔请求新增子部门的情况。因此，数据库也应该配置自引用外键，并使用 `Restrict` 等适合当前数据库的删除约束，避免删除仍被其他部门引用的记录。

这样就形成了两道保障：

- Service 提供清楚、友好的业务提示。
- 数据库负责阻止不符合完整性约束的删除。

两者的职责不同，不能因为有数据库外键就省略业务层的检查，也不能因为 Service 检查过就认为数据库不需要约束。

# 七、把这些规则落实到数据库设计

现在，需求与业务规则已经明确，可以开始调整数据库结构。

## 1. 修改 Prisma Schema

打开 `prisma/schema.prisma`，检查现有的 `Dept` 模型。

在保留原有字段的基础上，重点确认以下三项：

1. `code` 具有唯一约束。
2. `parentId` 与 `Dept` 建立自引用关系。
3. 新增 `DeptCodeCounter` 计数器模型。

核心结构如下：

```prisma
model Dept {
  id          String   @id @default(cuid())
  name        String
  code        String   @unique

  parentId    String?
  parent      Dept?    @relation(
    "DeptTree",
    fields: [parentId],
    references: [id],
    onDelete: Restrict
  )
  children    Dept[]   @relation("DeptTree")

  sort        Int      @default(10)
  status      Int      @default(1)
  description String?

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([parentId])
}

/// 记录各范围已经分配的最大部门序号
model DeptCodeCounter {
  scope String @id
  value Int    @default(0)
}
```

注意：如果现有模型已经包含这些字段，不要重复添加；应在原模型上调整约束和关系。

`children` 是 Prisma 的关系字段，不是必须存储在数据库中的独立列。它为查询部门及其下级提供关系映射。

`onDelete: Restrict` 则用于约束仍然存在下级引用的部门不能被直接删除。实际生成的数据库约束应以所使用的数据库及迁移结果为准。

## 2. 为什么要先检查历史数据？

新增唯一约束和外键之前，需要确认已有数据满足约束。

例如，现有部门可能使用了早期教程中的编码：

```text
总公司    HQ
技术部    DEV
前端组    FE
```

我们需要将其统一为新的编码体系：

| 部门 | 新编码 |
| --- | --- |
| 总公司 | `D001` |
| 技术部 | `D001-01` |
| 前端组 | `D001-01-01` |

修改之前，还需要确认：

- 是否存在重复编码；
- 是否存在指向不存在部门的 `parentId`；
- 是否存在不符合新编码规则的历史数据；
- 是否还有其他数据或业务逻辑依赖旧编码。

这些检查不能完全依靠 Prisma 自动完成。

如果数据库中已经存在不符合新约束的数据，迁移就可能失败。因此，应先备份数据，再完成必要的清理和迁移准备。

## 3. 执行数据库迁移

完成 Schema 调整并检查历史数据后，执行：

```bash
pnpm prisma migrate dev --name add_dept_relation_and_counter

npx prisma generate
```

这条命令会根据 Prisma Schema 生成迁移并应用到开发数据库。

执行完成后，应检查数据库中的实际表结构，确认唯一约束、外键和计数器表都已经创建。

注意：迁移与历史数据清理是两件事。如果现有编码尚未统一，不要直接在包含真实数据的环境中执行可能失败或造成数据风险的迁移。

# 八、历史数据的编码计数器如何初始化？

计数器表建立后，还不能马上开始新增部门。

原因是：数据库中已经存在的部门，其编码序号并没有自动记录到计数器中。

例如，技术部下面已经存在 `D001-01-03`，如果对应计数器仍然为 `0`，第一次新增就可能再次分配序号 `01`。

因此，在启用新增功能之前，需要先扫描历史数据，按范围统计已经分配的最大序号，并初始化计数器。

## 1. 先明确回填算法

回填时，对每个现有部门执行以下步骤：

1. 根据 `parentId` 确定它所属的计数范围。
2. 从编码中提取最后一段序号。
3. 找到该范围内的最大序号。
4. 将最大序号写入对应的计数器记录。

例如：

```text
D001          → 范围 __ROOT__，序号 1
D001-01       → 范围 总公司ID，序号 1
D001-01-03    → 范围 技术部ID，序号 3
```

注意，不能简单地把整个编码中的所有数字拼起来，也不能按部门总数计算。需要提取的是当前编码最后一段的序号。

对应的代码
```
import { db } from "../lib/db";

/** 扫描现有编码，按"范围"取最大序号，写入计数器。只需要在启用新增功能之前跑一次。 */
async function main() {
  const rows = await db.dept.findMany({ select: { parentId: true, code: true } });

  const maxByScope = new Map<string, number>();
  for (const row of rows) {
    const seq = Number(row.code.match(/(\d+)$/)?.[1] ?? 0); // 取编码最后一段数字
    const scope = row.parentId ?? "__ROOT__";
    maxByScope.set(scope, Math.max(maxByScope.get(scope) ?? 0, seq));
  }

  for (const [scope, value] of maxByScope) {
    await db.deptCodeCounter.upsert({
      where: { scope },
      update: { value },
      create: { scope, value },
    });
  }
  console.log("回填完成：", Object.fromEntries(maxByScope));
}

main().finally(() => db.$disconnect());
```

## 2. 回填脚本应该具备什么条件？

建议将一次性回填脚本放在：

```text
prisma/backfill-counters.ts
```

它属于数据库维护任务，而不是日常业务请求。

实现时应满足以下要求：

- 扫描现有部门数据；
- 按范围计算最大序号；
- 使用 `upsert` 写入计数器；
- 处理已有计数器，不能让历史已分配序号倒退；
- 对不符合新编码规则的记录给出错误提示；
- 完成后输出每个范围的回填结果。

特别要注意最后两点。

**第一，回填脚本不能无条件覆盖更大的计数器值。** 如果计数器此前已经使用过，而某些部门又被删除了，那么当前剩余部门的最大序号可能小于历史值。此时应该保留历史计数器值与当前扫描值中的较大者。

**第二，不能把回填脚本当成可以随时重复执行的普通初始化脚本。** 如果没有明确的迁移和恢复策略，重新扫描当前数据可能破坏原有的序号分配记录。

因此，第一次上线前，应先备份数据、核对历史编码，再执行回填。

## 3. 如何执行回填脚本？

本项目使用 TypeScript，可以通过 `tsx` 运行脚本：

```bash
pnpm dlx tsx prisma/backfill-counters.ts
```

这条命令会临时调用 `tsx` 执行指定的 TypeScript 文件。

回填完成后，应该检查计数器表中的数据是否与历史部门编码一致，而不是只看到控制台输出「完成」就认为初始化正确。

例如：

| scope | value | 含义 |
| --- | ---: | --- |
| `__ROOT__` | 1 | 顶级部门已分配到序号 1 |
| 总公司的 ID | 1 | 总公司下已分配到序号 1 |
| 技术部的 ID | 3 | 技术部下已分配到序号 3 |

以后新增部门时，系统就可以基于计数器分配新的序号。

# 九、代码应该放在哪里？

数据库准备完成后，还需要确定后续代码的组织方式。

这里不应该先画出一份包含所有文件的目录树，再强行让代码填进去，而应该根据各个模块承担的职责决定文件归属。

本项目建议采用以下结构：

```text
prisma/
├── schema.prisma
└── backfill-counters.ts

lib/
├── db.ts
└── biz-error.ts

server/
└── dept/
    ├── types.ts
    ├── schema.ts
    ├── dept-tools.ts
    ├── mappers.ts
    ├── service.ts
    └── actions.ts

app/
└── dept/
    ├── page.tsx
    ├── dept-workspace.tsx
    └── _components/
        ├── tree-node-item.tsx
        └── dept-edit-dialog.tsx
```

各个文件的职责如下。

## 1. `server/dept/schema.ts`

负责部门写操作的 Zod Schema。

例如，新增部门和修改部门可能有不同的输入要求，因此可以分别定义创建与更新 Schema，并从 Schema 推导对应的输入类型。

如果多个入口需要共享校验规则，就在这里统一维护，避免前后端各自编写一套不一致的规则。

## 2. `server/dept/types.ts`

保留现有的服务端业务类型。

这里可以定义服务层需要的类型，例如部门查询结果、内部业务参数等。

如果某个类型只属于前端展示，就不必为了方便而全部塞进这个文件。

## 3. `server/dept/dept-tools.ts`

负责部门业务规则中相对独立、可以单独测试的函数。

例如：

- `formatCode`：根据规则格式化编码；
- `nextDeptCode`：根据计数器生成下一个部门编码；
- `nextSort`：计算同级部门的下一个排序值。

这些函数属于部门业务，不需要放进通用 `lib/`。

其中，`formatCode` 可以设计成纯函数；涉及数据库计数器的函数，则应明确事务客户端和并发更新策略。

## 4. `server/dept/service.ts`

负责新增、修改、删除的完整业务流程。

它调用输入解析、业务规则函数和数据库操作，处理上级校验、防环、删除约束，以及需要保持一致性的事务。

## 5. `server/dept/actions.ts`

负责定义 Server Actions，接收客户端请求、解析输入、调用 Service，并将结果转换成前端能够理解的返回值。

这里还需要处理业务错误与系统错误的区别，不能把数据库异常或内部堆栈直接返回给用户。

Server Actions 是服务端入口，不应被当作天然可信的内部函数。需要在服务端执行输入校验，并根据实际项目的权限要求检查调用者是否有相应操作权限。

## 6. `app/dept/` 下的页面和组件

前端只负责交互与展示。

`dept-workspace.tsx` 管理弹窗状态、选择当前部门、调用 Action，并在操作成功后更新页面。

`dept-edit-dialog.tsx` 负责收集表单输入，可以在前端复用 Zod 规则，及时提示用户错误。

前端组件不应直接调用 Service，也不应该为了共享一个类型而导入整个服务端模块。

另外，新增和修改可以共用同一个表单组件，但需要根据当前模式决定哪些字段可编辑。例如，编码由系统生成，就不应该把编码输入框开放给用户。

# 十、数据写入之后，页面如何刷新？

最后还需要解决一个容易被忽略的问题：数据库已经修改，页面上的部门树和表格怎么更新？

前面的查询功能已经建立了服务端取数链路。

现在，写操作可以采用以下流程：

```text
用户提交表单
    ↓
Server Action 解析输入
    ↓
Service 执行业务校验与事务
    ↓
数据库写入成功
    ↓
重新验证 /dept 对应的缓存路径
    ↓
页面重新获取数据并渲染
    ↓
部门树与表格显示最新结果
```

在 Next.js 中，可以通过 `revalidatePath("/dept")` 重新验证对应路径的缓存。

但要注意：调用 `revalidatePath` 不等于数据库自动刷新，也不意味着任何客户端状态都会被重置。具体的重新取数和组件更新行为，还取决于页面的数据获取方式、缓存配置以及客户端状态管理方式。

因此，后续实现时要明确哪些数据来自服务端，哪些状态只属于弹窗，以及操作成功后需要更新哪些展示区域。

这样才能避免数据库中的部门已经更新，而左侧树和右侧表格仍显示旧数据的问题。

# 小结

这一篇没有急着写三个按钮，而是先把部门管理的业务规则和技术边界确定下来。

我们明确了：

1. 新增、修改和删除分别需要解决什么业务问题。
2. Zod 负责输入格式与字段约束，Service 负责业务规则，数据库负责完整性约束。
3. 编码由系统生成，使用计数器记录已分配序号，避免因删除而回收编号。
4. 修改上级部门时，需要同步处理整个下级子树的编码。
5. 删除有下级的部门必须受到业务层与数据库的双重约束。
6. 部门业务工具函数应放在 `server/dept/` 下，而不是为了复用而放进通用 `lib/`。
7. 通过清晰的文件职责划分，让输入校验、业务规则、数据写入和前端交互各司其职。

下一篇，我们将从最基础的规则函数开始，先实现编码格式化、计数器序号分配和排序计算，再通过单元测试验证这些规则。

**先把规则设计清楚，再把规则写成代码，最后用测试证明代码符合预期。** 这才是一个可持续维护的全栈业务模块应该采用的开发路径。
