# 6.4 部门管理实战：封装编码与排序规则，并用单元测试验证

# 一、前言

上一篇我们完成了部门编码规则的设计和数据库准备。

现在，部门表 `Dept` 已经具备以下基础：

- `code`：部门编码，具有唯一约束。
- `parentId`：上级部门 ID，通过自引用关系构建部门层级。
- `DeptCodeCounter`：部门编码计数器，用于记录不同范围内已经分配的序号。
- 历史数据：已经完成编码整理，计数器也已经初始化。

数据库准备好了，接下来就要开始写代码。

但在编写新增、修改、删除等业务流程之前，我们先解决一个问题：**如何把已经确定的业务规则变成可以独立使用、独立测试的代码？**

例如，新增一个部门时，我们需要知道：

1. 新部门应该生成什么编码？
2. 新部门的排序值应该是多少？
3. 如果上级部门不存在，应该如何处理？
4. 如何验证这些规则是正确的？

如果直接把这些逻辑全部写进新增部门的业务函数，代码就会同时处理参数校验、数据库查询、编码生成、排序计算和数据写入。逻辑一多，后续修改和测试都会变得困难。

因此，本篇先把编码和排序规则单独提取出来，形成独立的工具函数。

本篇完成后，我们将得到三个核心函数：

| 函数 | 作用 |
| --- | --- |
| `formatCode` | 根据上级编码和序号，生成完整部门编码 |
| `nextDeptCode` | 根据上级部门，分配下一个部门编码 |
| `nextSort` | 根据同级部门，计算下一个排序值 |

同时，我们还会学习如何使用 Vitest 编写单元测试，在不连接真实数据库的情况下验证这些规则。

需要注意：这里的目标不是提前完成部门新增流程，而是先把后续业务流程需要的规则准备好。

# 二、先把业务规则转换成代码设计

正式写代码之前，我们先明确每个规则的输入、处理过程和输出。

## 2.1 部门编码如何生成？

上一篇已经确定，部门编码采用层级结构。

例如：

```text
总公司       D001
├── 技术部   D001-01
│   ├── 开发组 D001-01-01
│   └── 测试组 D001-01-02
└── 销售部   D001-02
```

可以发现，部门编码实际上由两部分组成：

- 上级部门的编码。
- 当前层级分配的序号。

对于顶级部门，没有上级编码，因此直接生成 `D001`、`D002` 这样的编码。

对于下级部门，则在上级编码后面追加两位序号，例如 `D001-01`。

这意味着，编码格式本身不需要访问数据库。只要给它一个上级编码和一个序号，就可以计算出最终结果。

因此，我们先设计一个纯函数：

```typescript
formatCode(parentCode, seq)
```

这里有一个重要的知识点：**纯函数只负责计算，不负责查询数据库，也不修改外部状态。**

例如：

```typescript
formatCode(null, 1);       // D001
formatCode("D001", 1);     // D001-01
formatCode("D001-01", 2);  // D001-01-02
```

同样的输入始终得到同样的输出，不需要启动数据库，也不需要创建事务。

这样的函数非常适合单元测试。

## 2.2 序号从哪里来？

`formatCode` 只能负责格式转换，却不能决定下一个序号是多少。

假设技术部的编码是 `D001-01`，现在需要新增一个子部门。

我们不能简单地根据现有部门数量计算序号，因为部门可能被删除，历史序号也不能重新使用。

因此，序号应该由上一篇设计的 `DeptCodeCounter` 计数器维护。

它记录每个编码范围已经分配到的序号。例如：

| 编码范围 | 当前计数值 |
| --- | ---: |
| 顶级部门 | 4 |
| 技术部 `D001` | 3 |
| 销售部 `D002` | 2 |

当新增一个技术部的下级部门时，系统需要将技术部对应的计数器从 `3` 增加到 `4`，然后生成 `D001-04`。

这里涉及两个动作：

1. 从数据库中找到上级部门的编码。
2. 更新对应的计数器，并取得新的序号。

这已经不是纯粹的格式计算了，因为它需要访问数据库。

因此，我们将它封装为 `nextDeptCode`，并要求调用方传入事务客户端。

## 2.3 排序值如何计算？

部门编码和排序值是两套不同的规则。

编码用于标识部门，排序值则用于控制同级部门的显示顺序。

假设某个部门下面有三个子部门：

| 部门 | 排序值 |
| --- | ---: |
| 开发组 | 10 |
| 测试组 | 20 |
| 运维组 | 30 |

现在新增一个部门，系统应当读取同级部门的最大排序值，再加上 `10`，得到 `40`。

如果当前没有同级部门，则从 `10` 开始。

因此，排序规则可以表示为：

```text
下一个排序值 = 同级最大排序值 + 10
```

对应的函数是 `nextSort`。

它只需要查询数据库中的最大排序值，不需要修改计数器。

至此，我们已经明确了三个函数的职责：

- `formatCode`：负责格式转换。
- `nextDeptCode`：负责分配编码序号。
- `nextSort`：负责计算排序值。

接下来就可以开始实现。

# 三、先定义业务错误

在编写规则函数之前，我们先统一业务错误的表达方式。

为什么需要单独定义错误类？

因为系统中会出现不同类型的错误。

例如：

- 用户选择了一个不存在的上级部门。
- 数据库连接失败。
- Prisma 查询发生异常。
- 程序出现了未预料的错误。

这些错误不能全部用同一种方式展示。

像“上级部门不存在”这样的业务错误，可以向用户说明原因；数据库连接失败或内部异常，则应该记录详细信息，避免直接向用户暴露底层错误。

因此，我们先创建 `lib/biz-error.ts`。

```typescript
/**
 * 业务错误：message 是可以向用户展示的提示。
 */
export class BizError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "BizError";
  }
}
```

这里使用了 TypeScript 的 `class` 继承。

`BizError extends Error` 表示 `BizError` 继承 JavaScript 内置的 `Error` 类，因此它仍然是一个标准错误对象，可以使用 `throw` 抛出，也可以使用 `try...catch` 捕获。

例如：

```typescript
throw new BizError("上级部门不存在");
```

后续的业务服务就可以识别这种错误，并决定如何向前端返回提示。

这里暂时只定义错误类型，不负责处理 HTTP 响应，也不负责记录日志。这些属于后续业务流程的职责。

# 四、实现部门编码与排序工具

现在创建 `server/dept/dept-tools.ts`。输入如下代码：
```
import type { Prisma } from "@/app/generated/prisma/client";
import { BizError } from "@/lib/biz-error";

/** 事务客户端类型：$transaction 回调里拿到的 tx */
export type Tx = Prisma.TransactionClient;

export const ROOT_SCOPE = "__ROOT__";

/** 纯函数：上级编码 + 序号 → 完整编码。顶级 D001，下级 D001-01 */
export function formatCode(parentCode: string | null, seq: number): string {
  return parentCode
    ? `${parentCode}-${String(seq).padStart(2, "0")}`
    : `D${String(seq).padStart(3, "0")}`;
}

/**
 * 分配下一个部门编码。
 * 必须在事务里调用：计数器 +1 和部门插入要同生共死，由调用方决定何时提交。
 */
export async function nextDeptCode(tx: Tx, parentId: string | null): Promise<string> {
  let parentCode: string | null = null;
  if (parentId) {
    const parent = await tx.dept.findUnique({
      where: { id: parentId },
      select: { code: true },
    });
    if (!parent) throw new BizError("上级部门不存在");
    parentCode = parent.code;
  }

  const scope = parentId ?? ROOT_SCOPE;
  const counter = await tx.deptCodeCounter.upsert({
    where: { scope },
    update: { value: { increment: 1 } }, // 原子自增，事务内会锁住这一行
    create: { scope, value: 1 },          // 该范围第一次分配
  });
  return formatCode(parentCode, counter.value);
}

/** 同级现有最大排序 + 10；没有同级则从 10 开始 */
export async function nextSort(tx: Tx, parentId: string | null): Promise<number> {
  const result = await tx.dept.aggregate({
    where: { parentId },
    _max: { sort: true },
  });
  return (result._max.sort ?? 0) + 10;
}

```

## 4.1 引入事务客户端类型

先看两个基础定义：

```typescript
import type { Prisma } from "@/app/generated/prisma/client";
import { BizError } from "@/lib/biz-error";

export type Tx = Prisma.TransactionClient;

export const ROOT_SCOPE = "__ROOT__";
```

这里涉及三个知识点。

**第一，`import type` 是什么？**

```typescript
import type { Prisma } from "@/app/generated/prisma/client";
```

它表示只导入 TypeScript 类型，不需要将 `Prisma` 作为运行时对象导入。

类型信息会在编译过程中被处理，帮助 TypeScript 检查代码是否符合预期。

**第二，为什么定义 `Tx`？**

```typescript
export type Tx = Prisma.TransactionClient;
```

在 Prisma 中，通过交互式事务执行回调时，可以获得一个事务客户端：

```typescript
await db.$transaction(async (tx) => {
  // 在这里使用 tx 执行数据库操作
});
```

这个 `tx` 只能在当前事务上下文中使用。

我们将它的类型命名为 `Tx`，后续函数只要声明参数类型为 `Tx`，就能明确表示：调用方必须传入事务客户端，而不是随意传入一个普通数据库对象。

**第三，`ROOT_SCOPE` 有什么用？**

```typescript
export const ROOT_SCOPE = "__ROOT__";
```

顶级部门没有 `parentId`，但计数器表需要一个值来区分不同的编码范围。

因此，我们用 `__ROOT__` 表示顶级部门的编码范围。

它只是一个用于计数器的特殊标识，并不是真实的部门 ID。

## 4.2 实现纯函数 `formatCode`

先实现最简单的编码格式转换：

```typescript
/**
 * 上级编码 + 序号，生成完整部门编码。
 * 顶级：D001
 * 下级：D001-01
 */
export function formatCode(
  parentCode: string | null,
  seq: number
): string {
  return parentCode
    ? `${parentCode}-${String(seq).padStart(2, "0")}`
    : `D${String(seq).padStart(3, "0")}`;
}
```

逐段理解这段代码。

**第一，为什么 `parentCode` 的类型是 `string | null`？**

因为顶级部门没有上级编码，所以使用 `null` 表示不存在上级编码。

当 `parentCode` 有值时，说明当前部门属于某个上级部门；没有值时，则按照顶级部门规则生成编码。

**第二，`String(seq)` 有什么作用？**

序号最初是数字，但我们需要将它拼接到字符串中，因此先将数字转换为字符串。

**第三，`padStart()` 有什么作用？**

`padStart` 是 JavaScript 字符串的方法，用于在字符串左侧补齐指定长度。

例如：

```typescript
String(1).padStart(2, "0");   // "01"
String(12).padStart(2, "0");  // "12"

String(1).padStart(3, "0");   // "001"
```

因此，顶级部门使用三位序号，下级部门使用两位序号。

需要注意，`padStart` 只会补齐长度，不会截断超过指定长度的字符串。例如，`100` 仍然是 `100`，不会变成 `00`。

**第四，为什么这个函数不访问数据库？**

因为它只需要两个参数就能完成计算。

这让它可以被任何业务代码调用，也可以单独测试，而不需要准备数据库环境。

## 4.3 实现 `nextDeptCode`

接下来实现需要访问数据库的编码分配函数。

```typescript
/**
 * 分配下一个部门编码。
 * 必须在事务里调用，由调用方控制事务提交。
 */
export async function nextDeptCode(
  tx: Tx,
  parentId: string | null
): Promise<string> {
  let parentCode: string | null = null;

  if (parentId) {
    const parent = await tx.dept.findUnique({
      where: { id: parentId },
      select: { code: true },
    });

    if (!parent) {
      throw new BizError("上级部门不存在");
    }

    parentCode = parent.code;
  }

  const scope = parentId ?? ROOT_SCOPE;

  const counter = await tx.deptCodeCounter.upsert({
    where: { scope },
    update: {
      value: { increment: 1 },
    },
    create: {
      scope,
      value: 1,
    },
  });

  return formatCode(parentCode, counter.value);
}
```

这段代码可以分为三个步骤。

**第一步：获取上级部门编码。**

```typescript
let parentCode: string | null = null;

if (parentId) {
  const parent = await tx.dept.findUnique({
    where: { id: parentId },
    select: { code: true },
  });

  if (!parent) {
    throw new BizError("上级部门不存在");
  }

  parentCode = parent.code;
}
```

如果传入了 `parentId`，说明要创建的是子部门。

系统通过 `findUnique` 根据部门 ID 查询上级部门，只选择 `code` 字段，因为当前只需要它的编码，不需要读取整条部门记录。

如果查询不到上级部门，就抛出业务错误，后面的计数器操作也不会继续执行。

如果 `parentId` 是 `null`，则说明正在为顶级部门分配编码，不需要查询上级部门。

**第二步：确定计数器范围。**

```typescript
const scope = parentId ?? ROOT_SCOPE;
```

这里使用了空值合并运算符 `??`。

它的意思是：当 `parentId` 为 `null` 或 `undefined` 时，使用 `ROOT_SCOPE`；否则使用 `parentId`。

因此：

```typescript
null         // "__ROOT__"
"dept-001"   // "dept-001"
```

不同的上级部门拥有不同的计数器，互不影响。

**第三步：使用 `upsert` 更新计数器。**

```typescript
const counter = await tx.deptCodeCounter.upsert({
  where: { scope },
  update: {
    value: { increment: 1 },
  },
  create: {
    scope,
    value: 1,
  },
});
```

`upsert` 可以理解为“有则更新，无则创建”。

它包含两个分支：

- `update`：如果计数器已经存在，就将 `value` 增加 `1`。
- `create`：如果计数器不存在，就创建一条计数器记录，初始值为 `1`。

这里的：

```typescript
value: { increment: 1 }
```

是 Prisma 提供的原子递增操作。

与先读取当前值、再由应用程序计算并写回相比，原子递增可以避免多个操作都基于同一个旧值计算而产生的丢失更新问题。

不过，**原子递增不等于整个业务流程天然安全**。并发事务、唯一约束冲突、事务重试等情况仍然需要结合数据库结构和完整业务流程考虑。

另外，`upsert` 要求 `scope` 能够唯一定位计数器记录。这依赖于上一篇已经设计好的唯一约束。

最后，我们调用刚才实现的纯函数：

```typescript
return formatCode(parentCode, counter.value);
```

数据库负责分配序号，纯函数负责将序号转换成编码。

两者各司其职。

## 4.4 实现 `nextSort`

最后实现排序计算：

```typescript
/**
 * 同级现有最大排序值 + 10。
 * 没有同级部门时，从 10 开始。
 */
export async function nextSort(
  tx: Tx,
  parentId: string | null
): Promise<number> {
  const result = await tx.dept.aggregate({
    where: { parentId },
    _max: { sort: true },
  });

  return (result._max.sort ?? 0) + 10;
}
```

这里使用 Prisma 的 `aggregate` 聚合查询。

```typescript
where: { parentId }
```

表示只统计指定上级部门下面的子部门。

如果 `parentId` 为 `null`，则查询顶级部门。

```typescript
_max: { sort: true }
```

表示计算符合条件的记录中，`sort` 字段的最大值。

例如，同级部门的排序值为 `10`、`20`、`30`，那么聚合查询返回的最大值就是 `30`。

最后：

```typescript
return (result._max.sort ?? 0) + 10;
```

如果查询到了最大值，就在它的基础上加 `10`；如果没有任何同级部门，最大值就是 `null`，则先按 `0` 处理，最终返回 `10`。

这里也体现了一个设计原则：排序值的计算不需要读取全部同级部门，只需要获取最大值即可。

至此，三个工具函数已经实现。

但代码能够编译，并不代表规则一定正确。接下来我们需要验证它们。

# 五、使用 Vitest 编写单元测试

## 5.1 为什么要写单元测试？

如果只在页面上测试新增部门，我们需要准备数据库、启动服务、进入页面、填写表单，再观察结果。

这适合验证完整业务流程，但不适合快速检查一个个独立规则。

例如，我们只想确认：

```typescript
formatCode("D001", 3)
```

是否返回：

```text
D001-03
```

完全没有必要启动数据库。

单元测试的目的，就是把一个相对独立的功能拿出来，准备输入、执行代码，再检查输出是否符合预期。

本篇使用 Vitest 完成测试。

## 5.2 安装 Vitest

在项目根目录执行：

```bash
pnpm add -D vitest
```

这里的 `-D` 表示将 Vitest 安装为开发依赖。

测试工具通常用于开发和持续集成阶段，不需要作为应用程序的运行时依赖。

接下来，在 `package.json` 的 `scripts` 中增加：

```json
{
  "scripts": {
    "test": "vitest run"
  }
}
```

注意，如果项目原本已经有其他 `scripts`，只需要增加 `test` 这一项，不要覆盖原有配置。

## 5.3 如何在不连接数据库的情况下测试？

`formatCode` 是纯函数，直接调用即可。

但是，`nextDeptCode` 和 `nextSort` 都依赖数据库操作。测试时如果真的连接数据库，就会增加环境准备成本，也可能修改真实数据。

因此，我们使用 Mock，也就是模拟依赖。

Mock 的基本思路是：**不真正执行数据库操作，而是预先指定数据库调用应该返回什么结果。**

例如，测试 `nextSort` 时，我们可以模拟数据库返回：

```typescript
{
  _max: {
    sort: 30
  }
}
```

然后检查函数是否返回 `40`。

这样测试的重点就是排序计算规则，而不是数据库本身。

## 5.4 编写测试代码

新建 `tests/dept-tools.test.ts`：

```typescript
import { describe, it, expect, vi } from "vitest";
import {
  formatCode,
  nextDeptCode,
  nextSort,
  type Tx,
} from "../server/dept/dept-tools";

/**
 * 创建假的事务客户端。
 * 通过参数指定数据库操作的返回结果。
 */
function fakeTx(opts: {
  parentCode?: string;
  parentMissing?: boolean;
  counter?: number;
  maxSort?: number | null;
}) {
  const parentMissing = opts.parentMissing ?? false;

  return {
    dept: {
      findUnique: vi.fn().mockResolvedValue(
        parentMissing
          ? null
          : opts.parentCode === undefined
            ? null
            : { code: opts.parentCode }
      ),
      aggregate: vi.fn().mockResolvedValue({
        _max: {
          sort: opts.maxSort ?? null,
        },
      }),
    },
    deptCodeCounter: {
      upsert: vi.fn().mockResolvedValue({
        value: opts.counter ?? 1,
      }),
    },
  } as unknown as Tx;
}

describe("formatCode", () => {
  it("生成顶级部门编码", () => {
```

这里需要重点理解几个测试方法。

**第一，`describe` 用来组织测试。**

```typescript
describe("formatCode", () => {
  // ...
});
```

它将同一类功能的测试放在一起，方便阅读和定位问题。

**第二，`it` 描述具体的测试场景。**

例如：

```typescript
it("没有同级部门时返回 10", async () => {
  // ...
});
```

一个测试用例最好聚焦于一个明确的行为。

**第三，`expect` 用来验证结果。**

```typescript
expect(formatCode(null, 1)).toBe("D001");
```

这句话表示：执行 `formatCode(null, 1)` 后，结果必须严格等于 `"D001"`。

如果实际结果不同，测试就会失败。

**第四，`vi.fn()` 用来创建 Mock 函数。**

```typescript
findUnique: vi.fn().mockResolvedValue(null)
```

它模拟了一个异步数据库查询，并指定查询结果为 `null`。

类似地：

```typescript
upsert: vi.fn().mockResolvedValue({ value: 3 })
```

表示模拟计数器操作，返回一条计数值为 `3` 的记录。

这里的 `as unknown as Tx` 是 TypeScript 的类型断言，用来告诉编译器：这个模拟对象在测试中按照 `Tx` 使用。

它并没有真的创建 Prisma 事务客户端，也不会自动验证所有数据库行为。模拟对象必须与被测函数实际使用的接口保持一致。

另外，上面的测试模拟了数据库返回结果，但**不会验证真实数据库中的原子递增、事务回滚或并发行为**。这些能力需要在后续业务流程中通过集成测试等方式进一步验证。

## 5.5 运行测试

在项目根目录执行：

```bash
pnpm test
```

如果所有断言都通过，Vitest 就会报告测试成功。

如果测试失败，可以根据失败用例检查：

- 编码格式是否符合规则。
- 计数器是否使用了正确的范围。
- 上级不存在时是否提前抛出错误。
- 排序值是否按照最大值加 `10` 计算。

测试的价值不仅在于发现错误，更在于把业务规则固定下来。以后修改代码时，只要这些规则发生意外变化，测试就能及时给出反馈。

本篇没有直接实现部门新增、修改和删除，而是先把这些业务流程需要的规则准备好。
