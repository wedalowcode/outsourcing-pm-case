# 实操步骤

## 第六步：把按钮和弹窗接进容器

打开 `app/dept/dept-workspace.tsx`，在原来的基础上补五块。

**① 导入与辅助函数**（放在组件外面）

```tsx
import { useState } from "react";
import { createDeptAction, deleteDeptAction, updateDeptAction } from "@/server/dept/actions";
import { DeptEditDialog, emptyForm, type DeptForm } from "./_components/dept-edit-dialog";
import type { DeptInput, Row, TreeNode } from "@/server/dept/types";

type DialogState =
  | { mode: "create"; parentId: string | null }
  | { mode: "edit"; row: Row };

/** 一个节点及其全部子孙的 id */
function collectIds(node: TreeNode): string[] {
  return [node.id, ...node.children.flatMap(collectIds)];
}

/** 在树里找到指定 id 的节点，返回它和全部子孙的 id；找不到返回空数组 */
function subtreeIds(nodes: TreeNode[], id: string): string[] {
  for (const node of nodes) {
    if (node.id === id) return collectIds(node);
    const hit = subtreeIds(node.children, id);
    if (hit.length) return hit;
  }
  return [];
}
```

**② 组件内部：状态与提交**

```tsx
// null 表示弹窗关闭；create 记录"预选的上级"；edit 记录正在编辑的行
const [dialog, setDialog] = useState<DialogState | null>(null);
const [formError, setFormError] = useState("");
const [submitting, setSubmitting] = useState(false);

/** 打开"新建"：parentId 为 null 时建顶级部门，否则建到指定部门下 */
function openCreate(parentId: string | null) {
  setFormError("");
  setDialog({ mode: "create", parentId });
}

/** 打开"编辑" */
function openEdit(row: Row) {
  setFormError("");
  setDialog({ mode: "edit", row });
}

async function handleSubmit(form: DeptForm) {
  if (!dialog) return;
  setFormError("");
  setSubmitting(true);

  const payload: DeptInput = {
    name: form.name,
    parentId: form.parentId,
    // 留空就不传：新增时由服务端取"同级最大 + 10"，编辑时保持原值
    sort: form.sort.trim() ? Number(form.sort) : undefined,
    status: form.status,
    description: form.description,
  };

  try {
    const result =
      dialog.mode === "edit"
        ? await updateDeptAction(dialog.row.id, payload)
        : await createDeptAction(payload);

    if (!result.ok) {
      setFormError(result.message); // 服务端校验失败：留在弹窗里显示原因
      return;
    }
    setDialog(null); // 成功：关闭弹窗，页面由 revalidatePath 负责刷新
  } finally {
    setSubmitting(false); // 无论成功失败都要恢复按钮，否则按钮会一直卡在"保存中…"
  }
}

async function handleDelete(row: Row) {
  const ok = window.confirm(`确认删除「${row.name}」？（有下级时将无法删除）`);
  if (!ok) return;

  const result = await deleteDeptAction(row.id);
  if (!result.ok) window.alert(result.message); // 例如：存在下级部门，不能删除
}
```

**⑤ 挂上弹窗**（放在组件返回的最外层容器末尾）

```tsx
{dialog && (
  <DeptEditDialog
    key={dialog.mode === "edit" ? dialog.row.id : `create-${dialog.parentId ?? "root"}`}
    mode={dialog.mode}
    initial={
      dialog.mode === "edit"
        ? {
            name: dialog.row.name,
            code: dialog.row.code,
            parentId: dialog.row.parentId,
            sort: String(dialog.row.sort),
            status: dialog.row.status as DeptStatus,
            description: dialog.row.description ?? "", // 回填原有描述，避免保存时被清空
          }
        : emptyForm(dialog.parentId)
    }
    tree={tree}
    excludeIds={dialog.mode === "edit" ? subtreeIds(tree, dialog.row.id) : []}
    error={formError}
    submitting={submitting}
    onClose={() => setDialog(null)}
    onSubmit={handleSubmit}
  />
)}
```

（记得在导入里补上 `DeptStatus`：`import type { DeptInput, DeptStatus, Row, TreeNode } from "@/server/dept/types";`）

🔍 **为什么用一个 `dialog` 状态**

"弹窗开没开、什么模式、编辑哪一行、新建时预选谁"本来就是同一件事的不同侧面。拆成多个 `useState` 容易出现不一致（比如 `mode` 是 edit 但 `editing` 还是 null）；合成一个联合类型后，非法组合根本写不出来。

🔍 **为什么条件渲染 + `key`**

`{dialog && <DeptEditDialog key=... />}` 保证每次打开（包括从"编辑 A"切到"编辑 B"）都是新实例，表单天然是初始值；关闭即卸载，不残留上次内容。

🔍 **`submitting` 解决什么**

写库需要时间。`submitting` 为 `true` 时按钮变成"保存中…"并禁用，避免连点重复提交；`finally` 保证无论成败都会恢复。

## 第七步：删除为什么要二次确认

`handleDelete` 已在第六步写好，这里说明两个设计注意点：

1. **删除不可逆**：新增能删掉重来，编辑能改回去，删除没有"撤销"，所以一律先确认。
2. **失败要说清原因**：被拒绝时 `alert` 显示服务端原文——"存在下级部门，不能删除，建议改用停用"，比一句"删除失败"有用得多。

> 真实工程用统一的确认弹窗组件（标题、危险色、Promise 形式），课程里先用 `window.confirm` / `window.alert` 讲清流程，后面可替换。

* **\[x] 单元测试**：`formatCode`、`nextDeptCode`、`nextSort` 的用例全绿。

* **\[x] 新增顶级部门**：不填编码，保存后自动是 `D002`，排序为同级最大值 + 10。

* **\[x] 新增下级**：点"添加下级"，弹窗里上级已预选好；保存后编码形如 `D001-01-02`，左侧树和右侧表格同时出现。

* **\[x] 编码不复用**：把 `D001-01-02` 删掉再新增，编码是 `D001-01-03`，不会回到被删的号。

* **\[x] 编码只读**：新增时编码框是灰色占位"由系统自动生成"；编辑时显示现有编码且不能改。

* **\[x] 名称必填**：名称留空点保存，前端立即提示，且没有发请求。

* **\[x] 编辑回填**：弹窗里各字段（**包括描述**）是当前值；改完保存后表格和树一起更新，描述没被清空。

* **\[x] 换上级**：把"前端组"改成顶级，保存后编码变成新的顶级编码（如 `D003`），下级编码前缀同步变化；移回原处会拿到新号，不复用旧号。

* **\[x] 防环（界面）**：编辑"技术部"时，上级下拉里选不到它自己及其下级"前端组"。

* **\[x] 防环（服务端）**：临时加一个按钮直接调 `updateDeptAction("技术部的id", { name: "技术部", parentId: "前端组的id" })`，应返回"不能把自己（或其下级）设为上级，会形成循环"，数据不变；验证完删掉按钮。

* **\[x] 删除保护**：删"总公司"（有下级），提示"存在下级部门，不能删除，建议改用停用"，数据仍在。

* **\[x] 删除执行**：删最底层的"前端组"，确认后表格和树里都消失，Prisma Studio 里它名下的计数器记录也没了。

* **\[x] 无整页刷新**：以上操作页面都没有白屏重载，靠的是 `revalidatePath("/dept")`。

# 小结

这一模块表面上只加了三个按钮，真正花力气的是它们背后的规矩：

* **规则和流程分开**：`dept-tools.ts` 管"编码怎么算"，`service.ts` 管"什么时候算、算完怎么写"，前者可以脱离数据库单测。
* **事务保证对账**：计数器递增和部门写入同生共死；删除时清理计数器也在同一个事务里。
* **计数器只增不减**：编号永远不会复用，这是用计数器而不是 `count + 1` 的根本原因。
* **服务端是底线**：前端校验只管体验；字段合法性、上级存在、防环、删除检查都在服务端，数据库外键再兜一层。
* **Server Action 是公开端点**：真实项目里别忘了在每个 Action 里补上登录和权限校验。
