# 7.3 实现用户初始化与管理员创建

## 一、前言：系统第一次启动时，管理员从哪里来？

上一节，我们设计了 User、Role、Permission、UserRole 和 RolePermission 五张核心数据表，建立了用户、角色与权限之间的关系。

但是，现在还有一个问题没有解决。

数据库刚刚创建完成，里面没有任何用户。如果系统要求用户先登录才能进入后台，那么第一个用户应该如何创建？

如果我们直接开放一个注册页面，让任何人都可以注册管理员账号，那么系统就会面临严重的安全问题。

因此，在实现登录功能之前，我们需要先解决系统初始化问题。

本节将围绕一个具体目标展开：

**第一次部署系统时，通过受控的初始化脚本创建必要的权限数据和初始管理员；初始化完成后，重复执行脚本也不会产生重复账号或覆盖已有密码。**

完成本节后，我们将具备以下能力：

- 初始化系统所需的角色与权限。
- 安全地创建第一个管理员账号。
- 使用密码哈希存储密码。
- 防止重复初始化造成的数据冲突。
- 验证初始化结果是否符合预期。

## 二、为什么不能开放任意用户注册管理员账号？

### 2.1 注册账号与授予管理员权限是两件事

假设系统开放了一个注册接口，用户提交用户名和密码后，后台直接创建用户，并给用户分配管理员角色。

逻辑可能类似这样：

```ts
const user = await db.user.create({
  data: {
    username,
    passwordHash,
    name,
    status: "ACTIVE",
    userRoles: {
      create: {
        role: {
          connect: {
            code: "ADMIN",
          },
        },
      },
    },
  },
});
```

这段代码最大的问题不是创建用户，而是它把“注册账号”和“授予管理员权限”绑定在了一起。

任何能够访问注册接口的人，都有可能获得系统的最高权限。

一旦攻击者创建管理员账号，就可能进一步修改用户、分配权限、读取业务数据，甚至删除重要记录。

因此，我们必须明确：

- 用户注册解决的是账号创建问题。
- 管理员创建解决的是系统最高权限的初始授予问题。
- 普通用户是否可以注册、注册后拥有什么角色，应当由明确的业务规则决定。

对于企业内部管理系统，通常不需要公开注册入口。用户账号由管理员创建，或者由受控的邀请、审批流程创建。

### 2.2 为什么不应该在注册接口中写死管理员角色？

另一个容易被忽略的问题是：管理员角色本身也需要经过初始化。

如果我们把 `ADMIN` 写进注册代码，却没有在数据库中创建对应角色，用户创建过程就会失败。

即使角色已经存在，也不意味着所有注册用户都应该获得这个角色。

正确的职责划分应该是：

| 功能 | 职责 |
|---|---|
| 数据库迁移 | 创建表、字段、索引和约束 |
| 系统初始化 | 创建基础角色、权限和初始管理员 |
| 用户管理 | 创建、停用和维护普通用户 |
| 角色管理 | 为用户分配角色，维护角色权限 |
| 登录认证 | 验证身份，建立有效会话 |
| 服务端授权 | 判断当前用户是否有权执行具体操作 |

这些功能各自负责一件事，系统才容易维护。

### 2.3 为什么初始化脚本比手工插入数据更可靠？

如果每次部署都需要手动进入数据库，插入角色、权限和管理员记录，很容易出现遗漏。

例如：

- 创建了管理员账号，却忘记关联管理员角色。
- 创建了角色，却没有分配必要的权限。
- 密码直接以明文写入数据库。
- 重复执行 SQL，产生重复数据或冲突。
- 更换部署环境后，无法复现原来的初始化过程。

因此，我们需要把初始化过程写成脚本。

初始化脚本应该能够明确表达系统的基础数据，并通过程序逻辑与数据库约束确保结果正确。

## 三、设计初始管理员创建流程

在编写代码之前，我们先设计初始化流程。

### 3.1 初始化流程

系统第一次部署时，执行以下步骤：

```text
准备数据库
    ↓
执行 Prisma 数据库迁移
    ↓
检查管理员初始化参数
    ↓
初始化基础角色与权限
    ↓
检查初始管理员是否存在
    ↓
不存在：创建管理员并关联角色
已存在：不修改现有管理员
    ↓
验证初始化结果
```

这里需要区分两个概念：

**数据库迁移负责创建数据库结构，初始化脚本负责创建必要的业务数据。**

两者不能互相替代。

数据库表存在，并不意味着管理员账号已经存在；管理员账号存在，也不意味着他一定拥有正确的角色和权限。

### 3.2 初始管理员应该具备哪些信息？

本课程沿用 7.2 中的 User 模型。

创建初始管理员时，需要提供：

| 信息 | 来源 | 要求 |
|---|---|---|
| username | 环境变量 | 必填，符合用户名规则 |
| password | 环境变量或安全注入机制 | 必填，满足密码强度要求 |
| name | 环境变量或预设值 | 必填 |
| passwordHash | 初始化脚本 | 由密码哈希算法生成 |
| status | 初始化脚本 | 设置为 ACTIVE |
| role | 已初始化的角色 | 使用稳定的角色编码关联 |

这里不建议将真实管理员密码写进源代码。

源代码可能进入 Git 仓库，也可能被复制到其他环境。如果密码写死在脚本中，就很难保证它只被授权人员掌握。

更合理的方式是，通过环境变量或部署平台的密钥管理机制提供初始化密码。

### 3.3 管理员角色与权限应该如何初始化？

管理员角色使用稳定的编码，例如：

```text
ADMIN
```

系统初始化时，先确保这个角色存在，再将初始管理员与其关联。

这里还有一个重要的设计问题：管理员角色究竟拥有哪些权限？

本节先创建基础的 `ADMIN` 角色，并为它关联本节定义的全部基础权限。

在实际生产系统中，不应将来历不明的权限自动赋予管理员。权限集合应当由受控的初始化代码明确声明。

另外，管理员账号不应该因为初始化脚本重复运行，就自动恢复成某个默认密码。

我们将在后面的代码中落实这条原则。

## 四、密码如何安全存储？

### 4.1 为什么不能直接保存密码？

假设管理员设置的密码是：

```text
Admin@123456
```

如果数据库直接保存这段字符串，那么任何能够读取用户表的人，都可能直接获得管理员密码。

如果同一密码还被用于其他网站，风险就会进一步扩大。

因此，数据库中应该保存密码哈希，而不是原始密码。

例如：

```text
用户输入的密码
      ↓
密码哈希算法
      ↓
passwordHash
      ↓
写入数据库
```

登录时，程序读取密码哈希，并使用对应算法验证用户输入的密码。

不能通过简单的字符串比较来验证密码，也不应该使用 MD5 或 SHA-256 直接计算密码哈希作为密码存储方案。

### 4.2 为什么使用 Argon2id？

本课程使用 Argon2id 作为密码哈希算法。

Argon2id 是专门面向密码存储设计的算法，可以配置计算成本和内存成本，增加攻击者进行大规模密码猜测的代价。

在 Node.js 项目中，可以使用 `argon2` 包完成密码哈希和验证。

安装依赖：

```bash
pnpm add argon2
```

生成密码哈希：

```ts
import argon2 from "argon2";

const passwordHash = await argon2.hash(password, {
  type: argon2.argon2id,
});
```

验证密码：

```ts
const isValid = await argon2.verify(
  passwordHash,
  inputPassword,
);
```

实际部署时，应结合服务器性能和安全要求配置 Argon2id 的内存、时间及并行参数。

此外，密码应通过安全的环境变量或密钥注入机制传入脚本，避免出现在代码仓库、日志、终端命令历史或错误消息中。

## 五、编写初始化脚本

接下来进入代码实现。

在开始之前，请确认上一节已经创建了以下 Prisma 模型：

- `User`
- `Role`
- `Permission`
- `UserRole`
- `RolePermission`

并且 `UserStatus` 枚举包含 `ACTIVE` 和 `DISABLED`。

如果你的项目已经有统一的数据库访问模块，例如 `server/lib/db.ts`，应优先复用现有模块。下面假设数据库客户端从 `server/lib/db.ts` 导出。

### 5.1 定义初始化所需的基础数据

我们先创建一个独立的初始化脚本。

文件路径：

```text
prisma/seed-admin.ts
```

脚本将完成三个任务：

1. 确保管理员角色存在。
2. 确保基础权限存在，并与管理员角色关联。
3. 在管理员不存在时创建初始管理员。

本节的基础权限使用以下编码：

```ts
const permissions = [
  {
    code: "customer:read",
    name: "查看客户",
  },
  {
    code: "customer:create",
    name: "创建客户",
  },
  {
    code: "customer:update",
    name: "修改客户",
  },
  {
    code: "customer:delete",
    name: "删除客户",
  },
  {
    code: "project:read",
    name: "查看项目",
  },
  {
    code: "project:create",
    name: "创建项目",
  },
  {
    code: "task:read",
    name: "查看任务",
  },

    name: "分配任务",
  },
  {
    code: "worklog:create",
    name: "创建工时记录",

];
```

这里需要特别说明：这是一组用于演示初始化机制的基础权限，不代表项目已经实现了所有对应的业务接口。

随着后续课程逐步实现客户、项目、任务和工时模块，我们再为新增业务操作补充权限定义。

### 5.2 编写完整初始化脚本

将下面代码保存为 `prisma/seed-admin.ts`。

```ts
import "dotenv/config";
import argon2 from "argon2";
import { db } from "../server/lib/db";

const permissions = [
  { code: "customer:read", name: "查看客户" },
  { code: "customer:create", name: "创建客户" },
  { code: "customer:update", name: "修改客户" },
  { code: "customer:delete", name: "删除客户" },
  { code: "project:read", name: "查看项目" },
  { code: "project:create", name: "创建项目" },
  { code: "task:read", name: "查看任务" },
  { code: "task:assign", name: "分配任务" },
  { code: "worklog:create", name: "创建工时记录" },
];

async function main() {
  const username = process.env.INIT_ADMIN_USERNAME;
  const password = process.env.INIT_ADMIN_PASSWORD;
  const name = process.env.INIT_ADMIN_NAME;

  if (!username || !password || !name) {
    throw new Error(
      "必须设置 INIT_ADMIN_USERNAME、INIT_ADMIN_PASSWORD、INIT_ADMIN_NAME",
    );
  }

  if (username.length > 50 || name.length > 100) {
    throw new Error("用户名或姓名超过允许长度");
  }

  if (password.length < 12) {
    throw new Error("初始管理员密码至少需要 12 个字符");
  }

  if (username.trim() !== username || !/^[a-zA-Z0-9._-]+$/.test(username)) {
    throw new Error("用户名只能包含字母、数字、点、下划线和连字符，且不能有首尾空格");
  }

  await db.$transaction(async (tx) => {
    const adminRole = await tx.role.upsert({
      where: { code: "ADMIN" },
      update: {},
      create: {
        code: "ADMIN",
        name: "系统管理员",
        description: "负责系统基础配置与管理",
      },
    });

    for (const item of permissions) {
      const permission = await tx.permission.upsert({
        where: { code: item.code },
        update: {},
        create: item,
      });

      await tx.rolePermission.upsert({
        where: {
          roleId_permissionId: {
            roleId: adminRole.id,
            permissionId: permission.id,
          },
        },
        update: {},
        create: {
          roleId: adminRole.id,
          permissionId: permission.id,
        },
      });
    }

    const existingUser = await tx.user.findUnique({
      where: { username },
      select: { id: true },
    });

    if (existingUser) {
      console.log(
        `用户 ${username} 已存在，不修改其密码、状态或角色关联。`,
      );
      return;
    }

    const passwordHash = await argon2.hash(password, {
      type: argon2.argon2id,
    });

    const user = await tx.user.create({
      data: {
        username,
        passwordHash,
        name,
        status: "ACTIVE",
      },
    });

    await tx.userRole.create({
      data: {
        userId: user.id,
        roleId: adminRole.id,
      },
    });

    console.log(`初始管理员 ${username} 创建成功。`);
  });
}

main()
  .catch((error) => {
    console.error("系统初始化失败。", error);
    process.exitCode = 1;
  })
  .finally(async () => {
    await db.$disconnect();
  });
```

注意，这里的 `../server/lib/db` 必须与你上一节实际使用的数据库客户端路径保持一致。如果项目使用不同的目录结构，应调整导入路径。

### 5.3 理解脚本中的关键设计

**第一，使用 upsert 初始化基础角色与权限。**

`upsert` 的意思是：记录不存在时创建，记录存在时执行更新分支。

我们将 `update` 设置为空对象：

```ts
update: {}
```

这样，脚本重复执行时，不会擅自覆盖已有角色名称、权限名称或描述。

这里的 `upsert` 依赖对应的唯一约束，例如 Role 的 `code` 和 Permission 的 `code`。

**第二，使用数据库事务。**

```ts
await db.$transaction(async (tx) => {
  // 初始化角色、权限和管理员
});
```

事务确保本次初始化涉及的数据库写入作为一个整体提交。

如果中途发生异常，事务中的数据库变更将回滚，避免留下只创建了部分权限关联、却没有完成初始化的状态。

需要注意，事务只保护数据库操作，并不能让日志输出等外部副作用一起回滚。

**第三，创建管理员之前先检查账号是否存在。**

如果同名用户已经存在，脚本不会重新生成密码哈希，也不会修改该用户的密码、状态或角色关联。

这一点非常重要。

初始化脚本不应该成为重置管理员密码的隐蔽入口，否则任何能够重复运行脚本的人，都可能改变已有管理员账号的状态。

**第四，密码哈希只在需要创建新账号时生成。**

如果用户已经存在，就没有必要重新哈希密码。

这样既减少了不必要的计算，也避免脚本重复运行时对现有账号造成影响。

**第五，管理员与角色之间的关联必须单独创建。**

User 表保存的是用户信息，角色分配保存在 UserRole 表中。

创建用户成功，并不代表用户自动获得管理员权限。因此，脚本必须明确创建对应的 UserRole 记录。

## 六、配置安全的初始化参数

脚本需要从环境变量读取管理员信息。

开发环境可以使用本地 `.env` 文件，但要注意：**真实管理员密码不能提交到 Git 仓库，也不能放入示例配置文件。**

例如，在本地 `.env` 中配置：

```dotenv
INIT_ADMIN_USERNAME=admin
INIT_ADMIN_PASSWORD=替换为安全生成的初始密码
INIT_ADMIN_NAME=系统管理员
```

这里展示的是配置格式，不能将示例文字直接当成实际密码使用。

应确保 `.env` 已加入 `.gitignore`，并检查它没有被 Git 跟踪：

```bash
git check-ignore .env
```

如果命令没有返回预期结果，应检查 `.gitignore` 配置以及该文件是否已经被纳入版本控制。

对于生产环境，优先使用部署平台的密钥管理功能或安全注入机制提供密码，初始化完成后及时清理临时凭据。

另外，不要在日志中输出初始密码，也不要把包含密码的环境变量完整打印到终端。

## 七、执行初始化脚本

先确认 PostgreSQL 数据库已经启动，并且 Prisma Schema 已完成迁移。

可以先执行：

```bash
pnpm prisma validate
```

确认模型定义有效。

然后执行：

```bash
pnpm prisma migrate dev
```

开发环境下，这一步负责应用尚未执行的数据库迁移。

如果项目已有迁移历史，正常情况下不需要为每次初始化都重新创建迁移文件。

接下来，使用项目已有的 TypeScript 运行工具执行脚本。例如，项目已经安装 `tsx` 时，可以运行：

```bash
pnpm exec tsx prisma/seed-admin.ts
```

如果尚未安装 `tsx`，可以在项目中按既有工具链安装并统一使用。

第一次运行成功后，终端应显示类似信息：

```text
初始管理员 admin 创建成功。
```

这里的 `admin` 只是示例用户名，实际输出取决于你的环境变量。

## 八、验证初始化结果

初始化完成后，不要只看终端输出，还需要验证数据库中的实际记录。

可以通过 Prisma Studio 查看数据：

```bash
pnpm prisma studio
```

然后检查以下五张表。

### 8.1 检查 User 表

确认管理员账号已经创建，并检查：

- username 与预期一致。
- passwordHash 不等于原始密码。
- status 为 `ACTIVE`。
- createdAt、updatedAt 等字段符合预期。

不要把密码哈希复制到公开日志或文档中。

### 8.2 检查 Role 表

确认存在编码为 `ADMIN` 的角色。

如果系统中原本就有该角色，初始化脚本应该复用原有记录，而不是创建第二个管理员角色。

### 8.3 检查 Permission 表

确认本节定义的基础权限已经创建。

每条权限记录都应拥有唯一编码，重复执行脚本不应该增加重复权限。

### 8.4 检查 UserRole 表

确认初始管理员的用户 ID 与 `ADMIN` 角色的 ID 正确关联。

如果 User 表有管理员记录，但 UserRole 中没有对应关联，那么这个用户并没有通过本节的数据模型获得管理员角色。

### 8.5 检查 RolePermission 表

确认 `ADMIN` 角色关联了本节定义的所有基础权限。

这一点很容易遗漏：角色存在，不等于角色拥有权限。

只有角色与权限之间建立了正确的关联，后续的授权逻辑才能查询到相应权限。

## 九、验证脚本是否可以安全重复执行

一个可靠的初始化脚本，不能只在第一次执行时成功，还应该明确处理重复执行的情况。

### 测试一：首次执行

执行：

```bash
pnpm exec tsx prisma/seed-admin.ts
```

预期结果：创建基础角色、基础权限、权限关联和初始管理员。

### 测试二：再次执行

再次运行相同命令。

预期结果：

- 不产生重复角色。
- 不产生重复权限。
- 不产生重复角色权限关系。
- 不创建重复管理员。
- 不覆盖已有管理员密码。

脚本可能再次输出用户已存在的提示，这是正常行为。

### 测试三：修改初始化密码后重新执行

将 `INIT_ADMIN_PASSWORD` 改成另一个值，再运行脚本。

预期结果：已有管理员的密码哈希不发生变化。

因为本节的初始化脚本只负责创建初始管理员，不负责重置密码。

如果需要修改密码，应通过后续专门设计的密码修改或密码重置流程完成，并验证操作者身份及其授权。

### 测试四：中途发生异常

可以在独立的开发数据库中模拟初始化失败，并检查事务是否回滚。

例如，在测试环境中故意触发某个约束错误，然后确认本次事务中的角色、权限、关联和用户记录没有留下不完整的变更。

不要在生产数据库中通过破坏真实数据的方式进行故障测试。

### 测试五：管理员已经存在，但没有 ADMIN 角色

这是一个容易忽略的边界情况。

当前脚本发现用户名已存在后，会直接跳过管理员创建与角色关联，因此不会自动修复已有用户缺失的角色关系。

这是刻意采取的保守策略：初始化脚本不应该未经确认就把已有账号提升为管理员。

如果需要修复这种情况，应通过单独的、经过授权的管理操作完成，而不是让初始化脚本静默授予最高权限。

## 十、总结：初始化脚本也是系统安全边界的一部分

本节完成了系统首次部署时的基础数据初始化机制。

我们通过初始化脚本创建基础角色、权限及权限关联，并在管理员不存在时创建初始管理员。

同时，我们使用 Argon2id 对密码进行哈希处理，通过数据库事务保证初始化过程的一致性，并借助唯一约束和显式关联表控制重复数据。

本节最重要的并不是 `upsert` 这个 API，而是建立了几个系统设计原则：

1. 管理员权限必须通过受控流程授予，不能由公开注册接口随意分配。
2. 密码必须经过安全哈希处理，不能以明文保存。
3. 初始化操作应尽可能幂等，即重复执行不会产生重复记录或覆盖已有账号的安全状态。
4. 初始化账号与日常账号管理应当分离，避免脚本成为未经授权的提权或重置密码入口。
5. 数据库记录创建成功不等于权限配置正确，必须检查用户、角色、权限及关联关系。

到这里，系统已经拥有了第一个管理员账号，但管理员还不能真正登录使用系统。

接下来，我们需要实现登录认证：接收用户名和密码、验证密码哈希、建立安全会话，并让服务端能够识别每一次请求对应的用户身份。
