# 8.7 角色新增：从角色规则到完整的服务端写入流程

上一节我们完成了用户新增，实现了从表单输入、Zod 校验、Server Action、Service 到数据库写入的完整链路，并统一了密码哈希处理方式。

接下来实现角色新增。

角色管理与用户管理有一个明显的区别：用户是系统中的操作主体，角色则是权限分配的载体。 用户通过角色获得相应的功能权限，因此角色新增不仅需要考虑名称和编码，还需要考虑唯一性、角色类型以及后续的权限分配。

表面上看，角色新增只需要填写几个字段并执行一条 `INSERT`。但如果缺少合理的业务规则，后续很容易出现角色编码重复、系统内置角色被误操作、角色权限与角色资料混在一起等问题。

本节按照项目现有的分层结构，依次实现：

1. 明确角色新增的业务规则。
2. 定义角色新增的 Zod 校验规则。
3. 实现角色创建 Service。
4. 实现 Server Action。
5. 实现使用 shadcn/Base UI 组件的新增角色弹窗。
6. 在角色列表中接入新增按钮。
7. 验证新增流程及异常情况。

本节只实现角色基础资料的新增，暂不处理角色权限配置、用户关联、角色编辑和删除。这些功能分别在后续小节实现。

## 一、明确角色新增的业务规则

在编写代码之前，先明确角色管理的数据模型和业务边界。

假设当前系统的角色表包含以下字段：

| 字段   | 是否必填 | 规则                              |
| ---- | ---- | ------------------------------- |
| 角色编码 | 是    | 3～50 个字符，以字母开头，只允许字母、数字、下划线和连字符 |
| 角色名称 | 是    | 去除首尾空格，长度 2～50 个字符              |
| 角色描述 | 否    | 去除首尾空格，最长 500 个字符               |
| 角色状态 | 是    | 只能是 `ACTIVE` 或 `DISABLED`       |

这里需要先区分三个概念。

第一，角色编码是系统标识，角色名称是业务展示信息。

例如：

- `ADMIN`：系统管理员
- `PROJECT_MANAGER`：项目经理
- `DEVELOPER`：开发人员
- `SALES`：销售人员

角色名称可能随着业务调整而修改，但角色编码一旦被用户、权限或其他业务数据引用，就不应轻易修改。

本节先将角色编码作为创建时的唯一标识，后续不在普通编辑表单中修改它。

第二，角色新增不等于角色授权。

新增一个名为“项目经理”的角色，只代表系统中存在这个角色，并不意味着它已经获得项目管理权限。

后续需要通过角色权限配置，将角色与权限点关联起来，再通过用户与角色的关联关系，使用户获得相应的权限。

第三，角色状态不能代替权限校验。

将角色设置为停用，应当影响该角色的有效授权。但不能只在页面上隐藏菜单，就认为用户已经失去了权限。服务端执行操作时仍然必须检查用户的有效权限。

本节只保存角色基础资料，不实现上述授权逻辑。

### 1. 角色数据模型检查

在继续编写代码之前，先打开项目的 `prisma/schema.prisma`，确认现有的 `Role` 模型。

如果项目已经存在角色模型，应直接沿用，不要重复创建一张角色表。

以下是本节示例使用的模型结构：

```
enum RoleStatus {
  ACTIVE
  DISABLED
}

model Role {
  id          String     @id @default(cuid())
  code        String     @unique @db.VarChar(50)
  name        String     @db.VarChar(50)
  description String?    @db.VarChar(500)
  status      RoleStatus @default(ACTIVE)

  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt
}
```

这段代码用于说明本节所依赖的数据结构，不应直接覆盖项目现有的 `Role` 模型。

如果项目中的角色模型已经包含 `users`、`permissions` 等关联字段，应保留这些字段。如果已经定义了状态枚举，也应使用项目现有的枚举类型。

本节依赖的核心约束是：

- `code` 必须具有数据库唯一约束。
- `name` 是必填字段。
- `description` 可以为空。
- `status` 使用固定枚举值。

如果模型需要调整，完成迁移后再继续实现 Service。

## 二、定义角色新增的输入规则

与用户新增保持一致，将业务输入规则放在 `server/role/schema.ts` 中。

新建文件：

`server/role/schema.ts`

```
// server/role/schema.ts
import { z } from "zod";

const roleCodeSchema = z
  .string()
  .trim()
  .min(3, "角色编码至少需要 3 个字符")
  .max(50, "角色编码不能超过 50 个字符")
  .regex(
    /^[a-zA-Z][a-zA-Z0-9_-]*$/,
    "角色编码必须以字母开头，只能包含字母、数字、下划线和连字符",
  )
  .transform((value) => value.toUpperCase());

export const createRoleSchema = z.object({
  code: roleCodeSchema,

  name: z
    .string()
    .trim()
    .min(2, "角色名称至少需要 2 个字符")
    .max(50, "角色名称不能超过 50 个字符"),

  description: z
    .string()
    .trim()
    .max(500, "角色描述不能超过 500 个字符")
    .transform((value) => value || null),

  status: z.enum(["ACTIVE", "DISABLED"]),
});

export type CreateRoleInput = z.infer<typeof createRoleSchema>;
```

这里有几个值得注意的细节。

### 1. 角色编码统一转换为大写

输入 `admin`、`Admin` 或 `ADMIN`，最终都会转换为 `ADMIN`。

这样可以统一角色编码的格式，避免由于大小写不同产生难以理解的业务问题。

不过，代码层面的大小写转换不能代替数据库唯一约束。如果数据库使用大小写敏感的比较规则，历史数据中仍可能存在 `ADMIN` 和 `admin` 两条记录。正式使用前，应检查现有数据，并统一编码规范。

### 2. 角色描述统一转换为空值

当用户没有填写描述时，最终结果为 `null`，而不是空字符串。

这样可以减少数据库中空字符串和 `null` 混用的情况。

### 3. 只允许固定的角色状态

前端传入的 `ACTIVE` 和 `DISABLED` 是业务枚举，而不是任意字符串。

即使有人绕过前端，直接调用 Server Action，服务端仍然会执行相同的校验。

### 4. 输入校验不负责检查唯一性

Zod 负责检查格式和字段规则。

角色编码是否已经被其他角色使用，属于需要查询数据库的业务规则，应当放在 Service 中处理。

这样可以避免将数据库查询逻辑放入纯输入校验模块。

## 三、实现角色创建 Service

Service 负责角色创建的业务规则和数据库操作，不负责读取表单，也不直接管理页面状态。

新建或打开：

`server/role/service.ts`

如果该文件已经存在角色列表查询方法，应当保留现有实现，只增加角色创建相关代码。

```
// server/role/service.ts
import "server-only";

import { Prisma } from "@/lib/generated/prisma/client";
import { db } from "@/lib/db";
import type { CreateRoleInput } from "./schema";

export type CreateRoleResult =
  | {
      success: true;
    }
  | {
      success: false;
      code: "ROLE_CODE_EXISTS" | "ERROR";
      message: string;
    };

export async function createRole(
  input: CreateRoleInput,
): Promise<CreateRoleResult> {
  const code = input.code.trim().toUpperCase();

  // 1. 检查角色编码是否已存在。
  const existingRole = await db.role.findUnique({
    where: { code },
    select: { id: true },
  });

  if (existingRole) {
    return {
      success: false,
      code: "ROLE_CODE_EXISTS",
      message: "该角色编码已存在",
    };
  }

  try {
    // 2. 创建角色基础资料。
    await db.role.create({
      data: {
        code,
        name: input.name.trim(),
        description: input.description,
        status: input.status,
      },
    });

    return {
      success: true,
    };
  } catch (error) {
    // 3. 处理并发创建造成的唯一键冲突。
    if (
      error instanceof Prisma.PrismaClientKnownRequestError &&
      error.code === "P2002"
    ) {
      return {
        success: false,
        code: "ROLE_CODE_EXISTS",
        message: "该角色编码已存在",
      };
    }

    throw error;
  }
}
```

如果项目的 Prisma Client 生成路径不是 `@/lib/generated/prisma/client`，应当改成 `lib/db.ts` 所使用的实际导入路径，不要重新生成另一套 Prisma Client。

### 1. 为什么先检查角色编码？

在创建前查询数据库，可以提前向用户提供友好的提示。

例如，系统中已经存在 `PROJECT_MANAGER`，用户再次创建相同编码时，直接提示“该角色编码已存在”，而不必等待数据库异常。

但是，这个查询只是为了改善用户体验，并不能独立保证唯一性。

### 2. 为什么还要捕获 `P2002`？

考虑下面的并发情况：

```
请求 A：查询 ADMIN，不存在
请求 B：查询 ADMIN，不存在
请求 A：创建 ADMIN，成功
请求 B：创建 ADMIN，失败
```

如果只依赖创建前的查询，请求 B 仍然可能因为并发而创建失败。

因此，必须同时具备：

- 数据库唯一约束：保证数据正确性。
- Service 中的前置查询：改善用户体验。
- 唯一键异常处理：将并发冲突转换为明确的业务结果。

需要注意的是，Prisma 的 `P2002` 不一定只代表角色编码冲突。如果 `Role` 模型还存在其他唯一字段，应进一步根据异常的 `meta.target` 等信息判断具体冲突字段，避免把其他唯一键错误误报为角色编码重复。

本节假设角色编码是创建流程中需要处理的唯一业务标识。

### 3. 为什么新增角色不直接分配权限？

角色基础资料与角色权限是两类不同的数据。

如果在 `createRole()` 中直接写入权限，角色创建就会同时承担：

- 角色基础资料创建。
- 权限点校验。
- 角色与权限关联。
- 权限变更审计。

这会增加本节的复杂度，也会让后续角色编辑和权限配置难以复用。

因此，本节只创建角色基础资料，后续再单独实现角色授权。

## 四、实现 Server Action

接下来实现客户端与服务端之间的调用入口。

新建：

`server/role/actions.ts`

本项目将 Server Action 放在 `server/<模块>/actions.ts` 中，因此角色管理继续沿用相同约定。

Server Action 负责：

1. 检查当前登录状态。
2. 检查当前操作者是否拥有角色创建权限。
3. 校验客户端提交的数据。
4. 调用角色创建 Service。
5. 刷新角色列表。
6. 返回适合界面展示的结果。

```
// server/role/actions.ts
"use server";

import { revalidatePath } from "next/cache";

import { getCurrentSession } from "@/server/auth/session";
import { createRole } from "@/server/role/service";
import { createRoleSchema } from "@/server/role/schema";

export type CreateRoleActionState = {
  success: boolean;
  message: string;
  fieldErrors?: Record<string, string[] | undefined>;
};

export async function createRoleAction(
  input: unknown,
): Promise<CreateRoleActionState> {
  // 1. 检查登录状态。
  const session = await getCurrentSession();

  if (!session) {
    return {
      success: false,
      message: "登录状态已失效，请重新登录",
    };
  }

  // 2. 检查角色创建权限。
  // 接入项目已有的服务端权限校验函数。
  // 例如：
  // await requirePermission("role:create");

  // 注意：这里必须使用项目实际的权限服务，
  // 不能仅凭登录成功就允许创建角色。

  // 3. 校验输入。
  const parsed = createRoleSchema.safeParse(input);

  if (!parsed.success) {
    return {
      success: false,
      message: "请检查输入内容",
      fieldErrors: parsed.error.flatten().fieldErrors,
    };
  }

  try {
    // 4. 调用 Service。
    const result = await createRole(parsed.data);

    if (!result.success) {
      return {
        success: false,
        message: result.message,
      };
    }

    // 5. 刷新角色管理页面。
    revalidatePath("/roles");

    return {
      success: true,
      message: "角色创建成功",
    };
  } catch (error) {
    console.error("createRoleAction failed", error);

    return {
      success: false,
      message: "创建角色失败，请稍后重试",
    };
  }
}
```

这里有一个必须落实的安全要求：`getCurrentSession()` 只能证明当前请求具有有效会话，不能证明操作者拥有角色创建权限。

如果项目的权限服务已经实现，应当直接调用现有方法，并使用项目定义的权限标识。如果尚未实现，就需要先补齐服务端权限校验，再启用这个操作。

不要将示例中的注释视为已经完成的权限控制。 在真实项目中，如果跳过这一步，任何已登录但没有授权的用户都可能尝试创建角色。

另外，`revalidatePath("/roles")` 必须与你的实际路由一致。如果角色管理页面使用其他路径，应修改为实际路径。

## 五、实现新增角色弹窗

接下来实现客户端界面，继续使用项目已有的 shadcn/Base UI 组件。

新建：

`app/(dashboard)/roles/_components/create-role-dialog.tsx`

以下示例沿用前面用户新增的组件使用方式，包括：

- `Dialog` 管理弹窗。
- `Input` 录入角色信息。
- `Select` 选择角色状态。
- `Button` 触发操作。
- `useTransition` 管理提交状态。
- `createRoleAction` 调用服务端。
- `router.refresh()` 刷新服务端列表。

```
"use client";

import { useState, useTransition } from "react";
import { useRouter } from "next/navigation";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

import {
  Dialog,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
} from "@/components/ui/dialog";

import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from "@/components/ui/select";

import { createRoleAction } from "@/server/role/actions";

type Props = {
  onCreated?: () => void;
};

const initialForm = {
  code: "",
  name: "",
  description: "",
  status: "ACTIVE" as "ACTIVE" | "DISABLED",
};

const statusItems = [
  { value: "ACTIVE", label: "启用" },
  { value: "DISABLED", label: "停用" },
];

export function CreateRoleDialog({ onCreated }: Props) {
  const router = useRouter();

  const [open, setOpen] = useState(false);
  const [pending, startTransition] = useTransition();

  const [form, setForm] = useState(initialForm);
  const [message, setMessage] = useState("");

  const [fieldErrors, setFieldErrors] = useState<
    Record<string, string[] | undefined>
  >({});

  function updateField(
    field: keyof typeof initialForm,
    value: string,
  ) {
    setForm((current) => ({
      ...current,
      [field]: value,
    }));

    setFieldErrors((current) => ({
      ...current,
      [field]: undefined,
    }));

    setMessage("");
  }

  function closeDialog() {
    if (pending) return;

    setOpen(false);
    setForm(initialForm);
    setMessage("");
    setFieldErrors({});
  }

  function handleSubmit(
    event: React.FormEvent<HTMLFormElement>,
  ) {
    event.preventDefault();

    setMessage("");
    setFieldErrors({});

    startTransition(async () => {
      const result = await createRoleAction(form);

      if (!result.success) {
        setMessage(result.message);
        setFieldErrors(result.fieldErrors ?? {});
        return;
      }

      setOpen(false);
      setForm(initialForm);
      setMessage("");
      setFieldErrors({});

      router.refresh();
      onCreated?.();
    });
  }

  function errorFor(field: string) {
    return fieldErrors[field]?.[0];
  }

  return (
    <>
      <Button onClick={() => setOpen(true)}>
        新增角色
      </Button>

      {/* 沿用项目现有 Base UI Dialog 的条件渲染约定。 */}
      {open && (
        <Dialog
          open
          onOpenChange={(nextOpen) => {
            if (!nextOpen) {
              closeDialog();
            }
          }}
        >
          <DialogContent className="sm:max-w-lg">
            <DialogHeader>
              <DialogTitle>新增角色</DialogTitle>

              <DialogDescription>
                创建角色基础资料，权限可以在后续步骤中配置。
              </DialogDescription>
            </DialogHeader>

            <form
              onSubmit={handleSubmit}
              className="space-y-4"
            >
              <div className="space-y-2">
                <Label htmlFor="role-code">
                  角色编码 *
                </Label>

                <Input
                  id="role-code"
                  value={form.code}
                  onChange={(event) =>
                    updateField("code", event.target.value)
                  }
                  placeholder="例如：PROJECT_MANAGER"
                  autoComplete="off"
                  aria-invalid={Boolean(errorFor("code"))}
                  required
                  disabled={pending}
                />

                <p className="text-xs text-muted-foreground">
                  以字母开头，只能包含字母、数字、下划线和连字符。
                  保存时会统一转换为大写。
                </p>

                {errorFor("code") && (
                  <p className="text-sm text-destructive">
                    {errorFor("code")}
                  </p>
                )}
              </div>

              <div className="space-y-2">
                <Label htmlFor="role-name">
                  角色名称 *
                </Label>

                <Input
                  id="role-name"
                  value={form.name}
                  onChange={(event) =>
                    updateField("name", event.target.value)
                  }
                  placeholder="例如：项目经理"
                  aria-invalid={Boolean(errorFor("name"))}
                  required
                  disabled={pending}
                />

                {errorFor("name") && (
                  <p className="text-sm text-destructive">
                    {errorFor("name")}
                  </p>
                )}
              </div>

              <div className="space-y-2">
                <Label htmlFor="role-description">
                  角色描述
                </Label>

                <textarea
                  id="role-description"
                  value={form.description}
                  onChange={(event) =>
                    updateField(
                      "description",
                      event.target.value,
                    )
                  }
                  placeholder="描述该角色的业务职责和使用场景"
                  maxLength={500}
                  disabled={pending}
                  className="border-input placeholder:text-muted-foreground focus-visible:border-ring focus-visible:ring-ring/50 aria-invalid:ring-destructive/20 dark:aria-invalid:ring-destructive/40 aria-invalid:border-destructive flex min-h-24 w-full rounded-md border bg-transparent px-3 py-2 text-sm shadow-xs outline-none focus-visible:ring-[3px] disabled:cursor-not-allowed disabled:opacity-50"
                />

                {errorFor("description") && (
                  <p className="text-sm text-destructive">
                    {errorFor("description")}
                  </p>
                )}
              </div>

              <div className="space-y-2">
                <Label htmlFor="role-status">
                  角色状态
                </Label>

                <Select
                  items={statusItems}
                  value={form.status}
                  onValueChange={(value) =>
                    updateField(
                      "status",
                      value === "DISABLED"
                        ? "DISABLED"
                        : "ACTIVE",
                    )
                  }
                  disabled={pending}
                >
                  <SelectTrigger
                    id="role-status"
                    className="w-full"
                  >
                    <SelectValue />
                  </SelectTrigger>

                  <SelectContent>
                    {statusItems.map((item) => (
                      <SelectItem
                        key={item.value}
                        value={item.value}
                      >
                        {item.label}
                      </SelectItem>
                    ))}
                  </SelectContent>
                </Select>
              </div>

              {message && (
                <p
                  role="alert"
                  className="text-sm text-destructive"
                >
                  {message}
                </p>
              )}

              <DialogFooter>
                <Button
                  type="button"
                  variant="outline"
                  onClick={closeDialog}
                  disabled={pending}
                >
                  取消
                </Button>

                <Button
                  type="submit"
                  disabled={pending}
                >
                  {pending ? "正在创建..." : "创建角色"}
                </Button>
              </DialogFooter>
            </form>
          </DialogContent>
        </Dialog>
      )}
    </>
  );
}
```

### 1. 为什么角色编码不在前端直接转换为大写？

前端可以通过输入提示改善体验，但最终数据格式应当由服务端决定。

这里将大小写转换放在 Zod Schema 中，因此无论数据来自弹窗、其他客户端，还是直接调用 Server Action，最终都会执行相同的转换规则。

Service 再次调用 `toUpperCase()`，是为了让数据库操作明确遵循编码规范。服务端 Schema 仍然是统一的输入校验入口。

### 2. 为什么描述字段使用文本域？

角色名称和编码通常较短，而描述可能需要说明业务职责、数据范围和使用场景，因此使用多行输入更合理。

示例使用原生 `textarea`，目的是让代码能够在现有组件清单中直接运行。如果项目已经有基于 Base UI 的 `Textarea` 组件，应优先复用它，避免在项目中形成两套输入框样式。

### 3. 为什么创建失败时不清空表单？

如果角色编码重复，用户通常只需要调整编码；如果其他字段校验失败，也不应该重新填写全部内容。

因此，只有创建成功后才清空表单。失败时保留输入，并显示服务端返回的错误。

这与用户新增保持一致，也能形成统一的交互体验。

## 六、在角色列表中接入新增按钮

打开现有角色管理工作区，例如：

`app/(dashboard)/roles/role-workspace.tsx`

具体文件名应以项目现有目录为准。

首先引入新增角色弹窗：

```
import { CreateRoleDialog } from "./_components/create-role-dialog";
```

然后将新增按钮放在角色管理页面标题区的右侧：

```
<div className="flex items-start justify-between gap-4">
  <div>
    <h1 className="text-xl font-semibold">
      角色管理
    </h1>

    <p className="mt-1 text-sm text-muted-foreground">
      管理系统角色及其基础资料。
    </p>
  </div>

  <CreateRoleDialog />
</div>
```

如果当前页面已经有统一的标题组件和工具栏，应当将 `CreateRoleDialog` 放入现有布局，不要为了新增按钮重新创建一套页面结构。

创建成功后，弹窗调用 `router.refresh()`，重新获取服务端组件的数据。

如果角色列表采用 Server Component 直接调用 `listRolePage()`，刷新后即可重新读取角色列表。

这里需要区分两件事：

- `revalidatePath("/roles")`：使服务端对应路由的缓存失效。
- `router.refresh()`：请求刷新当前路由的 Server Component 数据。

两者承担的职责不同。本节保留它们与现有用户管理实现一致的使用方式。实际项目中，如果数据查询涉及额外缓存，应确认缓存失效策略覆盖角色列表使用的数据。

## 七、验证新增流程

实现完成后，不要只验证点击按钮后是否出现新记录，还需要检查服务端规则、数据库约束和异常处理。

| 测试场景            | 预期结果           |
| --------------- | -------------- |
| 正常填写角色编码和名称     | 创建成功，列表出现新角色   |
| 角色编码输入 `admin`  | 保存为 `ADMIN`    |
| 角色编码重复          | 返回友好提示，不产生重复记录 |
| 角色编码包含空格或特殊字符   | 服务端拒绝          |
| 角色名称为空          | 服务端拒绝          |
| 角色名称超长          | 服务端拒绝          |
| 描述超过 500 个字符    | 服务端拒绝          |
| 未知角色状态          | 服务端拒绝          |
| 绕过前端直接调用 Action | 仍然执行服务端校验和权限检查 |
| 未登录调用 Action    | 返回登录状态失效       |
| 当前用户没有创建角色权限    | 服务端拒绝          |
| 两个请求并发创建同一编码    | 数据库只允许一个请求成功   |
| 创建失败            | 弹窗保留输入并显示错误信息  |

建议特别验证以下三个场景。

### 场景一：验证编码统一规则

依次输入：

```
admin
Admin
ADMIN
```

每次提交后检查数据库。

第一次成功创建后，后续两次都应因为编码重复而失败。

### 场景二：验证并发唯一性

使用两个并发请求，同时提交相同的角色编码。

即使两个请求都通过了创建前的查询，数据库唯一约束仍然必须阻止重复记录。

### 场景三：验证权限边界

使用一个没有角色创建权限的普通用户，直接调用 `createRoleAction()`。

预期结果是服务端拒绝请求，数据库中不产生新角色。

如果项目当前尚未实现 `requirePermission()` 或等价的权限校验服务，那么这项测试还不能算通过。必须先接入真正的服务端权限检查。

## 八、本节小结

至此，角色新增形成了完整的数据写入链路：

新增角色弹窗

采集角色编码、名称、描述和状态

Server Action

检查会话 · 检查创建权限 · Zod 校验

Role Service

检查编码 · 处理业务规则 · 写入数据库

数据库唯一约束

确保角色编码不会重复

刷新角色列表

展示新创建的角色

本节真正需要掌握的，不是如何增加一个角色表单，而是如何将角色的业务规则、服务端校验、唯一性约束和页面交互组织成清晰的写入流程。

与用户新增相比，角色新增不需要密码哈希，却引入了另一个重要的设计问题：角色基础资料、用户关联和权限分配应当保持职责分离。

下一节可以实现角色编辑，修改角色名称、描述和状态，同时保持角色编码稳定。随后再单独实现角色权限配置，建立从权限点到角色、再到用户的完整授权链路。
