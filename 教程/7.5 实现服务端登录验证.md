# 7.5 使用 Server Actions 实现服务端登录验证

## 一、从登录页面到真正的身份验证

上一节，我们已经完成了登录页面，并使用 React Hook Form 实现了表单交互。

但是，页面能够接收用户名和密码，并不意味着系统已经验证了用户身份。

登录功能还需要解决几个问题：

- 用户是否真实存在？
- 用户输入的密码是否正确？
- 账号是否处于允许登录的状态？
- 如果有人绕过登录页面，直接提交请求，服务端能否拒绝不合法的数据？

这些问题不能只依靠前端解决。前端代码运行在用户可以控制的环境中，用户可以绕过页面校验，直接构造请求。

因此，本节需要把真正的认证逻辑放到服务端。

结合当前项目的架构，我们继续采用 Next.js Server Actions 作为 Web 管理端的操作入口，不提前增加 HTTP API。

本节的整体流程如下：

```text
用户填写用户名和密码
          ↓
登录页面进行基础表单校验
          ↓
调用 loginAction
          ↓
服务端使用 Zod 校验输入
          ↓
根据用户名查询数据库
          ↓
检查账号状态
          ↓
使用 Argon2id 验证密码
          ↓
返回凭据验证结果
```

本节完成后，我们能够验证用户名和密码是否正确，但暂时还不会建立登录会话。Session、Cookie 和登录状态管理将在下一节实现。

## 二、先明确代码的职责和目录

写代码之前，先确定每个模块应该负责什么。

本节采用以下目录结构：

```text
app/
└── login/
    └── page.tsx

lib/
└── db.ts

server/
└── auth/
    ├── schema.ts
    ├── actions.ts
    └── verify-credentials.ts

tests/
└── server/
    └── auth/
        └── verify-credentials.test.ts
```

各文件的职责如下。

| 文件 | 职责 |
|---|---|
| `app/login/page.tsx` | 展示登录表单、处理用户交互和基础校验 |
| `server/auth/schema.ts` | 定义服务端登录数据的 Zod Schema |
| `server/auth/actions.ts` | 接收登录操作、校验输入、组织认证流程 |
| `server/auth/verify-credentials.ts` | 查询用户、检查账号状态、验证密码 |
| `lib/db.ts` | 创建和导出项目统一使用的 Prisma 数据库客户端 |
| `tests/server/auth/verify-credentials.test.ts` | 测试凭据验证逻辑 |

这里有两个需要明确的设计决定。

### 2.1 为什么 Schema 放在 server 目录？

当前项目的部门管理 Schema 已经放在 `server/dept/schema.ts`，因此认证模块也采用一致的组织方式。

登录认证的完整校验规则由服务端负责。把 Schema 放在 `server/auth/schema.ts`，可以明确它属于认证服务的实现，而不是一个默认供所有模块使用的公共工具。

这里并不是说所有 Zod Schema 都必须放在 `server` 目录。是否共享，取决于实际需求。

如果一个 Schema 确实需要被客户端和服务端共同使用，可以放在不依赖服务端专属模块的共享位置。但本节不需要为了复用而额外引入这种结构。

### 2.2 为什么页面不能直接导入这个 Schema？

后续的 `server/auth/schema.ts` 会使用：

```ts
import "server-only";
```

这是为了限制该模块只能在服务端使用。

而 `app/login/page.tsx` 是客户端组件。客户端不能直接导入包含 `server-only` 的模块，否则会破坏服务端与客户端的模块边界。

因此，我们采用以下分工：

- 客户端：使用 React Hook Form 的基础规则，及时提示用户输入错误。
- 服务端：使用 Zod 完整校验所有提交数据。
- 认证服务：只接收已经通过服务端校验的数据，执行数据库查询和密码验证。

这意味着前后端会有少量基础规则重复，但模块边界清晰。对于当前项目而言，这比为了消除少量重复而引入额外的共享 Schema 结构更直接。

另外，数据库客户端仍然统一使用项目现有的 `@/lib/db`，不重复初始化 PrismaClient。

## 三、创建服务端登录 Schema

首先定义登录数据的合法格式。

创建文件：

`server/auth/schema.ts`

```ts
import "server-only";

import { z } from "zod";

export const loginSchema = z.object({
  username: z
    .string()
    .trim()
    .min(1, "请输入用户名")
    .max(50, "用户名不能超过 50 个字符")
    .regex(
      /^[a-zA-Z0-9._-]+$/,
      "用户名只能包含字母、数字、点、下划线和连字符",
    ),

  password: z
    .string()
    .min(1, "请输入密码")
    .max(1024, "密码长度不能超过 1024 个字符"),
});

export type LoginFormValues = z.infer<typeof loginSchema>;
```

这里沿用用户名和密码的基本规则，但需要理解每一条规则的作用。

### 3.1 校验用户名

```ts
username: z
  .string()
  .trim()
  .min(1, "请输入用户名")
  .max(50, "用户名不能超过 50 个字符")
  .regex(
    /^[a-zA-Z0-9._-]+$/,
    "用户名只能包含字母、数字、点、下划线和连字符",
  ),
```

首先要求用户名必须是字符串，然后去除首尾空白，再检查长度和允许使用的字符。

这样可以避免空用户名、超长用户名和不符合规则的用户名进入后续认证流程。

需要注意，`trim()` 只处理用户名首尾的空白，不会删除中间的字符。

### 3.2 校验密码

```ts
password: z
  .string()
  .min(1, "请输入密码")
  .max(1024, "密码长度不能超过 1024 个字符"),
```

这里要求密码不能为空，并设置长度上限。

注意，密码没有使用 `trim()`。密码中的空格可能是用户真实密码的一部分，服务端不应擅自修改用户输入的密码。

### 3.3 导出 TypeScript 类型

```ts
export type LoginFormValues = z.infer<typeof loginSchema>;
```

`z.infer` 可以根据 Schema 自动推导 TypeScript 类型。

这样，后续的认证服务就不必再手动定义一份相同的登录数据类型。

```ts
import type { LoginFormValues } from "@/server/auth/schema";
```

这里的类型导入只用于 TypeScript 类型检查，实际的输入校验仍然由 `loginSchema.safeParse()` 执行。

需要强调的是，Schema 放在服务端目录并不是为了隐藏校验规则，而是为了让服务端负责可信的输入校验。

## 四、实现凭据验证服务

接下来编写真正的认证逻辑。

创建文件：

`server/auth/verify-credentials.ts`

```ts
import "server-only";

import argon2 from "argon2";

import { db } from "@/lib/db";
import type { LoginFormValues } from "@/server/auth/schema";

export type CredentialFailureReason =
  | "INVALID_CREDENTIALS"
  | "ACCOUNT_DISABLED";

export type CredentialResult =
  | {
      ok: true;
      user: {
        id: string;
        username: string;
        name: string;
      };
    }
  | {
      ok: false;
      reason: CredentialFailureReason;
    };

export async function verifyCredentials(
  input: LoginFormValues,
): Promise<CredentialResult> {
  const user = await db.user.findUnique({
    where: {
      username: input.username,
    },
    select: {
      id: true,
      username: true,
      name: true,
      passwordHash: true,
      status: true,
    },
  });

  if (!user) {
    return {
      ok: false,
      reason: "INVALID_CREDENTIALS",
    };
  }

  if (user.status !== "ACTIVE") {
    return {
      ok: false,
      reason: "ACCOUNT_DISABLED",
    };
  }

  const passwordMatches = await argon2.verify(
    user.passwordHash,
    input.password,
  );

  if (!passwordMatches) {
    return {
      ok: false,
      reason: "INVALID_CREDENTIALS",
    };
  }

  return {
    ok: true,
    user: {
      id: user.id,
      username: user.username,
      name: user.name,
    },
  };
}
```

下面逐步理解这段代码。

### 4.1 为什么使用 `server-only`？

```ts
import "server-only";
```

这个模块会访问数据库，并使用 Argon2 验证密码，属于服务端专属逻辑。

加入 `server-only` 后，如果某个客户端模块错误地导入了该模块，Next.js 就能在构建或模块检查阶段发现问题。

它不是认证逻辑本身，而是用来约束模块使用边界的机制。

### 4.2 根据用户名查询用户

```ts
const user = await db.user.findUnique({
  where: {
    username: input.username,
  },
  select: {
    id: true,
    username: true,
    name: true,
    passwordHash: true,
    status: true,
  },
});
```

这里使用项目现有的 Prisma 数据库客户端：

```ts
import { db } from "@/lib/db";
```

前面的数据模型已经为 `User.username` 设置了唯一约束，因此可以使用 `findUnique()` 查询用户。

查询时，我们通过 `select` 明确指定需要的字段：

- `id`：用户的内部标识。
- `username`：登录用户名。
- `name`：用户显示名称。
- `passwordHash`：用于验证密码。
- `status`：判断账号是否允许登录。

为什么不直接查询整个用户对象？

因为凭据验证只需要这些字段。显式选择字段，可以减少不必要的数据读取，也有助于避免敏感字段在后续流程中被意外使用。

### 4.3 用户不存在时拒绝登录

```ts
if (!user) {
  return {
    ok: false,
    reason: "INVALID_CREDENTIALS",
  };
}
```

如果数据库中不存在对应用户，Prisma 会返回 `null`。

此时直接结束验证流程。

这里不单独向登录页面返回“用户名不存在”，而是使用统一的凭据失败结果。这样可以减少通过登录接口枚举有效用户名的风险。

### 4.4 检查账号状态

```ts
if (user.status !== "ACTIVE") {
  return {
    ok: false,
    reason: "ACCOUNT_DISABLED",
  };
}
```

当前项目的用户模型包含账号状态。账号被设置为 `DISABLED` 后，即使密码正确，也不应该继续登录。

因此，先检查账号状态，再验证密码。

需要注意：本节只是在登录时检查状态。下一节实现会话之后，受保护的服务端操作仍然需要根据实际的登录身份和账号状态进行必要的检查。

### 4.5 使用 Argon2id 验证密码

```ts
const passwordMatches = await argon2.verify(
  user.passwordHash,
  input.password,
);
```

前面初始化管理员时，我们使用 Argon2id 对密码进行哈希处理，并把结果保存在数据库中。

登录时，不应将用户输入的密码与 `passwordHash` 直接进行字符串比较，而应调用 `argon2.verify()` 验证。

这里传入两个参数：

1. 数据库中保存的密码哈希。
2. 用户本次输入的原始密码。

验证通过后，才继续执行成功分支。

### 4.6 只返回必要的用户信息

```ts
return {
  ok: true,
  user: {
    id: user.id,
    username: user.username,
    name: user.name,
  },
};
```

虽然数据库查询读取了 `passwordHash`，但验证成功后，我们没有将它放进返回结果。

这是服务端开发中需要坚持的原则：

**服务端为了处理业务而读取某个字段，不代表应该把这个字段返回给客户端。**

当前函数只返回后续认证流程可能需要的基本用户信息，不返回密码哈希，也不直接返回完整的 Prisma 用户对象。

## 五、实现登录 Server Action

凭据验证逻辑已经完成，接下来创建登录操作，连接页面与认证服务。

创建文件：

`server/auth/actions.ts`

```ts
"use server";

import { loginSchema } from "@/server/auth/schema";
import { verifyCredentials } from "@/server/auth/verify-credentials";

export type LoginActionResult =
  | {
      ok: true;
    }
  | {
      ok: false;
      message: string;
    };

export async function loginAction(
  input: unknown,
): Promise<LoginActionResult> {
  const parsed = loginSchema.safeParse(input);

  if (!parsed.success) {
    return {
      ok: false,
      message: "请检查用户名和密码的输入格式",
    };
  }

  try {
    const result = await verifyCredentials(parsed.data);

    if (!result.ok) {
      return {
        ok: false,
        message: "用户名或密码错误，或账号不可用",
      };
    }

    return {
      ok: true,
    };
  } catch (error) {
    console.error("登录凭据验证失败", error);

    return {
      ok: false,
      message: "服务暂时不可用，请稍后重试",
    };
  }
}
```

### 5.1 为什么参数使用 `unknown`？

```ts
export async function loginAction(
  input: unknown,
)
```

因为 Server Action 接收的输入不能被默认视为可信数据。

即使登录页面已经完成表单校验，调用者仍然可能绕过页面，直接构造请求。

因此，我们首先把输入视为未知数据，只有通过服务端 Schema 校验之后，才使用解析后的结果。

### 5.2 服务端为什么还要校验一次？

```ts
const parsed = loginSchema.safeParse(input);
```

前端校验主要用于改善用户体验；服务端校验则是数据进入业务逻辑之前必须经过的边界。

例如，用户可以绕过前端对用户名长度的限制，直接提交一个超长字符串。如果服务端没有校验，就可能把不符合预期的数据传给数据库查询和后续业务逻辑。

所以，任何来自客户端的数据，都应当在服务端重新验证。

这里使用 `safeParse()`，而不是直接调用 `parse()`，是因为它可以返回成功或失败的结果，让 Action 统一处理格式错误，而不需要依赖异常控制正常流程。

### 5.3 为什么 Action 不直接写数据库查询？

因为 Action 与凭据验证服务承担不同的职责。

`loginAction()` 负责：

1. 接收登录操作。
2. 校验提交的数据。
3. 调用凭据验证服务。
4. 将结果转换成适合页面使用的返回值。
5. 统一处理服务端异常。

`verifyCredentials()` 则负责查询用户、检查账号状态和验证密码。

这样划分后，凭据验证可以独立测试，其他服务端认证流程也能够在需要时复用它。

### 5.4 为什么不新增 API Route？

当前项目以 Next.js Web 管理端为主，部门管理等操作已经采用 Server Actions，因此登录也沿用同一种方式。

本节不需要额外创建：

```text
app/api/auth/login/route.ts
```

也不需要在页面中使用 `fetch()` 手动调用这个接口。

如果未来小程序、第三方系统或其他客户端需要通过 HTTP 调用认证能力，可以再增加 API Route 作为独立入口，并复用同一个凭据验证服务。

**入口可以不同，核心业务逻辑不需要重复实现。**

## 六、修改登录页面

现在服务端逻辑已经完成，需要修改 `app/login/page.tsx`，让表单真正调用 Server Action。

这里有一个关键点：由于 `page.tsx` 是客户端组件，我们不再从 `server/auth/schema.ts` 导入 `loginSchema`，也不再使用 `zodResolver(loginSchema)`。

客户端改用 React Hook Form 自带的规则进行基础校验，服务端则继续使用完整的 Zod Schema。

### 6.1 调整导入

保留现有页面需要的 React、React Hook Form 和 UI 组件导入。

删除原来的：

```tsx
import { zodResolver } from "@hookform/resolvers/zod";
import { loginSchema } from "@/lib/validations/auth";
```

增加：

```tsx
import { loginAction } from "@/server/auth/actions";
```

在客户端页面内定义表单类型：

```tsx
type LoginFormValues = {
  username: string;
  password: string;
};
```

这个类型只是帮助客户端进行 TypeScript 类型检查，不承担服务端校验职责，也不需要从 `server` 目录导入。

### 6.2 调整 `useForm`

将原来的 `zodResolver(loginSchema)` 移除，改为：

```tsx
const {
  register,
  handleSubmit,
  formState: { errors, isSubmitting },
} = useForm<LoginFormValues>();
```

如果页面已经使用了 `useForm`，只需调整其泛型和配置，不需要重复声明。

### 6.3 给输入框增加基础校验规则

用户名输入框使用：

```tsx
<Input
  id="username"
  {...register("username", {
    required: "请输入用户名",
    maxLength: {
      value: 50,
      message: "用户名不能超过 50 个字符",
    },
    pattern: {
      value: /^[a-zA-Z0-9._-]+$/,
      message: "用户名只能包含字母、数字、点、下划线和连字符",
    },
  })}
/>
```

密码输入框使用：

```tsx
<Input
  id="password"
  type="password"
  {...register("password", {
    required: "请输入密码",
    maxLength: {
      value: 1024,
      message: "密码长度不能超过 1024 个字符",
    },
  })}
/>
```

这里展示的是输入框的注册规则，需要保留原页面的 `Label`、`className`、字段错误提示以及其他 UI 属性。

如果原来的组件使用了不同的属性，例如 `type`、`placeholder` 或 `autoComplete`，应继续保留，不要因为修改校验逻辑而重写整个页面。

用户名的首尾空白由服务端 Schema 的 `trim()` 统一处理，密码则不做自动裁剪。

### 6.4 修改提交函数

将原来的提交处理函数替换为：

```tsx
async function onSubmit(values: LoginFormValues) {
  setSubmitError("");

  try {
    const result = await loginAction(values);

    if (!result.ok) {
      setSubmitError(result.message);
      return;
    }

    setSubmitError(
      "凭据验证成功，会话管理将在下一节接入。",
    );
  } catch {
    setSubmitError("提交失败，请稍后重试");
  }
}
```

其中，`setSubmitError` 沿用页面原有的错误提示状态。如果原页面使用的状态变量名称不同，替换成实际名称即可。

提交按钮继续使用：

```tsx
<Button type="submit" disabled={isSubmitting}>
  {isSubmitting ? "验证中..." : "登录"}
</Button>
```

具体属性应与项目当前使用的 Button 组件保持一致。

现在，页面提交时会真正调用服务端认证逻辑：

```text
app/login/page.tsx
        ↓
loginAction(values)
        ↓
loginSchema.safeParse(input)
        ↓
verifyCredentials(parsed.data)
        ↓
db.user.findUnique(...)
        ↓
argon2.verify(...)
        ↓
返回认证结果
```

页面不再只是打印日志，而是根据服务端的返回值显示认证结果。

同时，服务端只向客户端返回可序列化的业务结果，不把数据库对象、密码哈希或异常对象直接传回页面。

## 七、为凭据验证编写自动化测试

代码完成后，不能只看页面是否显示提示，还需要验证不同认证场景下的处理是否正确。

本节优先测试 `verifyCredentials()`，因为它包含查询用户、检查账号状态和验证密码等核心逻辑。

### 7.1 创建测试文件

创建：

`tests/server/auth/verify-credentials.test.ts`

```ts
import {
  beforeEach,
  describe,
  expect,
  it,
  vi,
} from "vitest";

const mocks = vi.hoisted(() => ({
  findUnique: vi.fn(),
  verify: vi.fn(),
}));

vi.mock("@/lib/db", () => ({
  db: {
    user: {
      findUnique: mocks.findUnique,
    },
  },
}));

vi.mock("argon2", () => ({
  default: {
    verify: mocks.verify,
  },
}));
```

### 7.2 理解测试中的 Mock

测试中有两处 Mock：

```ts
vi.mock("@/lib/db", () => ({
  db: {
    user: {
      findUnique: mocks.findUnique,
    },
  },
}));
```

这段代码模拟数据库查询，不需要连接真实 PostgreSQL。

另一处：

```ts
vi.mock("argon2", () => ({
  default: {
    verify: mocks.verify,
  },
}));
```

它模拟密码验证结果，让我们可以分别测试密码正确和密码错误的场景。

因此，这些测试主要验证的是业务分支和返回结果，并不能代替真实数据库及 Argon2 的集成测试。

## 九、本节总结

本节通过 Server Actions，将登录页面与服务端凭据验证连接起来。

整个实现分为三个主要层次：

1. **页面层**：负责表单展示、用户交互和基础校验。
2. **Action 层**：负责接收操作、进行服务端 Schema 校验、组织认证流程并返回结果。
3. **凭据验证层**：负责查询用户、检查账号状态和验证密码。

同时，我们明确了几个工程边界：

- 认证 Schema 放在 `server/auth/schema.ts`，与现有部门管理模块的组织方式保持一致。
- 客户端不导入带有 `server-only` 的 Schema 模块。
- 数据库客户端统一使用 `@/lib/db`。
- 当前 Web 管理端使用 Server Actions，不提前增加 HTTP API。
- 凭据验证逻辑独立于 Action，便于测试和后续复用。

这些设计并不是为了让目录看起来更复杂，而是让每个模块都有清楚的职责。

最后需要牢记：

**凭据验证成功，不等于用户已经登录。**

下一节，我们将继续实现登录会话，让系统能够在后续请求中识别当前用户。之后，访问部门管理、执行新增或删除操作时，才能基于真实的登录身份进一步检查权限。
