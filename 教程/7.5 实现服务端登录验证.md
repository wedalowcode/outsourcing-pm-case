# 7.5 实现服务端登录验证

## 一、明确本节的实现目标

上一节，我们通过 shadcn/ui 构建了登录页面，并使用 Zod 校验用户名和密码的格式。

但现在的登录按钮还没有真正连接数据库。用户即使输入一个不存在的用户名，只要符合表单格式，前端就会认为校验通过。

这显然不能满足系统的安全要求。

本节需要实现一条完整的服务端验证链路：

```text
浏览器提交用户名和密码
          ↓
服务端解析请求数据
          ↓
使用 Zod 验证数据结构
          ↓
根据用户名查询数据库
          ↓
检查账号是否存在、是否启用
          ↓
使用 Argon2id 验证密码
          ↓
认证失败：返回统一错误提示
          ↓
认证成功：返回安全的用户基本信息
```

这里先说明一个边界：本节实现的是**服务端凭据验证**。认证成功后如何设置安全 Cookie、建立会话，以及如何让后续请求识别登录用户，将在后续课程中实现。在会话建立之前，不能认为用户已经拥有持续有效的登录状态。

本节完成后，我们应该能够：

1. 接收前端提交的登录请求。
2. 根据用户名查询数据库中的用户。
3. 验证用户输入的密码是否与数据库中的密码哈希匹配。
4. 拒绝不存在、密码错误或已禁用的账号。
5. 避免向前端泄露密码哈希、数据库异常等内部信息。
6. 使用自动化测试验证登录逻辑。

## 二、先设计代码结构

为了避免将所有逻辑都写进一个 API 路由文件，我们先拆分职责。

建议使用以下结构：

```text
app/
└── api/
    └── auth/
        └── login/
            └── route.ts

lib/
├── auth/
│   └── verify-credentials.ts
└── validations/
    └── auth.ts

server/
└── lib/
    └── db.ts

tests/
└── auth/
    └── verify-credentials.test.ts
```

各文件的职责如下：

| 文件 | 职责 |
|---|---|
| `lib/validations/auth.ts` | 定义登录数据 Schema |
| `lib/auth/verify-credentials.ts` | 查询用户、检查状态、验证密码 |
| `app/api/auth/login/route.ts` | 接收 HTTP 请求并返回响应 |
| `tests/auth/verify-credentials.test.ts` | 验证凭据处理逻辑 |

这里延续 7.3 中的设计：数据库客户端通过统一的 `server/lib/db.ts` 导出，密码验证使用 Argon2id，登录数据使用 Zod 校验。

如果你的项目采用不同的目录结构，只需要调整对应的导入路径，不需要为了本节重新创建数据库客户端。

## 三、实现服务端凭据验证

### 3.1 为什么不把全部逻辑写进 route.ts？

Next.js App Router 中的 `route.ts` 负责处理 HTTP 请求，例如读取 JSON、返回状态码和响应数据。

但用户名查询、密码验证、账号状态判断属于认证业务逻辑。

如果全部写在路由中，后续单元测试就需要处理 HTTP 请求、数据库访问和密码验证等多个环节，测试会比较困难。

因此，我们先实现一个独立的凭据验证函数。

### 3.2 创建凭据验证模块

创建文件：

`lib/auth/verify-credentials.ts`

编写以下代码：

```ts
import "server-only";

import argon2 from "argon2";
import { db } from "@/server/lib/db";
import type { LoginFormValues } from "@/lib/validations/auth";

export type CredentialFailureReason =
  | "INVALID_CREDENTIALS"
  | "ACCOUNT_DISABLED";

export type CredentialResult =
  | {
      ok: true;
      user: {
        id: string;
        username: string;
        name: string;
      };
    }
  | {
      ok: false;
      reason: CredentialFailureReason;
    };

export async function verifyCredentials(
  input: LoginFormValues,
): Promise<CredentialResult> {
  const user = await db.user.findUnique({
    where: {
      username: input.username,
    },
    select: {
      id: true,
      username: true,
      name: true,
      passwordHash: true,
      status: true,
    },
  });

  if (!user) {
    return {
      ok: false,
      reason: "INVALID_CREDENTIALS",
    };
  }

  if (user.status !== "ACTIVE") {
    return {
      ok: false,
      reason: "ACCOUNT_DISABLED",
    };
  }

  const passwordMatches = await argon2.verify(
    user.passwordHash,
    input.password,
  );

  if (!passwordMatches) {
    return {
      ok: false,
      reason: "INVALID_CREDENTIALS",
    };
  }

  return {
    ok: true,
    user: {
      id: user.id,
      username: user.username,
      name: user.name,
    },
  };
}
```

注意：这里使用了 `server-only`，需要确保项目已经安装 Next.js 对应的依赖。它用于阻止这个模块被错误地导入客户端代码。

下面逐步理解这段代码。

### 3.3 第一步：根据用户名查询用户

```ts
const user = await db.user.findUnique({
  where: {
    username: input.username,
  },
  select: {
    id: true,
    username: true,
    name: true,
    passwordHash: true,
    status: true,
  },
});
```

这里使用 Prisma 的 `findUnique()` 查询用户。

因为 7.2 中已经将 `username` 定义为唯一字段，所以可以直接通过用户名查询一条记录。

这里使用 `select` 明确指定查询字段，而不是直接获取用户表中的全部信息。

我们需要：

- `id`：用户的内部标识。
- `username`：登录用户名。
- `name`：用户显示名称。
- `passwordHash`：验证密码所需的数据。
- `status`：判断账号是否允许登录。

即使用户表以后增加了邮箱、手机号、部门编号等字段，这个函数也不会自动读取所有字段。

这种显式查询的方式，有助于减少不必要的数据访问。

### 3.4 第二步：处理用户不存在的情况

```ts
if (!user) {
  return {
    ok: false,
    reason: "INVALID_CREDENTIALS",
  };
}
```

如果数据库中没有对应用户名，`findUnique()` 会返回 `null`。

此时应当直接结束验证流程。

这里没有把“用户不存在”作为公开的错误提示，而是将其归入 `INVALID_CREDENTIALS`，与密码错误使用相同的认证失败类别。

这样可以避免 API 明确告诉调用者某个用户名是否存在。

### 3.5 第三步：检查账号状态

```ts
if (user.status !== "ACTIVE") {
  return {
    ok: false,
    reason: "ACCOUNT_DISABLED",
  };
}
```

上一节的 User 模型使用了 `UserStatus` 枚举：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}
```

所以这里检查账号是否处于 `ACTIVE` 状态。

为什么必须在登录时检查账号状态？

假设一名开发人员已经离职，管理员将其账号设置为 `DISABLED`。即使这个用户仍然知道原来的密码，系统也不应该继续允许其登录。

需要注意，这个检查只发生在登录认证阶段。后续建立会话后，如果管理员停用了账号，系统还需要在适当的请求授权环节重新检查账号状态，或者撤销其有效会话。不能只在登录时检查一次，就认为账号以后永远有效。

### 3.6 第四步：使用 Argon2id 验证密码

```ts
const passwordMatches = await argon2.verify(
  user.passwordHash,
  input.password,
);
```

这是登录验证的核心。

7.3 中，我们使用以下代码创建密码哈希：

```ts
const passwordHash = await argon2.hash(password, {
  type: argon2.argon2id,
});
```

现在使用 `argon2.verify()` 验证用户输入的密码。

注意参数顺序：

- 第一个参数是数据库中保存的密码哈希。
- 第二个参数是用户本次输入的原始密码。

不要尝试将原始密码直接与数据库中的 `passwordHash` 进行字符串比较。密码哈希算法包含随机盐等信息，同一个密码多次生成的哈希字符串通常并不相同。

如果验证失败，函数返回统一的凭据错误类别。

### 3.7 第五步：只返回必要的用户信息

```ts
return {
  ok: true,
  user: {
    id: user.id,
    username: user.username,
    name: user.name,
  },
};
```

这里特意没有返回 `passwordHash`。

虽然查询用户时需要读取密码哈希，但那只是服务端验证密码所必需的内部操作。

认证成功后，业务代码只返回当前阶段需要的用户基本信息。

**查询数据库时读取了某个字段，不代表这个字段就应该进入 API 响应。**

这条原则在后续的用户管理、角色管理和业务接口中同样适用。

## 四、实现登录 API 路由

现在凭据验证逻辑已经完成，接下来需要让浏览器能够调用它。

### 4.1 创建路由文件

创建：

`app/api/auth/login/route.ts`

Next.js App Router 会将这个文件映射到：

```text
POST /api/auth/login
```

编写以下代码：

```ts
import { NextResponse } from "next/server";

import { loginSchema } from "@/lib/validations/auth";
import { verifyCredentials } from "@/lib/auth/verify-credentials";

export const runtime = "nodejs";

const INVALID_CREDENTIALS_MESSAGE = "用户名或密码错误";

export async function POST(request: Request) {
  let body: unknown;

  try {
    body = await request.json();
  } catch {
    return NextResponse.json(
      { error: "请求数据格式不正确" },
      { status: 400 },
    );
  }

  const parsed = loginSchema.safeParse(body);

  if (!parsed.success) {
    return NextResponse.json(
      {
        error: "请检查用户名和密码的输入格式",
      },
      { status: 400 },
    );
  }

  try {
    const result = await verifyCredentials(parsed.data);

    if (!result.ok) {
      return NextResponse.json(
        {
          error: INVALID_CREDENTIALS_MESSAGE,
        },
        { status: 401 },
      );
    }

    return NextResponse.json({
      ok: true,
      user: result.user,
      message: "凭据验证成功",
    });
  } catch (error) {
    // 只在服务端记录必要的诊断信息。
    // 不记录请求正文、原始密码或密码哈希。
    console.error("登录验证服务发生异常", error);

    return NextResponse.json(
      {
        error: "服务暂时不可用，请稍后重试",
      },
      { status: 500 },
    );
  }
}
```

这段代码完成了 HTTP 层的处理。

### 4.2 为什么请求数据使用 unknown？

```ts
let body: unknown;
```

因为客户端提交的数据不能被直接信任。

即使前端已经使用 Zod 校验过，攻击者仍然可以绕过页面，发送任意 JSON 数据。

因此，服务端首先把请求体作为未知数据处理，再调用：

```ts
const parsed = loginSchema.safeParse(body);
```

只有验证通过后，才能使用 `parsed.data` 作为符合 Schema 的登录数据。

这比直接将请求体断言为 `LoginFormValues` 更安全，因为 TypeScript 类型断言不会在运行时验证实际数据。

### 4.3 为什么使用 safeParse？

`safeParse()` 不会因为普通的数据校验失败而抛出异常，而是返回一个包含成功状态的结果。

校验成功：

```ts
{
  success: true,
  data: {
    username: "...",
    password: "..."
  }
}
```

校验失败：

```ts
{
  success: false,
  error: ...
}
```

因此，我们可以明确区分：

- 请求不是合法 JSON。
- 请求是合法 JSON，但字段不符合要求。
- 请求格式正确，但认证失败。
- 服务端处理发生异常。

这几种情况属于不同层次的问题，不应该全部使用同一种状态码处理。

### 4.4 为什么不直接返回 Zod 的全部错误？

例如，服务端可以返回完整的 `parsed.error.issues`。

但对于登录接口，我们没有必要向客户端暴露全部校验细节。

当前统一返回：

```json
{
  "error": "请检查用户名和密码的输入格式"
}
```

这样既能够让用户知道输入存在问题，也能避免将内部 Schema 的所有实现细节暴露出去。

对于普通业务表单，可以根据实际需要返回字段级错误；登录接口则可以采用更克制的响应策略。

### 4.5 为什么用户不存在和密码错误都返回 401？

凭据错误统一返回：

```json
{
  "error": "用户名或密码错误"
}
```

HTTP 状态码为 `401`。

无论用户名不存在还是密码错误，客户端得到的提示都相同。

而 `400` 表示请求数据无法通过输入校验，`500` 表示服务端发生内部错误。

需要注意，统一错误消息本身并不能完全消除账号枚举风险。不同分支仍可能表现出可观察的时间差异，因此生产系统还需要结合登录限流、监控以及必要的时序防护措施。

### 4.6 为什么这里没有返回账号禁用的具体提示？

当前代码对外将所有凭据验证失败统一处理。

服务端内部仍然可以区分 `INVALID_CREDENTIALS` 和 `ACCOUNT_DISABLED`，但不应直接把这些内部原因全部暴露给未认证的调用者。

对于企业内部系统，如果业务确实需要提示“账号已停用”，可以在经过安全评估后设计对应的交互，但不应不加区分地泄露账号状态。

### 4.7 为什么成功响应中没有 passwordHash？

成功响应只有：

```json
{
  "ok": true,
  "user": {
    "id": "用户内部标识",
    "username": "admin",
    "name": "系统管理员"
  },
  "message": "凭据验证成功"
}
```

这里展示的是响应结构示意，不是实际数据库数据。

`passwordHash` 不会进入响应。

同时，API 也不会返回用户提交的原始密码、数据库查询对象或内部异常堆栈。

需要特别强调：**当前成功响应只表示服务端验证了这次提交的凭据，并没有创建登录会话。** 后续实现会话之前，不能仅凭这个 JSON 响应就把用户视为已登录。

## 五、编写登录验证测试

代码编写完成后，我们不能只通过浏览器手工测试，还需要使用自动化测试验证核心业务规则。

这里先测试独立的 `verifyCredentials()` 函数，因为它是登录验证的核心。

HTTP 路由的 JSON 解析、状态码和响应结构，则可以在后续进一步补充集成测试。

### 5.1 安装测试依赖

如果项目还没有配置 Vitest，可以先安装：

```bash
pnpm add -D vitest
```

本节只展示核心单元测试。如果项目已经有统一的测试配置，应沿用现有配置，而不是重复建立测试环境。

在 `package.json` 中确认存在测试命令：

```json
{
  "scripts": {
    "test": "vitest run"
  }
}
```

如果项目已经有 `test` 脚本，应合并配置，不要覆盖其他已有命令。

### 5.2 为凭据验证编写单元测试

创建：

`tests/auth/verify-credentials.test.ts`

编写：

```ts
import { beforeEach, describe, expect, it, vi } from "vitest";

const { findUniqueMock, verifyMock } = vi.hoisted(() => ({
  findUniqueMock: vi.fn(),
  verifyMock: vi.fn(),
}));

vi.mock("@/server/lib/db", () => ({
  db: {
    user: {
      findUnique: findUniqueMock,
    },
  },
}));

vi.mock("argon2", () => ({
  default: {
    verify: verifyMock,
  },
}));

import { verifyCredentials } from "@/lib/auth/verify-credentials";

const credentials = {
  username: "admin",
  password: "TestPassword@123",
};

const activeUser = {
  id: "user-1",
  username: "admin",
  name: "系统管理员",
  passwordHash: "fake-argon2-hash",
  status: "ACTIVE",
};

describe("verifyCredentials", () => {
  beforeEach(() => {
    vi.clearAllMocks();
  });

  it("用户不存在时拒绝登录", async () => {
    findUniqueMock.mockResolvedValue(null);

    const result = await verifyCredentials(credentials);

    expect(result).toEqual({
      ok: false,
      reason: "INVALID_CREDENTIALS",
    });

    expect(verifyMock).not.toHaveBeenCalled();
  });

  it("账号禁用时拒绝登录", async () => {
    findUniqueMock.mockResolvedValue({
      ...activeUser,
      status: "DISABLED",
    });

    const result = await verifyCredentials(credentials);

    expect(result).toEqual({
      ok: false,
      reason: "ACCOUNT_DISABLED",
    });

    expect(verifyMock).not.toHaveBeenCalled();
  });

  it("密码错误时拒绝登录", async () => {
    findUniqueMock.mockResolvedValue(activeUser);
    verifyMock.mockResolvedValue(false);

    const result = await verifyCredentials(credentials);

    expect(result).toEqual({
      ok: false,
      reason: "INVALID_CREDENTIALS",
    });
  });

  it("密码正确时返回安全的用户信息", async () => {
    findUniqueMock.mockResolvedValue(activeUser);
    verifyMock.mockResolvedValue(true);

    const result = await verifyCredentials(credentials);

    expect(result).toEqual({
      ok: true,
      user: {
        id: "user-1",
        username: "admin",
        name: "系统管理员",
      },
    });

    expect(result.ok && "passwordHash" in result.user).toBe(false);

    expect(verifyMock).toHaveBeenCalledWith(
      activeUser.passwordHash,
      credentials.password,
    );
  });

  it("数据库异常时向调用者抛出异常", async () => {
    findUniqueMock.mockRejectedValue(
      new Error("Database unavailable"),
    );

    await expect(
      verifyCredentials(credentials),
    ).rejects.toThrow("Database unavailable");
  });
});
```

这组测试使用模拟对象替代真实数据库和 Argon2 实现，目的是验证不同业务分支的处理逻辑。

它并不验证 PostgreSQL 的实际查询行为，也不验证真实密码哈希是否匹配；这两部分还需要通过集成测试补充。

### 5.3 运行测试

执行：

```bash
pnpm test
```

预期覆盖以下情况：

| 测试场景 | 预期结果 |
|---|---|
| 用户不存在 | 拒绝登录 |
| 账号已禁用 | 拒绝登录 |
| 密码错误 | 拒绝登录 |
| 密码正确 | 返回安全的用户信息 |
| 数据库异常 | 异常向上抛出，由 API 层统一处理 |

如果测试失败，先检查数据库模块导入路径、Vitest 的别名配置以及模拟对象的返回结构是否与当前 Prisma 模型一致。

### 5.4 为什么测试中使用 fake-argon2-hash？

因为这里模拟了 `argon2.verify()`，所以不需要构造真实的密码哈希。

这能够让单元测试快速验证业务分支。

但是，在集成测试中，应该使用真实的 Argon2 实现，通过 `argon2.hash()` 生成测试密码哈希，再验证正确密码和错误密码的实际结果。

不要把模拟通过当成密码算法本身已经验证通过。

## 六、进一步验证 API 的实际行为

单元测试通过后，还应该验证 HTTP 路由。

可以使用 Postman、curl 或其他 HTTP 客户端。

### 6.1 提交格式错误的请求

例如发送一个合法 JSON，但用户名和密码为空：

```bash
curl -i \
  -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"","password":""}'
```

预期结果为 HTTP `400`，响应包含统一的输入格式提示。

### 6.2 提交不存在的用户

```bash
curl -i \
  -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"unknown-user","password":"WrongPassword@123"}'
```

预期结果为 HTTP `401`，返回：

```json
{
  "error": "用户名或密码错误"
}
```

### 6.3 提交错误密码

使用数据库中存在的用户名，但输入错误密码。

预期结果同样为 HTTP `401`，并返回相同的错误提示。

### 6.4 提交正确的账号和密码

使用 7.3 创建的初始管理员账号和真实密码进行测试。

预期结果为 HTTP `200`，返回用户基本信息，但不包含 `passwordHash`。

请注意：如果本节尚未建立会话，正确的响应只能证明服务端验证成功。刷新页面后仍然没有持久的登录身份，这是下一阶段需要解决的问题。

### 6.5 检查敏感信息是否泄露

打开浏览器开发者工具的 Network 面板，检查登录响应。

确认响应中不存在：

- `passwordHash`
- 用户输入的原始密码
- 数据库连接字符串
- 数据库异常堆栈
- 其他不必要的内部用户字段

同时检查服务端日志，确认没有输出完整的登录请求正文。

## 七、上线前还需要考虑哪些安全问题？

本节实现了基础的凭据验证，但生产环境仍然需要考虑几个问题。

### 7.1 登录限流

攻击者可能通过不断提交密码猜测账号凭据。

因此，登录 API 应当增加合理的限流机制，并监控异常的失败请求。

限流可以根据 IP、账号标识以及部署环境的实际情况设计。对于多实例部署，应采用共享存储或网关层限流，不能只依赖单个进程的内存计数器。

### 7.2 账号枚举与时序差异

统一的错误消息能够减少直接的信息泄露，但无法自动消除所有账号枚举风险。

例如，不存在的用户会提前返回，而真实用户可能需要执行 Argon2 验证，因此两种请求的处理时间可能不同。

生产系统应根据风险评估采用适当的时序防护、限流与监控措施。

### 7.3 仅通过 HTTPS 传输凭据

生产环境应使用 HTTPS 保护登录请求，避免用户名和密码在网络传输过程中被窃听或篡改。

开发环境的 localhost 调试与生产环境的安全要求不能混为一谈。

### 7.4 认证成功之后还需要会话

即使密码验证成功，也不能让客户端自行声明“我是管理员”。

下一阶段应使用经过验证的用户身份建立安全会话，并在服务端控制会话有效性、Cookie 属性以及退出登录后的会话失效。

角色和权限也不能仅仅因为前端收到用户信息就被视为可信。后续每个受保护的 API 都必须由服务端识别当前会话并执行授权检查。

## 八、本节总结

本节完成了服务端登录凭据验证的核心实现。

我们将登录流程拆分成数据校验、用户查询、账号状态检查和密码哈希验证四个步骤，并通过 Next.js Route Handler 暴露登录 API。

同时，我们使用 Zod 在服务端重新验证请求数据，通过统一的错误提示避免直接暴露用户名是否存在，并且只向前端返回必要的用户基本信息。

通过单元测试，我们验证了用户不存在、密码错误、账号禁用、验证成功和数据库异常等情况。

现在，系统已经具备验证用户名与密码的能力。

但需要记住：**验证通过只是认证过程中的一个环节，不等于已经建立登录会话，更不等于用户已经获得访问所有业务数据的权限。**

下一节，我们将继续实现安全会话与登录状态管理，让用户在认证成功后能够进入后台，并让后续请求可靠地识别当前登录身份。
