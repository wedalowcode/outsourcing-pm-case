# 八、实现部门删除功能

前面已经完成了部门新增和编辑功能。现在，用户可以通过弹窗录入部门数据，并调用 Action 将数据保存到数据库。

但一个完整的部门管理模块还缺少删除功能。

删除功能与新增、编辑的交互方式不同：新增和编辑需要打开表单，删除则不需要填写数据，而是由用户选中某个部门，确认删除意图，再调用后端 Action。

本节继续沿用前面的设计思路：

- `DeptTable` 负责展示删除按钮，并通过回调通知父组件。
- `dept-workspace.tsx` 负责确认删除、调用 Action、处理执行结果。
- `deleteDeptAction` 负责进入已经实现的后端删除流程。
- 删除成功后刷新部门列表；删除失败则显示错误信息。

这样，新增、编辑和删除三种操作都由部门工作区统一协调。

## 1. 添加删除确认组件

删除操作具有破坏性，不能让用户点击按钮后就直接删除数据。我们先使用 shadcn/ui 提供的 `AlertDialog` 实现确认窗口。

在项目终端执行：

```bash
pnpm dlx shadcn@latest add alert-dialog
```

安装后，检查 `components/ui/alert-dialog.tsx` 是否已经生成。

确认窗口需要表达三个信息：

1. 当前要删除的是哪个部门。
2. 删除操作需要用户明确确认。
3. 用户可以取消操作，不影响现有数据。

这里不直接使用浏览器的 `window.confirm()`，是为了让确认交互与项目现有的 shadcn/ui 界面保持一致。

## 2. 在部门工作区中维护删除状态

打开：

```text
app/dept/dept-workspace.tsx
```

前面已经在这个组件中维护了新增、编辑弹窗状态，以及提交过程中的错误信息。删除操作也放在这里处理。

首先，导入删除 Action：

```tsx
import {
  createDeptAction,
  updateDeptAction,
  deleteDeptAction,
} from "@/server/dept/actions";
```

接着，增加删除相关的状态：

```tsx
const [deleteTarget, setDeleteTarget] = useState<Row | null>(null);
const [deleting, setDeleting] = useState(false);
const [deleteError, setDeleteError] = useState("");
```

这三个状态分别表示：

- `deleteTarget`：当前准备删除的部门。为 `null` 时，确认窗口关闭。
- `deleting`：是否正在执行删除操作，用来防止重复提交。
- `deleteError`：删除失败时显示的错误信息。

这里直接使用已有的 `Row` 类型，不需要重新定义部门数据结构。

用户点击某一行的删除按钮时，我们只设置 `deleteTarget`，并不立即调用 Action。只有用户在确认窗口中点击“确认删除”，才真正执行删除。

## 3. 编写删除处理函数

在 `DeptWorkspace` 组件内部增加以下函数：

```tsx
async function handleDelete() {
  if (!deleteTarget || deleting) return;

  setDeleting(true);
  setDeleteError("");

  try {
    const result = await deleteDeptAction(deleteTarget.id);

    if (!result.ok) {
      setDeleteError(result.message);
      return;
    }

    // 删除成功，关闭确认窗口并刷新列表
    setDeleteTarget(null);
    router.refresh();
  } catch (error) {
    console.error("删除部门失败", error);
    setDeleteError("删除失败，请稍后重试");
  } finally {
    setDeleting(false);
  }
}
```

这段代码直接调用了项目中已经存在的 `deleteDeptAction`。

根据前面文章中的 Action 定义，删除入口接收部门 ID，并通过返回值表达执行结果：

```typescript
export async function deleteDeptAction(id: unknown)
```

这里使用 `unknown`，是因为 Action 仍然需要在服务端对输入进行校验，而不能默认客户端传入的数据一定合法。

Action 的结果使用 `result.ok` 判断是否成功。失败时通过 `result.message` 获取错误信息。因此，不能只使用 `try/catch` 判断删除结果。

### 为什么删除失败时不关闭窗口？

假设用户尝试删除一个不允许删除的部门，或者后端检测到其他业务限制。

如果前端直接关闭窗口，用户就无法立即看到错误原因；如果将错误显示在确认窗口中，用户可以了解失败原因，然后取消操作或进一步处理。

因此，这里的处理原则与新增、编辑一致：**成功才关闭窗口，失败则保留当前上下文并展示错误信息。**

另外，前端的确认窗口只是交互保护，不是安全边界。真正能否删除，仍然由服务端的校验和业务规则决定。

## 4. 为表格增加删除入口

前面已经给 `DeptTable` 增加了 `onEdit` 回调，让表格通过回调通知父组件用户想要编辑哪个部门。

现在采用同样的方式增加 `onDelete`。

打开：

```text
app/dept/_components/dept-table.tsx
```

为组件增加一个回调参数：

```tsx
export function DeptTable({
  rows,
  filteredByParent,
  onEdit,
  onDelete,
}: {
  rows: Row[];
  filteredByParent: boolean;
  onEdit: (row: Row) => void;
  onDelete: (row: Row) => void;
}) {
  // 保留原有表格实现
}
```

接着，在每一行的操作列中增加删除按钮：

```tsx
<td className="py-2">
  <div className="flex items-center gap-3">
    <button
      type="button"
      className="text-blue-600 hover:underline"
      onClick={() => onEdit(row)}
    >
      编辑
    </button>

    <button
      type="button"
      className="text-destructive hover:underline"
      onClick={() => onDelete(row)}
    >
      删除
    </button>
  </div>
</td>
```

如果原来的操作列已经包含编辑按钮，只需要将它们放进同一个容器，再添加删除按钮即可。

表格仍然只负责渲染和触发回调，不直接调用 Action。这样，即使将来表格被其他页面复用，也不会与某个特定的后端操作绑定。

因为删除按钮仍然位于原来的操作列中，所以通常不需要再增加表头。如果此前还没有操作列，则需要补充“操作”表头，并同步调整空数据行的 `colSpan`。

## 5. 在父组件中接入删除回调

回到 `dept-workspace.tsx`，找到已有的 `DeptTable`：

```tsx
<DeptTable
  rows={pageData.rows}
  filteredByParent={selectedId !== null}
  onEdit={openEditDialog}
  onDelete={(row) => {
    setDeleteError("");
    setDeleteTarget(row);
  }}
/>
```

用户点击删除按钮时，父组件记录当前部门，并清空上一次的删除错误。

此时不会删除数据库数据，只会打开后续的确认窗口。

这种设计与新增、编辑的处理方式保持一致：子组件发起操作，父组件统一管理业务流程。

## 6. 渲染删除确认窗口

首先，在 `dept-workspace.tsx` 中导入确认窗口组件：

```tsx
import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
} from "@/components/ui/alert-dialog";
```

然后，在 `DeptWorkspace` 的 JSX 中增加：

```tsx
{deleteTarget && (
  <AlertDialog
    open
    onOpenChange={(open) => {
      if (!open && !deleting) {
        setDeleteTarget(null);
        setDeleteError("");
      }
    }}
  >
    <AlertDialogContent>
      <AlertDialogHeader>
        <AlertDialogTitle>确认删除部门？</AlertDialogTitle>

        <AlertDialogDescription>
          确定要删除部门“{deleteTarget.name}”吗？
          此操作将提交到服务端执行，请确认后再继续。
        </AlertDialogDescription>
      </AlertDialogHeader>

      {deleteError ? (
        <p className="text-sm text-destructive">
          {deleteError}
        </p>
      ) : null}

      <AlertDialogFooter>
        <AlertDialogCancel disabled={deleting}>
          取消
        </AlertDialogCancel>

        <AlertDialogAction
          disabled={deleting}
          onClick={(event) => {
            event.preventDefault();
            void handleDelete();
          }}
        >
          {deleting ? "删除中…" : "确认删除"}
        </AlertDialogAction>
      </AlertDialogFooter>
    </AlertDialogContent>
  </AlertDialog>
)}
```

这里需要注意几个细节。

第一，弹窗以 `deleteTarget` 为条件整体挂载和卸载，而不是常驻在页面上、只切换 `open`。原因见下面的「为什么不能写成 `open={deleteTarget !== null}`」。

第二，点击“取消”只会关闭窗口，不会调用 Action。

第三，点击“确认删除”后调用 `handleDelete()`。在处理完成之前禁用按钮，避免用户重复提交。

第四，删除失败时保留确认窗口，并在窗口中显示服务端返回的错误信息。

### 为什么不能写成 `open={deleteTarget !== null}`

直觉上更自然的写法是让弹窗常驻，只切换 `open`：

```tsx
<AlertDialog open={deleteTarget !== null} onOpenChange={...}>
```

但在当前 Base UI 版本下，这种写法在“删除成功”这条路径上会把弹窗卡住。实际现象是：

- 部门确实被删除了，列表也刷新了；
- 但确认窗口仍然悬浮在页面上，遮挡并阻塞后续操作；
- 此时按 Escape、点“取消”都没有任何反应。

原因是 Base UI 的弹窗在关闭时要等退出动画播完才真正卸载。删除成功后紧接着调用了 `router.refresh()`，这次重渲染会打断退出动画，动画结束事件不再触发，弹窗就停在“已经进入关闭态、但元素没有卸载”的中间状态。检查 DOM 可以看到弹窗节点上已经带上了 `data-closed` 和 `data-ending-style`，说明关闭指令已经生效，只是卸载没有完成——所以 Escape 和“取消”也失效了，因为在 Base UI 看来它已经关闭。

把挂载和卸载交给 React（`{deleteTarget && ...}`）就没有这个问题：状态置空时整个子树直接卸载，不依赖动画生命周期。新增、编辑弹窗也采用了同样的方式。

**注意：** 上述代码采用当前 shadcn/ui Base UI 组件常见的 API 组织方式。若项目生成的 `AlertDialogAction` 类型或事件处理签名与示例不同，应以实际生成的 `components/ui/alert-dialog.tsx` 为准，保持组件 API 一致。

## 7. 验证删除操作的完整流程

完成代码后，执行：

```bash
pnpm lint
pnpm build
```

随后在部门管理页面进行验证。

| 测试场景 | 预期结果 |
|---|---|
| 点击某一行的删除按钮 | 打开确认窗口，并显示对应部门名称 |
| 点击取消 | 关闭窗口，数据库数据不变 |
| 点击确认删除 | 调用 `deleteDeptAction` |
| 删除成功 | 关闭窗口并刷新部门列表 |
| 删除失败 | 保留窗口并显示服务端错误 |
| 删除过程中再次点击确认 | 不会重复提交 |
| 尝试删除违反后端业务规则的部门 | 服务端拒绝操作，前端显示错误 |

特别要验证：**前端显示了删除按钮，并不意味着所有部门都一定允许删除。** 如果 Service 已经定义了删除限制，就应当通过真实的业务场景验证这些限制是否仍然生效。

不要为了让前端删除按钮“看起来可用”，而绕过现有 Service 直接操作数据库。

## 8. 小结

至此，部门管理已经具备新增、编辑和删除三种基本操作。

三种操作的交互有所不同，但整体架构是一致的：

- 新增和编辑通过弹窗收集数据。
- 删除通过确认窗口表达用户的删除意图。
- 父组件统一调用相应的 Server Action。
- Service 负责执行后端业务规则。
- 前端根据 Action 的结果决定关闭窗口、刷新列表或显示错误。

这里没有额外开发一个通用 CRUD 引擎，也没有将所有业务操作塞进表格组件，而是沿用现有组件和 Action 的分层方式完成扩展。

这正是当前阶段更合适的开发方式：先把业务流程做完整，再根据后续客户、商机、项目模块中反复出现的真实需求，决定哪些能力值得进一步抽象。
