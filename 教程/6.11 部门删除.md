# 八、实现部门删除功能

前面已经完成了部门新增和编辑功能。现在，用户可以通过弹窗录入部门数据，并调用 Action 将数据保存到数据库。

但一个完整的部门管理模块还缺少删除功能。

删除功能与新增、编辑的交互方式不同：新增和编辑需要打开表单，删除则不需要填写数据，而是由用户选中某个部门，确认删除意图，再调用后端 Action。

本节继续沿用前面的设计思路：

- `DeptTable` 负责展示删除按钮，并通过 `onDelete` 回调通知父组件。
- `DeleteDeptDialog` 负责确认删除、调用 Action、维护删除中状态与错误信息。
- `workspace.tsx` 只记录“要删除哪一行”，并在需要时挂载确认弹窗。
- `deleteDeptAction` 负责进入已经实现的后端删除流程。
- 删除成功后卸载弹窗并刷新部门列表；删除失败则在弹窗内显示错误信息。

这样，删除的执行细节收拢在弹窗里，父组件只保留“选中了哪一行”这一份状态。和第 6.10 节的表单弹窗一样，弹窗自己管理提交状态与错误，父组件只负责挂载和卸载。

## 1. 添加删除确认组件

删除操作具有破坏性，不能让用户点击按钮后就直接删除数据。我们先使用 shadcn/ui 提供的 `AlertDialog` 实现确认窗口。

在项目终端执行：

```bash
pnpm dlx shadcn@latest add alert-dialog
```

安装后，检查 `components/ui/alert-dialog.tsx` 是否已经生成。

确认窗口需要表达三个信息：

1. 当前要删除的是哪个部门。
2. 删除操作需要用户明确确认。
3. 用户可以取消操作，不影响现有数据。

这里不直接使用浏览器的 `window.confirm()`，是为了让确认交互与项目现有的 shadcn/ui 界面保持一致。

新建文件：

```text
app/dept/_components/delete-dialog.tsx
```

完整代码如下：

```tsx
"use client";

import { useState } from "react";
import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
} from "@/components/ui/alert-dialog";
import { deleteDeptAction } from "@/server/dept/actions";
import type { Row } from "@/server/dept/types";

/**
 * 删除确认弹窗：自行管理删除中状态与错误。
 *
 * 由父组件条件渲染（target 存在时才挂载），删除成功后由 onDeleted 通知父组件卸载。
 */
export function DeleteDeptDialog({
  target,
  onClose,
  onDeleted,
}: {
  target: Row;
  onClose: () => void;
  onDeleted: () => void;
}) {
  const [deleting, setDeleting] = useState(false);
  const [error, setError] = useState("");

  async function handleDelete() {
    if (deleting) return;

    setDeleting(true);
    setError("");

    const result = await deleteDeptAction(target.id).catch(() => null);

    setDeleting(false);

    if (!result?.ok) {
      setError(result?.message ?? "删除失败，请稍后重试");
      return;
    }

    onDeleted();
  }

  return (
    <AlertDialog
      open
      onOpenChange={(open) => {
        if (!open && !deleting) onClose();
      }}
    >
      <AlertDialogContent>
        <AlertDialogHeader>
          <AlertDialogTitle>确认删除部门？</AlertDialogTitle>

          <AlertDialogDescription>
            将删除部门“{target.name}”，删除后无法恢复。存在下级部门时不能删除。
          </AlertDialogDescription>
        </AlertDialogHeader>

        {error ? (
          <p className="text-sm text-destructive">{error}</p>
        ) : null}

        <AlertDialogFooter>
          <AlertDialogCancel disabled={deleting}>取消</AlertDialogCancel>

          <AlertDialogAction
            disabled={deleting}
            onClick={(event) => {
              event.preventDefault();
              void handleDelete();
            }}
          >
            {deleting ? "删除中…" : "确认删除"}
          </AlertDialogAction>
        </AlertDialogFooter>
      </AlertDialogContent>
    </AlertDialog>
  );
}
```

这个组件接收三个参数：

- `target`：当前要删除的表格行 `Row`。父组件保证挂载时它一定存在。
- `onClose`：用户取消、点击遮罩或按 Escape 时调用，由父组件负责卸载弹窗。
- `onDeleted`：Action 返回成功后调用，通知父组件“可以卸载弹窗了”。

组件内部维护 `deleting` 和 `error` 两个状态。它们跟着弹窗一起挂载，也一起卸载，不需要父组件在每次打开前手动清空。

## 2. 在部门工作区中维护删除状态

打开：

```text
app/dept/_components/workspace.tsx
```

前面已经在这个组件中维护了新增、编辑的弹窗状态。删除操作也由这里发起，但只保留一份最小状态：

```tsx
const [deleteTarget, setDeleteTarget] = useState<Row | null>(null);
```

这个状态表示当前准备删除的部门。为 `null` 时，确认窗口不挂载；非 `null` 时，弹窗以该行为目标渲染。

这里直接使用已有的 `Row` 类型，不需要重新定义部门数据结构。

同时，`workspace` 不再负责删除执行过程，删除中状态和错误都交给弹窗，页面级不再保留这两类状态；它也不再从 `@/server/dept/actions` 引入 `deleteDeptAction`，改为引入弹窗组件：

```tsx
import { DeleteDeptDialog } from "./delete-dialog";
```

用户点击某一行的删除按钮时，我们只设置 `deleteTarget`，并不立即调用 Action。只有用户在确认窗口中点击“确认删除”，才真正执行删除。

## 3. 编写删除处理函数

删除处理函数写在 `DeleteDeptDialog` 内部，不再放在 `DeptWorkspace` 里：

```tsx
async function handleDelete() {
  if (deleting) return;

  setDeleting(true);
  setError("");

  const result = await deleteDeptAction(target.id).catch(() => null);

  setDeleting(false);

  if (!result?.ok) {
    setError(result?.message ?? "删除失败，请稍后重试");
    return;
  }

  onDeleted();
}
```

这段代码直接调用了项目中已经存在的 `deleteDeptAction`。

根据前面文章中的 Action 定义，删除入口接收部门 ID，并通过返回值表达执行结果：

```typescript
export async function deleteDeptAction(id: unknown)
```

这里使用 `unknown`，是因为 Action 仍然需要在服务端对输入进行校验，而不能默认客户端传入的数据一定合法。

Action 的结果使用 `result.ok` 判断是否成功。失败时通过 `result.message` 获取错误信息。因此，不能只使用 `try/catch` 判断删除结果；调用本身抛出的异常用 `.catch(() => null)` 折算成同一条失败分支，展示兜底的“删除失败，请稍后重试”。

删除成功后不做额外处理，只是调用 `onDeleted()`，由父组件决定是否刷新页面、是否卸载弹窗。

### 为什么删除失败时不关闭窗口？

假设用户尝试删除一个不允许删除的部门，或者后端检测到其他业务限制。

如果前端直接关闭窗口，用户就无法立即看到错误原因；而把错误显示在确认窗口内部，用户可以了解失败原因，然后取消操作或进一步处理。

因此，这里的处理原则与新增、编辑一致：**成功才关闭窗口，失败则保留当前上下文并展示错误信息。**

弹窗之所以能“留下”，是因为失败时没有调用 `onDeleted`，父组件的 `deleteTarget` 仍然非空，弹窗就继续挂载；错误则通过组件自己的 `error` 状态显示在弹窗内。此时 `deleting` 已恢复为 `false`，用户仍然可以点击“取消”关闭窗口。

另外，前端的确认窗口只是交互保护，不是安全边界。真正能否删除，仍然由服务端的校验和业务规则决定。

## 4. 为表格增加删除入口

前面已经给 `DeptTable` 增加了 `onEdit` 回调，让表格通过回调通知父组件用户想要编辑哪个部门。

现在采用同样的方式增加 `onDelete`。

打开：

```text
app/dept/_components/dept-table.tsx
```

完整代码如下：

```tsx
import { DEPT_STATUS, type Row } from "@/server/dept/types";
import { Badge } from "@/components/ui/badge";
import { Button } from "@/components/ui/button";
import {
  Table,
  TableBody,
  TableCell,
  TableHead,
  TableHeader,
  TableRow,
} from "@/components/ui/table";

const COLUMNS = ["编码", "部门名称", "上级部门", "排序", "状态", "操作"];

export function DeptTable({
  rows,
  emptyText,
  onEdit,
  onDelete,
}: {
  rows: Row[];
  emptyText: string; // 空状态文案由父组件决定，表格不关心业务
  onEdit: (row: Row) => void;
  onDelete: (row: Row) => void;
}) {
  return (
    <Table>
      <TableHeader>
        <TableRow>
          {COLUMNS.map((column) => (
            <TableHead key={column}>{column}</TableHead>
          ))}
        </TableRow>
      </TableHeader>

      <TableBody>
        {rows.length === 0 ? (
          <TableRow>
            <TableCell
              colSpan={COLUMNS.length}
              className="h-24 text-center text-muted-foreground"
            >
              {emptyText}
            </TableCell>
          </TableRow>
        ) : (
          rows.map((row) => {
            const enabled = row.status === DEPT_STATUS.ENABLED;

            return (
              <TableRow key={row.id}>
                <TableCell className="font-mono text-xs text-muted-foreground">
                  {row.code}
                </TableCell>
                <TableCell className="font-medium">{row.name}</TableCell>
                <TableCell className="text-muted-foreground">
                  {row.parentName ?? "—"}
                </TableCell>
                <TableCell className="text-muted-foreground">
                  {row.sort}
                </TableCell>
                <TableCell>
                  <Badge variant={enabled ? "secondary" : "outline"}>
                    {enabled ? "启用" : "停用"}
                  </Badge>
                </TableCell>
                <TableCell>
                  <div className="flex items-center gap-1">
                    <Button
                      type="button"
                      variant="ghost"
                      size="sm"
                      onClick={() => onEdit(row)}
                    >
                      编辑
                    </Button>

                    <Button
                      type="button"
                      variant="ghost"
                      size="sm"
                      className="text-destructive hover:text-destructive"
                      onClick={() => onDelete(row)}
                    >
                      删除
                    </Button>
                  </div>
                </TableCell>
              </TableRow>
            );
          })
        )}
      </TableBody>
    </Table>
  );
}
```

这份实现有几个需要注意的地方：

第一，表格使用 shadcn 的 `Table`、`TableHeader`、`TableBody`、`TableRow`、`TableHead`、`TableCell`，不再手写 `<table>` 和 `<td>`，列宽、边框和间距由组件统一处理。

第二，状态列使用 `Badge`：启用的部门用 `secondary`，停用的部门用 `outline`。

第三，表格不再接收 `filteredByParent`，空状态文案改由父组件通过 `emptyText` 传入。表格不关心“当前是不是按上级筛选”，只负责把文案显示出来。

第四，操作列在原来的“编辑”按钮旁多了“删除”按钮。两个按钮统一使用 `Button variant="ghost" size="sm"`，删除按钮额外加上 `text-destructive`，提示这是破坏性操作。

表头和空数据行的列数由 `COLUMNS` 统一维护，`colSpan` 使用 `COLUMNS.length`，以后增删列不需要再手动改数字。

表格仍然只负责渲染和触发回调，不直接调用 Action。这样，即使将来表格被其他页面复用，也不会与某个特定的后端操作绑定。

## 5. 在父组件中接入删除回调

回到 `workspace.tsx`，找到已有的 `DeptTable`：

```tsx
<DeptTable
  rows={pageData.rows}
  emptyText={
    selectedId ? "该部门下暂无子部门" : "没有符合条件的部门"
  }
  onEdit={(row) =>
    setDialog({
      mode: "edit",
      deptId: row.id,
      initial: toForm(row),
    })
  }
  onDelete={setDeleteTarget}
/>
```

用户点击删除按钮时，`onDelete` 直接把这一行交给 `setDeleteTarget`。

这里不需要像旧写法那样“先清空上一次的删除错误再记录目标”：错误状态已经搬进弹窗，每次挂载都是初始值，不会再残留上一次的信息。

此时不会删除数据库数据，只会打开后续的确认窗口。

这种设计与新增、编辑的处理方式保持一致：子组件发起操作，父组件统一管理业务流程。

## 6. 渲染删除确认窗口

`workspace.tsx` 不再直接接触 `AlertDialog` 系列组件，只需要导入删除弹窗：

```tsx
import { DeleteDeptDialog } from "./delete-dialog";
```

然后，在 `DeptWorkspace` 的 JSX 中增加：

```tsx
{deleteTarget && (
  <DeleteDeptDialog
    target={deleteTarget}
    onClose={() => setDeleteTarget(null)}
    onDeleted={() => {
      // 删除了当前选中的部门时，清掉 URL 里的 parent 筛选
      if (deleteTarget.id === selectedId) go({ parent: null });
      setDeleteTarget(null);
    }}
  />
)}
```

这里需要注意几个细节。

第一，弹窗以 `deleteTarget` 为条件整体挂载和卸载，而不是常驻在页面上、只切换 `open`。原因见下面的「为什么不能写成 `open={deleteTarget !== null}`」。

第二，用户取消、点击遮罩或按 Escape 时，弹窗内部调用 `onClose`，父组件把 `deleteTarget` 置空即可；它不会调用 Action，也不会改动数据。删除进行中时，弹窗的 `onOpenChange` 会拦住关闭动作。

第三，点击“确认删除”由弹窗自己调用 `deleteDeptAction`，父组件不参与执行过程。成功时弹窗调用 `onDeleted`。

第四，`onDeleted` 里多了一个判断：如果删掉的正好是左侧组织树当前选中的部门，页面上的 `parent` 筛选就失效了。此时调用 `go({ parent: null })` 清掉 URL 里的 `parent`，让列表回到未筛选状态；随后 `setDeleteTarget(null)` 卸载弹窗。删除其他部门时，不影响当前筛选。

第五，删除成功后的列表刷新由 Action 内部的 `revalidatePath("/dept")` 完成，父组件不需要再调用 `router.refresh()`。

### 为什么不能写成 `open={deleteTarget !== null}`

直觉上更自然的写法是让弹窗常驻，只切换 `open`：

```tsx
<AlertDialog open={deleteTarget !== null} onOpenChange={...}>
```

但在当前 Base UI 版本下，这种写法在“删除成功”这条路径上会把弹窗卡住。实际现象是：

- 部门确实被删除了，列表也刷新了；
- 但确认窗口仍然悬浮在页面上，遮挡并阻塞后续操作；
- 此时按 Escape、点“取消”都没有任何反应。

原因是 Base UI 的弹窗在关闭时要等退出动画播完才真正卸载。删除成功后，Action 里的 `revalidatePath` 会让页面紧接着重新渲染，这次重渲染会打断退出动画，动画结束事件不再触发，弹窗就停在“已经进入关闭态、但元素没有卸载”的中间状态。检查 DOM 可以看到弹窗节点上已经带上了 `data-closed` 和 `data-ending-style`，说明关闭指令已经生效，只是卸载没有完成——所以 Escape 和“取消”也失效了，因为在 Base UI 看来它已经关闭。

把挂载和卸载交给 React（`{deleteTarget && ...}`）就没有这个问题：状态置空时整个子树直接卸载，不依赖动画生命周期。新增、编辑弹窗也采用了同样的方式。

**注意：** 上述代码采用当前 shadcn/ui Base UI 组件常见的 API 组织方式。若项目生成的 `AlertDialogAction` 类型或事件处理签名与示例不同，应以实际生成的 `components/ui/alert-dialog.tsx` 为准，保持组件 API 一致。

## 7. 验证删除操作的完整流程

完成代码后，执行：

```bash
pnpm lint
pnpm build
```

随后在部门管理页面进行验证。

| 测试场景 | 预期结果 |
|---|---|
| 点击某一行的删除按钮 | 打开确认窗口，并显示对应部门名称 |
| 点击取消 | 关闭窗口，数据库数据不变 |
| 点击确认删除 | 调用 `deleteDeptAction` |
| 删除成功 | 卸载弹窗并刷新部门列表 |
| 删除失败 | 保留窗口，并在弹窗内部显示服务端错误 |
| 删除过程中再次点击确认 | 不会重复提交 |
| 删除当前选中的部门且删除成功 | 清掉 URL 里的 `parent` 筛选，列表回到未筛选状态 |
| 尝试删除存在下级部门的部门 | 服务端拒绝操作，弹窗内显示错误 |

特别要验证：**前端显示了删除按钮，并不意味着所有部门都一定允许删除。** 如果 Service 已经定义了删除限制，就应当通过真实的业务场景验证这些限制是否仍然生效。

不要为了让前端删除按钮“看起来可用”，而绕过现有 Service 直接操作数据库。

## 8. 小结

至此，部门管理已经具备新增、编辑和删除三种基本操作。

三种操作的交互有所不同，但整体架构是一致的：

- 新增和编辑通过弹窗收集数据。
- 删除通过确认窗口表达用户的删除意图。
- 弹窗自己调用对应的 Server Action，并管理提交中状态与错误。
- 父组件只记录操作对象，条件渲染弹窗，并在成功回调里卸载。
- Service 负责执行后端业务规则。
- 成功时 Action 负责刷新列表，弹窗通知父组件卸载；失败时错误留在弹窗内部。

这里没有额外开发一个通用 CRUD 引擎，也没有将所有业务操作塞进表格组件，而是沿用现有组件和 Action 的分层方式完成扩展。

这正是当前阶段更合适的开发方式：先把业务流程做完整，再根据后续客户、商机、项目模块中反复出现的真实需求，决定哪些能力值得进一步抽象。
