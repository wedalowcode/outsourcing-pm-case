# 7.6 建立登录会话与安全退出

## 一、为什么验证密码后还需要会话？

上一节，我们已经完成了服务端凭据验证。

用户提交用户名和密码后，系统会查询 PostgreSQL 中的用户，检查账号状态，再使用 Argon2id 验证密码。

验证成功后，`loginAction` 返回：

```ts
return {
  ok: true,
};
```

这只能说明一件事：**这一次提交的用户名和密码是正确的。**

但用户登录后，还需要继续访问部门管理、项目管理等页面。每次点击菜单、刷新页面，甚至发起一个新的服务端请求，系统都需要知道当前用户是谁。

问题来了：HTTP 请求之间通常是独立的。第一次请求验证了密码，并不意味着后续请求会自动知道验证结果。

假设用户完成登录后，接下来访问：

```text
GET /dept
```

服务端收到请求时，并不会自动记得这个用户刚才输入过正确的密码。

如果每次请求都重新输入密码，显然不合理。如果仅仅在浏览器中保存一个 `isLoggedIn = true`，也不安全，因为用户可以修改浏览器中的数据。

所以，我们需要一种机制，把登录时验证通过的身份延续到后续请求中。

这就是**登录会话（Session）**要解决的问题。

登录认证的完整过程可以理解为：

```text
用户提交用户名和密码
          ↓
服务端验证凭据
          ↓
创建登录会话
          ↓
浏览器保存会话凭证
          ↓
后续请求携带凭证
          ↓
服务端验证会话
          ↓
识别当前用户
          ↓
继续处理业务请求
```

这里要区分两个概念：

- **凭据验证**：证明用户在登录时提供了正确的身份凭据。
- **会话管理**：让服务端能够在后续请求中持续识别这个用户。

前者解决“能不能通过登录验证”，后者解决“登录后如何持续保持身份”。

## 二、Cookie、Session、Token 有什么区别？

理解会话之前，先区分三个经常一起出现的概念。

### 2.1 Cookie：浏览器保存和发送数据的机制

Cookie 是浏览器提供的一种机制，服务端可以通过 HTTP 响应设置 Cookie，浏览器在符合条件的后续请求中自动携带它。

例如，服务端可以返回：

```http
Set-Cookie: session=某个会话凭证; HttpOnly; Secure; SameSite=Lax; Path=/
```

之后浏览器会在符合 Cookie 规则的请求中发送：

```http
Cookie: session=某个会话凭证
```

Cookie 解决的是：**浏览器如何保存凭证，以及后续请求如何携带凭证。**

它本身并不负责验证用户身份。即使浏览器保存了一个名为 `session` 的 Cookie，也不代表这个 Cookie 一定有效。

服务端还需要判断它对应的会话是否真实存在、是否过期，以及账号是否仍然允许登录。

### 2.2 Session：服务端维护的登录状态

Session 通常表示服务端保存的一份会话记录。

例如：

| 字段 | 作用 |
|---|---|
| `id` | 会话记录标识 |
| `userId` | 会话所属用户 |
| `tokenHash` | 会话凭证的哈希值 |
| `expiresAt` | 会话过期时间 |
| `createdAt` | 会话创建时间 |

浏览器只保存会话凭证，服务端根据凭证查找对应的 Session，再确定当前用户。

Session 解决的是：**服务端如何持续识别用户，以及如何控制会话的有效期和撤销。**

注意，Session 并不一定非要存放在数据库中，也可以使用其他服务端存储。本项目选择 PostgreSQL，是为了利用现有基础设施，并获得可查询、可撤销的会话记录。

### 2.3 Token：用于表示或证明身份的凭证

Token 是一个更宽泛的概念，表示用于传递或证明某种身份、授权或其他信息的凭证。

例如：

- 随机生成的、不包含用户信息的会话令牌。
- 包含声明并由服务端签名的 JWT。

Token 可以放在 Cookie 中，也可以通过其他方式传递。它和 Cookie 不是同一类概念。

JWT 也不等于 Session。JWT 通常可以通过验证签名和声明来判断有效性，而数据库 Session 则通常需要查询服务端的会话记录。两种方案在过期、撤销和状态管理方面有不同的取舍。

### 2.4 三者之间的关系

可以把它们理解成三个不同的问题：

```text
Cookie：凭证如何由浏览器保存和携带？
Token：请求携带的凭证是什么？
Session：服务端如何维护和验证登录状态？
```

它们可以组合使用，并不是互相排斥的三种方案。

本项目接下来采用的就是：

**浏览器 Cookie + 随机 Session Token + PostgreSQL 会话记录。**

## 三、为什么当前项目选择数据库 Session？

前面已经确定，当前系统是以 Next.js Web 管理端为主的业务系统。

后续不仅需要登录，还需要识别用户、加载角色和权限、控制菜单，以及保护部门管理等业务操作。

结合现有技术栈，我们使用 PostgreSQL 保存会话记录，通过 Cookie 携带随机会话凭证。

选择这种方式，主要考虑以下几点。

### 3.1 可以主动撤销会话

假设用户退出登录，或者管理员需要让某个账号的会话失效。

如果会话记录存储在数据库中，我们可以删除对应记录。之后浏览器即使继续发送原来的凭证，服务端也无法再查询到有效会话。

这比只依赖一个有较长有效期、没有服务端撤销机制的 Token 更容易管理。

### 3.2 可以检查账号状态

我们的 `User` 模型已经有：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}
```

会话查询时可以同时读取用户状态。即使某个用户曾经成功登录，只要账号已经被停用，后续请求就不应该继续获得正常的访问权限。

### 3.3 复用已有数据库

当前项目已经使用 Prisma 7 和 PostgreSQL，不需要为了会话管理额外引入 Redis 等基础设施。

对于目前的实战项目，数据库 Session 已经能够满足学习和实现需求。

当然，这并不意味着数据库 Session 在任何系统中都最好。如果系统规模、并发量、跨服务调用方式发生变化，还需要重新评估会话存储与管理方案。

## 四、为用户增加 Session 数据模型

确定方案后，第一步不是写 Cookie，而是先设计会话数据结构。

因为会话属于持久化业务数据，所以我们先修改 Prisma Schema。

### 4.1 在 `User` 模型中增加会话关联

打开 `prisma/schema.prisma`，在 `User` 模型中增加一个关联字段：

```prisma
model User {
  id           String     @id @default(cuid())
  username     String     @unique @db.VarChar(50)
  passwordHash String     @db.VarChar(255)
  name         String     @db.VarChar(100)
  email        String?    @db.VarChar(255)
  phone        String?    @db.VarChar(30)
  status       UserStatus @default(ACTIVE)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  userRoles UserRole[]
  sessions  Session[]

  @@index([status])
}
```

这里的 `sessions` 是 Prisma 关系字段，用来表示一个用户可以拥有多个登录会话。

例如，同一个用户可能在电脑浏览器和另一台设备上分别登录，因此数据库中可以存在多条属于同一用户的会话记录。

### 4.2 新增 `Session` 模型

继续在 `prisma/schema.prisma` 中增加：

```prisma
model Session {
  id        String   @id @default(cuid())
  userId    String
  tokenHash String   @unique @db.VarChar(64)
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
}
```

下面解释几个重要字段。

**`userId`**

表示这个会话属于哪个用户。通过外键关联 `User`，后续查询会话时就可以同时取得用户信息。

**`tokenHash`**

保存会话凭证的哈希值，而不是浏览器实际持有的原始 Token。

**`expiresAt`**

表示会话的失效时间。服务端查询会话时，不能只判断数据库记录是否存在，还必须检查是否已经过期。

**`onDelete: Cascade`**

当用户记录被删除时，关联的会话记录也会被删除，避免留下没有所属用户的会话。

### 4.3 为什么数据库不直接保存原始 Token？

假设浏览器持有一个随机会话凭证：

```text
N3...一串随机生成的字符
```

如果数据库直接保存这串原始凭证，那么数据库记录一旦被泄露，攻击者可能直接利用这些凭证冒充用户。

因此，我们只保存凭证的 SHA-256 哈希值。

验证时，服务端将浏览器提交的原始 Token 再计算一次哈希，然后查询数据库。

```text
浏览器持有原始 Token
          ↓
请求携带 Cookie
          ↓
服务端计算 Token 的 SHA-256
          ↓
查询 Session.tokenHash
          ↓
检查会话是否存在、是否过期
          ↓
取得所属用户
```

原始 Token 只在创建会话时生成并交给浏览器，不需要持久化保存到数据库。

### 4.4 执行数据库迁移

修改 Schema 后，按照项目现有的 Prisma 工作流创建迁移。

开发环境中执行：

```bash
pnpm exec prisma migrate dev --name add_session
```

迁移完成后，生成 Prisma Client：

```bash
pnpm exec prisma generate
```

这里需要检查迁移是否成功，并确认 `Session` 模型已经出现在生成的 Prisma Client 中。

注意：不要直接修改生产数据库结构来代替项目迁移。数据库结构变化应当通过版本化迁移管理。

## 五、实现会话服务

数据模型准备好后，接下来实现创建、读取和删除会话的功能。

创建文件：

`server/auth/session.ts`

```ts
import "server-only";

import { createHash, randomBytes } from "node:crypto";
import { cookies } from "next/headers";

import { db } from "@/lib/db";

const SESSION_COOKIE_NAME = "session";
const SESSION_DURATION_SECONDS = 60 * 60 * 24 * 7;

function hashToken(token: string) {
  return createHash("sha256")
    .update(token)
    .digest("hex");
}

function getCookieOptions(expires: Date) {
  return {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax" as const,
    path: "/",
    expires,
  };
}

/** 创建会话，并将原始 Token 写入浏览器 Cookie。 */
export async function createSession(userId: string) {
  const token = randomBytes(32).toString("base64url");
  const tokenHash = hashToken(token);
  const expiresAt = new Date(
    Date.now() + SESSION_DURATION_SECONDS * 1000,
  );

  await db.session.create({
    data: {
      userId,
      tokenHash,
      expiresAt,
    },
  });

  const cookieStore = await cookies();

  cookieStore.set(
    SESSION_COOKIE_NAME,
    token,
    getCookieOptions(expiresAt),
  );
}

/** 根据浏览器 Cookie 识别当前用户。 */
export async function getCurrentSession() {
  const cookieStore = await cookies();
  const token = cookieStore.get(SESSION_COOKIE_NAME)?.value;

  if (!token) {
    return null;
  }

  const session = await db.session.findUnique({
    where: {
      tokenHash: hashToken(token),
    },
    select: {
      id: true,
      userId: true,
      expiresAt: true,
      user: {
        select: {
          id: true,
          username: true,
          name: true,
          status: true,
        },
      },
    },
  });

  if (!session) {
    return null;
  }

  if (session.expiresAt.getTime() <= Date.now()) {
    return null;
  }

  if (session.user.status !== "ACTIVE") {
    return null;
  }

  return {
    sessionId: session.id,
    user: session.user,
    expiresAt: session.expiresAt,
  };
}

/** 删除当前会话，并清除浏览器 Cookie。 */
export async function deleteCurrentSession() {
  const cookieStore = await cookies();
  const token = cookieStore.get(SESSION_COOKIE_NAME)?.value;

  if (token) {
    await db.session.deleteMany({
      where: {
        tokenHash: hashToken(token),
      },
    });
  }

  cookieStore.delete(SESSION_COOKIE_NAME);
}
```

下面逐步理解。

### 5.1 生成随机 Token

```ts
const token = randomBytes(32).toString("base64url");
```

这里使用 Node.js 的 `crypto` 模块生成 32 字节的随机数据，再编码为适合放进 Cookie 的字符串。

Token 不使用用户名、用户 ID、时间戳等可预测的数据拼接生成，而是使用密码学安全的随机数。

用户 ID 本身不是秘密，不能直接拿来充当登录凭证。

### 5.2 设置 Cookie 安全属性

```ts
return {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax" as const,
  path: "/",
  expires,
};
```

这里的配置分别解决不同的问题。

| 属性 | 作用 |
|---|---|
| `httpOnly` | 阻止客户端 JavaScript 直接读取 Cookie |
| `secure` | 生产环境中要求通过 HTTPS 发送 Cookie |
| `sameSite: "lax"` | 限制部分跨站请求自动携带 Cookie 的行为 |
| `path: "/"` | 让 Cookie 适用于站点下的各个路径 |
| `expires` | 设置 Cookie 的过期时间 |

需要注意，`HttpOnly` 并不能防止所有 XSS 攻击，`SameSite` 也不能代替所有 CSRF 防护措施。后续如果引入更复杂的跨站操作或外部客户端，需要结合实际场景继续评估。

生产环境应使用 HTTPS，并保证应用的代理、部署配置与 Cookie 安全属性一致。

### 5.3 创建数据库会话

```ts
await db.session.create({
  data: {
    userId,
    tokenHash,
    expiresAt,
  },
});
```

这里将用户 ID、Token 哈希值和过期时间写入 PostgreSQL。

随后再通过 `cookies()` 写入原始 Token。

这两个步骤共同构成了会话建立过程：

- 数据库记录负责让服务端能够验证和撤销会话。
- Cookie 负责让浏览器在后续请求中携带会话凭证。

这里的 Cookie 是在服务端代码中设置的。Next.js 的 `cookies()` API 是异步的，因此需要使用 `await cookies()`。

### 5.4 为什么会话有效期是七天？

本例设置七天有效期：

```ts
const SESSION_DURATION_SECONDS = 60 * 60 * 24 * 7;
```

这只是当前实战项目采用的策略，并不是所有系统都应该使用七天。

如果是处理高敏感业务的系统，可能需要更短的会话有效期、闲置超时、重新认证，或者针对特定操作再次验证身份。

同时，Cookie 的过期时间和数据库 Session 的过期时间必须保持一致。不能只依赖浏览器删除 Cookie，也不能只判断数据库记录是否存在。

### 5.5 读取当前会话

```ts
const token = cookieStore.get(SESSION_COOKIE_NAME)?.value;
```

首先读取浏览器携带的 Cookie。

如果没有 Token，直接返回 `null`。

如果存在 Token，服务端计算它的哈希值，再查询数据库：

```ts
const session = await db.session.findUnique({
  where: {
    tokenHash: hashToken(token),
  },
  // ...
});
```

查询之后还需要检查：

1. 会话记录是否存在。
2. 会话是否已经过期。
3. 所属用户是否仍然处于启用状态。

只有全部满足条件，才返回当前会话和用户信息。

这里的 `getCurrentSession()` 返回的是服务端查询结果，不是客户端自行声明的登录状态。

注意：读取会话时，如果发现会话已经过期，本例会将其判定为无效，但不会在 Server Component 渲染过程中修改 Cookie。过期记录可以在后续的清理任务中处理；即使数据库中暂时保留过期记录，也不能因此恢复会话有效性。

### 5.6 删除当前会话

退出登录时，需要同时处理两个地方：

- 删除数据库中的会话记录。
- 清除浏览器中的 Cookie。

```ts
await db.session.deleteMany({
  where: {
    tokenHash: hashToken(token),
  },
});

cookieStore.delete(SESSION_COOKIE_NAME);
```

这里使用 `deleteMany()`，即使对应记录已经不存在，也可以安全地完成删除流程。

只清除 Cookie 不够。假设攻击者已经复制了原始 Token，那么仅清除当前浏览器的 Cookie，并不会让复制出去的 Token 失效。

删除数据库记录后，后续请求即使携带原始 Token，也无法再找到有效的会话记录。

## 六、让登录成功后真正建立会话

现在会话服务已经完成，需要将它接入上一节的 `loginAction`。

打开：

`server/auth/actions.ts`

在现有导入中增加：

```ts
import { createSession } from "@/server/auth/session";
```

然后调整 `loginAction`。

```ts
"use server";

import { loginSchema } from "@/server/auth/schema";
import { verifyCredentials } from "@/server/auth/verify-credentials";
import { createSession } from "@/server/auth/session";

export type LoginActionResult =
  | {
      ok: true;
    }
  | {
      ok: false;
      message: string;
    };

export async function loginAction(
  input: unknown,
): Promise<LoginActionResult> {
  const parsed = loginSchema.safeParse(input);

  if (!parsed.success) {
    return {
      ok: false,
      message: "请检查用户名和密码的输入格式",
    };
  }

  try {
    const result = await verifyCredentials(parsed.data);

    if (!result.ok) {
      return {
        ok: false,
        message: "用户名或密码错误，或账号不可用",
      };
    }

    await createSession(result.user.id);

    return {
      ok: true,
    };
  } catch (error) {
    console.error("登录处理失败", error);

    return {
      ok: false,
      message: "登录失败，请稍后重试",
    };
  }
}
```

与上一节相比，真正的变化只有一处：

```ts
await createSession(result.user.id);
```

但这一步改变了登录流程的含义。

上一节是：

```text
凭据验证成功
          ↓
返回成功
```

现在变成：

```text
凭据验证成功
          ↓
创建数据库 Session
          ↓
设置浏览器 Cookie
          ↓
返回成功
```

只有凭据验证成功并完成会话创建，Action 才会返回成功。

这里要注意异常处理：会话创建或 Cookie 设置失败时，不能向页面报告登录成功。

在更严格的生产实现中，还应进一步考虑数据库写入与 Cookie 写入之间的失败处理、登录限流，以及安全审计等问题。本节先建立最小可用的会话闭环。

## 七、登录成功后跳转到后台

上一节的登录页面在认证成功后，显示的是：

```text
凭据验证成功，会话管理将在下一节接入。
```

现在会话已经建立，这段提示就不再合适了。

打开 `app/login/page.tsx`，增加：

```tsx
import { useRouter } from "next/navigation";
```

在 `LoginPage` 组件中获取路由对象：

```tsx
const router = useRouter();
```

然后将 `onSubmit` 中的成功分支修改为：

```tsx
async function onSubmit(values: LoginFormValues) {
  setSubmitError("");

  try {
    const result = await loginAction(values);

    if (!result.ok) {
      setSubmitError(result.message);
      return;
    }

    router.replace("/dept");
    return;
  } catch {
    setSubmitError("登录失败，请稍后重试");
  }
}
```

这里只使用 `router.replace("/dept")`，让登录成功后进入部门管理页面。replace 跳到新页面会重新请求 layout，因此不需要 refresh。

需要理解的是：**跳转本身不负责建立登录状态。真正建立登录状态的是服务端写入的 Cookie 和数据库 Session。**

后续页面能够识别当前用户，是因为浏览器携带了 Cookie，服务端能够据此查找到有效的会话记录。

## 八、保护后台页面：不能只靠登录页面跳转

到这里，用户登录后已经有了会话。

但还存在一个问题：如果用户没有登录，直接在地址栏输入 `/dept`，会发生什么？

检查当前项目的：

`app/(dashboard)/layout.tsx`

目前它只是渲染后台布局：

```tsx
import type { ReactNode } from "react";
import { AppLayout } from "@/components/layout/app-layout";

export default function DashboardLayout({
  children,
}: {
  children: ReactNode;
}) {
  return <AppLayout userName={/* TODO 来自 session */}>{children}</AppLayout>;
}
```

它没有检查用户是否登录。

因此，我们需要在后台布局中加入服务端会话检查。

### 8.1 修改后台布局

将 `app/(dashboard)/layout.tsx` 修改为：

```tsx
import type { ReactNode } from "react";
import { redirect } from "next/navigation";

import { AppLayout } from "@/components/layout/app-layout";
import { getCurrentSession } from "@/server/auth/session";

export default async function DashboardLayout({
  children,
}: {
  children: ReactNode;
}) {
  const session = await getCurrentSession();

  if (!session) {
    redirect("/login");
  }

  return <AppLayout userName={session.user.name}>{children}</AppLayout>;
}
```

这里有三个关键点。

第一，`DashboardLayout` 是服务端组件，因此可以直接调用服务端的会话读取函数。

第二，没有有效会话时，使用 `redirect("/login")` 跳转到登录页面。

第三，检查发生在服务端，而不是仅仅在浏览器里隐藏导航菜单。

这样，访问后台页面时，系统会先验证会话，再渲染对应的后台内容。

### 8.2 页面保护不等于操作保护

现在 `/dept` 页面已经增加了会话检查，但这还不够。

回顾 `server/dept/actions.ts`，当前新增、修改和删除部门的 Action 仍然存在这样的注释：

```ts
// TODO：先校验登录态和新增权限
```

这说明部门操作本身还没有真正执行登录校验。

Server Actions 不能因为页面已经检查过登录状态，就默认所有调用都来自已登录用户。调用者可以尝试直接请求某个 Action，而不必先访问页面。

因此，新增、修改、删除等服务端操作也必须独立检查当前会话。

例如，在 `server/dept/actions.ts` 中增加导入：

```ts
import { getCurrentSession } from "@/server/auth/session";
```

然后在新增部门操作开头检查：

```ts
export async function createDeptAction(input: unknown) {
  const session = await getCurrentSession();

  if (!session) {
    return {
      ok: false as const,
      message: "登录状态已失效，请重新登录",
    };
  }

  // 后续继续执行现有的输入校验与业务逻辑
}
```

修改和删除操作也需要同样的登录态检查。实际修改时，应保留原来的 ID 校验、Schema 校验、错误处理和业务服务调用，不要用上面这段示例替换整个函数。

本节先建立统一的登录身份检查。后续实现角色和权限时，还需要继续判断当前用户是否有权执行具体操作。

请记住：

**页面访问控制负责保护页面，服务端操作校验负责保护数据。二者不能互相替代。**

## 九、实现安全退出

用户可以登录，也必须能够主动退出登录。

退出时不能只让页面跳转到登录页，还需要使当前会话在服务端失效。

### 9.1 创建退出登录 Action

在 `server/auth/actions.ts` 中增加：

```ts
import { deleteCurrentSession } from "@/server/auth/session";
```

然后添加退出登录操作：

```ts
export async function logoutAction() {
  await deleteCurrentSession();

  return {
    ok: true as const,
  };
}
```

该 Action 不需要接收用户 ID，也不应该相信客户端传入的某个 ID 来决定删除谁的会话。

它通过当前请求携带的 Cookie 找到对应会话，删除数据库记录，再清除 Cookie。

这样，退出登录操作就与当前浏览器持有的会话绑定。

### 9.2 在后台顶部增加退出按钮

布局拆成 AppLayout + Sidebar + Header + UserActions，顶栏右侧的退出按钮在 UserActions 里。

`components/layout/user-actions.tsx` 是客户端组件，负责渲染用户名和退出按钮。核心代码如下。

先增加导入：

```tsx
import { useState } from "react";
import { useRouter } from "next/navigation";

import { Button } from "@/components/ui/button";
import { logoutAction } from "@/server/auth/actions";
```

在 `UserActions` 组件中增加状态：

```tsx
const router = useRouter();
const [isLoggingOut, setIsLoggingOut] = useState(false);
const [errorMessage, setErrorMessage] = useState("");
```

添加处理函数：

```tsx
async function handleLogout() {
  if (isLoggingOut) return;

  setIsLoggingOut(true);
  setErrorMessage("");

  try {
    const result = await logoutAction();

    if (result.ok) {
      router.replace("/login");
      // 成功：保持 "退出中..." 直到页面跳转，不恢复按钮
      return;
    }

    setErrorMessage("退出登录失败，请重试");
  } catch {
    setErrorMessage("退出登录失败，请稍后重试");
  }

  // 只有失败才会走到这里，恢复按钮可点状态
  setIsLoggingOut(false);
}
```

`replace` 跳到新页面会重新请求 layout，因此不需要 `router.refresh()`；成功后也不主动恢复按钮状态，让"退出中..."保持到页面跳转即可。

退出错误提示放在用户名左边，按钮位置不动。渲染结构大致为：

```tsx
<div className="flex items-center gap-3">
  {/* 错误提示放在名字左边，出现时按钮位置不动 */}
  {errorMessage && (
    <span className="text-sm text-destructive" role="alert">
      {errorMessage}
    </span>
  )}

  <span className="text-sm text-muted-foreground">{userName}</span>

  <Button
    variant="outline"
    size="sm"
    disabled={isLoggingOut}
    onClick={handleLogout}
  >
    {isLoggingOut ? "退出中..." : "退出登录"}
  </Button>
</div>
```

`userName` 通过 props 传入。AppLayout 在服务端读取 session 后将 `session.user.name` 传下来，因此 UserActions 不需要自己再查会话。真实接入时，把 AppLayout 示例里的 `/* TODO 来自 session */` 替换为实际的 session 用户名即可。

### 9.3 退出后为什么不能再访问后台？

退出登录成功后，会发生两件事：

1. 数据库中的当前 Session 被删除。
2. 浏览器中的会话 Cookie 被清除。

之后用户再次访问 `/dept`，后台布局会调用 `getCurrentSession()`。

由于浏览器没有有效的 Cookie，服务端返回 `null`，页面就会被重定向到 `/login`。

即使某人之前复制过旧 Token，服务端也无法再通过它查询到已经删除的 Session。

这才是完整的退出登录，而不仅仅是切换到另一个页面。

## 十、验证刷新页面后登录状态仍然有效

代码完成后，需要验证的不是“登录按钮能不能点击”，而是会话是否真正跨请求生效。

建议按以下顺序测试。

### 10.1 正常登录

使用初始化的管理员账号和正确密码提交登录表单。

预期结果：

- 服务端验证凭据。
- PostgreSQL 中创建一条 Session 记录。
- 浏览器收到 `session` Cookie。
- 页面跳转到 `/dept`。
- 部门管理页面正常显示。

可以在开发环境中通过浏览器开发者工具检查 Cookie，也可以通过数据库客户端查看 Session 记录。

不要把真实 Token 复制到日志、博客或截图中。即使是测试环境，也应把会话凭证当作敏感信息处理。

### 10.2 刷新页面

在 `/dept` 页面按浏览器刷新按钮。

预期结果：

- 浏览器继续携带有效 Cookie。
- 服务端读取 Cookie 并计算 Token 哈希。
- 服务端在 PostgreSQL 中找到对应 Session。
- 服务端确认会话没有过期，用户状态仍然是 `ACTIVE`。
- 页面继续正常显示，不需要重新输入密码。

这一步证明，登录状态不是只保存在 React 组件的内存中，而是由浏览器 Cookie 和服务端会话记录共同维持。

### 10.3 直接访问后台地址

退出登录后，直接在地址栏输入：

```text
/dept
```

预期结果：后台布局检查不到有效会话，跳转到 `/login`。

这一步验证的是服务端页面保护，而不是前端菜单隐藏。

### 10.4 测试退出登录

重新登录后，点击顶部的“退出登录”按钮。

预期结果：

- 数据库中当前会话记录被删除。
- 浏览器的 `session` Cookie 被清除。
- 页面跳转到 `/login`。

随后重新访问 `/dept`，应该再次被重定向到登录页面。

### 10.5 测试会话过期

在开发环境中，可以将数据库里某条 Session 的 `expiresAt` 设置为过去的时间，再刷新后台页面。

预期结果：即使 Cookie 还存在，服务端也会因为会话已经过期而返回无效状态，页面跳转到登录页。

这一步验证的是服务端的过期判断，而不是单纯依赖浏览器删除 Cookie。

### 10.6 测试账号停用

将测试用户的 `status` 改为 `DISABLED`，再尝试访问后台页面。

预期结果：`getCurrentSession()` 检查到账号已停用，返回 `null`，后台不再正常显示。

这里的实现能够阻止停用账号继续通过会话检查，但生产系统还应考虑主动撤销该用户的全部会话，以便清理数据库记录，并使失效行为更明确。

## 十一、本节总结

本节在前一节凭据验证的基础上，建立了完整的登录会话闭环。

我们完成了以下工作：

1. 为用户增加 `Session` 数据模型。
2. 使用密码学安全的随机数生成会话 Token。
3. 在 PostgreSQL 中保存 Token 的哈希值，而不是原始凭证。
4. 通过 `HttpOnly` Cookie 保存和传递会话凭证。
5. 实现创建会话、读取当前会话和删除当前会话的服务端函数。
6. 在登录成功后创建 Session。
7. 在后台布局中检查登录状态。
8. 实现退出登录，并让旧会话失效。
9. 为部门管理的 Server Actions 增加登录校验的入口。
10. 通过刷新页面、直接访问后台、退出登录和过期测试验证会话机制。

整个认证流程现在变成：

```text
用户名 + 密码
      ↓
服务端凭据验证
      ↓
创建 Session
      ↓
设置 HttpOnly Cookie
      ↓
浏览器携带 Cookie 访问后台
      ↓
服务端查询 Session
      ↓
确认有效后识别当前用户
      ↓
执行页面与业务操作
      ↓
退出时删除 Session 并清除 Cookie
```

还要注意两个尚未在本节彻底完成的边界。

第一，当前后台顶部的“管理员”仍然是静态文本。下一阶段需要通过会话获取当前用户信息，再将真实姓名展示在界面上。

第二，登录态校验不等于权限校验。当前用户有有效会话，只能说明系统识别了这个用户；他是否有权新增部门、删除部门，仍然需要在服务端结合角色和权限进行判断。

因此，下一节可以继续沿着主线推进：**获取当前用户信息、加载角色和权限，并让后台布局与菜单根据真实的登录身份工作。**
