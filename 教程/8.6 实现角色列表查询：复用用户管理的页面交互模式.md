# 8.5 实现角色列表查询：复用用户管理的页面交互模式

前面已经建立了 RBAC 的基本数据模型，定义了用户、角色、权限，以及用户与角色、角色与权限之间的关联关系。

接下来实现角色管理的第一个功能：**角色列表查询**。

这一节不再单独设计一套列表页面，而是沿用用户管理模块已经验证过的实现方式。通过统一的查询条件组件、状态筛选组件、表格组件和分页组件，让不同业务模块具有一致的交互体验。

## 一、明确角色列表的功能需求

角色列表需要展示以下信息：

| 字段 | 说明 |
|---|---|
| 角色编码 | 系统内部使用的唯一标识，例如 `PROJECT_MANAGER` |
| 角色名称 | 面向管理人员展示，例如项目经理 |
| 角色描述 | 说明角色的职责和适用范围 |
| 状态 | 正常、已禁用 |
| 用户数量 | 当前关联该角色的用户数量 |
| 权限数量 | 当前分配给该角色的权限数量 |
| 创建时间 | 角色创建的时间 |

同时，需要支持三个查询维度：

1. **关键字查询**：按照角色编码、角色名称、角色描述进行模糊匹配。
2. **状态筛选**：全部状态、正常、已禁用。
3. **分页查询**：支持上一页、下一页，并显示总记录数和当前页码。

页面交互与用户管理保持一致：查询条件发生变化时，更新 URL 查询参数，再由服务端页面重新获取数据。

## 二、规划代码结构

本节主要涉及三个文件：

```text
server/
└── role/
    └── service.ts                 # 角色列表查询服务

app/
└── (dashboard)/
    └── roles/
        ├── page.tsx               # 服务端页面
        └── role-workspace.tsx     # 客户端交互工作区
```

其中：

- `service.ts` 负责构建 Prisma 查询条件、查询角色及关联统计数据。
- `page.tsx` 负责解析 URL 参数、调用 Service、获取初始数据。
- `role-workspace.tsx` 负责搜索、筛选、分页和列表展示。

查询条件和分页直接复用项目现有的公共组件：

```text
components/
└── common/
    ├── search-bar.tsx
    └── pagination.tsx
```

UI 则使用已有的 shadcn 组件，包括 `Button`、`Select` 和 `Table`。不再为角色模块重复实现搜索框和分页器。

## 三、实现角色列表查询服务

首先创建 `server/role/service.ts`。

### 3.1 定义查询参数

角色列表服务需要接收关键字、状态、页码和每页条数。

```ts
import { Prisma } from "@/lib/generated/prisma/client";
import { db } from "@/lib/db";

export type RoleListParams = {
  keyword?: string;
  status?: "ACTIVE" | "DISABLED" | "ALL";
  page?: number;
  pageSize?: number;
};
```

这里的 `status` 与数据库中的角色状态枚举保持一致。

页面上显示的是中文标签，但传给 Service 的仍然是 `ACTIVE`、`DISABLED` 等业务值，避免将展示文本与数据库字段混在一起。

### 3.2 规范化查询参数

URL 参数来自用户输入，不能直接假定它们始终合法。

```ts
const MAX_PAGE_SIZE = 100;

function normalizePage(value: number | undefined) {
  if (!Number.isSafeInteger(value) || value! < 1) {
    return 1;
  }

  return value!;
}

function normalizePageSize(value: number | undefined) {
  if (!Number.isSafeInteger(value) || value! < 1) {
    return 10;
  }

  return Math.min(value!, MAX_PAGE_SIZE);
}

function normalizeStatus(
  value: RoleListParams["status"],
): RoleListParams["status"] {
  if (
    value === "ACTIVE" ||
    value === "DISABLED" ||
    value === "ALL"
  ) {
    return value;
  }

  return "ALL";
}
```

这里设置每页最多查询 100 条记录，避免不合理的分页参数导致一次性读取过多数据。

### 3.3 编写列表查询方法

```ts
export async function listRoles(
  params: RoleListParams = {},
) {
  const keyword =
    params.keyword?.trim().slice(0, 100) ?? "";

  const status = normalizeStatus(params.status);
  const requestedPage = normalizePage(params.page);
  const pageSize = normalizePageSize(params.pageSize);

  const where: Prisma.RoleWhereInput = {
    ...(status !== "ALL" ? { status } : {}),
    ...(keyword
      ? {
          OR: [
            {
              code: {
                contains: keyword,
                mode: "insensitive",
              },
            },
            {
              name: {
                contains: keyword,
                mode: "insensitive",
              },
            },
            {
              description: {
                contains: keyword,
                mode: "insensitive",
              },
            },
          ],
        }
      : {}),
  };

  const total = await db.role.count({ where });

  const totalPages = Math.ceil(total / pageSize);
  const page = Math.min(
    requestedPage,
    Math.max(1, totalPages),
  );

  const items = await db.role.findMany({
    where,
    orderBy: [
      { createdAt: "desc" },
      { id: "desc" },
    ],
    skip: (page - 1) * pageSize,
    take: pageSize,
    include: {
      _count: {
        select: {
          userRoles: true,
          rolePermissions: true,
        },
      },
    },
  });

  return {
    items,
    total,
    page,
    pageSize,
    totalPages,
  };
}
```

这段代码有几个需要理解的地方。

**第一，使用 `where` 统一组织查询条件。**

状态条件和关键字条件通过对象展开组合。没有填写关键字时，不增加 `OR` 条件；选择全部状态时，不增加状态过滤条件。

**第二，使用 `contains` 进行模糊查询。**

例如，输入 `PROJECT`，可以匹配编码为 `PROJECT_MANAGER` 的角色。`mode: "insensitive"` 用于 PostgreSQL 下的不区分大小写匹配。

**第三，使用 `_count` 查询关联数量。**

```ts
include: {
  _count: {
    select: {
      userRoles: true,
      rolePermissions: true,
    },
  },
},
```

这里统计的是 `UserRole` 和 `RolePermission` 关联记录的数量，不需要为了展示用户数量和权限数量，再分别循环查询数据库。

**第四，使用 `skip` 和 `take` 实现分页。**

```ts
skip: (page - 1) * pageSize,
take: pageSize,
```

例如，每页 10 条，查询第 3 页时跳过前 20 条，再获取接下来的 10 条。

**第五，处理超出范围的页码。**

当用户原本查看第 5 页，删除或筛选数据后总页数减少，服务端会将页码限制在当前有效范围内。这样不会因为请求了不存在的页码而一直显示空列表。

> 注意：上述代码假定项目中的 `Role`、`UserRole`、`RolePermission` 模型以及关联字段名与前面建立的数据模型一致。如果实际 Prisma Schema 中使用了不同的名称，需要以真实 Schema 为准。

## 四、实现服务端页面

创建 `app/(dashboard)/roles/page.tsx`。

这个页面与用户列表一样，负责解析 URL 查询参数并调用 Service。查询属于读取操作，因此不需要为了查询列表再创建一个 Server Action。

```tsx
import { listRoles } from "@/server/role/service";
import { RoleWorkspace } from "./role-workspace";

type SearchParams = {
  keyword?: string | string[];
  status?: string | string[];
  page?: string | string[];
  pageSize?: string | string[];
};

function firstValue(
  value: string | string[] | undefined,
) {
  return Array.isArray(value) ? value[0] : value;
}

function positiveInteger(
  value: string | undefined,
  fallback: number,
) {
  if (!value || !/^\d+$/.test(value)) {
    return fallback;
  }

  const number = Number(value);

  return Number.isSafeInteger(number) && number > 0
    ? number
    : fallback;
}

export default async function RolesPage({
  searchParams,
}: {
  searchParams: Promise<SearchParams>;
}) {
  const params = await searchParams;

  const keyword =
    firstValue(params.keyword)?.trim().slice(0, 100) ?? "";

  const rawStatus = firstValue(params.status);

  const status =
    rawStatus === "ACTIVE" ||
    rawStatus === "DISABLED"
      ? rawStatus
      : "";

  const page = positiveInteger(
    firstValue(params.page),
    1,
  );

  const pageSize = Math.min(
    positiveInteger(firstValue(params.pageSize), 10),
    100,
  );

  const pageData = await listRoles({
    keyword,
    status: status || "ALL",
    page,
    pageSize,
  });

  return (
    <RoleWorkspace
      pageData={pageData}
      keyword={keyword}
      status={status}
    />
  );
}
```

这里使用了 Next.js App Router 的异步 `searchParams` 写法。

例如，访问：

```text
/roles?keyword=PROJECT&status=ACTIVE&page=2
```

服务端会解析出：

- 关键字：`PROJECT`
- 状态：`ACTIVE`
- 页码：`2`
- 每页条数：默认 `10`

然后调用 `listRoles()`，将查询结果和当前筛选条件交给客户端工作区。

这样，刷新页面或者复制 URL 后重新打开，都能恢复对应的查询状态。

## 五、实现客户端角色工作区

创建 `app/(dashboard)/roles/role-workspace.tsx`。

整体实现方式与 `UserWorkspace` 保持一致，复用相同的公共查询组件和 UI 组件。

### 5.1 定义组件类型和依赖

```tsx
"use client";

import { useRouter } from "next/navigation";
import { useTransition } from "react";

import { SearchBar } from "@/components/common/search-bar";
import { Pagination } from "@/components/common/pagination";
import { Button } from "@/components/ui/button";

import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from "@/components/ui/select";

import {
  Table,
  TableBody,
  TableCell,
  TableHead,
  TableHeader,
  TableRow,
} from "@/components/ui/table";

type RoleStatus = "ACTIVE" | "DISABLED";

type RoleItem = {
  id: string;
  code: string;
  name: string;
  description: string | null;
  status: RoleStatus;
  createdAt: Date;
  _count: {
    userRoles: number;
    rolePermissions: number;
  };
};

type RolePageData = {
  items: RoleItem[];
  total: number;
  page: number;
  pageSize: number;
  totalPages: number;
};

type RoleWorkspaceProps = {
  pageData: RolePageData;
  keyword: string;
  status: "" | RoleStatus;
};
```

`RoleItem` 中的 `_count` 来自前面 Prisma 查询的关联统计结果。

如果项目采用了不同的关联字段名，需要同步调整 Service 和这里的类型。

### 5.2 实现 URL 查询导航

```tsx
export function RoleWorkspace({
  pageData,
  keyword,
  status,
}: RoleWorkspaceProps) {
  const router = useRouter();
  const [isPending, startTransition] = useTransition();

  function go(next: {
    keyword?: string;
    status?: "" | RoleStatus;
    page?: number;
  }) {
    const nextKeyword = next.keyword ?? keyword;

    const nextStatus =
      next.status === undefined
        ? status
        : next.status;

    const nextPage = next.page ?? 1;

    const params = new URLSearchParams();

    if (nextKeyword) {
      params.set("keyword", nextKeyword);
    }

    if (nextStatus) {
      params.set("status", nextStatus);
    }

    if (nextPage > 1) {
      params.set("page", String(nextPage));
    }

    const query = params.toString();
    const url = query ? `/roles?${query}` : "/roles";

    startTransition(() => {
      router.push(url);
    });
  }

  function handleStatusChange(value: string | null) {
    if (value === "全部状态") {
      go({ status: "", page: 1 });
      return;
    }

    if (value === "正常") {
      go({ status: "ACTIVE", page: 1 });
      return;
    }

    if (value === "已禁用") {
      go({ status: "DISABLED", page: 1 });
    }
  }

  function handleReset() {
    startTransition(() => {
      router.push("/roles");
    });
  }

  // 后续继续编写 JSX
}
```

这里的 `go()` 是整个工作区的查询导航入口。

搜索时调用：

```tsx
go({ keyword: value, page: 1 });
```

切换状态时调用：

```tsx
go({ status: "DISABLED", page: 1 });
```

分页时调用：

```tsx
go({ page });
```

**关键点是：每次更改查询条件，都从第一页开始；只有翻页操作才保留当前关键字和状态。**

`useTransition` 用于跟踪导航过渡状态，后续可以用 `isPending` 提示用户正在加载新的列表数据。

### 5.3 实现查询条件区域

在 `RoleWorkspace` 中，将前面的导航函数与以下 JSX 合并，作为组件的返回内容：

```tsx
return (
  <div className="space-y-4">
    <div>
      <h1 className="text-xl font-semibold">
        角色管理
      </h1>

      <p className="mt-1 text-sm text-muted-foreground">
        查询和查看系统角色及其关联情况。
      </p>
    </div>

    <div className="flex flex-wrap items-center gap-3">
      <SearchBar
        key={keyword}
        defaultValue={keyword}
        placeholder="搜索角色编码 / 名称 / 描述"
        onSearch={(value) =>
          go({ keyword: value, page: 1 })
        }
      />

      <Select
        value={
          status === "ACTIVE"
            ? "正常"
            : status === "DISABLED"
              ? "已禁用"
              : "全部状态"
        }
        onValueChange={handleStatusChange}
      >
        <SelectTrigger className="w-36">
          <SelectValue placeholder="全部状态" />
        </SelectTrigger>

        <SelectContent>
          <SelectItem value="全部状态">
            全部状态
          </SelectItem>

          <SelectItem value="正常">
            正常
          </SelectItem>

          <SelectItem value="已禁用">
            已禁用
          </SelectItem>
        </SelectContent>
      </Select>

      <Button
        type="button"
        variant="outline"
        disabled={isPending}
        onClick={handleReset}
      >
        重置
      </Button>
    </div>

    {/* 列表区域接在这里 */}
  </div>
);
```

这里没有重新编写搜索框和分页器，而是直接使用：

```tsx
import { SearchBar } from "@/components/common/search-bar";
import { Pagination } from "@/components/common/pagination";
```

`SearchBar` 内部维护输入草稿，提交时调用 `onSearch`；状态筛选使用已有的 shadcn `Select`；重置操作则将 URL 恢复为 `/roles`。

`key={keyword}` 可以在服务端传入的关键字变化时，重新初始化搜索框的内部状态。

继续在同一个 `return` 中，将上面的列表区域占位内容替换为以下代码：

表格使用与用户列表相同的 `Table` 组件和 Tailwind 样式约定。

- 没有数据时，显示“没有符合条件的角色”，而不是留下一张空白表格。

目前只实现查询和展示，不提前加入编辑、删除等尚未实现的操作按钮。后续开发角色管理功能时，再将这些操作逐步接入。

### 5.5 接入公共分页组件

在表格后面增加：

```tsx
<Pagination
  page={pageData.page}
  total={pageData.total}
  pageSize={pageData.pageSize}
  onChange={(page) => go({ page })}
/>
```

至此，角色列表已经复用了项目的公共分页组件。

该组件负责展示总记录数、当前页码，并在点击上一页或下一页时调用 `onChange`。角色工作区只需要将页码交给 `go()`，不必再次编写分页按钮。

`role-workspace.tsx` 的最终结构是：

```text
RoleWorkspace
├── 标题与说明
├── 查询条件
│   ├── SearchBar
│   ├── Select
```

请注意：上面几个 JSX 片段属于同一个 `RoleWorkspace` 组件，不能分别作为独立组件直接粘贴。将导航函数和各段 JSX 合并后，才能形成完整文件。

## 六、验证查询功能

实现后，按照以下场景进行验证。

| 测试场景 | 预期结果 |
|---|---|
| 首次进入 `/roles` | 显示全部角色，默认第 1 页 |
| 输入角色名称并查询 | 仅显示匹配的角色 |
| 输入角色编码的一部分 | 能够进行模糊匹配 |
| 选择“正常” | 只显示 `ACTIVE` 角色 |
| 选择“已禁用” | 只显示 `DISABLED` 角色 |
| 点击重置 | 清除关键字、状态和页码 |
| 点击下一页 | 页码变化，查询条件保持不变 |
| 输入不存在的关键字 | 显示空结果提示 |
| 访问超过总页数的 URL | 页码被限制在有效范围内 |

同时检查以下技术细节：

1. Prisma Schema 中的关联字段名与 `_count` 查询保持一致。
2. 角色状态枚举与 Service 的过滤条件保持一致。
3. 公共 `SearchBar` 和 `Pagination` 的导入路径使用项目实际路径。
4. 不要为了列表读取额外创建 Server Action。
5. 不要将角色权限的关联记录数量误认为已经通过授权检查的有效权限数量。

## 七、本节总结

角色列表查询看似简单，实际上已经串起了一个后台管理模块的基本结构：

```text
用户操作
   ↓
SearchBar / Select / Pagination
   ↓
更新 URL 查询参数
   ↓
Next.js 服务端页面解析参数
   ↓
Role Service 构建 Prisma 查询
   ↓
PostgreSQL 返回数据
   ↓
RoleWorkspace 展示结果
```

这个结构与用户管理模块保持一致，后续开发项目、客户、任务等业务列表时，可以继续沿用同样的模式。

这里真正值得复用的不是某一个表格，而是**查询参数的组织方式、前后端职责划分、公共交互组件，以及列表结果的数据结构**。

下一节可以在这个基础上实现角色创建功能，再逐步补充角色编辑、用户授权和权限分配。角色列表中的“用户数量”和“权限数量”只是统计信息，真正的访问控制仍需要在服务端执行权限校验，不能因为角色已经出现在列表中就认为授权体系已经完成。
