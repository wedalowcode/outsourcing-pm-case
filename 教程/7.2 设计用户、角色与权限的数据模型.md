# 7.2 设计用户、角色与权限的数据模型

## 一、前言：为什么需要设计用户、角色与权限？

上一节，我们已经规划了系统的整体运行流程：

用户访问系统，进入登录页面，输入用户名和密码。登录成功后，系统根据用户的权限加载对应的菜单，用户点击菜单进入业务页面，并在页面中执行相应的操作。

这条流程看起来很简单，但如果继续向下拆解，就会遇到几个问题。

假设我们正在开发一个外包项目管理平台，系统中存在三类人员：

- 销售人员：负责客户、商机等业务。
- 项目经理：负责项目、任务、工时等业务。
- 开发人员：负责查看任务、填写工时、提交工作成果。

我们希望不同的人员登录系统后，看到的菜单不同，能够执行的操作也不同。

例如：

销售人员可以创建客户，但不能删除项目；项目经理可以分配任务，但不能随意修改用户账号；开发人员可以填写自己的工时，但不能查看所有项目的成本数据。

如果直接在代码中判断用户名，就会出现大量类似下面的逻辑：

```ts
if (user.name === "张三") {
  // 允许创建客户
}

if (user.name === "李四") {
  // 允许分配任务
}
```

这种方式无法适应真实的业务场景。人员会发生变化，职责也可能调整。如果每次调整权限都需要修改代码，系统就很难维护。

更合理的做法是，把人员身份、岗位职责和具体权限分开管理。

- **用户（User）**：回答谁在使用系统。
- **角色（Role）**：回答这个用户承担什么职责。
- **权限（Permission）**：回答这个用户可以执行哪些操作。

我们通过数据模型建立这三者之间的关系，再由程序根据这些关系判断用户能够访问哪些页面、执行哪些操作。

本节的目标，就是把这套权限管理机制需要的数据结构设计出来。

## 二、先理解用户、角色与权限的关系

在设计数据库之前，我们先不要急着写 Prisma 模型，而是从业务需求出发，分析需要保存哪些信息。

### 2.1 用户表：系统中的人是谁？

用户表保存系统中每一个使用者的基本信息。

对于一个企业管理系统，至少需要考虑以下字段：

| 字段 | 用途 | 设计考虑 |
|---|---|---|
| id | 用户唯一标识 | 使用系统内部 ID，不依赖用户名 |
| username | 登录用户名 | 必须唯一 |
| passwordHash | 密码哈希 | 保存经过安全哈希处理的密码，不能保存明文 |
| name | 用户姓名 | 用于页面展示 |
| email | 电子邮箱 | 可选，是否唯一需要结合业务要求 |
| phone | 联系电话 | 可选 |
| status | 用户状态 | 区分正常、停用等状态 |
| createdAt | 创建时间 | 记录账号创建时间 |
| updatedAt | 更新时间 | 记录账号最近修改时间 |

这里有几个值得注意的设计问题。

**第一，登录用户名与用户姓名不是同一个概念。**

username 用于识别登录账号，name 用于展示真实姓名。

例如，用户的登录名可以是 `zhangsan`，页面上显示的姓名是“张三”。姓名可能重复，但登录用户名通常要求唯一。

**第二，密码不能以明文保存。**

数据库应该保存密码哈希值，而不是用户输入的原始密码。登录时，通过成熟的密码哈希算法验证用户输入的密码是否正确。

实际项目中，可以使用 Argon2id 等适合密码存储的算法，并正确处理盐值与参数配置。

**第三，用户状态必须进入数据模型。**

用户离职、账号被停用时，我们通常不希望直接删除其记录，因为历史工时、项目任务、审批记录等业务数据可能仍然引用该用户。

因此，可以通过 status 字段控制账号是否允许登录，而不是通过删除用户来实现停用。

### 2.2 角色表：用户承担什么职责？

用户表解决了“谁在使用系统”的问题，但还没有解决权限分配的问题。

如果把所有权限直接放到用户表中，就会产生大量权限字段。例如：

```text
canCreateCustomer
canDeleteCustomer
canCreateProject
canAssignTask
canViewCost
```

随着业务功能增加，用户表会越来越复杂，而且每增加一种操作，都可能需要调整数据库结构。

因此，我们引入角色。

角色代表一组相对稳定的业务职责。例如：

| 角色 | 典型职责 |
|---|---|
| 销售 | 客户管理、商机管理 |
| 项目经理 | 项目管理、任务分配、工时审核 |
| 开发人员 | 任务查看、工时填写 |
| 系统管理员 | 用户管理、角色配置、系统设置 |

角色本身并不直接执行操作，它只是把一组权限组织起来，方便统一分配和维护。

例如，新增一名项目经理时，不需要逐项给他配置十几种权限，只需要为他分配“项目经理”角色即可。

当项目经理的职责发生变化时，我们可以调整这个角色关联的权限，而不必逐个修改所有用户。

### 2.3 用户与角色是什么关系？

这里需要根据业务场景判断是一对一，还是多对多。

如果每个用户只能拥有一个角色，可以设计成：

```text
User 1 ───── N Role
```

但在实际企业系统中，一个用户可能同时承担多种职责。

例如，一名技术负责人既需要开发人员的任务处理权限，也需要项目经理的任务分配权限。

因此，我们采用**用户与角色多对多关系**：

```text
User
  │
  ├── UserRole ── Role
  │
  └── UserRole ── Role
```

其中，UserRole 是连接用户与角色的中间表。

它解决了两个问题：

- 一个用户可以拥有多个角色。
- 一个角色可以分配给多个用户。

关系表还可以记录角色分配时间、分配人等信息，为后续审计提供基础。不过，本节先实现最基本的关联关系，后续再根据需要扩展。

### 2.4 角色与权限是什么关系？

接下来考虑角色和权限。

一个角色通常包含多个权限，而同一种权限也可能分配给多个角色。

例如：

- 销售角色拥有客户查看、客户创建、商机查看等权限。
- 项目经理角色拥有客户查看、项目管理、任务分配等权限。
- 系统管理员角色拥有用户管理、角色管理等权限。

因此，角色与权限同样是多对多关系。

我们使用 RolePermission 作为中间表。

```text
Role ── RolePermission ── Permission
```

这样，角色负责组织权限，权限负责表达系统允许执行的具体操作。

当需要调整角色职责时，只需要修改角色与权限之间的关联关系。

### 2.5 权限究竟应该如何定义？

这是整个权限模型中最重要的设计问题之一。

我们不能只定义“客户管理”这种笼统的权限，因为进入客户管理页面，并不意味着用户可以执行页面上的所有操作。

例如，客户管理页面可能包含：

- 查看客户列表。
- 查看客户详情。
- 创建客户。
- 修改客户。
- 删除客户。
- 导出客户数据。

如果这些操作共用一个权限，那么我们就无法实现精细化控制。

因此，我们需要将权限设计到具体的业务操作层面。

本课程采用“资源 + 操作”的方式定义权限。

例如：

| 权限编码 | 含义 |
|---|---|
| customer:read | 查看客户 |
| customer:create | 创建客户 |
| customer:update | 修改客户 |
| customer:delete | 删除客户 |
| project:read | 查看项目 |
| project:create | 创建项目 |
| task:assign | 分配任务 |
| worklog:create | 创建工时记录 |

这里的权限编码是系统内部稳定的标识，不应该直接使用中文名称作为程序判断依据。

权限名称可以修改，但权限编码一旦投入使用，就应当尽量保持稳定。

需要强调的是，**角色是权限的集合，用户通过角色获得权限，但最终是否允许执行某个操作，必须由服务端进行验证。**

前端隐藏按钮只是改善操作体验，不能代替后端的权限检查。

## 三、菜单、页面与业务操作如何关联权限？

有了用户、角色和权限的概念，还需要解决一个问题：菜单、页面、按钮和 API 到底是什么关系？

它们之间有关联，但不能简单地认为它们是同一种东西。

### 3.1 菜单是导航入口

菜单的主要作用是告诉用户系统中有哪些功能入口。

例如：

```text
工作台
客户管理
  ├── 客户列表
  └── 商机管理
项目管理
  ├── 项目列表
  └── 任务管理
系统设置
  ├── 用户管理
  └── 角色管理
```

系统根据用户的权限，决定向其展示哪些菜单。

但是，菜单本身并不是安全边界。

即使用户看不到“用户管理”菜单，也可能通过直接输入 URL 访问对应页面。因此，服务端仍然必须检查权限。

### 3.2 页面是业务功能的承载位置

页面通常对应一个业务功能，例如客户列表页、项目详情页、任务处理页。

一个页面可能包含多种操作，因此页面和权限也不一定是一对一关系。

例如，客户详情页可以允许某个用户查看客户信息，却不允许其修改或删除客户。

所以，我们不应该仅仅通过“是否有权访问页面”来决定用户是否有权执行页面上的所有操作。

### 3.3 业务操作才是权限校验的核心

对于真正影响业务数据的操作，必须在服务端校验对应权限。

例如：

```text
打开客户列表
    ↓
校验 customer:read
    ↓
允许查询客户数据

点击创建客户
    ↓
校验 customer:create
    ↓
允许创建客户记录

点击删除客户
    ↓
校验 customer:delete
    ↓
允许执行删除操作
```

如果用户没有对应权限，即使绕过前端页面，直接调用 API，也应该被服务端拒绝。

另外，权限校验并不等于数据范围校验。

例如，开发人员可能拥有 `project:read` 权限，但只能查看自己参与的项目；项目经理可能可以查看其负责的项目。

这种限制涉及数据范围、组织范围或资源归属，需要在权限模型之上进一步实现。

### 3.4 菜单和权限应该如何关联？

对于本课程，我们采用下面的设计原则：

- 菜单负责组织导航结构。
- 权限负责控制功能操作。
- 菜单可以关联一个用于控制显示的权限。
- 页面和 API 分别在适当的位置执行访问控制。
- 业务数据的访问范围由服务端单独校验。

菜单可以关联权限，但不必强制要求每个菜单都对应一个独立权限。

例如，父级菜单“项目管理”可能只是一个分组，它的子菜单分别关联项目查看、任务查看等权限。

这也意味着，菜单、页面、权限并不是简单的一一对应关系。

我们先建立用户、角色、权限三套基础模型，再逐步引入菜单模型和 API 权限检查，避免一开始就把所有问题混在一起。

## 四、把业务关系转换成数据模型

现在，我们已经明确了需要解决的业务问题。

接下来，把这些关系整理成数据库设计。

本节需要创建五张核心表：

| 模型 | 作用 |
|---|---|
| User | 保存用户账号信息 |
| Role | 保存角色定义 |
| Permission | 保存权限定义 |
| UserRole | 关联用户与角色 |
| RolePermission | 关联角色与权限 |

整体关系如下：

```text
User
  │
  └── UserRole ── Role
                    │
                    └── RolePermission ── Permission
```

这里的 UserRole 和 RolePermission 是显式中间表。

我们没有直接使用 Prisma 隐式多对多关系，是因为显式中间表能够明确表达数据库约束，也便于以后添加授权时间、授权人等审计字段。

接下来开始编写 Prisma Schema。

## 五、使用 Prisma 定义用户、角色与权限

### 5.1 定义用户模型 User

打开项目中的 `prisma/schema.prisma`，在现有模型后面添加以下定义。

注意：如果项目已经定义了 User 模型，不要重复创建，而是将需要的字段合并到现有模型中。

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}

model User {
  id           String     @id @default(cuid())
  username     String     @unique @db.VarChar(50)
  passwordHash String     @db.VarChar(255)
  name         String     @db.VarChar(100)
  email        String?    @db.VarChar(255)
  phone        String?    @db.VarChar(30)
  status       UserStatus @default(ACTIVE)

  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt

  userRoles    UserRole[]

  @@index([status])
}
```

逐项解释几个关键定义。

`@id` 表示主键，`@default(cuid())` 表示由 Prisma 生成唯一标识。

`@unique` 表示用户名不能重复。即使两个请求同时尝试创建相同的用户名，数据库也会通过唯一约束拒绝其中一个请求。

`passwordHash` 保存密码哈希，而不是明文密码。

`UserStatus` 使用枚举定义账号状态，避免在程序中随意使用 `"正常"`、`"禁用"`、`"停用"` 等不同字符串。

`userRoles UserRole[]` 表示一个用户可以关联多条用户角色关系。

`@@index([status])` 为状态字段建立索引，便于常见的状态筛选。但是否保留该索引，最终应结合查询频率和数据规模判断。

这里没有把 `email` 设置为唯一字段，因为不同企业对邮箱是否必填、是否允许共享邮箱的要求并不相同。如果业务明确要求邮箱唯一，应再添加相应约束。

### 5.2 定义角色模型 Role

角色用于描述系统中的业务职责。

```prisma
model Role {
  id          String   @id @default(cuid())
  code        String   @unique @db.VarChar(50)
  name        String   @db.VarChar(100)
  description String?  @db.VarChar(500)

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  userRoles       UserRole[]
  rolePermissions RolePermission[]
}
```

其中：

- `code` 是角色编码，例如 `SALES`、`PROJECT_MANAGER`、`DEVELOPER`。
- `name` 是角色显示名称，例如“销售”“项目经理”“开发人员”。
- `description` 用于说明角色的职责。

为什么角色还需要独立的 `code`？

因为角色名称可能修改。例如，“开发人员”以后可能改名为“研发工程师”。如果程序使用角色名称判断权限，就容易受到名称调整的影响。

程序和初始化脚本应优先使用稳定的角色编码。

同样，角色编码必须唯一，避免系统中出现两个相同编码的角色。

### 5.3 定义权限模型 Permission

权限用于描述系统允许执行的具体操作。

```prisma
model Permission {
  id          String   @id @default(cuid())
  code        String   @unique @db.VarChar(100)
  name        String   @db.VarChar(100)
  description String?  @db.VarChar(500)

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  rolePermissions RolePermission[]
}
```

例如，系统可以预先定义以下权限：

```text
customer:read
customer:create
customer:update
customer:delete

project:read
project:create

task:read
task:assign

worklog:create
```

这里需要区分两个概念：

**权限模型定义的是权限记录的结构，而不是自动生成所有业务权限。**

实际项目中，权限通常由系统初始化脚本或权限管理模块创建。业务开发人员需要先明确系统支持哪些操作，再建立对应的权限记录。

不建议让普通用户随意创建任意权限编码，否则可能出现代码根本不识别、无法执行的权限。

### 5.4 定义用户角色关系 UserRole

用户和角色之间是多对多关系，需要一张中间表。

```prisma
model UserRole {
  userId    String
  roleId    String
  createdAt DateTime @default(now())

  user User @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  role Role @relation(
    fields: [roleId],
    references: [id],
    onDelete: Cascade
  )

  @@id([userId, roleId])
  @@index([roleId])
}
```

这里有两个关键设计。

第一，`@@id([userId, roleId])` 使用两个字段组成联合主键。

这意味着同一个用户不能重复分配同一个角色。

第二，`@relation` 建立了真正的数据库关联。

`userId` 必须引用存在的用户，`roleId` 必须引用存在的角色。数据库外键约束可以防止关系表引用不存在的记录。

`onDelete: Cascade` 表示删除用户或角色时，自动删除对应的关系记录，而不是删除其他业务数据。

例如，删除用户时，其 UserRole 记录会被删除，但不会因此删除该用户创建的项目、工时或历史业务记录。

对于已经投入使用的企业系统，还应根据审计要求决定是否允许删除角色。很多情况下，停用角色或限制删除比直接删除更加合适。

### 5.5 定义角色权限关系 RolePermission

角色和权限之间同样采用多对多关系。

```prisma
model RolePermission {
  roleId       String
  permissionId String
  createdAt    DateTime @default(now())

  role Role @relation(
    fields: [roleId],
    references: [id],
    onDelete: Cascade
  )

  permission Permission @relation(
    fields: [permissionId],
    references: [id],
    onDelete: Cascade
  )

  @@id([roleId, permissionId])
  @@index([permissionId])
}
```

这个模型与 UserRole 非常相似。

区别在于：

- UserRole 表示用户拥有哪些角色。
- RolePermission 表示角色包含哪些权限。

两张关系表分别承担不同职责，不应该混为一谈。

例如，给项目经理角色增加 `task:assign` 权限，只需要建立一条 RolePermission 记录。所有拥有该角色的用户，就可以通过角色获得这项权限。

注意，实际请求能否成功，还需要检查用户状态、会话有效性、资源归属和数据范围等条件。

## 六、理解数据库约束为什么重要

到这里，我们已经完成了五张表的模型设计。但不能认为字段定义完成，就代表数据模型已经可靠。

真正的数据库设计，还需要考虑如何避免错误数据进入系统。

### 6.1 主键约束

每张核心表都需要唯一标识一条记录。

例如：

```prisma
id String @id @default(cuid())
```

主键保证每条用户、角色和权限记录都有独立标识。

### 6.2 唯一约束

用户名、角色编码、权限编码分别需要唯一约束。

```prisma
username String @unique
code     String @unique
```

需要注意，虽然不同模型中都可以存在名为 `code` 的字段，但唯一约束只在各自的数据库表内生效。

因此，角色编码 `PROJECT_MANAGER` 与权限编码 `PROJECT_MANAGER` 即使相同，也不会因为这两个约束而互相冲突。

### 6.3 外键约束

中间表中的关联字段必须引用真实存在的记录。

例如：

```prisma
user User @relation(
  fields: [userId],
  references: [id],
  onDelete: Cascade
)
```

如果某个用户不存在，数据库就不应该允许建立指向该用户的角色关联。

这能够避免关系表中出现无法追溯到真实用户的孤立记录。

### 6.4 联合主键约束

用户和角色之间的关系具有唯一性。

```prisma
@@id([userId, roleId])
```

同一个用户可以拥有多个不同角色，但同一个用户不能重复关联同一个角色。

RolePermission 使用相同的设计思路，防止同一个角色重复关联同一个权限。

### 6.5 索引约束与查询效率

索引不是越多越好。

本节中，我们为用户状态、角色关联字段和权限关联字段建立了必要的辅助索引。

它们可以帮助常见的筛选与关联查询，但也会增加写入和存储开销。后续应结合实际查询、执行计划和数据规模继续优化。

### 6.6 为什么不能只依靠前端？

假设前端在用户管理页面中隐藏了“删除用户”按钮。

这只能说明页面没有向用户展示删除入口，并不能阻止用户直接请求删除接口。

真正可靠的权限控制必须形成完整链路：

1. 用户通过身份认证，建立有效会话。
2. 服务端识别当前用户。
3. 服务端读取或验证其角色与权限。
4. 服务端检查当前业务操作是否被允许。
5. 必要时继续检查目标数据是否属于允许访问的范围。
6. 通过检查后才执行数据库操作。

因此，本节设计的数据库模型只是权限体系的基础。后续还需要通过服务端代码将模型真正应用到业务请求中。

## 七、执行 Prisma 迁移，创建数据库表

模型编写完成后，需要将 Prisma Schema 同步到 PostgreSQL 数据库。

在项目根目录执行：

```bash
pnpm prisma format
```

这条命令用于格式化 Prisma Schema，便于检查模型结构。

然后执行：

```bash
pnpm prisma validate
```

用于检查 Schema 是否符合 Prisma 的语法与关系定义要求。

确认没有错误后，再执行：

```bash
pnpm prisma migrate dev --name add_user_role_permission
```

这条命令会根据 Schema 与当前数据库之间的差异生成迁移，并在开发数据库中应用迁移。

迁移完成后，可以查看生成的迁移文件，确认数据库中创建了对应的表、主键、唯一约束、索引和外键。

需要注意：如果现有项目已经有其他业务表，Prisma Schema 中必须保留已有模型，不能为了添加权限模型而覆盖原有定义。

如果项目使用的是生产数据库，则不应直接运行 `migrate dev`，而应采用经过审核的迁移文件，并在适当的部署流程中执行 `prisma migrate deploy`。

## 八、验证数据模型是否符合预期

数据库迁移成功，并不意味着设计一定正确。

我们还需要通过实际操作验证约束是否生效。

建议至少完成以下测试：

**测试一：创建两个相同用户名的用户。**

预期结果：第二次创建失败，数据库拒绝重复用户名。

**测试二：创建两个相同编码的角色。**

预期结果：第二次创建失败。

**测试三：给同一个用户重复分配同一个角色。**

预期结果：第二次插入失败，联合主键阻止重复关联。

**测试四：建立不存在的用户与角色之间的关联。**

预期结果：数据库外键约束拒绝无效关联。

**测试五：给角色关联多个权限。**

预期结果：同一个角色可以拥有多个不同权限，关联记录能够正常保存。

**测试六：删除一个用户后检查关联关系。**

预期结果：对应的 UserRole 关系记录被删除，其他用户、角色以及业务数据不会因为这条关系而被错误删除。

这些测试的目的，不只是确认程序能否运行，更是验证数据库设计是否真正表达了业务规则。

## 九、本节总结

本节从一个真实的企业管理系统出发，将用户、角色与权限之间的业务关系转换成了 Prisma 数据模型。

我们最终建立了五张核心表：

- User：保存用户账号。
- Role：定义业务角色。
- Permission：定义具体权限。
- UserRole：维护用户与角色之间的关联。
- RolePermission：维护角色与权限之间的关联。

通过主键、唯一约束、外键、联合主键和索引，我们让数据库不仅能够保存数据，还能在数据层面约束部分业务规则。

更重要的是，我们明确了三条设计原则：

第一，**用户、角色和权限必须分离**，避免把权限判断写死在用户或角色名称中。

第二，**菜单展示与服务端权限校验必须分开**，隐藏按钮不等于保护业务接口。

第三，**权限控制与数据范围控制是两个层面**，拥有某项业务权限，并不代表可以访问所有业务数据。

到这里，我们已经完成了权限体系的数据基础。

下一步，需要继续解决一个实际问题：用户登录成功后，系统如何识别当前用户，读取他的角色与权限，并据此决定显示哪些菜单、允许调用哪些业务接口？

这就是接下来实现登录认证、会话管理与权限加载的基础。
