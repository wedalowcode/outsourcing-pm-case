# 6.6 部门管理实战：为服务层编写单元测试

## 一、前言

上一篇，我们完成了部门管理的三个服务函数：

- `createDept`：新增部门，负责校验输入、分配编码、计算排序并保存数据。
- `updateDept`：修改部门，负责维护部门属性、检查层级循环，以及同步更新下级部门编码。
- `deleteDept`：删除部门，负责检查下级部门并执行删除。

至此，部门管理的服务层已经具备了基本的业务能力。

但还有一个问题：**我们怎么知道这些代码真的符合预期？**

例如，新增部门时，如果名称为空，系统是否会拒绝保存？修改部门时，如果将自己的下级设为上级，系统是否能识别出循环？移动一个部门后，它下面的多级子部门是否都能正确更新编码？

如果每次修改代码，都要打开页面、填写表单、点击按钮，再逐一检查结果，不仅耗时，而且很容易遗漏边界情况。

因此，本篇开始为服务层建立自动化测试。

我们将从实际业务出发，完成三个任务：

1. 设计测试用例，明确每个服务函数应该验证什么。
2. 使用 Vitest 编写测试，通过模拟数据库隔离业务逻辑。
3. 执行测试，根据结果判断代码是否符合预期，并理解单元测试的能力边界。

本篇不追求测试数量，而是建立一套可以迁移到客户、项目、任务等其他业务模块的测试方法。

## 二、先理解单元测试在测试什么

### 2.1 从一个新增部门的需求开始

假设我们有这样一个需求：

新增部门时，部门名称不能为空；如果没有指定排序值，则自动取同级最大排序值加 10；如果上级部门不存在，则拒绝新增。

我们可以把它拆成三个问题：

| 业务规则 | 测试输入 | 预期结果 |
| --- | --- | --- |
| 名称不能为空 | 名称为空字符串 | 抛出业务错误 |
| 排序自动计算 | 未传排序值，同级最大值为 30 | 使用排序值 40 |
| 上级必须存在 | 传入不存在的上级 ID | 新增失败 |

这就是测试用例的基本思路：

**输入一个明确的条件，执行一段代码，检查实际结果是否符合预期。**

在 Vitest 中，最常用的三个方法是：

```typescript
expect(actual).toBe(expected);

expect(actual).toEqual(expected);

await expect(promise).rejects.toThrow("错误提示");
```

它们分别用于判断：

- `toBe`：比较基本值或对象引用。
- `toEqual`：比较对象、数组等结构是否相等。
- `rejects.toThrow`：判断异步操作是否以异常结束，并检查错误信息。

例如：

```typescript
expect(2 + 3).toBe(5);

expect({ name: "技术部" }).toEqual({
  name: "技术部",
});
```

这两个例子虽然简单，但已经体现了测试的基本结构：执行操作，然后对结果作出断言。

### 2.2 为什么不直接连接数据库？

本篇要测试的是服务层的业务逻辑。

如果每次运行测试都需要启动 PostgreSQL、准备部门数据、清理历史记录，测试成本就会增加，而且测试结果还可能受到环境影响。

因此，我们先使用**单元测试**，将数据库替换为模拟对象。

例如，测试 `createDept` 时，我们可以让模拟数据库直接返回一条部门记录，然后检查服务函数是否正确调用了编码分配、排序计算和数据写入。

这样就能快速验证业务分支，而不需要真的创建数据库记录。

不过要注意：模拟数据库并不能证明真实数据库事务一定能够回滚。事务、外键、唯一约束等行为，还需要通过后续的集成测试验证。

本篇先解决第一层问题：服务函数的业务行为是否正确。

## 三、设计测试用例

正式写代码前，我们先根据三个服务函数的职责设计测试用例。

### 3.1 新增部门 `createDept`

新增部门的流程是：

```text
接收输入
  ↓
校验数据
  ↓
开启事务
  ↓
分配编码、确定排序
  ↓
写入部门
  ↓
返回结果
```

对应的测试用例如下：

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| C01 | 部门名称为空 | 抛出业务错误 |
| C02 | 部门名称超过 50 个 UTF-16 代码单元 | 抛出业务错误 |
| C03 | 未指定排序值 | 调用排序函数计算默认值 |
| C04 | 指定排序值为 0 | 保留排序值 0 |
| C05 | 未指定状态 | 默认使用启用状态 |
| C06 | 上级部门不存在 | 返回业务错误，不插入部门 |
| C07 | 数据库写入失败 | 异常向外传播 |

这里不必为每一个字段组合都编写测试。我们优先覆盖业务规则、默认值以及容易出现错误的边界条件。

例如，排序值为 `0` 就是一个很有价值的测试场景。因为如果代码错误地使用 `||` 处理默认值，`0` 就会被当成没有提供。

### 3.2 修改部门 `updateDept`

修改部门比新增部门复杂，除了校验输入，还要维护层级关系。

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| U01 | 部门不存在 | 抛出业务错误 |
| U02 | 只修改部门名称 | 保留原编码 |
| U03 | 未提交描述 | 保留原描述 |
| U04 | 主动清空描述 | 将描述更新为 `null` |
| U05 | 将自己设为上级 | 拒绝修改 |
| U06 | 将自己的下级设为上级 | 拒绝修改 |
| U07 | 修改上级且未指定排序 | 重新计算排序值 |
| U08 | 修改上级并指定排序 | 使用指定排序值 |
| U09 | 移动部门后存在多级下级 | 正确同步编码前缀 |
| U10 | 下级编码不符合旧前缀 | 抛出业务错误 |

其中，U06 和 U09 尤其重要。

只测试“自己不能成为自己的上级”，不足以证明防环逻辑有效。真正需要验证的是：系统能否发现通过多级关系形成的间接循环。

同样，编码同步也不能只测试一个直接下级。我们还要验证孙级部门的编码是否跟着变化。

### 3.3 删除部门 `deleteDept`

删除操作需要验证的场景相对集中。

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| D01 | 部门不存在 | 抛出业务错误 |
| D02 | 存在下级部门 | 拒绝删除 |
| D03 | 不存在下级部门 | 调用删除方法 |
| D04 | 数据库删除失败 | 异常向外传播 |

到这里，我们已经将三个服务函数转换成了一份测试清单。

这份清单不是代码，而是测试的设计依据。后面编写测试时，每个测试用例都应该能对应到其中一个业务规则。

## 五、构造模拟数据库

### 5.1 为什么要模拟数据库？

回顾一下服务函数的调用方式：

```typescript
return db.$transaction(async (tx) => {
  // 业务逻辑
});
```

服务函数依赖两个对象：

- `db`：提供事务入口。
- `tx`：在事务回调中执行具体数据库操作。

如果要进行单元测试，我们可以模拟这两个对象，让事务回调接收到一个假的数据库客户端。

例如：

```typescript
const fakeTx = {
  dept: {
    findUnique: vi.fn(),
    create: vi.fn(),
    update: vi.fn(),
    delete: vi.fn(),
    findFirst: vi.fn(),
    findMany: vi.fn(),
  },
};
```

这里的 `vi.fn()` 会创建一个模拟函数。

我们既可以指定它返回什么数据，也可以检查它是否被调用过、调用了几次以及接收了什么参数。

### 5.2 模拟事务入口

为了让服务函数可以正常执行，我们还需要模拟 `$transaction`。

本篇采用的方式是：让模拟事务立即执行传入的回调，并把 `fakeTx` 作为参数传进去。

这样，服务函数就可以像平时一样执行，而不需要连接真实数据库。

但必须明确：**这种模拟只验证事务回调里的业务行为，不会真的执行数据库事务，也不会自动回滚已经修改的模拟数据。**

在单元测试中，我们会为每个用例重新配置模拟对象，避免测试之间相互影响。

### 5.3 编写测试文件的基础结构

在 `tests/dept-service.test.ts` 中写入：

```typescript
import {
  beforeEach,
  describe,
  expect,
  it,
  vi,
} from "vitest";

const mocks = vi.hoisted(() => ({
  db: {
    $transaction: vi.fn(),
  },
  nextDeptCode: vi.fn(),
  nextSort: vi.fn(),
}));

vi.mock("@/lib/db", () => ({
  db: mocks.db,
}));

vi.mock("@/server/dept/dept-tools", () => ({
  nextDeptCode: mocks.nextDeptCode,
  nextSort: mocks.nextSort,
  ROOT_SCOPE: "__ROOT__",
}));

import {
  createDept,
  updateDept,
  deleteDept,
} from "@/server/dept/service";
```

这段代码涉及两个知识点。

**第一，`vi.hoisted`。**

Vitest 会对模块模拟进行提升处理。使用 `vi.hoisted` 创建共享的模拟对象，可以避免模拟工厂执行时访问尚未初始化的变量。

**第二，`vi.mock`。**

这里将真实数据库和部门工具函数替换为模拟对象。

这样测试服务层时，我们可以单独控制编码函数、排序函数的返回值，不必再次测试它们内部的实现。

上一篇已经测试过 `formatCode`、`nextDeptCode` 和 `nextSort`，本篇关注的是服务层如何正确使用这些工具。

### 5.4 创建 `fakeTx`

继续在同一个文件中添加：

```typescript
function fakeTx() {
  return {
    dept: {
      findUnique: vi.fn(),
      findFirst: vi.fn(),
      findMany: vi.fn(),
      create: vi.fn(),
      update: vi.fn(),
      delete: vi.fn(),
    },
  };
}

let tx: ReturnType<typeof fakeTx>;

beforeEach(() => {
  vi.clearAllMocks();

  tx = fakeTx();

  mocks.db.$transaction.mockImplementation(
    async (callback: (tx: typeof tx) => Promise<unknown>) => {
      return callback(tx);
    }
  );

  mocks.nextDeptCode.mockResolvedValue("D001");
  mocks.nextSort.mockResolvedValue(10);
});
```

每次执行测试之前，我们都会重新创建一个 `tx`，并设置默认的编码和排序返回值。

不过，上面的事务回调类型有一个 TypeScript 细节：`typeof tx` 在回调参数位置可能产生自引用类型问题。为避免这个问题，可以直接采用下面这种更稳妥的写法替换事务模拟：

```typescript
mocks.db.$transaction.mockImplementation(
  async (callback: (tx: any) => Promise<unknown>) => {
    return callback(tx);
  }
);
```

这里的 `any` 只用于测试基础设施中的模拟边界，不建议扩散到正式业务代码。

至此，测试环境已经具备三个能力：

1. 可以控制数据库查询结果。
2. 可以检查数据库写入是否发生。
3. 可以让服务函数执行事务回调。

## 六、测试新增部门 `createDept`

### 6.1 测试名称为空

先验证最简单的一条业务规则。

```typescript
describe("createDept", () => {
  it("名称为空时应拒绝新增", async () => {
    await expect(
      createDept({
        name: "   ",
        parentId: null,
      })
    ).rejects.toThrow("请填写部门名称");

    expect(
      mocks.db.$transaction
    ).not.toHaveBeenCalled();
  });
});
```

这个测试不仅检查了错误提示，还检查事务没有启动。

为什么要检查这一点？

因为名称为空时，服务函数应该在业务校验阶段就终止操作，不应该继续访问数据库。

如果错误信息正确，但事务已经启动并执行了一系列数据库操作，仍然说明实现可能存在不必要的副作用。

### 6.2 测试默认排序和默认状态

接下来，测试新增成功的情况。

```typescript
it("未指定排序和状态时使用默认值", async () => {
  tx.dept.create.mockResolvedValue({
    id: "dept-1",
    name: "技术部",
    code: "D001",
    parentId: null,
    sort: 10,
    status: 1,
    description: null,
  });

  const result = await createDept({
    name: " 技术部 ",
    parentId: null,
  });

  expect(result.name).toBe("技术部");
  expect(result.code).toBe("D001");

  expect(mocks.nextDeptCode).toHaveBeenCalledWith(
    tx,
    null
  );

  expect(mocks.nextSort).toHaveBeenCalledWith(
    tx,
    null
  );

  expect(tx.dept.create).toHaveBeenCalledWith({
    data: {
      name: "技术部",
      code: "D001",
      parentId: null,
      sort: 10,
      status: 1,
      description: null,
    },
  });
});
```

这个测试同时验证了多个行为：

- 部门名称经过了 `trim()` 处理。
- 编码函数使用了正确的上级 ID。
- 排序函数被调用。
- 未传状态时默认启用。
- 最终传给 Prisma 的数据符合预期。

这里使用 `toHaveBeenCalledWith`，可以检查模拟函数接收到的参数是否与预期一致。

### 6.3 测试排序值为 0

再补充一个边界测试：

```typescript
it("显式传入排序值 0 时应保留 0", async () => {
  tx.dept.create.mockResolvedValue({
    id: "dept-2",
    name: "临时部门",
    code: "D001",
    parentId: null,
    sort: 0,
    status: 1,
    description: null,
  });

  await createDept({
    name: "临时部门",
    parentId: null,
    sort: 0,
  });

  expect(mocks.nextSort).not.toHaveBeenCalled();

  expect(tx.dept.create).toHaveBeenCalledWith({
    data: expect.objectContaining({
      sort: 0,
    }),
  });
});
```

为什么需要专门测试 `0`？

因为下面两种写法的行为不同：

```typescript
const sort1 = input.sort ?? 10;
const sort2 = input.sort || 10;
```

当 `input.sort` 为 `0` 时：

- `sort1` 的结果是 `0`。
- `sort2` 的结果是 `10`。

这就是为什么测试不应只覆盖常见输入，还要覆盖可能改变程序行为的边界值。

### 6.4 测试数据库写入失败

```typescript
it("部门写入失败时应向外抛出异常", async () => {
  tx.dept.create.mockRejectedValue(
    new Error("database failure")
  );

  await expect(
    createDept({
      name: "技术部",
      parentId: null,
    })
  ).rejects.toThrow("database failure");
});
```

这个测试验证异常不会被服务函数意外吞掉。

但请注意：由于当前测试中的事务只是模拟回调，因此它不能证明计数器会真实回滚。真实事务回滚需要在 PostgreSQL 集成测试中验证。

## 七、测试修改部门 `updateDept`

### 7.1 测试部门不存在

```typescript
describe("updateDept", () => {
  it("部门不存在时应拒绝修改", async () => {
    tx.dept.findUnique.mockResolvedValue(null);

    await expect(
      updateDept("missing-id", {
        name: "技术部",
        parentId: null,
      })
    ).rejects.toThrow(
      "部门不存在，可能已被删除"
    );

    expect(tx.dept.update).not.toHaveBeenCalled();
  });
});
```

这个测试验证了服务函数会先检查记录是否存在。

如果部门不存在，后续更新操作就不应该发生。

### 7.2 测试只修改名称时保留编码

```typescript
it("只修改名称时保留原编码", async () => {
  tx.dept.findUnique.mockResolvedValue({
    id: "dept-1",
    name: "技术部",
    code: "D001",
    parentId: null,
    sort: 10,
    status: 1,
    description: "原始描述",
  });

  tx.dept.update.mockResolvedValue({
    id: "dept-1",
    name: "研发部",
    code: "D001",
    parentId: null,
    sort: 10,
    status: 1,
    description: "原始描述",
  });

  await updateDept("dept-1", {
    name: "研发部",
    parentId: null,
  });

  expect(mocks.nextDeptCode).not.toHaveBeenCalled();

  expect(tx.dept.update).toHaveBeenCalledWith({
    where: { id: "dept-1" },
    data: expect.objectContaining({
      name: "研发部",
      code: "D001",
      parentId: null,
      description: "原始描述",
    }),
  });
});
```

这个测试验证了一条非常重要的规则：编码由系统维护，但并不是每次修改都要重新生成。

如果只是修改名称，编码应该保持不变。

### 7.3 测试将自己的下级设为上级

这个场景需要模拟一棵简单的部门树。

```text
技术部
└── 开发组
    └── 前端组
```

现在尝试将“技术部”的上级设为“前端组”。

测试代码如下：

```typescript
it("不能将自己的下级设为上级", async () => {
  tx.dept.findUnique.mockResolvedValue({
    id: "tech",
    name: "技术部",
    code: "D001",
    parentId: null,
    sort: 10,
    status: 1,
    description: null,
  });

  tx.dept.findMany.mockResolvedValue([
    { id: "tech", parentId: null, code: "D001" },
    { id: "dev", parentId: "tech", code: "D001-01" },
    {
      id: "frontend",
      parentId: "dev",
      code: "D001-01-01",
    },
  ]);

  await expect(
    updateDept("tech", {
      name: "技术部",
      parentId: "frontend",
    })
  ).rejects.toThrow(
    "不能把自己（或其下级）设为上级，会形成循环"
  );

  expect(tx.dept.update).not.toHaveBeenCalled();
});
```

这里的关键不在于模拟了多少条记录，而在于测试数据能否准确表达业务场景。

只有构造出多级部门树，才能验证防环逻辑是否真的能识别间接循环。

### 7.4 测试移动部门后同步下级编码

接下来验证更复杂的业务规则。

假设原来的部门树是：

```text
技术部 D001
└── 开发组 D001-01
    └── 前端组 D001-01-01
```

现在将“开发组”移动到新的顶级部门下，它的编码变为 `D002`。

预期结果是：

```text
新部门 D002
└── 开发组 D002-01
    └── 前端组 D002-01-01
```

在单元测试中，我们不需要真的修改数据库，只要模拟查询结果，并检查更新调用即可。

```typescript
it("移动部门时应同步更新多级下级编码", async () => {
  tx.dept.findUnique.mockResolvedValue({
    id: "dev",
    name: "开发组",
    code: "D001-01",
    parentId: "tech",
    sort: 10,
    status: 1,
    description: null,
  });

  tx.dept.findMany
    .mockResolvedValueOnce([
      { id: "tech", parentId: null, code: "D001" },
      { id: "dev", parentId: "tech", code: "D001-01" },
      {
        id: "frontend",
        parentId: "dev",
        code: "D001-01-01",
      },
    ])
    .mockResolvedValueOnce([
      { id: "tech", parentId: null, code: "D001" },
      { id: "dev", parentId: null, code: "D002" },
      {
        id: "frontend",
        parentId: "dev",
        code: "D001-01-01",
      },
    ]);

  mocks.nextDeptCode.mockResolvedValue("D002");
  mocks.nextSort.mockResolvedValue(20);

  tx.dept.update.mockResolvedValue({
    id: "dev",
    name: "开发组",
    code: "D002",
    parentId: null,
    sort: 20,
    status: 1,
    description: null,
  });

  await updateDept("dev", {
    name: "开发组",
    parentId: null,
  });

  expect(tx.dept.update).toHaveBeenCalledWith({
    where: { id: "dev" },
    data: expect.objectContaining({
      code: "D002",
      parentId: null,
      sort: 20,
    }),
  });

  expect(tx.dept.update).toHaveBeenCalledWith({
    where: { id: "frontend" },
    data: {
      code: "D002-01-01",
    },
  });
});
```

这里通过 `mockResolvedValueOnce` 为两次 `findMany` 调用提供不同的数据：

- 第一次为防环逻辑提供原始部门树。
- 第二次为编码同步逻辑提供原始编码快照。

这样可以让测试过程与服务函数的实际执行顺序对应起来。

这个用例也说明了：当一个服务函数涉及多个内部步骤时，测试数据必须与调用顺序匹配，否则可能出现测试失败并非业务逻辑错误，而是模拟配置不正确的情况。

## 八、测试删除部门 `deleteDept`

### 8.1 存在下级时禁止删除

```typescript
describe("deleteDept", () => {
  it("存在下级部门时拒绝删除", async () => {
    tx.dept.findUnique.mockResolvedValue({
      id: "tech",
      name: "技术部",
      code: "D001",
      parentId: null,
      sort: 10,
      status: 1,
      description: null,
    });

    tx.dept.findFirst.mockResolvedValue({
      id: "dev",
    });

    await expect(
      deleteDept("tech")
    ).rejects.toThrow(
      "存在下级部门，不能删除，建议改用停用"
    );

    expect(tx.dept.delete).not.toHaveBeenCalled();
  });
});
```

这个测试验证了删除前置条件。

即使调用方绕过前端页面，直接请求删除接口，服务层也必须拒绝删除仍然有下级的部门。

### 8.2 没有下级时允许删除

```typescript
it("没有下级部门时执行删除", async () => {
  tx.dept.findUnique.mockResolvedValue({
    id: "dev",
    name: "开发组",
    code: "D001-01",
    parentId: "tech",
    sort: 10,
    status: 1,
    description: null,
  });

  tx.dept.findFirst.mockResolvedValue(null);

  tx.dept.delete.mockResolvedValue({
    id: "dev",
    name: "开发组",
  });

  const result = await deleteDept("dev");

  expect(result.id).toBe("dev");

  expect(tx.dept.delete).toHaveBeenCalledWith({
    where: { id: "dev" },
  });
});
```

这个用例验证正常删除路径。

测试不仅要验证错误场景，也要验证正常场景，否则代码即使拒绝了所有操作，也可能让测试全部通过。

### 9.1 如何判断测试是否通过？

如果全部测试通过，Vitest 会显示测试文件以及通过的测试数量。

需要注意，本篇列出的代码片段是用于讲解不同测试场景的分段示例，**不是可以直接拼接后保证一次运行通过的完整测试文件**。实际项目中应将这些用例合并到同一文件，并确保模拟对象、类型定义和调用顺序一致。

执行时，如果出现失败，不要马上修改业务代码，先区分问题属于哪一类：

1. **业务逻辑错误**：实际结果与需求不符，应修改服务函数。
2. **模拟配置错误**：模拟数据没有覆盖实际调用路径，应修正测试配置。
3. **类型错误**：模拟对象与正式代码的接口不一致，应补齐类型或调整测试辅助函数。
4. **环境问题**：Vitest 配置、路径别名或依赖安装存在问题，应先修复测试环境。

测试失败本身不是坏事。它的价值在于把原本需要人工发现的问题提前暴露出来。

## 十、单元测试不能证明什么？

本篇使用模拟数据库，确实能够快速验证业务逻辑，但它有明确的边界。

例如，新增部门时，真实代码执行的是：

```typescript
await tx.deptCodeCounter.upsert({
  // ...
});

await tx.dept.create({
  // ...
});
```

如果第二步失败，真实 PostgreSQL 事务应当回滚第一步。

但在单元测试里，我们只是执行了一个 JavaScript 回调。模拟对象不会自动撤销已经发生的变化。

因此，下面这些问题需要通过真实数据库的集成测试验证：

- 计数器更新和部门插入是否真正处于同一事务。
- 唯一约束冲突时，数据库是否回滚整个操作。
- 下级编码更新到一半失败时，所有更新是否回滚。
- 外键约束是否阻止非法删除。
- 并发创建或移动部门时，是否会发生编码冲突或组织关系竞争。

这也是为什么软件测试不能只依赖一种测试类型。

**单元测试负责快速验证局部规则，集成测试负责验证多个真实组件协作时的行为。**

后续我们可以专门建立测试数据库，为关键事务场景编写集成测试，而不必把所有测试都放进当前这篇教程。

## 十一、本篇小结

本篇围绕部门管理的三个服务函数，建立了自动化测试的基本思路。

我们先从业务需求出发设计测试用例，再使用 Vitest 模拟数据库和工具函数，分别验证新增、修改与删除过程中的关键行为。

通过这些实践，我们可以得到三个重要认识：

**第一，测试不是为了证明代码能够运行，而是为了验证业务规则是否得到正确实现。**

**第二，好的测试用例来自对业务边界的理解。** 例如排序值为 0、间接循环、描述字段清空以及多级编码同步，都比简单重复测试正常输入更有价值。

**第三，单元测试和集成测试解决的是不同问题。** 模拟数据库可以快速验证服务层逻辑，但事务回滚、唯一约束和并发行为仍然需要真实数据库验证。

到这里，部门管理服务层的核心业务规则已经有了相应的测试设计。
