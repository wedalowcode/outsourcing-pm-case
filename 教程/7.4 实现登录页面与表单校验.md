# 7.4 实现登录页面与表单校验

## 一、前言：登录页面不只是两个输入框

上一节，我们通过 Prisma 初始化了用户、角色与权限数据，并创建了初始管理员账号。

现在，数据库中已经有了可以登录的用户，但用户还无法通过页面与系统交互。

本节开始实现登录功能的第一步：构建登录页面，并对用户提交的数据进行校验。

对于一个现代后台管理系统，登录页面看似简单，实际上需要考虑多个问题：

- 页面应该如何布局，才能与后续的后台管理界面保持统一？
- 用户名和密码为空时，应该如何提示？
- 用户输入了不符合要求的数据，应该在哪里拦截？
- 前端校验通过后，服务端是否还需要重新校验？
- 用户输入错误的密码时，应该如何提示？
- 用户名不存在、密码错误或账号被停用时，是否应该返回不同的提示？

这些问题如果没有提前考虑，后续实现登录接口时就容易出现重复校验、错误提示不统一、前后端职责混乱等问题。

本节先完成登录页面和表单校验，为下一步实现真正的身份认证做好准备。

需要明确：**完成本节后，登录页面可以收集并校验数据，但还不代表已经实现了完整登录功能。** 密码验证、会话建立和登录后的跳转，属于后续认证流程。

## 二、先明确本节需要掌握的知识点

开始写代码之前，我们先梳理需要解决的技术问题。

### 2.1 shadcn/ui：构建登录界面

我们使用 shadcn/ui 构建登录页面。

与从零开始编写输入框、按钮和表单样式相比，shadcn/ui 提供了一套可以直接集成到项目中的组件，能够帮助我们统一界面的视觉风格和交互细节。

本节会使用以下组件：

| 组件 | 用途 |
|---|---|
| Card | 登录面板容器 |
| CardHeader | 登录标题和说明 |
| CardContent | 登录表单主体 |
| Input | 用户名和密码输入 |
| Label | 输入字段标签 |
| Button | 登录按钮 |
| Form 相关组件 | 表单字段、错误提示及校验状态 |

需要注意，shadcn/ui 不是一个只需要安装依赖就自动提供全部组件的传统组件库。它会将选定的组件源码添加到项目中，因此需要先确认组件已经安装。

### 2.2 React：管理表单状态

登录页面需要记录用户输入的用户名、密码，以及当前是否正在提交。

例如：

```text
username：用户输入的用户名
password：用户输入的密码
isSubmitting：是否正在提交
errors：当前表单的校验错误
```

React 负责管理这些状态，并根据状态变化更新页面。

### 2.3 Zod：定义登录数据规则

Zod 用于定义数据结构和校验规则。

例如，我们可以规定：

- 用户名不能为空。
- 用户名不能超过 50 个字符。
- 用户名只能包含指定的字符。
- 密码不能为空。
- 密码不能超过系统允许的长度。

将规则集中定义，可以避免页面组件中散落大量判断逻辑，也方便后续在服务端复用相同的 Schema。

### 2.4 前后端校验为什么都需要？

前端校验的主要目的是改善用户体验。

例如，用户忘记填写密码，页面可以立即提示，而不必发送请求。

但前端校验并不可靠。用户可以绕过页面，直接向服务端发送请求。

因此，服务端必须再次校验请求数据。

本节先实现前端校验，同时把 Schema 设计成可以供后续服务端复用的形式。

## 四、先设计登录表单的校验规则

我们先不急着编写页面，而是先明确用户可以提交什么样的数据。

假设上一节的 User 模型使用以下字段：

```prisma
username     String @unique
passwordHash String
```

其中，username 用于登录，passwordHash 用于保存密码哈希。

用户登录时提交的是原始密码，而不是 passwordHash。

因此，登录表单的数据结构应该是：

```ts
{
  username: string;
  password: string;
}
```

这里需要特别注意：**登录时不能要求用户输入符合新密码设置规则的密码，因为登录的任务是验证已有凭据，而不是要求用户重新设置密码。**

例如，一个历史账号的密码可能不满足后来增加的复杂度要求，但只要它仍然符合当前账号的有效凭据规则，就应该交由认证流程验证，而不是仅凭新密码规则拒绝登录。

### 4.1 创建登录 Schema

在项目中创建目录：

```text
lib/
└── validations/
    └── auth.ts
```

在 `lib/validations/auth.ts` 中编写：

```ts
import { z } from "zod";

export const loginSchema = z.object({
  username: z
    .string()
    .trim()
    .min(1, "请输入用户名")
    .max(50, "用户名长度不能超过 50 个字符")
    .regex(
      /^[a-zA-Z0-9._-]+$/,
      "用户名格式不正确",
    ),

  password: z
    .string()
    .min(1, "请输入密码")
    .max(1024, "密码长度超出允许范围"),
});

export type LoginFormValues = z.infer<typeof loginSchema>;
```

这段代码定义了登录表单的数据结构和输入规则。

我们逐项理解。

**第一，使用 `z.object()` 定义对象结构。**

```ts
z.object({
  username: z.string(),
  password: z.string(),
})
```

这表示登录数据必须包含符合要求的用户名和密码字段。

**第二，使用 `min(1)` 检查必填项。**

```ts
.min(1, "请输入用户名")
```

对于用户名，空字符串经过 `trim()` 后会变成空字符串，因此可以被正确拦截。

对于密码，我们没有使用 `trim()`，因为密码中的空格可能是用户密码的一部分，不应该在校验过程中擅自删除。

**第三，使用 `max()` 限制输入长度。**

```ts
.max(50, "用户名长度不能超过 50 个字符")
```

数据库中的用户名字段最大长度为 50，因此表单也应采用一致的限制。

密码长度限制用于控制异常输入和不必要的资源消耗。这里的 1024 是请求输入上限，不是建议用户设置 1024 个字符的密码。后续还需要根据实际密码哈希方案设置合理的密码长度上限，并在服务端保持一致。

**第四，使用正则表达式限制用户名格式。**

```ts
.regex(/^[a-zA-Z0-9._-]+$/, "用户名格式不正确")
```

这与上一节初始化脚本中的用户名规则保持一致，允许英文字母、数字、点、下划线和连字符。

**第五，使用 `z.infer` 自动推导 TypeScript 类型。**

```ts
export type LoginFormValues = z.infer<typeof loginSchema>;
```

这样，表单的数据类型由 Schema 自动生成，不必再单独维护一份重复的类型定义。

以后调整 Schema 时，TypeScript 类型也会随之变化，减少规则与类型定义不一致的问题。

### 4.2 为什么 Schema 应该独立于页面？

如果直接在登录页面中编写全部校验规则，后续登录接口、测试代码可能会重复实现相同的判断。

例如：

```ts
if (!username) {
  // 用户名不能为空
}
```

这种判断本身没有问题，但当项目中存在多个接口时，重复编写很容易造成规则不一致。

将 Schema 放到独立文件后，前端页面可以使用它，服务端登录接口也可以使用它。

不过，要注意一个边界：前后端可以复用同一份校验规则，但客户端提交的数据仍然必须在服务端重新验证。不能把客户端已经校验过作为可信依据。

## 五、构建登录页面

接下来开始实现页面。

### 5.1 规划页面布局

我们先设计一个简洁的后台登录界面。

页面整体采用居中布局，登录卡片包含：

- 系统名称。
- 登录说明。
- 用户名输入框。
- 密码输入框。
- 字段级错误提示。
- 登录按钮。
- 统一的表单错误提示区域。

布局示意：

```text
┌─────────────────────────────────┐
│                                 │
│        外包项目管理平台           │
│        登录后进入工作台           │
│                                 │
│        用户名                    │
│        [___________________]    │
│                                 │
│        密码                      │
│        [___________________]    │
│                                 │
│        [       登  录       ]    │
│                                 │
│        登录失败时显示统一提示     │
│                                 │
└─────────────────────────────────┘
```

这里不需要过度装饰。登录页面的主要目标是让用户明确知道自己正在访问哪个系统，以及应该输入什么信息。

### 5.2 创建登录页面文件

假设项目采用 Next.js App Router，登录路由为 `/login`。

创建文件：

```text
app/
└── login/
    └── page.tsx
```

登录页面需要使用 React Hook Form，因此表单组件必须是客户端组件。

我们把页面容器和交互逻辑放在同一个文件中，先完成基础实现，后续如果需要复用，再拆分成独立的组件。

在 `app/login/page.tsx` 中编写：

```tsx
"use client";

import { useState } from "react";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

import {
  loginSchema,
  type LoginFormValues,
} from "@/lib/validations/auth";

import {
  Card,
  CardContent,
  CardDescription,
  CardHeader,
  CardTitle,
} from "@/components/ui/card";

import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";
import { Button } from "@/components/ui/button";

export default function LoginPage() {
  const [submitError, setSubmitError] = useState("");

  const {
    register,
    handleSubmit,
    formState: {
      errors,
      isSubmitting,
    },
  } = useForm<LoginFormValues>({
    resolver: zodResolver(loginSchema),
    defaultValues: {
      username: "",
      password: "",
    },
    mode: "onBlur",
  });

  async function onSubmit(values: LoginFormValues) {
    setSubmitError("");

    // 本节只验证表单数据。
    // 下一节再接入真正的登录认证接口。
    console.log("表单校验通过", {
      username: values.username,
    });

    setSubmitError(
      "表单校验已通过，登录认证接口将在下一节接入。",
    );
  }

  return (
    <main className="flex min-h-screen items-center justify-center bg-muted/40 px-4 py-10">
      <Card className="w-full max-w-md">
        <CardHeader className="space-y-2">
          <CardTitle className="text-2xl">
            外包项目管理平台
          </CardTitle>

          <CardDescription>
            请输入账号和密码，登录系统
          </CardDescription>
        </CardHeader>

        <CardContent>
          <form
            onSubmit={handleSubmit(onSubmit)}
            className="space-y-5"
            noValidate
          >
            <div className="space-y-2">
              <Label htmlFor="username">
                用户名
              </Label>

              <Input
                id="username"
                autoComplete="username"
                placeholder="请输入用户名"
                aria-invalid={!!errors.username}
                aria-describedby={
                  errors.username
                    ? "username-error"
                    : undefined
                }
                {...register("username")}
              />

              {errors.username && (
                <p
                  id="username-error"
                  className="text-sm text-destructive"
                  role="alert"
                >
                  {errors.username.message}
                </p>
              )}
            </div>

            <div className="space-y-2">
              <Label htmlFor="password">
                密码
              </Label>

              <Input
                id="password"
                type="password"
                autoComplete="current-password"
                placeholder="请输入密码"
                aria-invalid={!!errors.password}
                aria-describedby={
                  errors.password
                    ? "password-error"
                    : undefined
                }
                {...register("password")}
              />

              {errors.password && (
                <p
                  id="password-error"
                  className="text-sm text-destructive"
                  role="alert"
                >
                  {errors.password.message}
                </p>
              )}
            </div>

            {submitError && (
              <p
                className="text-sm text-destructive"
                role="alert"
              >
                {submitError}
              </p>
            )}

            <Button
              type="submit"
              className="w-full"
              disabled={isSubmitting}
            >
              {isSubmitting ? "正在提交..." : "登录"}
            </Button>
          </form>
        </CardContent>
      </Card>
    </main>
  );
}
```

这里有几个实现细节需要重点理解。

**第一，使用 `zodResolver` 将 Zod 规则接入表单。**

```tsx
resolver: zodResolver(loginSchema)
```

React Hook Form 会根据 Schema 校验表单数据，并把错误信息放到 `errors` 中。

这样，页面组件不需要再手动判断用户名是否为空、密码是否为空。

**第二，使用 `mode: "onBlur"` 控制校验时机。**

用户离开输入框时，表单会执行校验。

这样既可以及时提示错误，也避免用户每输入一个字符就出现错误信息。

在提交时，表单还会进行完整校验。

**第三，使用 `noValidate` 统一管理校验提示。**

```tsx
<form noValidate>
```

这会关闭浏览器原生的表单提交校验提示，让我们通过 Zod 统一处理输入错误。

浏览器依然可以使用 `type="password"`、`autoComplete` 等输入属性改善用户体验。

**第四，使用 `aria-invalid` 和 `aria-describedby`。**

这两个属性帮助辅助技术识别字段是否存在错误，以及对应的错误信息在哪里。

登录页面不仅需要视觉上的错误提示，也应该考虑键盘操作和辅助技术的使用体验。

**第五，当前代码还没有真正执行登录。**

本节的 `onSubmit` 只是演示校验通过后的处理过程，并没有请求后端验证密码，也没有建立会话。

因此，当前页面显示“表单校验已通过”并不代表登录成功。后续接入认证接口时，需要将这段演示逻辑替换为真实的认证请求。

另外，示例代码没有输出密码，也没有把密码写入日志。实际开发中应保持这一原则。

## 六、处理空值、格式错误与无效输入

现在页面已经可以显示校验错误，我们再从用户操作的角度验证各种情况。

### 6.1 用户名为空

操作步骤：

1. 打开 `/login`。
2. 不输入用户名。
3. 点击用户名输入框之外的位置，或者直接点击登录按钮。

预期结果：

```text
请输入用户名
```

因为 Schema 使用了 `trim()` 和 `min(1)`，所以空字符串以及只包含普通首尾空格的输入都能够被正确识别。

### 6.2 密码为空

不输入密码，直接提交表单。

预期结果：

```text
请输入密码
```

这里的密码校验不应该偷偷把用户输入的空格删除，因为空格可能是密码本身的一部分。

如果密码只包含空格，它并不是空字符串。是否允许这种密码，应由密码设置规则决定；本节只负责识别真正的空值和明显不合理的输入。

### 6.3 用户名格式错误

例如，输入：

```text
zhang san
```

用户名中包含空格，不符合当前 Schema 定义的规则。

预期结果：

```text
用户名格式不正确
```

注意，用户名规则必须与用户初始化逻辑保持一致。

如果初始化脚本允许某些字符，而登录表单拒绝这些字符，就会出现账号已经创建，却无法通过表单正常登录的问题。

### 6.4 用户名超过最大长度

输入超过 50 个字符的用户名。

预期结果：

```text
用户名长度不能超过 50 个字符
```

这项规则应与数据库字段长度和服务端验证保持一致。

### 6.5 提交正常格式的数据

例如，输入一个符合格式的用户名和一段非空密码。

预期结果：表单校验通过，进入 `onSubmit`。

此时不要把“校验通过”理解成“密码正确”。

当前页面还没有向服务端验证密码，因此无法判断用户是否存在、密码是否正确或账号是否被停用。

## 七、为什么要统一登录失败提示？

接下来讨论一个与安全相关的问题。

假设用户输入了错误的账号或密码，服务端可能返回不同的情况：

- 用户名不存在。
- 密码错误。
- 账号已经停用。
- 账号不允许登录。
- 登录请求发生内部错误。

如果把这些信息全部原样显示给用户，可能暴露系统内部的账号状态。

例如，攻击者可以反复提交不同用户名，根据提示判断哪些账号真实存在，再针对这些账号尝试密码。

因此，登录认证阶段应该对外提供统一的失败提示。

建议统一使用：

```text
用户名或密码错误
```

对于停用账号，也可以在统一认证失败提示中处理，避免向未认证用户泄露过多账号信息。

但是，统一提示不意味着所有错误都应该被吞掉。

在系统内部，仍然应该记录必要的安全事件，例如登录失败、账号停用导致的拒绝登录、异常请求等。

需要注意：

- 不要记录明文密码。
- 不要把完整的认证请求写入日志。
- 不要向用户暴露数据库异常、SQL 错误或堆栈信息。
- 对外提示尽量一致，对内日志则保留必要的诊断信息。
- 对登录接口增加合理的限流或失败尝试控制，降低密码猜测风险。

本节尚未接入真实登录接口，因此统一失败提示目前只是设计要求。下一节实现服务端认证时，需要真正落实这套规则。

### 8.2 检查页面布局

确认：

- 登录卡片能够正常显示。
- 用户名和密码输入框正常工作。
- 登录按钮可以点击。
- 页面在较窄的屏幕上没有明显溢出。
- 页面没有因缺失 shadcn/ui 组件而报错。

### 8.3 检查字段校验

依次测试：

| 测试输入 | 预期结果 |
|---|---|
| 用户名为空 | 显示用户名必填提示 |
| 密码为空 | 显示密码必填提示 |
| 用户名包含空格 | 显示用户名格式错误 |
| 用户名超过 50 个字符 | 显示长度错误 |
| 用户名和密码格式正常 | 进入提交处理函数 |

### 8.4 检查浏览器控制台

观察控制台，确认没有 React 错误、组件导入错误或未处理异常。

同时确认代码不会打印用户输入的密码。

如果页面能够显示，但输入错误时没有提示，优先检查以下位置：

1. `loginSchema` 是否正确导出。
2. `zodResolver(loginSchema)` 是否配置正确。
3. 输入框是否使用了 `register()`。
4. 页面是否正确读取了 `formState.errors`。
5. shadcn/ui 组件导入路径是否正确。

## 九、本节总结

本节完成了登录页面的第一阶段：界面构建与数据校验。

我们使用 shadcn/ui 构建了登录界面，使用 React Hook Form 管理表单状态，并通过 Zod 定义用户名和密码的校验规则。

同时，我们明确了前端校验与服务端认证的区别。

前端校验可以帮助用户尽早发现输入错误，但不能证明用户身份有效。只有服务端完成凭据验证，并建立安全会话后，系统才能认为用户已经登录。

本节还明确了统一登录失败提示的设计原则：对外避免泄露账号是否存在等敏感信息，对内保留必要的安全审计和诊断记录。

接下来，我们将进入真正的登录认证流程：服务端接收登录请求、验证用户名和密码、检查账号状态，并在认证成功后建立安全会话。

从那一刻起，登录页面才真正成为整个后台系统的入口。
