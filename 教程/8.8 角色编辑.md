# 8.4 角色编辑：实现资料回显、服务端更新与业务规则校验

上一节我们完成了用户资料编辑，实现了从列表选择目标记录、回显现有资料、提交修改，到 Server Action、Service 和 Prisma 更新的完整流程。

本节继续实现角色编辑。

角色编辑与用户编辑有相似之处，都需要回显数据、校验输入、控制可修改字段，并通过服务端完成更新。但角色管理还有一个需要特别注意的地方：角色不仅是一条基础资料记录，还可能被用户、权限配置和其他业务数据引用。

因此，角色编辑不能简单地把整个角色对象提交给 Prisma 更新。我们需要明确哪些字段允许修改，以及修改角色状态可能对后续权限管理产生什么影响。

本节最终实现的功能是：在角色列表中点击“编辑”，弹出角色编辑窗口，修改角色名称、描述和状态，提交后由服务端校验并保存，成功后刷新列表。

本节不修改角色编码，不处理角色权限分配、用户关联、删除和权限缓存失效，这些内容分别在后续小节处理。

## 一、明确允许修改的字段

假设当前系统的 `Role` 模型包含以下字段：

```
model Role {
  id          String     @id @default(cuid())
  code        String     @unique @db.VarChar(50)
  name        String     @db.VarChar(50)
  description String?    @db.VarChar(500)
  status      RoleStatus @default(ACTIVE)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

这只是本节需要的基础结构。如果项目现有的角色模型还包含 `userRoles`、`rolePermissions` 等关联字段，应保留原有字段，不要覆盖现有模型。

先明确各字段的修改规则。

| 字段            | 本节是否允许修改 | 原因           |
| ------------- | -------- | ------------ |
| `id`          | 否        | 数据记录的唯一标识    |
| `code`        | 否        | 角色的稳定业务标识    |
| `name`        | 是        | 角色展示名称       |
| `description` | 是        | 角色职责说明       |
| `status`      | 是        | 控制角色是否处于启用状态 |
| `createdAt`   | 否        | 创建时间         |
| `updatedAt`   | 自动更新     | 由 Prisma 维护  |
| 用户关联          | 否        | 属于用户与角色关系管理  |
| 权限关联          | 否        | 属于角色授权管理     |

这里有三个重要的设计原则。

### 1. 角色编码创建后保持稳定

例如，系统中存在以下角色：

| 角色编码              | 角色名称  |
| ----------------- | ----- |
| `ADMIN`           | 系统管理员 |
| `PROJECT_MANAGER` | 项目经理  |
| `DEVELOPER`       | 开发人员  |

角色名称可能因为组织调整而修改，但角色编码通常会被其他代码、权限规则或业务数据引用。

如果允许随意修改角色编码，就需要考虑所有关联数据、权限缓存以及外部系统引用是否同步更新。

因此，本节只允许修改角色名称、描述和状态。角色编码在编辑窗口中以只读形式展示。

### 2. 角色状态不是普通展示字段

将角色从 `ACTIVE` 改为 `DISABLED`，不仅仅是改变列表中的状态标签。

如果系统采用基于角色的访问控制（RBAC），停用角色后，系统在计算用户有效权限时应当排除该角色的授权。

但如果用户的会话中已经缓存了权限，或者权限检查只读取旧的会话信息，停用操作可能不会立即生效。

因此，本节先实现角色状态的数据库更新。后续完善权限管理时，还需要统一处理有效权限计算、缓存失效以及必要的会话刷新。

### 3. 前端回显不代表服务端信任该数据

编辑窗口中的角色资料来自服务端查询，但客户端提交的数据仍然可以被修改。

因此，Server Action 需要重新校验输入，Service 需要检查目标角色是否存在，数据库更新只允许写入明确指定的字段。

## 二、定义角色编辑的 Zod Schema

打开 `server/role/schema.ts`，在已有的 `createRoleSchema` 后增加编辑专用的 Schema。

```
// server/role/schema.ts

export const updateRoleSchema = z.object({
  id: z.string().min(1, "角色 ID 不能为空"),

  name: z
    .string()
    .trim()
    .min(2, "角色名称至少需要 2 个字符")
    .max(50, "角色名称不能超过 50 个字符"),

  description: z
    .string()
    .trim()
    .max(500, "角色描述不能超过 500 个字符")
    .transform((value) => value || null),

  status: z.enum(["ACTIVE", "DISABLED"]),
});

export type UpdateRoleInput = z.infer<
  typeof updateRoleSchema
>;
```

注意，文件开头已经存在 `zod` 的导入，可以直接复用。

本节沿用角色新增时的名称、描述和状态规则，不需要重新定义一套不同的校验标准。

### 为什么不直接复用 `createRoleSchema`？

新增和编辑的输入要求不同。

新增需要角色编码，而编辑不允许修改角色编码。如果直接复用新增 Schema，编辑时就会被迫提交不需要修改的字段，导致两个操作的职责混在一起。

现在两个 Schema 的职责很明确：

- `createRoleSchema`：校验创建角色所需的完整输入。
- `updateRoleSchema`：校验角色编辑时允许修改的字段。

这里还有一个值得注意的细节：`id` 只是用于定位目标记录，并不代表客户端有权修改该记录。真正的访问控制还需要在 Server Action 中执行。

## 三、实现角色更新 Service

打开 `server/role/service.ts`，保留已有的角色列表查询和 `createRole()`，增加角色更新方法。

```
// server/role/service.ts

import type { UpdateRoleInput } from "./schema";

export type UpdateRoleResult =
  | {
      success: true;
    }
  | {
      success: false;
      code: "NOT_FOUND";
      message: string;
    };

export async function updateRole(
  input: UpdateRoleInput,
): Promise<UpdateRoleResult> {
  // 1. 检查目标角色是否存在。
  const existingRole = await db.role.findUnique({
    where: { id: input.id },
    select: { id: true },
  });

  if (!existingRole) {
    return {
      success: false,
      code: "NOT_FOUND",
      message: "角色不存在或已被删除",
    };
  }

  // 2. 只更新允许修改的字段。
  await db.role.update({
    where: { id: input.id },
    data: {
      name: input.name.trim(),
      description: input.description,
      status: input.status,
    },
  });

  return {
    success: true,
  };
}
```

这里使用了项目现有的 `db`，不需要重新创建 Prisma Client。

这段代码有三个关键点。

### 1. 先检查目标角色是否存在

角色列表打开后，目标记录可能已经被其他管理员删除。

因此，不能假设用户点击编辑时存在的角色，在提交时仍然存在。

预先查询可以返回明确的业务提示。不过，查询和更新之间仍然可能发生并发删除，所以还需要在 Action 中处理更新时的 `P2025` 异常。

### 2. 显式指定允许修改的字段

这里没有使用：

```
data: input
```

而是明确写出：

```
data: {
  name: input.name.trim(),
  description: input.description,
  status: input.status,
}
```

这样，即使客户端额外提交了 `code`、`id` 或其他属性，这些字段也不会被传入 Prisma 的更新数据中。

这是服务端防止意外字段写入的重要做法。

### 3. 不需要手动更新 `updatedAt`

如果项目的 Prisma 模型已经定义：

```
updatedAt DateTime @updatedAt
```

那么正常执行更新时，Prisma 会自动维护更新时间。

### 4. 为什么还要考虑并发删除？

例如：

```
请求 A：检查角色存在
请求 B：删除角色
请求 A：更新角色
```

请求 A 在查询时发现角色存在，但更新时记录已经被删除。

因此，前置查询用于改善用户体验，真正的更新仍然必须以数据库操作结果为准。后续 Action 会将目标记录不存在的异常转换成友好提示。

## 四、实现更新角色的 Server Action

接下来在 `server/role/actions.ts` 中增加 `updateRoleAction()`。

保留已有的 `createRoleAction()`，只增加本节需要的导入和方法。

```
// server/role/actions.ts

import { updateRoleSchema } from "@/server/role/schema";
import { updateRole } from "@/server/role/service";

export async function updateRoleAction(
  input: unknown,
): Promise<CreateRoleActionState> {
  // 1. 检查登录状态。
  const session = await getCurrentSession();

  if (!session) {
    return {
      success: false,
      message: "登录状态已失效，请重新登录",
    };
  }

  // 2. 检查角色编辑权限。
  // 接入项目已有的服务端权限校验函数。
  // 例如：await requirePermission("role:update");

  // 3. 服务端重新校验输入。
  const parsed = updateRoleSchema.safeParse(input);

  if (!parsed.success) {
    return {
      success: false,
      message: "请检查输入内容",
      fieldErrors: parsed.error.flatten().fieldErrors,
    };
  }

  try {
    // 4. 调用 Service。
    const result = await updateRole(parsed.data);

    if (!result.success) {
      return {
        success: false,
        message: result.message,
      };
    }

    // 5. 刷新角色列表。
    revalidatePath("/roles");

    return {
      success: true,
      message: "角色资料更新成功",
    };
  } catch (error) {
    // 目标角色可能在查询后、更新前被删除。
    if (
      error instanceof Prisma.PrismaClientKnownRequestError &&
      error.code === "P2025"
    ) {
      return {
        success: false,
        message: "角色不存在或已被删除",
      };
    }

    console.error("updateRoleAction failed", error);

    return {
      success: false,
      message: "更新角色资料失败，请稍后重试",
    };
  }
}
```

上面的方法使用了现有的 `CreateRoleActionState` 作为返回类型。它描述的是通用的成功状态、错误信息和字段错误结构，因此也能用于编辑。

如果后续角色模块的新增、编辑和删除都使用同样的返回约定，可以在公共服务端类型文件中统一定义 `ActionResult`，避免类型名称与具体操作不一致。

### 权限检查必须真正接入

这里的 `requirePermission("role:update")` 只是示例，不是已经实现的权限校验。

如果项目已有统一的权限服务，应使用真实的方法名和项目定义的权限标识。如果尚未实现，则必须先补齐服务端权限控制，再启用角色编辑功能。

不能仅仅因为当前用户已登录，或者前端没有显示编辑按钮，就认定该用户有权修改角色。

另外，`revalidatePath("/roles")` 应与你的角色管理实际路由一致。

## 五、实现编辑角色弹窗

现在实现客户端编辑界面。

按照角色管理模块现有的目录约定，新建：

`app/(dashboard)/roles/_components/edit-role-dialog.tsx`

目录结构如下：

```
app/(dashboard)/roles/
├── page.tsx
├── role-workspace.tsx
└── _components/
    └── edit-role-dialog.tsx
```

如果项目中的工作区文件或组件目录名称不同，应沿用实际路径。

下面的实现继续使用项目现有的 shadcn/Base UI 组件，并沿用用户编辑中的交互原则：

- 打开弹窗时回显现有角色资料。
- 角色编码只读。
- 提交时调用 Server Action。
- 服务端校验失败时保留输入。
- 保存成功后关闭弹窗并刷新列表。
- 关闭弹窗时通过条件渲染卸载组件。

```
"use client";

import { useEffect, useState, useTransition } from "react";
import { useRouter } from "next/navigation";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

import {
  Dialog,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
} from "@/components/ui/dialog";

import {
  Select,
  SelectContent,
  SelectItem,
  SelectTrigger,
  SelectValue,
} from "@/components/ui/select";

import { updateRoleAction } from "@/server/role/actions";

export type EditableRole = {
  id: string;
  code: string;
  name: string;
  description: string | null;
  status: "ACTIVE" | "DISABLED";
};

type Props = {
  role: EditableRole;
  open: boolean;
  onOpenChange: (open: boolean) => void;
};

const statusItems = [
  { value: "ACTIVE", label: "启用" },
  { value: "DISABLED", label: "停用" },
];

export function EditRoleDialog({
  role,
  open,
  onOpenChange,
}: Props) {
  const router = useRouter();
  const [pending, startTransition] = useTransition();

  const [name, setName] = useState(role.name);
  const [description, setDescription] = useState(
    role.description ?? "",
  );

  const [status, setStatus] = useState<
    "ACTIVE" | "DISABLED"
  >(role.status);

  const [message, setMessage] = useState("");

  const [fieldErrors, setFieldErrors] = useState<
    Record<string, string[] | undefined>
  >({});

  // 每次打开弹窗，都使用最新的角色资料初始化表单。
  useEffect(() => {
    if (!open) return;

    setName(role.name);
    setDescription(role.description ?? "");
    setStatus(role.status);

    setMessage("");
    setFieldErrors({});
  }, [open, role]);

  function handleSubmit(
    event: React.FormEvent<HTMLFormElement>,
  ) {
    event.preventDefault();

    setMessage("");
    setFieldErrors({});

    startTransition(async () => {
      const result = await updateRoleAction({
        id: role.id,
        name,
        description,
        status,
      });

      if (!result.success) {
        setMessage(result.message);
        setFieldErrors(result.fieldErrors ?? {});
        return;
      }

      onOpenChange(false);
      router.refresh();
    });
  }

  function errorFor(field: string) {
    return fieldErrors[field]?.[0];
  }

  // 沿用项目现有 Base UI Dialog 的条件渲染约定。
  if (!open) return null;

  return (
    <Dialog
      open
      onOpenChange={(nextOpen) => {
        if (!pending) {
          onOpenChange(nextOpen);
        }
      }}
    >
      <DialogContent className="sm:max-w-lg">
        <DialogHeader>
          <DialogTitle>编辑角色</DialogTitle>

          <DialogDescription>
            修改角色名称、描述和状态。角色编码创建后不可修改。
          </DialogDescription>
        </DialogHeader>

        <form
          onSubmit={handleSubmit}
          className="space-y-4"
        >
          <div className="space-y-2">
            <Label htmlFor="edit-role-code">
              角色编码
            </Label>

            <Input
              id="edit-role-code"
              value={role.code}
              readOnly
              disabled
            />

            <p className="text-xs text-muted-foreground">
              角色编码用于系统识别，不支持在此处修改。
            </p>
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-role-name">
              角色名称 *
            </Label>

            <Input
              id="edit-role-name"
              value={name}
              onChange={(event) =>
                setName(event.target.value)
              }
              aria-invalid={Boolean(errorFor("name"))}
              disabled={pending}
              required
            />

            {errorFor("name") && (
              <p className="text-sm text-destructive">
                {errorFor("name")}
              </p>
            )}
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-role-description">
              角色描述
            </Label>

            <textarea
              id="edit-role-description"
              value={description}
              onChange={(event) =>
                setDescription(event.target.value)
              }
              placeholder="描述角色的业务职责和使用场景"
              maxLength={500}
              disabled={pending}
              className="border-input placeholder:text-muted-foreground focus-visible:border-ring focus-visible:ring-ring/50 aria-invalid:ring-destructive/20 dark:aria-invalid:ring-destructive/40 aria-invalid:border-destructive flex min-h-24 w-full rounded-md border bg-transparent px-3 py-2 text-sm shadow-xs outline-none focus-visible:ring-[3px] disabled:cursor-not-allowed disabled:opacity-50"
            />

            <p className="text-xs text-muted-foreground">
              最多 500 个字符。
            </p>

            {errorFor("description") && (
              <p className="text-sm text-destructive">
                {errorFor("description")}
              </p>
            )}
          </div>

          <div className="space-y-2">
            <Label htmlFor="edit-role-status">
              角色状态
            </Label>

            <Select
              items={statusItems}
              value={status}
              onValueChange={(value) => {
                if (
                  value === "ACTIVE" ||
                  value === "DISABLED"
                ) {
                  setStatus(value);
                }
              }}
              disabled={pending}
            >
              <SelectTrigger
                id="edit-role-status"
                className="w-full"
              >
                <SelectValue placeholder="选择角色状态" />
              </SelectTrigger>

              <SelectContent>
                {statusItems.map((item) => (
                  <SelectItem
                    key={item.value}
                    value={item.value}
                  >
                    {item.label}
                  </SelectItem>
                ))}
              </SelectContent>
            </Select>
          </div>

          {message && (
            <p
              role="alert"
              className="text-sm text-destructive"
            >
              {message}
            </p>
          )}

          <DialogFooter>
            <Button
              type="button"
              variant="outline"
              disabled={pending}
              onClick={() => onOpenChange(false)}
            >
              取消
            </Button>

            <Button
              type="submit"
              disabled={pending}
            >
              {pending ? "正在保存..." : "保存修改"}
            </Button>
          </DialogFooter>
        </form>
      </DialogContent>
    </Dialog>
  );
}
```

### 1. 为什么编辑时不允许修改角色编码？

角色编码通常承担系统标识的作用。

例如，权限规则可能引用 `ADMIN`，而不是直接引用“系统管理员”这个中文名称。

如果在普通编辑操作中修改编码，就会引入关联更新和兼容性问题。因此，本节将编码作为只读字段展示。

即使有人绕过前端提交 `code`，由于 `updateRoleSchema` 不包含这个字段，而且 Service 只更新指定字段，角色编码也不会被修改。

### 2. 为什么打开弹窗时重新初始化表单？

组件初次渲染时会根据 `role` 初始化状态，但 React 不会因为 props 变化就自动重置所有 `useState`。

因此，通过 `useEffect` 在每次打开弹窗时同步当前角色数据，能够避免上一次编辑留下的输入内容影响下一次操作。

### 3. 为什么关闭弹窗后不保留旧表单？

编辑窗口的任务是修改当前选中的角色。关闭后，父组件可以卸载弹窗组件；再次打开时，会重新读取传入的角色资料。

这样既能避免旧数据残留，也能让编辑交互保持一致。

3. 编辑弹窗显示该角色的编码、名称、描述和状态。
4. 用户修改资料并提交。
5. Server Action 校验输入和权限，然后调用 Service。
6. 更新成功后关闭弹窗，并通过 `router.refresh()` 刷新列表。

这里不需要重新编写角色列表，也不需要把所有角色数据复制到客户端状态中。父组件只需要维护当前正在编辑的角色即可。

## 七、验证角色编辑功能

开发完成后，应验证正常更新、异常输入以及服务端边界。

| 测试场景         | 预期结果                 |
| ------------ | -------------------- |
| 点击编辑         | 弹窗正确显示现有角色资料         |
| 修改角色名称       | 数据库更新，列表同步刷新         |
| 修改角色描述       | 数据库更新                |
| 描述留空         | 保存为 `null`           |
| 名称为空         | 服务端拒绝                |
| 名称超长         | 服务端拒绝                |
| 描述超过 500 个字符 | 服务端拒绝                |
| 将状态改为停用      | 数据库状态更新为 `DISABLED`  |
| 修改角色编码       | 界面不提供编辑入口，服务端也不接受该字段 |
| 提交额外的关联字段    | 不会被写入更新操作            |
| 目标角色已被删除     | 返回角色不存在的提示           |
| 未登录调用 Action | 服务端拒绝                |
| 操作者没有编辑角色权限  | 服务端拒绝                |
| 连续点击保存       | 提交期间按钮禁用             |
| 更新失败         | 弹窗保留输入并显示错误信息        |

建议特别验证以下三个场景。

### 场景一：验证角色编码不会变化

打开 `PROJECT_MANAGER` 对应的角色，修改名称后保存。

预期结果：

- 角色名称发生变化。
- 角色编码仍然是 `PROJECT_MANAGER`。
- 该角色原有的用户关联和权限关联不受影响。

### 场景二：验证状态变更

将一个角色从启用改为停用，再检查数据库中的状态字段。

预期结果是状态正确更新。

但需要注意：数据库状态更新成功，并不自动证明该角色的权限已经从所有用户的有效权限中移除。权限计算与缓存失效还需要后续权限管理模块配合实现。

### 场景三：验证服务端字段边界

直接调用 `updateRoleAction()`，尝试提交以下额外字段：

```
{
  id: "existing-role-id",
  code: "ADMIN",
  name: "新的角色名称",
  description: "",
  status: "ACTIVE",
  rolePermissions: [],
}
```

由于 Schema 只定义了 `id`、`name`、`description` 和 `status`，并且 Service 只更新允许修改的字段，因此 `code` 和 `rolePermissions` 不会进入本次数据库更新。

需要注意，Zod 对象默认会剥离未知字段；如果项目配置了严格对象校验，也可以选择直接拒绝包含额外字段的请求。无论采取哪种策略，都不能将未经允许的字段直接传入 Prisma 更新操作。

## 八、本节小结

本节完成了角色编辑的完整流程：

角色列表

选择需要编辑的角色

编辑角色弹窗

回显资料 · 修改名称、描述和状态

Server Action

检查会话 · 检查编辑权限 · Zod 校验

Role Service

检查目标角色 · 显式指定更新字段

Prisma 更新与列表刷新

保存资料 · 返回结果 · 刷新页面数据

用户编辑与角色编辑采用了相同的工程结构，但具体的业务边界有所不同：

- 用户编辑不修改用户名和密码。
- 角色编辑不修改角色编码和权限关联。
- 两者都只允许更新明确指定的字段。
- 两者都必须在服务端执行输入校验和权限检查。

这种设计让每个操作的职责更清楚，也为后续实现角色删除、角色授权和用户角色关联提供了稳定基础。

下一节建议实现角色删除。 在删除之前，需要检查该角色是否仍被用户关联、是否为系统内置角色，以及是否存在必须保留的管理角色。只有明确这些业务约束，才能避免简单的数据库删除破坏系统的权限结构。
