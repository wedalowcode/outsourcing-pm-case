# 6.5 部门管理实战：实现新增、修改与删除服务

## 一、前言

上一篇（6.4），我们完成了部门编码与排序规则的封装。

现在，系统已经有了三个工具函数：

- `formatCode`：根据上级编码和序号生成完整编码。
- `nextDeptCode`：通过计数器分配下一个部门编码。
- `nextSort`：根据同级部门计算下一个排序值。

这些函数解决的是局部问题：编码怎么算、序号怎么分配、排序值怎么确定。

但一个真实的业务操作，并不是调用一个函数就结束了。

例如，新增部门时，系统需要校验名称、检查上级部门、分配编码、计算排序值，最后才能将数据写入数据库。如果中途发生异常，还必须保证之前的数据库操作不会留下不完整的数据。

修改部门则更加复杂。如果将一个部门从技术部移动到销售部，不仅要修改它自己的上级关系，还要同步修改整个下级部门树的编码。

删除部门也不能简单地执行一条 `DELETE` 语句。只要该部门还有下级，就可能破坏现有的组织结构。

因此，本篇开始实现真正的业务流程：

| 服务函数         | 需要解决的问题                |
| ------------ | ---------------------- |
| `createDept` | 校验数据、分配编码、计算排序、保存部门    |
| `updateDept` | 修改部门属性，必要时调整层级并更新下级编码  |
| `deleteDept` | 检查删除条件，保证部门关系和编码规则不被破坏 |

本篇的核心不是学习如何调用 Prisma 的增删改查方法，而是学习如何把多个数据库操作组织成一个完整的业务过程。

## 二、先理解服务层要解决什么问题

### 2.1 为什么不直接在页面里写数据库操作？

假设新增部门的逻辑全部写在页面事件中，大致会变成这样：

```text
用户点击保存
    ↓
检查部门名称
    ↓
查询上级部门
    ↓
获取下一个编码
    ↓
计算排序值
    ↓
插入部门数据
    ↓
显示操作结果
```

看起来没有问题，但如果以后还有其他入口需要新增部门呢？

例如：

- 管理后台新增部门。
- 导入 Excel 批量创建部门。
- 管理员通过其他业务接口创建部门。

如果每个入口都自己实现一遍上述流程，就会出现多个版本的业务规则。一旦编码规则发生变化，就必须修改多处代码。

因此，我们将业务操作集中到服务层。

本篇采用这样的分工：

- **页面层**：负责展示表单、收集用户输入。
- **入口层**：负责接收请求、调用服务函数，并将结果转换为适当的响应。
- **服务层**：负责业务校验、组织数据库操作、控制事务。
- **工具层**：负责可复用的编码与排序规则。
- **数据库**：通过唯一约束、外键等机制保护数据完整性。

本篇只实现服务层，暂时不接入页面和 Server Actions。下一篇再为这些服务函数建立前端调用入口。

### 2.2 服务函数为什么需要事务？

先看一个新增部门的过程。

假设系统需要新增顶级部门，分配到的编码是 `D005`。

这个过程至少涉及两次数据库写操作：

1. 将顶级部门的计数器递增。
2. 将编码为 `D005` 的部门插入 `Dept` 表。

如果第一次操作成功，第二次操作失败，就可能出现计数器已经变化、部门却没有创建成功的情况。

因此，我们需要一个机制，让这两次操作作为一个整体执行。

Prisma 提供了交互式事务：

```typescript
await db.$transaction(async (tx) => {
  // 在这里组织多个数据库操作
});
```

这里的 `tx` 是事务客户端。

只要回调中的数据库操作都通过 `tx` 执行，事务就可以统一管理这些操作的提交与回滚。

例如：

```typescript
await db.$transaction(async (tx) => {
  await tx.deptCodeCounter.upsert({
    // ...
  });

  await tx.dept.create({
    // ...
  });
});
```

如果回调正常结束，事务提交；如果中途抛出异常，事务回滚。

需要注意，事务只能保证数据库操作的原子性，并不意味着所有并发场景都自动安全。唯一约束冲突、事务隔离级别以及必要的重试策略，仍然需要结合具体业务处理。

### 2.3 本篇先明确三个业务约束

开始写代码之前，我们先确定服务层必须维护的规则。

**第一，部门编码由系统生成。**

新增和修改部门时，前端不能自行指定编码。修改部门名称也不应该随意改变编码。

只有在调整部门上级时，才需要重新分配当前部门的编码，并同步更新下级部门的编码前缀。

**第二，部门层级不能形成循环。**

例如：

```text
技术部
└── 开发组
    └── 前端组
```

不能将技术部的上级设置为前端组，否则就会形成循环关系。

**第三，删除部门不能破坏组织结构。**

存在下级部门时，禁止删除当前部门。人员关联等约束，可以在后续建立人员管理模块后继续补充。

明确这些约束之后，我们再把它们转换成代码。

### 2.4 先看本篇的完整代码

开始逐块写之前，先把本篇结束时的 `server/dept/service.ts` 完整贴出来，建立一个整体印象。

本篇新增的是 `assertNoCycle`、`recodeDescendants`，以及三个服务函数 `createDept` / `updateDept` / `deleteDept`；文件开头的 `import "server-only"` 和 `listDepts`、`listDeptPage` 是前几篇已经写好的部分，一并列出以便整体对照。后面几节会按“先看全局，再看局部”的顺序，逐段拆解这些代码。

```typescript
import "server-only";
import { db } from "@/lib/db";
import { BizError } from "@/lib/biz-error";
import {
  nextDeptCode,
  nextSort,
  type Tx,
} from "@/server/dept/utils";
import type { DeptInput } from "@/server/dept/types";

/** 全量读取：给组织树和“上级部门名称”用 */
export async function listDepts() {
  return db.dept.findMany({
    orderBy: [{ sort: "asc" }, { code: "asc" }],
  });
}

/** 部门列表分页查询：筛选与分页都在数据库完成 */
export async function listDeptPage(options: {
  keyword?: string;
  parentId?: string;
  page?: number;
  pageSize?: number;
}) {
  const pageSize = options.pageSize ?? 10;
  const keyword = options.keyword?.trim();

  // where 是“动态拼装”的：条件为空时就不加入此条件
  const where = {
    ...(keyword
      ? {
          OR: [
            { name: { contains: keyword, mode: "insensitive" as const } },
            { code: { contains: keyword, mode: "insensitive" as const } },
          ],
        }
      : {}),
    ...(options.parentId ? { parentId: options.parentId } : {}),
  };

  // 先查总数：算出总页数，才能把 page 限制在合法范围内
  const total = await db.dept.count({ where });
  const pageCount = Math.max(1, Math.ceil(total / pageSize));
  const page = Math.min(Math.max(1, Math.floor(options.page ?? 1)), pageCount);

  const rows = await db.dept.findMany({
    where,
    orderBy: [{ sort: "asc" }, { code: "asc" }],
    skip: (page - 1) * pageSize, // 跳过前面几页
    take: pageSize, // 只取一页
  });

  return { rows, total, page, pageSize };
}

/**
 * 防止将自己或自己的下级设为上级。
 */
async function assertNoCycle(
  tx: Tx,
  id: string,
  parentId: string
) {
  const all = await tx.dept.findMany({
    select: {
      id: true,
      parentId: true,
    },
  });

  const parentOf = new Map(
    all.map((row) => [row.id, row.parentId])
  );

  let cursor: string | null = parentId;

  while (cursor) {
    if (cursor === id) {
      throw new BizError(
        "不能把自己（或其下级）设为上级，会形成循环"
      );
    }

    cursor = parentOf.get(cursor) ?? null;
  }
}

/**
 * 将当前部门所有下级的编码前缀同步更新。
 */
async function recodeDescendants(
  tx: Tx,
  id: string,
  oldCode: string,
  newCode: string
) {
  const all = await tx.dept.findMany({
    select: {
      id: true,
      parentId: true,
      code: true,
    },
  });

  const childrenOf = new Map<
    string,
    typeof all
  >();

  for (const row of all) {
    if (!row.parentId) continue;

    const list = childrenOf.get(row.parentId) ?? [];
    list.push(row);
    childrenOf.set(row.parentId, list);
  }

  const queue = [id];

  while (queue.length > 0) {
    const current = queue.shift()!;

    for (const child of childrenOf.get(current) ?? []) {
      if (!child.code.startsWith(`${oldCode}-`)) {
        throw new BizError(
          "下级部门的编码与上级不一致，请先修正数据"
        );
      }

      await tx.dept.update({
        where: { id: child.id },
        data: {
          code: newCode + child.code.slice(oldCode.length),
        },
      });

      queue.push(child.id);
    }
  }
}

/**
 * 新增部门。
 * 编码分配、排序计算和部门写入在同一个事务中完成。
 */
export async function createDept(input: DeptInput) {
  const parentId = input.parentId ?? null;

  return db.$transaction(async (tx) => {
    // 1. 检查上级部门，并分配编码
    const code = await nextDeptCode(tx, parentId);

    // 2. 如果没有指定排序值，则计算同级最大值 + 10
    const sort =
      input.sort ?? (await nextSort(tx, parentId));

    // 3. 写入部门
    return tx.dept.create({
      data: {
        name: input.name,
        code,
        parentId,
        sort,
        status: input.status ?? 1,
        description: input.description || null,
      },
    });
  });
}

/**
 * 修改部门。
 * 调整上级时，重新分配编码并同步更新全部下级。
 */
export async function updateDept(
  id: string,
  input: DeptInput
) {
  const parentId = input.parentId ?? null;

  return db.$transaction(async (tx) => {
    // 1. 查询当前部门
    const row = await tx.dept.findUnique({
      where: { id },
    });

    if (!row) {
      throw new BizError("部门不存在，可能已被删除");
    }

    // 2. 默认保留原编码和原排序
    let code = row.code;
    let sort = input.sort ?? row.sort;

    // 3. 判断上级是否变化
    const parentChanged = parentId !== row.parentId;

    if (parentChanged) {
      // 新上级不能是自己或自己的下级
      if (parentId) {
        await assertNoCycle(tx, id, parentId);
      }

      // 为新层级分配编码
      code = await nextDeptCode(tx, parentId);

      // 未指定排序时，排到新上级的末尾
      if (input.sort === undefined) {
        sort = await nextSort(tx, parentId);
      }
    }

    // 4. 更新当前部门
    const updated = await tx.dept.update({
      where: { id },
      data: {
        name: input.name,
        code,
        parentId,
        sort,
        status: input.status ?? row.status,
        description:
          input.description === undefined
            ? row.description
            : input.description || null,
      },
    });

    // 5. 上级发生变化时，同步更新全部下级
    if (parentChanged) {
      await recodeDescendants(
        tx,
        id,
        row.code,
        code
      );
    }

    return updated;
  });
}

/**
 * 删除部门。
 * 存在下级时禁止删除。
 */
export async function deleteDept(id: string) {
  return db.$transaction(async (tx) => {
    // 1. 查询当前部门
    const row = await tx.dept.findUnique({
      where: { id },
    });

    if (!row) {
      throw new BizError("部门不存在，可能已被删除");
    }

    // 2. 检查是否存在下级部门
    const child = await tx.dept.findFirst({
      where: { parentId: id },
      select: { id: true },
    });

    if (child) {
      throw new BizError(
        "存在下级部门，不能删除，建议改用停用"
      );
    }

    // 3. 删除部门
    return tx.dept.delete({
      where: { id },
    });
  });
}
```

## 三、先准备服务层使用的数据类型

上一篇已经建立了部门的展示和查询逻辑。本篇需要为新增、修改操作定义统一的输入类型。

在 `server/dept/types.ts` 中补充：

```typescript
export type DeptStatus = 0 | 1;

/**
 * 新增或修改部门的输入。
 * 编码不由前端传入，而是由服务端生成。
 */
export type DeptInput = {
  name: string;
  parentId: string | null;
  sort?: number;
  status?: DeptStatus;
  description?: string;
};
```

这里有几个值得注意的地方。

### 3.1 为什么不允许传入 `code`？

因为编码属于系统维护的业务数据。

如果将 `code` 放进输入类型，调用方就可以尝试提交任意编码，服务层也需要额外判断这个编码是否符合规则。

更合理的方式是：调用方只提供部门名称、上级部门等业务信息，编码由服务端根据规则生成。

### 3.2 为什么 `sort` 和 `status` 是可选字段？

```typescript
sort?: number;
status?: DeptStatus;
```

这两个字段允许调用方不传。

新增部门时：

- 没有传 `sort`，就计算同级最大排序值加 `10`。
- 没有传 `status`，默认启用。

修改部门时：

- 没有传 `sort`，就保留原排序值；如果调整了上级，则默认排到新上级的末尾。
- 没有传 `status`，就保留原状态。

这里的规则需要由服务层明确实现，不能只依赖表单默认值。

### 3.3 为什么要区分“没有描述”和“清空描述”？

`description` 是可选字段，但这不意味着两种情况相同：

```typescript
{}                         // 没有提交描述
{ description: "" }        // 用户主动提交空描述
{ description: "研发中心" } // 用户提交新描述
```

修改时，如果没有提交描述，通常应该保留数据库里的原值；如果用户主动清空描述，才将它改为 `null`。

后面的 `updateDept` 会专门处理这个区别，避免编辑操作意外清空原数据。

## 四、校验交给入口层，Service 只做数据转换

输入校验统一在 Server Action 中由 Zod schema 完成（`server/dept/schema.ts`，详见 6.9 篇）。服务函数拿到的 `DeptInput` 已经满足：

- `name` 已去除首尾空白、非空、不超过 50 个字；
- `sort` 是整数；
- `status` 只能是 0 或 1；
- `description` 不超过 500 个字。

因此 `service.ts` 不再保留手写的 `validate()`。两套校验规则同时存在时，很容易逐渐不一致：例如旧实现只检查了描述的类型，没有检查长度上限，Zod 更新后服务层却仍按旧规则放行。

职责划分因此变得清晰：

- 入口层（Server Action + Zod）：判断“输入是否合法”，把外部数据收敛成可信的 `DeptInput`；
- 服务层：处理业务规则（上级是否存在、是否成环、能否删除）与数据转换。

服务层唯一保留的转换，是把空字符串描述转成 `null`：

```typescript
description: input.description || null,
```

修改操作还要区分“没传”和“传了空串”：

```typescript
description:
  input.description === undefined
    ? row.description
    : input.description || null,
```

`undefined` 表示调用方不打算修改描述，沿用原值；`""` 表示用户主动清空，落库为 `null`。这也是为什么不能简写成 `input.description || row.description`——那样空串也会退化成“保留原值”，编辑页就无法清空描述了。

### 4.1 那还需要服务层测试吗？

需要，但测试重点不再是输入格式，而是业务规则：防环、编码前缀同步、默认排序、事务回滚等。输入格式的用例已经在 Action 层（6.9）覆盖，重复测试只会增加维护成本。

## 五、实现新增部门 `createDept`

### 5.1 先拆解新增流程

新增部门需要完成以下工作：

```text
接收 Action 层已校验的输入
  ↓
开启数据库事务
  ↓
检查上级并分配部门编码
  ↓
确定排序值
  ↓
插入部门数据
  ↓
提交事务
```

这里有一个关键点：编码分配和部门插入必须属于同一个事务。

### 5.2 编写代码

在 `server/dept/service.ts` 中增加：

```typescript
/**
 * 新增部门。
 * 编码分配、排序计算和部门写入在同一个事务中完成。
 */
export async function createDept(input: DeptInput) {
  const parentId = input.parentId ?? null;

  return db.$transaction(async (tx) => {
    // 1. 检查上级部门，并分配编码
    const code = await nextDeptCode(tx, parentId);

    // 2. 如果没有指定排序值，则计算同级最大值 + 10
    const sort =
      input.sort ?? (await nextSort(tx, parentId));

    // 3. 写入部门
    return tx.dept.create({
      data: {
        name: input.name,
        code,
        parentId,
        sort,
        status: input.status ?? 1,
        description: input.description || null,
      },
    });
  });
}
```

### 5.3 理解事务中的三个步骤

**第一步：分配编码。**

```typescript
const code = await nextDeptCode(tx, parentId);
```

这里没有直接查询计数器，而是调用上一篇封装好的工具函数。

工具函数会根据 `parentId` 找到对应的编码范围，并分配下一个序号。

如果上级部门不存在，它会抛出 `BizError`，当前事务不会继续执行。

**第二步：确定排序值。**

```typescript
const sort =
  input.sort ?? (await nextSort(tx, parentId));
```

这里使用 `??` 判断调用方是否提供排序值。

如果传入 `0`，它仍然是一个有效的整数，不会被错误地当成“没有传值”。

如果没有提供排序值，才调用 `nextSort`。

**第三步：插入数据库。**

```typescript
return tx.dept.create({
  data: {
    name,
    code,
    parentId,
    sort,
    status: input.status ?? 1,
    description: description ?? null,
  },
});
```

注意这里使用的是 `tx.dept.create`，而不是 `db.dept.create`。

这是为了确保插入操作也属于当前事务。

如果部门插入失败，之前在同一事务中执行的计数器更新也会回滚。

至此，新增部门服务已经完成。

## 六、实现修改部门 `updateDept`

修改部门是本篇最复杂的部分。

因为修改名称和调整部门层级，实际上是两种不同的业务操作。

### 6.1 先判断修改会产生什么影响

假设当前部门结构如下：

```text
技术部 D001
└── 开发组 D001-01
    └── 前端组 D001-01-01
```

如果只是将“开发组”改名为“研发组”，部门编码不应该改变：

```text
技术部 D001
└── 研发组 D001-01
    └── 前端组 D001-01-01
```

但是，如果将“开发组”移动到另一个上级部门，编码前缀就需要变化。

例如：

```text
销售部 D002
└── 研发组 D002-01
    └── 前端组 D002-01-01
```

这说明修改部门时，服务层首先需要判断：**上级部门是否发生变化？**

如果没有变化，只修改允许修改的字段。

如果发生变化，则需要额外完成：

1. 检查新上级是否会造成循环。
2. 为当前部门分配新的编码。
3. 根据新上级计算排序值（如果调用方没有指定）。
4. 修改当前部门。
5. 同步更新所有下级部门的编码前缀。

这些操作必须在一个事务中完成。

### 6.2 实现防环函数 `assertNoCycle`

先解决部门树不能形成循环的问题。

我们使用一个简单的判断方法：从准备设置的新上级开始，沿着上级关系逐级向上查找。

如果查找过程中遇到当前正在修改的部门，就说明调整后会形成循环。

```typescript
/**
 * 防止将自己或自己的下级设为上级。
 */
async function assertNoCycle(
  tx: Tx,
  id: string,
  parentId: string
) {
  const all = await tx.dept.findMany({
    select: {
      id: true,
      parentId: true,
    },
  });

  const parentOf = new Map(
    all.map((row) => [row.id, row.parentId])
  );

  let cursor: string | null = parentId;

  while (cursor) {
    if (cursor === id) {
      throw new BizError(
        "不能把自己（或其下级）设为上级，会形成循环"
      );
    }

    cursor = parentOf.get(cursor) ?? null;
  }
}
```

### 6.3 逐步理解防环逻辑

首先，查询部门 ID 和上级 ID：

```typescript
const all = await tx.dept.findMany({
  select: {
    id: true,
    parentId: true,
  },
});
```

这里只需要构建树的关系，不需要查询部门名称、编码等其他字段。

接着，将数据转换成 `Map`：

```typescript
const parentOf = new Map(
  all.map((row) => [row.id, row.parentId])
);
```

`Map` 可以根据部门 ID 快速找到它的上级 ID。

例如：

```text
技术部 → null
开发组 → 技术部ID
前端组 → 开发组ID
```

最后，从新上级开始向上遍历：

```typescript
let cursor: string | null = parentId;

while (cursor) {
  if (cursor === id) {
    throw new BizError(
      "不能把自己（或其下级）设为上级，会形成循环"
    );
  }

  cursor = parentOf.get(cursor) ?? null;
}
```

如果当前部门是“开发组”，而准备将“前端组”设为它的新上级，那么遍历路径就是：

```text
前端组 → 开发组
```

遍历时遇到正在修改的“开发组”，立即抛出业务错误。

这里的判断比单纯检查 `parentId !== id` 更完整，因为它可以发现间接循环，而不仅是“自己不能当自己的上级”。

本实现每次读取整张部门表，适合规模不大的组织树。对于更大规模的数据，可以考虑递归 CTE 等数据库能力。

另外，这个检查建立在现有部门树本身有效的前提下。如果历史数据已经存在循环，还需要专门的数据修复逻辑。

### 6.4 实现下级编码同步函数 `recodeDescendants`

现在解决第二个问题：调整上级之后，如何修改整棵子树的编码？

例如，当前部门编码从 `D001-01` 变成 `D002-01`，那么所有下级编码都必须保持对应的层级后缀。

```text
原编码                         新编码

D001-01                       D002-01
D001-01-01                    D002-01-01
D001-01-01-01                 D002-01-01-01
```

我们不需要为每个下级重新分配序号，而是保留原有后缀，只替换根部门的编码前缀。

```typescript
/**
 * 将当前部门所有下级的编码前缀同步更新。
 */
async function recodeDescendants(
  tx: Tx,
  id: string,
  oldCode: string,
  newCode: string
) {
  const all = await tx.dept.findMany({
    select: {
      id: true,
      parentId: true,
      code: true,
    },
  });

  const childrenOf = new Map<
    string,
    typeof all
  >();

  for (const row of all) {
    if (!row.parentId) continue;

    const list = childrenOf.get(row.parentId) ?? [];
    list.push(row);
    childrenOf.set(row.parentId, list);
  }

  const queue = [id];

  while (queue.length > 0) {
    const current = queue.shift()!;

    for (const child of childrenOf.get(current) ?? []) {
      if (!child.code.startsWith(`${oldCode}-`)) {
        throw new BizError(
          "下级部门的编码与上级不一致，请先修正数据"
        );
      }

      await tx.dept.update({
        where: { id: child.id },
        data: {
          code: newCode + child.code.slice(oldCode.length),
        },
      });

      queue.push(child.id);
    }
  }
}
```

### 6.5 这里用到了哪些知识点？

**第一，为什么要建立 `childrenOf`？**

我们需要根据一个部门的 ID，快速找到它的直接下级。

因此，将查询结果转换成：

```text
父部门ID → 直接下级部门列表
```

这样就不必在每一轮遍历时都重新扫描全部部门。

**第二，为什么使用队列 `queue`？**

```typescript
const queue = [id];
```

队列中保存的是接下来需要处理的部门 ID。

每处理一个部门，就找到它的直接下级，更新这些下级的编码，再把它们放入队列。

这个过程会逐层向下展开，最终覆盖整棵子树。

**第三，为什么只替换前缀？**

```typescript
newCode + child.code.slice(oldCode.length)
```

例如：

```typescript
const oldCode = "D001-01";
const newCode = "D002-01";
const childCode = "D001-01-03";

newCode + childCode.slice(oldCode.length);
// D002-01-03
```

原来的后缀 `-03` 得到保留，因此同级序号和层级结构不会被重新计算。

**第四，为什么还要检查旧前缀？**

```typescript
if (!child.code.startsWith(`${oldCode}-`)) {
  throw new BizError(
    "下级部门的编码与上级不一致，请先修正数据"
  );
}
```

这是一项数据一致性检查。

如果下级编码本来就不符合上级编码规则，直接修改前缀可能会掩盖已有的数据问题，因此这里选择中止操作。

注意：这个函数使用的是查询时的旧编码快照。它会按照旧的树关系遍历，并在当前事务中更新数据库。如果中途发生异常，整个事务应当回滚，避免只修改部分下级。

### 6.6 实现 `updateDept`

有了防环和编码同步函数之后，就可以组织完整的修改流程了。

```typescript
/**
 * 修改部门。
 * 调整上级时，重新分配编码并同步更新全部下级。
 */
export async function updateDept(
  id: string,
  input: DeptInput
) {
  const parentId = input.parentId ?? null;

  return db.$transaction(async (tx) => {
    // 1. 查询当前部门
    const row = await tx.dept.findUnique({
      where: { id },
    });

    if (!row) {
      throw new BizError("部门不存在，可能已被删除");
    }

    // 2. 默认保留原编码和原排序
    let code = row.code;
    let sort = input.sort ?? row.sort;

    // 3. 判断上级是否变化
    const parentChanged = parentId !== row.parentId;

    if (parentChanged) {
      // 新上级不能是自己或自己的下级
      if (parentId) {
        await assertNoCycle(tx, id, parentId);
      }

      // 为新层级分配编码
      code = await nextDeptCode(tx, parentId);

      // 未指定排序时，排到新上级的末尾
      if (input.sort === undefined) {
        sort = await nextSort(tx, parentId);
      }
    }

    // 4. 更新当前部门
    const updated = await tx.dept.update({
      where: { id },
      data: {
        name: input.name,
        code,
        parentId,
        sort,
        status: input.status ?? row.status,
        description:
          input.description === undefined
            ? row.description
            : input.description || null,
      },
    });

    // 5. 上级发生变化时，同步更新全部下级
    if (parentChanged) {
      await recodeDescendants(
        tx,
        id,
        row.code,
        code
      );
    }

    return updated;
  });
}
```

### 6.7 重点理解修改流程中的判断

**为什么先查询原部门？**

因为修改操作需要知道原来的上级、编码、排序和状态。

如果部门已经被删除，就不能继续修改，因此需要先检查记录是否存在。

**为什么默认保留原编码？**

```typescript
let code = row.code;
```

编码不是普通的编辑字段。只修改名称时，原编码应保持不变。

只有 `parentChanged` 为 `true` 时，才调用 `nextDeptCode` 重新分配编码。

**为什么换上级时要重新计算排序？**

```typescript
if (input.sort === undefined) {
  sort = await nextSort(tx, parentId);
}
```

部门移动到新的上级之后，原来的排序值可能不适合新位置。

因此，当调用方没有明确指定排序值时，将其排到新上级的末尾。

如果用户明确指定了排序值，就保留用户提交的值。

**为什么描述字段需要单独判断？**

```typescript
description:
  description === undefined
    ? row.description
    : description,
```

这里不能简单使用：

```typescript
description: description ?? row.description
```

虽然在当前值域下也能保留原值，但显式判断更清楚地表达了业务含义：

- `undefined`：调用方没有提交描述，保留原值。
- `null`：调用方主动清空描述。
- 字符串：更新为新的描述。

这样就不会因为修改部门名称而意外清空原来的描述。

**为什么整个流程都在事务中？**

因为调整上级涉及多条数据的修改：

1. 计数器更新。
2. 当前部门更新。
3. 所有下级部门编码更新。

只要其中任一步骤失败，就应该回滚整个事务，不能让部门关系和编码前缀处于不一致状态。

## 七、实现删除部门 `deleteDept`

### 7.1 删除部门前，需要检查什么？

部门删除并不只是删除一条记录。

例如：

```text
技术部
└── 开发组
    └── 前端组
```

如果直接删除技术部，开发组和前端组就会失去原有的上级关系。

因此，本篇规定：**存在下级部门时，不允许删除当前部门，应该先调整组织结构，或者将部门停用。**

此外，未来加入员工管理后，还需要检查部门是否仍然关联在职员工。

### 7.2 编写删除函数

```typescript
/**
 * 删除部门。
 * 存在下级时禁止删除。
 */
export async function deleteDept(id: string) {
  return db.$transaction(async (tx) => {
    // 1. 查询当前部门
    const row = await tx.dept.findUnique({
      where: { id },
    });

    if (!row) {
      throw new BizError("部门不存在，可能已被删除");
    }

    // 2. 检查是否存在下级部门
    const child = await tx.dept.findFirst({
      where: { parentId: id },
      select: { id: true },
    });

    if (child) {
      throw new BizError(
        "存在下级部门，不能删除，建议改用停用"
      );
    }

    // 3. 删除部门
    return tx.dept.delete({
      where: { id },
    });
  });
}
```

这里使用 `findFirst`，只需要知道是否存在下级部门，并不需要查询全部下级记录。

如果找到了任何一条记录，就说明当前部门不能删除。

数据库中的自引用外键和 `onDelete: Restrict` 也可以作为最后一道保护，防止绕过服务层的代码破坏部门关系。

### 7.3 为什么不再删除计数器？

这里需要明确一个设计原则：**计数器记录的不只是当前数据，还记录了编码分配进度。**

如果直接删除计数器，就会失去这部分历史信息。

本篇选择保留计数器记录。部门删除后，其 ID 不会重新分配给其他部门，因此对应的计数器可以作为历史分配记录保留。

这样做的好处是，编码分配历史更加完整，也避免把计数器清理误当成业务删除的必要步骤。

如果未来确实需要清理历史计数器，就应当先明确计数器的生命周期和编号不复用策略，再决定是否允许清理，而不是在每次删除部门时无条件删除。

未来建立人员管理模块后，还可以补充类似的保护：

```typescript

//   throw new BizError(

```

## 八、如何验证三个服务函数？

代码写完后，不应该只通过页面点击来判断是否正确。

本篇的服务函数涉及真实数据库事务，因此验证时需要区分两类测试。

### 8.1 单元测试：验证业务规则

对于 `assertNoCycle`、默认排序以及编码前缀转换等逻辑，可以通过模拟数据或提取独立函数来测试。

建议至少覆盖这些场景：

| 功能   | 测试场景        | 预期结果   |
| ---- | ----------- | ------ |
| 新增   | 未指定排序和状态    | 使用默认值  |
| 新增   | 显式传入排序值 0    | 保留 0   |
| 新增   | 描述传空字符串     | 存为 `null` |
| 防环   | 将自己设为上级     | 拒绝修改   |
| 防环   | 将自己的下级设为上级  | 拒绝修改   |
| 编码同步 | 下级编码符合旧前缀   | 正确替换前缀 |
| 编码同步 | 下级编码与旧前缀不一致 | 拒绝修改   |
| 修改   | 不传描述        | 保留原值   |
| 修改   | 描述传空字符串     | 清空为 `null` |

输入格式（名称为空、超长、排序非整数、状态非法）属于 Action 层的职责，相关用例放在 6.9，这里不重复测试。

### 8.2 集成测试：验证数据库行为

单元测试不能证明真实数据库事务一定正确。

因此，还需要在测试数据库中验证：

- 新增成功后，部门记录和计数器变化符合预期。
- 新增失败后，计数器更新能够回滚。
- 修改上级成功后，整棵子树的编码保持一致。
- 修改下级编码过程中发生异常时，整个事务回滚。
- 删除存在下级的部门时，数据保持不变。
- 删除成功后，历史编码分配记录仍然保留。

尤其要测试编码同步失败时的回滚情况。因为这里会更新多条部门记录，只看最终页面显示正确，并不足以证明中间任何一步失败时都不会留下部分更新。

本篇暂时不展开完整的测试基础设施，后续可以在服务层稳定后统一补齐。

## 九、本篇小结

本篇完成了部门管理的三个核心服务函数。

**`createDept`：新增部门。**

先接收已校验的输入，再在事务中分配编码、计算排序并插入数据，保证数据库操作作为一个整体完成。

**`updateDept`：修改部门。**

修改普通字段时保留原编码；调整上级时先防环，再分配新编码、调整排序，并同步更新整棵子树的编码前缀。

**`deleteDept`：删除部门。**

先确认部门存在，再检查是否有下级，最后执行删除。历史计数器不随部门删除而清理。

通过这一篇，我们开始将独立的工具函数组织成完整的业务流程。

这里最重要的认识是：**服务层的职责不是把数据库增删改查简单包装一下，而是保证一个业务操作从开始到结束都符合业务规则。**

下一篇（6.6），我们将通过 Server Actions 为这三个服务函数建立调用入口，让前端可以真正发起新增、修改和删除操作，并将服务层的业务错误转换为用户能够理解的提示。
