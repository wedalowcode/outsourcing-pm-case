# 7.1 从访问网址到进入系统：梳理后台系统的完整流程

## 一、先明确我们要解决什么问题

上一阶段，我们已经为系统搭建了后台管理的整体骨架。

目前，用户可以访问工作台，通过左侧菜单进入部门管理页面，并完成部门的增删改查。系统已经具备了基本的页面结构和业务功能。

但是，现在的系统还存在一个明显的问题：**任何能够访问网址的人，都可以直接进入后台页面。**

例如，我们访问：

```text
http://localhost:3000/dashboard
```

系统就会显示工作台。如果继续访问：

```text
http://localhost:3000/dept
```

也可以直接进入部门管理页面。

这在开发阶段没有问题，但对于一个真正投入使用的管理系统来说，显然是不够的。

一个正常的后台系统，至少需要回答以下问题：

- 谁在访问系统？
- 这个人是否已经登录？
- 如果没有登录，应该进入哪里？
- 如果已经登录，应该显示哪些菜单？
- 用户能不能访问某个页面，能不能执行某项操作？
- 当用户退出登录后，系统如何阻止他继续访问受保护的页面？

这些问题并不是孤立的功能，而是共同组成了一个完整的系统访问流程。

因此，在编写登录功能之前，我们先把整条主线梳理清楚。

## 二、从用户视角梳理系统使用流程

假设我们正在建设一套外包项目管理平台，系统中有销售、项目经理和开发人员等不同角色。

用户打开浏览器，输入系统网址，接下来会发生什么？

### 1. 用户访问系统

用户首先访问系统的入口地址，例如：

```text
http://localhost:3000/
```

系统需要判断当前访问者是否已经登录。

如果用户尚未登录，系统不应该直接展示工作台或业务页面，而是引导用户进入登录页面。

如果用户已经登录，则可以继续进入后台系统。

### 2. 用户输入用户名和密码

在登录页面，用户输入自己的用户名和密码，然后提交登录请求。

服务端需要完成以下工作：

1. 检查输入内容是否符合基本格式要求。
2. 根据用户名查询对应的用户记录。
3. 验证用户输入的密码是否正确。
4. 检查用户是否处于允许登录的状态。
5. 验证通过后，建立登录状态。

需要注意，用户名和密码的验证必须在服务端完成。不能因为前端页面显示登录成功，就认为用户已经通过身份验证。

### 3. 登录成功后进入后台

登录成功后，系统需要让浏览器在后续请求中能够证明自己已经建立了有效的登录状态。

例如，用户进入：

```text
/dashboard
```

系统识别出当前登录用户后，才允许其进入工作台。

如果用户刷新页面，或者直接在浏览器地址栏输入 `/dept`，系统也应该能够识别其登录状态，而不是要求用户每次重新登录。

### 4. 系统根据用户权限加载菜单

不同岗位的用户，工作内容并不相同。

例如：

- 销售人员主要关注客户和商机。
- 项目经理主要关注项目、任务和工时。
- 管理人员可能需要查看成本、回款和统计数据。

因此，登录成功并不意味着所有用户都应该看到相同的菜单。

系统应该根据当前用户所拥有的权限，决定向其展示哪些菜单，以及允许其进入哪些页面。

在本阶段，我们暂时不实现这部分功能，只需要明确：**菜单不应该永久写死在前端，而应该能够根据用户权限动态生成。**

### 5. 用户进入业务页面并执行操作

用户点击菜单，进入部门管理页面，或者后续进入客户、项目、任务等业务模块。

在页面中，系统可以根据权限决定是否展示新增、编辑、删除等操作入口。

但这还不够。

即使前端隐藏了删除按钮，用户仍然可能尝试直接调用对应的服务端操作。因此，在真正修改数据库之前，服务端还必须重新验证用户是否有权执行该操作。

这意味着权限控制不能只停留在菜单和页面上，还必须覆盖最终的业务操作。

### 6. 用户退出登录

当用户点击退出登录时，系统应该清除或使当前登录状态失效。

退出后，如果用户再次访问 `/dashboard` 或 `/dept`，系统就应该将其引导到登录页面。

至此，用户从访问系统到退出登录，形成了一个完整的使用闭环。

## 四、这里需要区分三个核心概念

在实现登录功能之前，有三个概念必须分清楚。

### 1. 身份认证：你是谁？

身份认证（Authentication）解决的是用户身份问题。

例如，系统需要确认：

- 当前用户对应哪个账号？
- 用户提交的密码是否正确？
- 当前登录状态是否有效？

当系统确认用户是账号 `zhangsan` 对应的真实使用者后，就完成了身份认证。

但身份认证并不意味着用户可以访问系统中的所有功能。

### 2. 权限控制：你能做什么？

权限控制（Authorization）解决的是访问范围和操作范围问题。

例如，张三是销售人员，系统允许他查看客户和商机，但不允许他删除部门；李四是项目经理，可以管理项目和任务，但不一定拥有系统用户管理权限。

这两个用户都可能已经成功登录，但他们能执行的操作不同。

因此，我们必须记住：

**登录解决的是“你是谁”，权限控制解决的是“你能做什么”。**

### 3. 登录状态：系统如何记住你？

HTTP 请求本身并不会自动让服务端记住用户之前是否登录。

用户第一次提交正确的用户名和密码后，系统需要建立某种登录状态，并让后续请求能够关联到当前用户。

这个机制通常涉及 Session、Cookie 或其他会话凭证。

本课程后续会选择适合当前 Next.js 项目的实现方式，并进一步讲解登录状态的建立、读取、过期和退出。

本节不提前编写这部分代码，只需要理解：**登录成功不是一次性的页面跳转，而是建立一种可以被后续请求持续识别的有效状态。**

## 五、结合当前项目，明确后续要改造什么

回到我们已经完成的外包项目管理平台。

目前系统主要包含以下几个部分：

| 现有部分 | 当前状态 | 后续改造方向 |
|---|---|---|
| 根布局 `app/layout.tsx` | 已有 | 保留全局布局职责 |
| 后台布局 | 已有基本骨架 | 接入登录状态检查 |
| 工作台 `/dashboard` | 已有基础页面 | 仅允许符合条件的用户访问 |
| 部门管理 `/dept` | 已有 CRUD | 接入页面和操作权限 |
| 左侧菜单 | 当前为静态配置 | 后续根据用户权限动态加载 |
| 用户身份 | 尚未建立完整机制 | 建立用户数据和身份认证 |
| 登录状态 | 尚未建立完整机制 | 实现会话管理和退出登录 |

这里有一个重要的设计原则：**不需要推倒已经完成的业务模块，而是逐步为现有系统增加身份认证和权限控制能力。**

部门管理模块已经具备真实的数据库操作和服务端业务逻辑。后续我们可以用它作为验证对象，检查登录、页面访问和操作权限是否真正生效。

## 六、后续课程按照什么顺序展开？

明确了完整流程后，接下来就可以按照实际开发的依赖关系逐步实现。

第一步，建立用户、角色和权限所需的数据模型。没有用户数据，系统就无法准确识别访问者；没有角色和权限数据，也就无法决定用户可以访问哪些功能。

第二步，建立初始管理员账号和登录页面，让用户能够提交登录请求。

第三步，实现服务端身份验证与登录状态管理，解决登录成功后如何识别当前用户的问题。

第四步，将登录状态接入后台布局，让未登录用户无法直接进入受保护的页面。

第五步，建立角色与权限关系，根据当前用户的权限加载菜单。

第六步，将权限控制落实到页面和服务端业务操作中，并以部门管理模块进行验证。

最后，通过完整的测试流程检查从登录到退出的各个环节，确保权限不仅在界面上生效，在真正执行数据库操作时也能够生效。

具体的数据模型、认证方案和代码实现，我们放到对应的小节中逐步讨论，而不是在这一节提前把所有内容混在一起。

## 七、本节小结

一个完整的后台管理系统，不应该只是打开网址就能看到菜单和业务页面，而应该围绕用户身份建立一条完整的访问链路：

**访问系统 → 判断登录状态 → 完成身份认证 → 加载用户权限 → 进入业务页面 → 验证操作权限 → 执行业务操作 → 退出登录。**

这条链路决定了后续认证和权限模块的设计顺序。

接下来，我们先从最基础的数据开始：系统需要保存哪些用户信息？用户、角色和权限之间是什么关系？这些数据应该如何组织，才能支撑后续的登录、动态菜单和业务操作授权？

这就是下一节 **7.2 用户、角色与权限的数据模型设计** 要解决的问题。
